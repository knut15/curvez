## 1. 무엇을 뜯어봤나

`curvez/plugins/curvez` 의 제어면·작업면·핸드오프·실행기·훅을 정적 분석하고, `doctor`·
`bootstrap`·훅을 실제로 돌려 공식 플러그인 규격과 대조했다. 보고서 본문은 외부 도구(codex)가 쓴
2차 분석을 그대로 옮긴 것이고, 점수와 판정도 작성자의 것이다. 기준일 2026-08-16.

## 2. 무엇을 알아냈나

두 계층이다. Agent 도구는 `curvez-orchestrator` 하나만 갖고, 실행 트리를 오케스트레이터 → 워커 두
층으로 제한해 재귀 위임과 비용 폭증을 막는다. 동시 워커 상한은 5명이고, 에이전트 12종의 `owns`
선언에 대해 경로 교집합·무소유 경로·읽기전용 모순을 기계가 검사한다.

핸드오프가 데이터 계약이다. `from/to/status/summary/artifacts/decisions/blocked_on/verification`
8개 필드가 필수이고 알 수 없는 최상위 키를 거부한다. `done` 은 `verification[]` 1건 이상을
요구하고 `blocked` 는 `blocked_on[]` 1건 이상을 요구해, 워커가 사용자에게 직접 묻지 못하는 제약을
질문 데이터로 바꿨다.

실측 결과는 doctor 정적 규약 7/7, 에이전트 정의 12/12, 스킬 정의 15/15, guard-bash 회귀 15/15,
`claude plugin validate` 2/2 통과다. 가중 합계 91.6 으로 종합 92점.

## 3. 무엇이 남았나

실제 팀 실행의 end-to-end 증거가 없다. 설치 → bootstrap → 승인 → 복수 Agent → 핸드오프 → 질문
중계 → QA·리뷰까지 왕복한 기록이 없어, Agent 동시성·훅 실제 발화·모델 산출 품질은 평가 범위
밖이다. 분석 대상 루트에 `.curvez/handoff/` 가 없어 핸드오프 검사 자체가 생략됐다.

실행 상관관계 식별자가 없다. 스키마에 `run_id`·`round_id`·`task_id`·`attempt` 가 없어, 워커 수와
새 핸드오프 파일 수를 대조하는 방식이 동시 실행·재실행·부분 재개에 취약하다.

문서 수치 검사에 사각지대가 남았다. `GOAL.md` 완료 기준의 `에이전트 11/11 · 스킬 13/13` 이 실제
값 12/12 · 15/15 와 어긋나는데, doctor 는 "12종 에이전트" 형태만 잡고 비율 표기를 실제 파일 개수와
대조하지 못해 이 한 줄을 놓친다.
