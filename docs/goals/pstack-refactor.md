# curvez 리팩터링 설계안 — pstack 참고

> 상태: 초안 · 갱신: 2026-09-28 · 브랜치: `feature/pstack-refactor` (main `69bb418` 에서 분기)

## 1. 목표

curvez 가 **사람 없이 일하고, 스스로 머지까지 하게** 만든다. 지금 curvez 는 단계마다 사람을 기다린다. 팀 구성을 승인받아야 워커를 띄우고, `curvez-git` 은 사용자가 요청할 때만 돈다.

사람 없이 돌리려면 두 가지가 먼저 있어야 한다. 에이전트가 내린 판단을 믿을 수 있어야 하고, 머지 전에 결과를 독립적으로 확인할 수 있어야 한다. 이를 위해 pstack 에서 네 가지를 가져온다.

| 가져올 것                 | pstack 에서의 모습                                                                         | curvez 에서 풀 문제                                                    |
| ------------------------- | ------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------- |
| 원칙 분리와 인덱스        | 원칙 22개를 파일 하나씩 두고, 입구에는 "언제 적용하는가" 한 줄만 둔다                      | 같은 규칙이 파일 수십 곳에 복사돼 있다                                 |
| 작업 종류별 플레이북 입구 | `poteto-mode` 가 요청을 플레이북에 맞추고, 단계를 할 일 목록에 그대로 옮긴다               | 입구가 역할(에이전트)뿐이라 버그 수정과 기능 추가가 같은 라운드를 돈다 |
| 지시서(brief) 템플릿      | GOAL·SCOPE·CONTEXT·ACCEPTANCE·VERIFY·FORBIDDEN·REPORT. 빈 칸이 있으면 워커를 띄우지 않는다 | 워커 지시가 자유 서술이다. 목표·수용 기준·검증 명령이 빠진다           |
| 다른 모델 교차 검토       | 같은 diff 를 여러 모델이 따로 보고, 여러 모델이 함께 낸 지적을 가장 강한 신호로 본다       | 리뷰어가 구현자와 같은 모델이라 같은 맹점을 공유한다                   |

pstack 은 Cursor 전용 기능(`Task` 의 `model` 인자, `environment: "cloud"`, `mode: true`)에 기댄다. 이 부분은 Claude Code 에 맞게 바꾼다(각 절에 적었다).

## 2. 지금 curvez 에서 확인한 사실

에이전트가 `main` 에서 읽고 셌다. 경로는 `plugins/curvez/` 기준이다.

- **규칙이 복사돼 있다.**
  - "profile.json 이 없으면 blocked" 행이 17개 파일에 있다.
  - "2회 재시도 뒤 partial" 행이 에이전트 12개의 에러 핸들링 표에 모두 있다.
  - 단일 출처 원칙의 이유 문장("어느 쪽이 맞는지 판정할 근거가 사라진다")도 14개 파일에 15번 복사돼 있다.
  - `team-orchestration` 은 "사본을 믿지 마라"고 적고도 `curvez-orchestrator.md` 의 수합 표, findings 합치기, blocked 라우팅을 옮겨 적었다.
- **정본의 방향이 섞여 있다.** `design-rationale.md` §9 는 "절차는 스킬, 역할은 에이전트"로 정했다.
  - 실제로는 스킬 5개(architecture-setup, nextjs-implementation, retrospective, wireframe-spec, team-orchestration)가 에이전트를 정본으로 가리킨다.
  - 반대로 에이전트 3개(researcher, structure-reviewer, git)는 스킬을 정본으로 가리킨다.
- **검증기는 `agents/`·`skills/` 밖을 보지 않는다.** 새 폴더를 만들면 막히지는 않지만 아무 검사도 받지 않는다. §8 은 "검사를 추가하지 않은 규칙은 존재하지 않는 것"으로 정했다.
- **워커 지시에 GOAL·ACCEPTANCE·VERIFY 칸이 없다.** 필수 4항목은 담당 범위, 입력 경로, 핸드오프 위치, blocked 지시다.
- **다른 모델을 부르는 코드가 없다.** 반면 `quality-model.md` L90-97 은 "같은 컨텍스트에서 자기 리뷰를 하면 판단을 정당화하게 된다"고 적었다.
- **main 의 검증 결과**
  - `doctor.mjs`(cwd: `plugins/curvez`): exit 0
  - `validate-skills`: 16/16 통과
  - `validate-agents`: 12/12 통과
  - 훅 테스트: 35/35, 17/17 통과
  - eslint·prettier: 통과
  - CI 는 doctor 와 검증기를 돌리지 않는다.

## 3. 설계

### 3.1 원칙 분리와 인덱스

**위치.** `plugins/curvez/principles/<slug>.md`. 원칙은 스킬이 아니다. 사용자가 부를 일이 없어서 스킬 규칙(따옴표 트리거 3개, 트리거 경계 섹션)이 맞지 않는다. 스킬로 만들면 스킬 수 표기가 문서 곳곳에서 어긋나는 문제도 생긴다.

**형식.** pstack 의 뼈대를 따른다.

```markdown
---
name: numbers-not-adjectives
applies_when: 검증 결과를 보고하거나 핸드오프의 verification 을 채울 때
---

# 수치로 보고한다

<규칙 한두 문장>

**이유:** <한 문단>

**패턴:** <목록>

**판정 질문:** <참인지 거짓인지 판정할 수 있는 질문>
```

**인덱스.** 새 모드 스킬(3.2)의 `## 원칙` 절에 원칙마다 한 줄씩 둔다. 형식은 `- **이름** (principles/<slug>.md) — 언제 적용하는가. 한 줄 규칙.` 이다. 에이전트 정의에서 규칙을 복사한 문단은 지우고, `principles/<slug>.md` 를 가리키는 줄로 바꾼다.

**검사(§8).** `scripts/validate-principles.mjs` 를 새로 만들고 doctor 에 넣는다.

- 프론트매터 `name` 이 파일 이름과 같다.
- `applies_when` 이 있다.
- `이유:` 와 `판정 질문:` 이 있다.
- 인덱스와 `principles/` 의 파일이 1:1 로 맞는다.
- 원칙마다 최소 한 곳에서 참조된다.
- 인덱스에 적힌 한 줄이 원칙 파일의 첫 규칙 문장과 같다. 두 벌이 서로 어긋나지 않게 하려는 것이다.

**초기 원칙 후보 12개** (조사에서 복사 횟수가 많은 순)

| slug                     | 규칙                                                               | 지금 복사된 곳                      |
| ------------------------ | ------------------------------------------------------------------ | ----------------------------------- |
| why-first                | 금지·강제 규칙에는 이유를 붙인다                                   | 39개 파일, 410회 (검증기가 강제)    |
| blocked-over-guessing    | 추측으로 채우지 않고 blocked 로 돌아온다                           | 24개 파일, 71회                     |
| retry-twice-then-partial | 2회 재시도한 뒤 partial 로 보고한다                                | 16개 파일                           |
| numbers-not-adjectives   | "통과했다"가 아니라 명령과 수치로 보고하고, 실패는 이름으로 적는다 | quality-gate, qa, wireframe-spec 등 |
| single-source            | 정본은 한 곳에 두고 나머지는 가리킨다                              | 14개 파일, 15회                     |
| exclusive-ownership      | 소유 경로가 겹치면 순차로 내린다                                   | 13개 파일, 40회                     |
| read-only-reviewer       | 리뷰어는 쓰지 않고, Bash 로 우회해서도 쓰지 않는다                 | 5곳                                 |
| orchestrator-owns-spawn  | 워커는 오케스트레이터만 띄운다                                     | 4곳                                 |
| tie-break-order          | 안전한 쪽 → 기존 결정 → 하나를 고르고 되돌릴 지점을 남긴다         | 에이전트 12개 전부                  |
| batch-questions          | 질문은 모아서 한 번에 한다                                         | 4곳                                 |
| commands-from-profile    | 검증 명령은 `profile.json` 에서만 읽는다                           | 여러 곳                             |
| approval-boundary        | 무엇이 승인이고 무엇이 항상 멈추는 행동인가                        | 3곳 (3.5 에서 새로 씀)              |

### 3.2 작업 종류별 플레이북 입구

**새 스킬 `curvez-mode`.** 요청을 플레이북 하나에 맞추고, 그 단계를 TodoWrite 목록에 그대로 옮긴다. 건너뛰는 단계도 목록에 남기고 `skip: <이유>` 를 적는다.

- 워커는 직접 띄우지 않는다. 팀이 필요한 단계에서는 지시서(3.3)를 써서 `curvez-orchestrator` 에 넘긴다. 워커는 오케스트레이터만 띄운다는 §7 결정을 지키기 위해서다.
- 기존 스킬과 트리거가 겹치지 않도록, 명시적으로 부를 때만 켠다("curvez 로 해줘", "/curvez-mode").

**플레이북 위치.** `skills/curvez-mode/playbooks/<name>.md`. `validate-skills` 에 플레이북 검사를 더한다.

- 번호 단계가 있다.
- 마지막 단계가 `보고:` 다.
- 부르는 스킬과 에이전트 이름이 실제로 있다.
- 모드 스킬의 목록과 파일이 1:1 로 맞는다.

**초기 플레이북 6개.** 적게 시작하고, 필요할 때 늘린다.

| 플레이북       | 단계 요약                                                                                                         |
| -------------- | ----------------------------------------------------------------------------------------------------------------- |
| feature        | 요구사항과 AC → 설계(architect·designer) → 구현 → quality-gate → 리뷰와 교차 검토 → (자율 권한이 있으면) shipping |
| bug-fix        | 재현하는 실패 테스트를 먼저 커밋 → 원인 추적 → 수정 → 실패에서 통과로 바뀐 출력을 첨부 → 리뷰 → shipping          |
| refactoring    | 동작을 고정하는 테스트 → 목표 구조 → 작게 옮기기 → 동등성 확인 → 구조 리뷰 → shipping                             |
| investigation  | 읽기 전용. 조사 결과를 출처와 함께 보고한다. 코드는 바꾸지 않는다                                                 |
| autonomous-run | goal 과 완료 조건을 받아 위 플레이북들을 이어 돌리고, 완료 조건을 확인할 때까지 멈추지 않는다                     |
| shipping       | 머지 전에 독립 판정을 한다(3.4). 조건을 모두 채운 것만 머지한다(3.5)                                              |

**Claude Code 로 옮기며 바꾸는 것.** pstack 의 sticky mode(`mode: true`)는 Claude Code 에 없다. 이번에는 만들지 않는다. 필요해지면 UserPromptSubmit 훅으로 다시 검토한다.

### 3.3 지시서(brief) 템플릿

**정본.** `agent-contract` 스킬에 `## 지시서` 절을 더한다. 지금 이 스킬에는 핸드오프(워커 → 오케스트레이터)만 있다. 지시서(오케스트레이터 → 워커)를 같은 곳에 두면 계약의 들어오는 쪽과 나가는 쪽이 한 파일에 모인다.

```
GOAL        한 문장. 대화를 모르는 사람도 실행할 수 있게
SCOPE       쓸 수 있는 경로 / 쓸 수 없는 경로 (에이전트 owns 에서 옮김)
CONTEXT     입력 파일 경로. 앞 단계 핸드오프에 기대면 그 핸드오프 경로
ACCEPTANCE  판정 가능한 기준, 한 줄에 하나 (.curvez/requirements.md 의 AC ID)
VERIFY      실행할 명령 (profile.json 의 commands 에서)
FORBIDDEN   소유 경로 밖 쓰기, 강제 push, 의존성 추가, 그리고 이 작업만의 금지
REPORT      .curvez/handoff/<name>.<ts>.json, status 규칙
STANDING    .curvez/standing.md 경로 (고정 지시문)
```

- TIMEBOX 는 뺀다. Claude Code 서브에이전트에는 실행 시간 상한이 없다. 대신 기존의 "2회 재시도 뒤 partial" 원칙으로 갈음한다.
- **고정 지시문 `.curvez/standing.md`:** 번호 붙은 줄 하나에 제약 하나. 같은 지시를 두 번 하게 되면 여기에 한 줄을 더한다.

**강제.** 새 PreToolUse 훅 `hooks/check-brief.mjs`(matcher: `Agent`).

- `subagent_type` 이 `curvez:` 로 시작하는 호출만 검사한다.
- 프롬프트에 칸 8개가 모두 있고 비어 있지 않은지 본다.
- 하나라도 비면 exit 2 로 막는다. pstack 의 "빈 칸이 있으면 띄우지 않는다"를 글이 아니라 훅으로 강제하는 것이다.
- 훅 테스트는 기존 형식(`hooks/tests/*.test.py`)을 따른다.
- 한 줄짜리 작은 작업은 칸을 한 문단으로 줄여도 된다. 다만 GOAL, SCOPE, VERIFY, REPORT 네 칸은 반드시 채운다.

### 3.4 다른 모델 교차 검토

**새 에이전트 `curvez-cross-reviewer`.**

- 모델은 sonnet 이다. 판단은 codex 가 하고, 이 에이전트는 codex 를 부르고 결과를 옮기기만 한다.
- 쓰기 도구는 막는다. 이름에 review 가 들어가서 검증기도 이것을 요구한다.
- 하는 일:
  1. diff 와 루브릭을 파일로 만든다.
  2. `codex exec -s read-only` 로 검토를 맡긴다.
  3. 출력을 findings JSON 으로 옮겨 반환한다.

**설정.** `profile.json` 에 `crossReview: { "cli": "codex", "model": "<모델>" }` 를 둔다.

- 값이 없거나 codex 가 설치돼 있지 않으면 이 단계를 `blocked` 로 기록한다. 조용히 건너뛰지 않는다.
- 자율 권한(3.5)으로 머지하려면 교차 검토가 반드시 있어야 한다.

**합치기.** 오케스트레이터의 findings 합치기 규칙에 한 줄을 더한다. curvez-reviewer 와 codex 가 각자 따로 같은 지적을 냈으면 가장 강한 신호로 본다. 한쪽만 낸 지적은 등급을 한 단계 내린다(pstack interrogate 와 같은 방식).

**기존 결정과의 충돌.** §2 는 외부 CLI 없이 내장 서브에이전트만 쓰는 것을 골랐다. 이번 설계는 그 원칙을 이렇게 유지한다.

- 워커는 계속 내장 서브에이전트다.
- codex 는 읽기 전용 리뷰어 한 명이 Bash 로 부르는 도구로만 쓴다.
- 결과는 기존의 대필 경로(오케스트레이터가 JSON 을 핸드오프로 기록)를 그대로 탄다.

§2 에는 이 예외와 그 이유를 한 줄 더한다.

### 3.5 자율 권한과 자체 머지

**자율 권한 파일 `.curvez/grant.md`.** 사용자가 작업을 시작할 때 쓰거나, 사용자의 말을 오케스트레이터가 그대로 옮겨 적는다. 담는 것은 다음과 같다.

- 머지 대상 브랜치
- 권한이 끝나는 조건 (예: goal 완료, 날짜)
- 사용자 원문

**권한이 있을 때 바뀌는 것**

| 지금                                   | 자율 권한이 있을 때                                                                |
| -------------------------------------- | ---------------------------------------------------------------------------------- |
| 팀 구성을 승인받은 뒤 워커를 띄운다    | 구성안을 `.curvez/team.md` 에 적고 곧바로 띄운다. 보고는 끝에 한 번 한다           |
| 질문이 생기면 모아서 사용자에게 묻는다 | 실행해서 확인할 수 있는 질문이면 확인해서 정하고 기록한다. 제품·취향 문제만 묻는다 |
| `curvez-git` 은 요청할 때만 돈다       | shipping 조건을 모두 채우면 PR 을 만들고 머지한다                                  |

**shipping 조건** (모두 참이어야 머지한다)

1. quality-gate 의 모든 게이트가 exit 0 이다.
2. curvez-reviewer 의 blocker 가 0 이다.
3. 교차 검토에서 두 모델이 함께 낸 blocker 가 0 이다.
4. 브랜치가 머지 대상 브랜치의 최신 커밋 위에 있다.
5. CI 가 있으면 CI 가 green 이다.

**항상 멈추는 행동.** 자율 권한이 있어도 멈춘다. `principles/approval-boundary.md` 가 정본이고, 그중 기계로 막을 수 있는 것은 `guard-bash` 가 막는다.

- 강제 push, 원격 브랜치 삭제, `git reset --hard`, `git clean`
- 의존성 추가·변경, 패키지 설치
- 배포, 외부 발행과 전송
- curvez 자체(`plugins/curvez/`) 수정
- 비밀값·환경변수 파일 수정

**전역 규칙과의 충돌.** `~/.claude/CLAUDE.md` 0번은 push·머지를 할 때마다 승인받게 한다. 따라서 자율 권한이 실제로 작동하려면 전역 규칙에 예외 한 줄이 필요하다. 예: "`.curvez/grant.md` 에 사용자 원문으로 적힌 범위의 머지는 승인으로 본다." 이 문구를 넣을지는 사용자가 정한다(미결 4). 넣기 전까지 shipping 은 머지 직전에 멈추고 승인을 기다린다.

### P1 에서 바꾼 것

처음 설계는 복사된 규칙 문장을 지우고 원칙을 가리키는 줄로 바꾸는 것이었다. 실제로 찾아보니 "어느 쪽이 맞는지 판정할 근거가 사라진다" 같은 문장은 대부분 **그 파일에서만 쓰는 규칙의 `이유:`** 였다. 지우면 그 규칙의 이유가 없어지고, `validate-skills` 의 why-missing 검사에도 걸린다.

그래서 이렇게 바꿨다.

- 원칙 파일에는 일반 규칙을 둔다
- 그 규칙이 처음 적혀 있던 정본 위치(오케스트레이터의 승인 절차, quality-gate 의 수치 보고 등)에 `(원칙: principles/<slug>.md)` 를 붙인다
- 파일마다 다른 이유는 그대로 둔다

검증기는 원칙마다 원칙 파일 밖에서 가리키는 곳이 최소 한 곳 있는지 본다.

### P3 에서 바꾼 것

- **합치기 규칙.** 설계는 "한쪽만 낸 지적은 등급을 한 단계 내린다" 였다. 실제로는 `curvez-cross-reviewer` 만 낸 지적만 내리고, `curvez-reviewer` 만 낸 지적은 그대로 둔다. 기존 리뷰어의 판정을 새 리뷰어가 못 봤다는 이유로 약하게 만들면 교차 검토를 넣기 전보다 기준이 느슨해지기 때문이다.
- **플러그인 경로.** `CLAUDE_PLUGIN_ROOT` 는 훅 실행 환경에만 있고 에이전트의 Bash 에는 전달되지 않는다(메인 세션과 서브에이전트 모두 빈 값). P3 에서는 `.curvez/tmp/plugin-root` 파일로 넘겼다가, 바로 다음 PR 에서 SessionStart 훅이 `CLAUDE_ENV_FILE` 로 `CURVEZ_ROOT` 를 내보내는 방식으로 바꾸고 에이전트·스킬의 `$CLAUDE_PLUGIN_ROOT` 50곳을 `$CURVEZ_ROOT` 로 옮겼다.

## 5. 하지 않는 것

- pstack 의 나머지 스킬(arena, swarm, how, why, unslop 등)은 가져오지 않는다.
- 클라우드 실행(`environment: "cloud"`)과 sticky mode 는 만들지 않는다.
- 기존 에이전트 12개의 역할은 바꾸지 않는다. 바꾸는 것은 복사된 규칙을 포인터로 바꾸는 것과, 지시서·교차 검토·자율 권한 분기를 더하는 것뿐이다.
- CI 에서 doctor 를 돌리는 일은 이번 범위 밖이다. 따로 정할 일로 남긴다.
