# DDD 아키텍처

curvez 는 프로젝트 구조를 매번 새로 설계하지 않는다. **DDD** 프리셋을 기준으로 삼고,
3~5문 인터뷰로 몇 군데만 틀어서 `.curvez/architecture.md` 로 굳힌다.

이 문서는 **왜 DDD 하나인가, 그것이 무엇을 해결하고 무엇을 대가로 치르는가,
규모가 안 맞을 때 어떻게 조정하는가**를 다룬다.

읽기 전에 경계를 알아 두면 좋다.

| 알고 싶은 것                                                 | 정본                                 |
| ------------------------------------------------------------ | ------------------------------------ |
| 어떤 순서로 고르고 무엇을 묻는가 (절차·인터뷰)               | `skills/architecture-setup/SKILL.md` |
| 몇 개부터 어느 프리셋인가 (판정 수치), 산출물 헤딩·통과 기준 | `agents/curvez-architect.md`         |
| 레이어 정의와 폴더 구조 (실행용)                             | `presets/architecture/ddd.md`        |
| 각 프리셋을 왜 고르는가 / 무엇을 잃는가                      | **이 문서**                          |

> **이 문서는 선택 근거를 담는다.** 실행용 레이어 정의와 폴더 구조는
> `presets/architecture/ddd.md` 에 있다. 프리셋 파일을 읽지 못하면 `curvez-architect` 가
> 내장 폴백 레이어로 진행하고 그 사실을 `decisions` 에 남긴다.

## 왜 프리셋 하나인가

curvez 는 DDD 하나만 제공한다.

### 백지 설계의 두 가지 비용

매 프로젝트마다 아키텍처를 처음부터 설계하면 두 가지를 잃는다. **시간** — 경계를 정하는 대화가
구현을 시작하기 전에 며칠을 먹는다. 그리고 **프로젝트 간 일관성** — 같은 팀의 두 저장소가 다른
어휘를 쓰면 사람이 옮겨 다닐 때마다 다시 배운다.

### 그런데 선택지가 넷이면 그것도 비용이다

프리셋이 여럿이면 "무엇을 고를 것인가" 라는 질문이 매번 생기고, 각 프리셋의 판정 수치를
어딘가에 적어 두어야 하며, 규약이 바뀔 때마다 넷을 함께 고쳐야 한다.
넷 중 셋이 실제로 쓰이지 않으면 그 유지 비용은 아무것도 사지 못한다.

**그래서 하나로 줄였다.** 고를 것이 없으면 인터뷰는 "무엇을 쓸까" 가 아니라
"이 구조를 이 프로젝트에 어떻게 맞출까" 로 좁아진다.

### 규모가 안 맞으면 프리셋을 바꾸지 않고 레이어를 줄인다

DDD 가 과한 규모(라우트 6개 이하, 엔티티 4개 이하)에서는 `application` 을 두지 않고
`presentation → domain` 두 층으로 쓴다. **이것은 다른 아키텍처로 가는 것이 아니라
같은 아키텍처의 축소판이다** — 나중에 규모가 커지면 층을 도로 넣으면 되고, 그 사이에
어휘가 바뀌지 않는다.

반대로 도메인이 여러 개로 갈리면 컨텍스트를 나눈다. 그것도 DDD 안에서의 조정이다 —
상세는 `presets/architecture/ddd.md` 의 `## 인터뷰에서 조정할 것`.

### 인터뷰가 3~5문을 넘지 않는 이유

**6문째부터는 프리셋을 쓰는 의미가 사라진다.** 질문이 여섯 개를 넘으면 사실상 백지에서 설계하는
것과 같아진다. 프리셋의 이점은 "정해진 것을 다시 논의하지 않는 것" 인데, 문항이 늘수록 정해진
것이 줄어든다.

더 나쁜 쪽은 답의 품질이다. **확신이 없는 사람은 침묵하지 않고 답을 지어낸다.** 다섯 문항까지는
사람이 실제로 아는 것을 답하지만, 그 뒤로는 "글쎄요, 그럼 그렇게 할까요" 가 나오기 시작한다.
그리고 그렇게 나온 답이 `.curvez/architecture.md` 에 **확정으로** 굳는다. 문서에 적힌 결정은
근거가 있어 보이기 때문에 다음 사람이 뒤집지 못한다.

그래서 curvez 는 반대로 설계했다 — 확신이 없는 항목은 **묻지 말고** 프리셋 기본값으로 정하고,
결정 로그에 되돌릴 위치를 남긴다. 되돌릴 위치가 적힌 기본값은 언제든 뒤집을 수 있고,
지어낸 답은 뒤집을 근거조차 남기지 않는다.

문항 선택 규칙과 무엇을 묻지 않는지는 `skills/architecture-setup/SKILL.md` 의 3단계와
`agents/curvez-architect.md` 의 절차 2 가 정본이다.

## DDD — 도메인 규칙이 화면보다 복잡할 때

### 무엇을 해결하려는 구조인가

비즈니스 규칙이 프레임워크·DB·화면보다 오래 산다는 관찰에서 출발한다. "주문은 결제 완료 전에
취소할 수 있다" 는 규칙은 Next.js 를 버리고 Remix 로 가도, Postgres 를 Dynamo 로 바꿔도,
웹에서 앱으로 옮겨도 그대로다. 그런데 규칙을 컴포넌트나 API 라우트 안에 쓰면 그것들과 함께 죽는다.

DDD 프리셋은 **오래 사는 것을 안쪽에, 자주 바뀌는 것을 바깥쪽에** 둔다.

### 핵심 경계

**도메인(규칙)과 그 규칙을 실행하는 모든 것을 분리한다.** 안쪽에서 바깥쪽으로 흐르는 의존은 없다.

내장 폴백 기준 레이어는 `domain` → `application` → `infrastructure` / `presentation` 이다
(정확한 목록은 `agents/curvez-architect.md` 의 절차 1 폴백 표).

- `domain` — 엔티티, 값 객체, 도메인 규칙. import 하는 것이 거의 없다
- `application` — 유스케이스. 도메인 객체를 조립해 하나의 작업을 만든다. 트랜잭션 경계가 여기다
- `infrastructure` — DB, HTTP 클라이언트, 외부 SDK. 도메인이 선언한 인터페이스를 구현한다
- `presentation` — 화면, 라우트, 컴포넌트

### 무엇을 대가로 치르는가

**파일 수가 늘고 간접 층이 생긴다.** 한 줄이면 되는 조회에도 도메인 타입 + 리포지터리 인터페이스 +
구현 + 유스케이스가 필요해진다. CRUD 하나에 파일 넷이다.

**의존 역전을 이해해야 한다.** 도메인이 인터페이스를 선언하고 인프라가 그걸 구현한다는 방향은
처음 보면 거꾸로 보인다. 팀에 이 개념이 없으면 도메인 안에 Prisma 타입이 그대로 들어오고,
레이어는 폴더 이름으로만 남는다.

**얇은 도메인에서는 전부 낭비다.** 규칙이 "필수 입력 체크" 뿐인 화면에 유스케이스 레이어를 두면
그 파일은 인자를 그대로 넘기는 함수 하나가 된다.

### 언제 적합하고 언제 과한가

적합: 서버 상태와 계산 로직이 제품의 핵심일 때. 같은 규칙이 여러 화면에서 쓰일 때.
규칙이 자주 바뀌고 그 변경이 화면 변경과 독립일 때. 도메인 로직을 런타임 없이 테스트하고 싶을 때.

과함: 화면이 대부분 폼과 목록이고 규칙이라 할 것이 검증 몇 줄일 때. 프로토타입.
이럴 때 DDD 는 경계를 만드는 게 아니라 파일만 만든다.

### 스택 매핑

|                  | Next.js                                       | React Native                                     |
| ---------------- | --------------------------------------------- | ------------------------------------------------ |
| `domain`         | 프레임워크 없는 순수 TS 모듈                  | 동일. 웹과 그대로 공유 가능한 유일한 레이어다    |
| `application`    | 서버에서 호출되는 유스케이스 함수             | 화면 훅이 호출하는 유스케이스 함수               |
| `infrastructure` | DB 클라이언트, `fetch` 래퍼, 외부 SDK         | HTTP 클라이언트, 로컬 저장소, 네이티브 모듈 래퍼 |
| `presentation`   | App Router 의 라우트·서버/클라이언트 컴포넌트 | 화면 컴포넌트와 네비게이터                       |

monorepo 에서 DDD 가 가장 잘 맞는 이유가 여기 있다. `domain` 이 프레임워크를 참조하지 않으면
`packages/domain` 하나를 웹과 앱이 그대로 공유한다. 참조하면 공유는 그 순간 불가능해진다.

`profile.json` 의 `paths.domain` 에 소유자를 두지 않은 것도 같은 이유다 — 웹 담당도 앱 담당도
아닌 공용 경로여야 한다.

## 왜 DDD 를 남겼는가

사용자가 아무것도 지정하지 않으면 DDD 로 간다. 되묻지 않는다.

기본값을 정할 때의 기준은 "가장 좋은 것" 이 아니라 **"틀렸을 때 되돌리기 가장 싼 것"** 이다.
DDD 는 이 기준에서 유리하다.

**과하게 나눈 것은 합치기 쉽고, 덜 나눈 것은 나누기 어렵다.** DDD 로 시작했다가 과하다고
판단되면 `application` 을 걷어내고 `presentation` 이 도메인을 직접 부르면 된다 — 삭제 작업이다.
반대로 경계 없이 시작했다가 규칙이 두꺼워지면, 이미 컴포넌트와 라우트 핸들러에 눌어붙은
로직을 전부 다시 써야 한다. 그 시점에는 테스트도 없어서 옮기는 것 자체가 위험해진다.

**어느 쪽이 두꺼워질지 모를 때 안전하다.** 프로젝트 초기에는 화면이 많아질지 규칙이 많아질지
알 수 없다. DDD 는 규칙이 두꺼워지는 쪽에 대비돼 있고, 화면이 두꺼워지면 `presentation` 안에서
기능별로 나누면 된다. 화면 중심 구조는 반대 방향의 대비가 없다 — 규칙이 늘어날 자리가 없다.

**도메인 독립이 이름에 드러난다.** `domain` 이라는 레이어 이름 자체가 "여기는 규칙만 있다" 를
말하므로, 거기에 `react` import 가 들어오면 규칙을 몰라도 어색해 보인다.
경계가 이름에 없으면 위반이 눈에 띄지 않는다.

### 규모가 안 맞을 때 — 벗어나지 말고 조정한다

DDD 가 안 맞아 보이는 신호는 셋이고, 셋 다 **DDD 안에서 해결한다.**

| 신호                                          | 조정                                                                              |
| --------------------------------------------- | --------------------------------------------------------------------------------- |
| 규모가 작다. 라우트 6개 이하, 엔티티 4개 이하 | `application` 을 두지 않는다. `presentation → domain` 두 층                       |
| 화면 수가 도메인 엔티티 수를 크게 앞선다      | `presentation` 안에서 기능별로 나눈다. 레이어를 바꾸지 않는다                     |
| 도메인이 셋 이상으로 갈린다                   | 바운디드 컨텍스트를 나눈다. `presets/architecture/ddd.md` 의 "컨텍스트를 나눌 때" |

세 신호 모두 **관찰 가능한 수치**로 판정한다. "이 프로젝트는 복잡해 보인다" 는 신호가 아니다.
판정선은 `agents/curvez-architect.md` 의 `## 판단 기준` 표에 있다.

**구조를 통째로 바꾸는 것은 이 세 조정으로 안 될 때, 그리고 사용자가 명시적으로 요청할 때만이다.**
그때는 프리셋을 고르는 일이 아니라 **그 프로젝트의 아키텍처를 인터뷰로 직접 구성하는 일**이다.
문항은 `curvez:architecture-setup` 의 `### DDD 를 쓰지 않기로 했을 때` 에 있고,
산출물의 형식은 DDD 와 완전히 같다 — 필수 헤딩 7개, `## 금지 import` 표, lint 강제.

직접 구성한 아키텍처는 **그 프로젝트에만 남는다.** 프리셋으로 승격하지 않는 이유는
한 번 쓴 구조가 검증 없이 기본값이 되는 것을 막기 위해서다. 같은 구조를 반복해서 쓰게 되면
그때 판단한다.

## 공통 원칙 — 도메인은 프레임워크를 참조하지 않는다

**이건 협상 대상이 아니다.** 인터뷰 문항에도 없다.

레이어 이름을 팀 용어로 바꿔도(`domain` → `core` 등) 이 규칙은 그대로 따라간다.
가장 안쪽 레이어가 `next`, `react`, `react-native` 와 네이티브 모듈을 import 하지 않는다 — 이름이 무엇이든.

### 왜 예외를 두지 않는가

**프레임워크 교체에서 도메인을 분리하는 것이 이 구조들을 쓰는 이유 자체다.**
도메인이 프레임워크에 붙어 있으면 레이어를 나눈 이유가 없어진다. 폴더 이름만 남는다.

**모노레포에서 웹과 앱이 같은 도메인을 공유하려면 양쪽 프레임워크 의존이 모두 없어야 한다.**
`domain` 이 `next/headers` 를 하나라도 import 하면 RN 앱이 그 패키지를 못 쓴다. 반대도 같다.
공유는 "대부분 공유" 가 성립하지 않는다 — 한 줄이면 전체가 막힌다.
`profile.json` 의 `paths.domain` 을 웹·모바일 어느 쪽 소유로도 두지 않은 이유가 이것이다.

**요청 컨텍스트에 묶인 도메인은 테스트도 재사용도 불가능해진다.** 도메인 함수가 쿠키나 세션을
직접 읽으면 그 함수를 테스트하는 데 요청 객체가 필요해진다. 단위 테스트가 통합 테스트가 되고,
느려지고, 결국 안 짜게 된다. 재사용도 마찬가지다 — 배치 작업이나 스크립트에서 그 함수를 부를 수 없다.

필요한 값은 **인자로 받는다.** 누가 호출하는지를 도메인이 알면 안 된다.

### 이 원칙이 실제 규칙으로 어떻게 내려오는가

`.curvez/architecture.md` 의 `## 금지 import` 표 첫 두 행이 대개 이것이다 — 도메인 경로에서
웹 프레임워크 import 를 금지하는 규칙, RN import 를 금지하는 규칙. 실제 패턴 예시는
`agents/curvez-architect.md` 의 `## 입출력 프로토콜` 에 있다.

문장으로 "도메인은 프레임워크를 참조하지 않는다" 라고만 적으면 이 원칙은 3주를 못 간다.
왜 그런지가 다음 절이다.

## 규칙은 기계가 검사할 수 있어야 한다

### 문장으로 적힌 경계는 지켜지지 않는다

"`ui` 는 `data` 를 직접 부르지 않는다" 는 문장은 읽으면 이해되지만, **지켜졌는지 확인할 방법이
없다.** 확인할 수 없는 규칙은 위반해도 아무 일이 일어나지 않는다. 아무 일도 일어나지 않는 규칙은
몇 주 뒤에 존재하지 않는다. 문서에는 남아 있지만 코드는 그 문서를 따르지 않고, 그때부터
문서는 읽는 사람을 오도한다.

그래서 curvez 는 **경계 규칙을 정규식으로 쓴다.** `## 금지 import` 는 이 형식이다.

```
| ARCH-001 | 검사 경로 | 금지 패턴 (ERE) | 이유 |
```

세 번째 열이 `grep -E` 에 **그대로** 들어간다. 사람이 옮겨 적거나 해석하는 단계가 없다.
표를 읽어서 검사 명령을 만드는 것이 아니라, 표의 셀이 곧 검사 명령의 인자다.

부작용으로 규칙의 품질이 걸러진다. **정규식으로 표현할 수 없는 규칙은 규칙이 아니라 권고다.**
"컴포넌트는 너무 커지지 않게 한다" 같은 것은 검사할 수 없으므로 `## 예외` 가 아니라 `## 권고` 로
간다. 규칙과 권고를 섞지 않는 것이 규칙의 신뢰를 유지한다.

행 형식·최소 건수·통과 기준의 정본은 `agents/curvez-architect.md` 의 `## 품질 자체 검증` 이다.

### 함정 — 파싱 실패가 "깨끗함" 으로 위장한다

마크다운 표 안에서 `|` 는 열 구분자라서, 정규식의 교대(`a|b`)는 `\|` 로 이스케이프해야 한다.
그러면 검사 스크립트는 표를 파싱한 뒤 **이스케이프를 되돌려야** 한다.

되돌리지 않으면 어떻게 되는가. 패턴이 `from ['\"](next\|react)` 인 채로 `grep -E` 에 들어가고,
`\|` 는 리터럴 파이프 문자로 해석돼 어떤 파일도 매치하지 않는다. **결과는 위반 0건이다.**

이건 실측으로 확인됐다 — 이스케이프 복원을 빼면 규칙 세 개 전부가 0건으로 나온다.
그리고 0건은 "위반이 없다" 와 구별되지 않는다. **검사가 고장 난 상태가 통과로 보인다.**
이런 실패는 아무도 신고하지 않기 때문에 오래 산다.

같은 표를 다루는 다른 함정들(필드 구분자 선택, `grep -c` 의 exit code, `grep --include` 의
따옴표)도 이 검사 경로에 몰려 있다. 전부 `[셸 함정](shell-pitfalls.md)` 에 실측 결과와 함께 정리돼 있다.
검증 스크립트를 직접 손볼 계획이라면 그 문서를 먼저 읽는 편이 싸다.

### 규칙이 없으면 프리셋도 없다

프리셋을 고르는 일과 규칙을 쓰는 일은 하나다. 프리셋을 골라도 `## 금지 import` 가 비어 있으면
그 프로젝트의 구조는 폴더 이름뿐이다. 구현 에이전트는 규칙 표를 읽고 판단하지, 레이어 이름의
어감으로 판단하지 않는다. 구조 감사(`curvez-structure-reviewer`)의 판정 기준도 그 표다.

## 레이어를 더 둘 것인가

프리셋을 확인한 뒤에도 남는 질문이다. `application` 을 둘 것인가 — 이것이 DDD 에서
유일하게 갈리는 레이어다.

### 레이어가 늘면 경계가 아니라 파일만 늘 수 있다

레이어를 하나 더 두면 새 폴더가 생기고, 그 폴더를 통과하는 코드가 생긴다.
**그 코드가 아무것도 하지 않으면 레이어가 아니라 통행세다.** 인자를 그대로 다음 층으로 넘기는
함수만 들어 있는 레이어는 파일 수와 스택 깊이만 늘리고 아무것도 격리하지 않는다.

레이어의 값은 "무엇을 막는가" 로만 판정된다. 막는 것이 없으면 이름이 몇 개든 구조는 평평하다.

### 레이어가 실제로 값을 하는 신호

| 신호                                             | 왜 레이어가 필요하다는 뜻인가                                 |
| ------------------------------------------------ | ------------------------------------------------------------- |
| 같은 로직이 화면 여럿에서 반복된다               | 그 로직의 자리가 없다는 뜻이다. 새 층이 그 자리가 된다        |
| 화면을 안 건드리는 변경인데 화면 파일이 수정된다 | 변경의 축과 폴더의 축이 어긋나 있다                           |
| 도메인 테스트에 런타임·요청 객체·모킹이 필요하다 | 격리되지 않은 것이다. 층을 끼워 의존을 밀어내야 한다          |
| 한 파일이 조회·계산·표현을 다 한다               | 세 가지가 서로 다른 이유로 바뀐다. 함께 두면 셋 다 위험해진다 |
| 트랜잭션 경계가 어디인지 코드로 안 보인다        | 유스케이스 층이 없다는 신호다                                 |

### 레이어를 두지 말아야 할 신호

| 신호                                                      | 왜                                        |
| --------------------------------------------------------- | ----------------------------------------- |
| 새 층의 파일이 전부 위임 한 줄이다                        | 격리하는 것이 없다                        |
| 층을 추가한 이유를 "원래 이렇게 한다" 로만 설명할 수 있다 | 이 프로젝트의 문제에서 나온 결정이 아니다 |
| 그 층을 지웠을 때 깨지는 규칙을 말할 수 없다              | 검사 가능한 경계가 없다                   |

### 판정선

curvez 는 이 판단을 감이 아니라 **규모 기준**으로 가른다. 라우트(화면) 수와 도메인 엔티티 수
양쪽을 보고, 둘 다 작으면 두지 않고 하나라도 넘으면 둔다.

정확한 값은 `agents/curvez-architect.md` 의 `## 판단 기준` 표가 정본이다. 여기에 옮겨 적지 않는 이유는
값이 바뀌었을 때 두 문서가 다른 말을 하는 상황을 만들지 않기 위해서다.

이 선을 수치로 둔 이유는 두 가지다. **작은 규모에서는 경계가 안 생기고 파일 수만 는다.**
그리고 **넘어선 뒤에 레이어를 끼우는 비용이 처음부터 두는 비용보다 크다** — 경계 없이 자란 코드는
이미 서로를 자유롭게 참조하고 있어서, 층을 끼우려면 참조를 먼저 끊어야 한다.

그래서 판정이 애매하면 **레이어가 적은 쪽**을 고르되, 넘을 것이 예상되면 미리 둔다.
`curvez-architect` 의 tie-break 규칙도 같은 방향이다.

## 정리

- 프리셋은 **검증된 경계 배치의 이름**이다. 고르는 순간 논의가 하나로 줄어든다
- 인터뷰는 팀 어휘와 예외만 조정한다. 3~5문을 넘기면 프리셋의 이점이 사라지고 답의 품질이 떨어진다
- DDD 가 기본인 이유는 최선이어서가 아니라 **틀렸을 때 되돌리기 가장 싸서**다
- 프리셋이 무엇이든 **도메인은 프레임워크를 참조하지 않는다.** 이건 인터뷰 항목이 아니다
- 경계 규칙은 **정규식으로 쓴다.** 검사할 수 없는 규칙은 규칙이 아니라 권고다
- 레이어는 **막는 것이 있을 때만** 값을 한다. 늘리기 전에 무엇을 막는지 말할 수 있어야 한다
