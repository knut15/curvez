# 왜 이 구조인가 — curvez 설계 근거

curvez 의 구조에는 다르게 갈 수 있었던 갈림길이 여럿 있었다. 이 문서는 그 갈림길마다
**무엇을 골랐고, 무엇을 버렸고, 왜 그랬고, 뒤집으려면 어디를 고쳐야 하는지**를 남긴다.

이 기록이 없으면 나중에 누군가 — 반년 뒤의 나를 포함해서 — 이미 답이 난 고민을 처음부터 다시 한다.
더 나쁜 경우, 버린 대안이 더 좋아 보여서 되돌렸다가 그것을 버린 이유를 다시 발견한다.

읽는 순서는 상관없다. 다만 2번이 3번을, 3번이 4번과 5번을 낳았다. 이 셋은 한 덩어리로 읽는 편이 낫다.

절차나 규칙 값은 여기에 없다. 이 문서는 **왜**만 담는다. 무엇을 어떤 순서로 하는지는 스킬에,
누가 무엇을 책임지는지는 에이전트 정의에, 수치는 `scripts/lib/spec.mjs` 에 있다.

---

## 1. 배포 형태 — 플러그인 마켓플레이스

**골랐다:** Claude Code 플러그인 마켓플레이스. 저장소 루트가 마켓플레이스(`.claude-plugin/marketplace.json`),
그 안의 `plugins/curvez` 가 플러그인이다. 새 프로젝트는 마켓플레이스를 등록하고 플러그인을 설치한다.

**버렸다:**

- **템플릿 복사(스캐폴딩).** `curvez init` 같은 명령으로 에이전트·스킬·스크립트를 프로젝트에 복사해 넣는 방식.
- **하이브리드.** 규약과 검증기는 플러그인으로 배포하고, 에이전트 정의만 복사해 프로젝트가 직접 고치게 하는 방식.

**왜:**

복사 방식의 문제는 **개선이 전파되지 않는다**는 것 하나로 요약된다. curvez 의 핵심 산출물은
"새 에이전트·스킬을 어떻게 쓰는가"의 규약과 그것을 강제하는 검증 스크립트다. 규약은 실제로 쓰면서
계속 바뀐다 — 이 문서의 8번과 9번이 그 사례다. 복사본을 쓰는 프로젝트 다섯 개가 있으면
규칙 하나를 고칠 때마다 다섯 곳을 고쳐야 하고, 실제로는 세 곳만 고쳐지고 두 곳은 낡은 규칙으로 계속 돈다.
이 상태를 나중에 발견하면 어느 쪽이 정본인지 판단할 근거조차 없다.

하이브리드도 같은 문제를 절반만 안는다. 게다가 "이 파일은 고쳐도 되고 저 파일은 고치면 안 된다"는
경계를 사람이 기억해야 하는데, 그 경계는 문서에만 있고 강제되지 않는다.

플러그인 방식의 대가는 **프로젝트가 curvez 의 에이전트 정의를 직접 수정할 수 없다**는 점이다.
이건 대가가 아니라 의도다. curvez 는 보일러플레이트고, 프로젝트 고유의 에이전트·스킬은
프로젝트가 **따로 만든다**. 그 작성 규약을 제공하는 것이 `authoring-agents` · `authoring-skills` 스킬이고,
프로젝트가 만든 결과물도 같은 검증기를 통과한다. 확장 방법은 [확장 가이드](extending.md)에 있다.

**뒤집으려면:** `.claude-plugin/marketplace.json` 과 `plugins/curvez/.claude-plugin/plugin.json`.
다만 뒤집기 전에, 복사본 다섯 벌을 동기화할 방법을 먼저 정해야 한다. 그 방법이 없으면 뒤집을 이유도 없다.

## 2. 병렬 런타임 — Claude Code 내장 서브에이전트

**골랐다:** Claude Code 의 `Agent` 도구. 오케스트레이터가 서브에이전트를 띄우고, 각 서브에이전트는
자기 컨텍스트에서 작업한 뒤 결과를 돌려준다.

**버렸다:** **tmux 워커 방식**(oh-my-claudecode 가 쓰는 모델). 별도 CLI 프로세스를 tmux 패널에 띄우고
패널끼리 메시지를 주고받는 구조.

**왜:**

두 가지다.

**설치 의존성이 없다.** tmux 방식은 tmux 가 깔려 있어야 하고, 워커가 될 CLI 가 각각 인증되어 있어야 하고,
패널 이름 규약이 맞아야 한다. curvez 는 "설치하면 바로 팀 병렬 개발에 들어갈 수 있어야 한다"가 목표인데,
그 앞에 환경 준비 단계가 붙으면 목표가 무너진다. 같은 이유로 스크립트도 외부 의존성 0 의 node ESM 으로 고정했다 —
설치 시점에 `pnpm install` 을 강요하지 않기 위해서다.

**컨텍스트 격리가 깨끗하다.** 서브에이전트는 자기 대화 컨텍스트만 갖는다. 구현 에이전트가 리뷰어의
사고 과정을 보지 않고, 리뷰어가 구현 에이전트의 시행착오를 보지 않는다. tmux 방식은 패널 출력을
서로 읽을 수 있어서 격리가 규약으로만 유지된다. 리뷰의 독립성이 중요한 하네스에서 이 차이는 크다
(6번 참조).

**대가:** 서브에이전트끼리 **실시간 대화가 불가능하다.** 띄우면 끝날 때까지 말을 걸 수 없고,
서브에이전트는 사용자에게 질문할 수도 없다. 실제로 이 제약 때문에 아키텍처 인터뷰 3~5문이
시작조차 못 하는 상황이 나왔고, 오케스트레이터가 질문을 중계하는 구조로 풀었다.
그리고 이 대가가 3번을 낳았다 — 대화가 안 되면 남는 통신 수단은 파일뿐이다.

**뒤집으려면:** `agents/curvez-orchestrator.md` 의 `tools` 에서 `Agent` 를 빼고,
`skills/team-orchestration/SKILL.md` 의 실행 절차를 통째로 갈아야 한다.
핸드오프 계약(3번)은 그대로 살아남는다 — 파일 기반 계약은 런타임과 독립이다.
팀 실행 모델의 세부는 [팀 실행 모델](team-execution.md)에 있다.

## 3. 에이전트 간 통신 — 파일 기반 핸드오프

**골랐다:** `.curvez/handoff/<from>.<timestamp>.json`. 에이전트는 작업을 마치면 이 경로에 계약 파일을 쓴다.
스키마 정본은 `scripts/schema/handoff.schema.json`, 검증은 `scripts/validate-handoff.mjs`.

**버렸다:**

- **메시지 패싱.** 2번에서 실시간 대화를 버렸으니 애초에 선택지가 아니었다.
- **단일 상태 파일 덮어쓰기.** `.curvez/handoff.json` 하나를 계속 갱신하는 방식.
- **`.curvez/` 를 gitignore.** 상태 디렉터리는 산출물이 아니니 커밋하지 말자는 안.

**왜 파일인가:** 2번의 결론이다. 대화가 불가능하면 남는 것은 공유 저장소뿐이다.
파일은 그 중에서 가장 검사하기 쉽고, 스키마로 강제할 수 있고, diff 로 볼 수 있다.

**왜 덮어쓰지 않고 쌓는가:** 회고가 **실행 이력을 시간순으로 재구성**하기 때문이다.
`curvez-retrospector` 는 "어디서 어긋났는가"를 찾는데, 그러려면 각 에이전트가 **그 시점에**
무엇을 알고 있었고 무엇을 결정했는지가 남아 있어야 한다. 덮어쓰면 마지막 상태만 남고,
마지막 상태에는 "왜 두 번 돌았는지"가 없다. 파일명에 타임스탬프를 넣는 것도 같은 이유다 —
정렬만으로 순서가 복원된다.

부수 효과로 같은 라운드에서 여러 에이전트가 동시에 핸드오프를 써도 서로 충돌하지 않는다.
파일명이 `<from>` 으로 갈리므로 소유권이 자동으로 분리된다(4번과 같은 원리다).

**왜 git 에 커밋하는가:** 에이전트 간 계약이 **리뷰 가능해야** 하기 때문이다.
핸드오프는 "이 에이전트가 무엇을 근거로 done 이라고 했는가"의 기록이다. 이게 커밋에 안 들어가면
PR 을 보는 사람은 코드 변경만 보고, 그 변경이 어떤 계약 아래 나왔는지는 볼 수 없다.
`.curvez/architecture.md` 의 결정 로그도 같다 — 결정은 코드와 같은 커밋에 남아야 나중에 대조된다.
예외는 `.curvez/tmp/` 하나이고, 여기만 gitignore 대상이다.

**뒤집으려면:** 스키마는 `scripts/schema/handoff.schema.json`, 검증 규칙은 `scripts/validate-handoff.mjs`,
필드 목록은 `scripts/lib/spec.mjs`. 세 곳이 아니라 실질적으로 두 곳이다 — 필드 정의가 `spec.mjs` 에 모여 있다.
상태 전이와 필드별 의미는 [핸드오프 계약](handoff-contract.md)에 있다.

## 4. 파일 소유권 분할 — 겹치면 병렬을 포기한다

**골랐다:** 병렬로 띄우는 에이전트마다 **쓰기 가능한 경로를 배타적으로** 배정한다.
배정이 겹치면 병렬 실행을 포기하고 순차 실행으로 강등한다. 판정과 강등은 오케스트레이터가 한다.

**버렸다:**

- **락 파일.** 먼저 잡은 쪽이 쓰고 나중 쪽은 기다리는 방식.
- **머지 후처리.** 둘 다 쓰게 두고 나중에 충돌을 합치는 방식.
- **경로 폴백.** 프로파일에 경로가 없으면 에이전트가 관례로 추측하게 하는 방식.

**왜:**

병렬 실행에서 두 에이전트가 같은 파일을 고치면 **나중에 쓴 쪽이 앞선 쪽을 조용히 지운다.**
"조용히"가 핵심이다. 에러도 경고도 없고, 두 에이전트 모두 자기 작업이 성공했다고 보고한다.
사라진 변경은 나중에 테스트가 깨지거나 리뷰에서 우연히 발견되는데, 그때는 어느 라운드에서
날아갔는지 추적하기 어렵다.

락 파일은 이 문제를 막지만 대가가 크다. 서브에이전트는 서로 통신할 수 없으므로(2번)
락을 기다리는 동안 할 수 있는 일이 없고, 결국 순차 실행과 같아지면서 락 관리 코드만 추가된다.
머지 후처리는 더 나쁘다 — 두 에이전트의 의도를 알아야 합칠 수 있는데, 그 의도는 핸드오프의
`summary` 한 줄뿐이다.

**경로 폴백을 버린 이유는 실제로 드러난 문제다.** 구현 에이전트마다 "경로가 없으면 이렇게 찾는다"를
각자 정의했더니, monorepo 스택에서 `curvez-nextjs` 와 `curvez-react-native` 의 폴백이
같은 디렉터리를 가리키게 됐다. 폴백은 소유권 충돌을 **만들어내는** 장치였다.
그래서 스택별 필수 경로 키를 정하고, 없으면 추측하지 말고 `blocked` 를 내도록 바꿨다.
필수 키 목록은 [핸드오프 계약](handoff-contract.md)과 `skills/bootstrap/SKILL.md` 에 있다.

예외가 둘 있다.

**`paths.tests` 는 폴백을 허용한다.** 테스트 위치는 관례가 강해 추측이 어긋날 여지가 작고,
어긋나도 기존 파일을 덮어쓰지 않는다 — 엉뚱한 곳에 새 테스트가 생길 뿐이고 그건 눈에 보인다.
소유권 사고와 성질이 다르다.

**`paths.domain` 은 소유자를 두지 않는다.** 도메인 레이어는 웹과 모바일이 함께 쓰는 코드다.
어느 한쪽에 소유권을 주면 다른 쪽이 도메인을 고쳐야 할 때마다 막히고, 둘 다 주면 4번의 사고가 난다.
그래서 소유자를 아예 두지 않고, 이 경로를 건드리는 작업이 있으면 두 구현 에이전트를 동시에
띄우지 않는 것으로 처리한다. **소유권을 나누는 대신 병렬을 포기한 것**이고, 이게 이 절의 원칙 그대로다.

**뒤집으려면:** 병렬 판정과 강등 절차는 `skills/team-orchestration/SKILL.md`,
경로 필수 규칙은 `skills/bootstrap/SKILL.md` 와 프로파일 스키마.
소유권 경계는 각 에이전트 정의의 `## 협업과 팀 내 위치` 섹션에도 적혀 있다.

## 5. 검증 없는 완료를 금지한다

**골랐다:** `status: done` 은 `verification` 이 비면 쓸 수 없다. 스키마 수준에서 막고,
`scripts/validate-handoff.mjs` 가 검사한다. `blocked` 는 `blocked_on` 이 비면 쓸 수 없다는 규칙도 같은 쌍이다.

**버렸다:**

- **`done` 을 자유롭게 쓰게 하고 나중에 검증.** 에이전트가 완료를 선언하면 믿고, 최종 단계에서 한 번 확인하는 방식.
- **`verification` 을 권고 사항으로.** 필드는 두되 비어도 통과시키는 방식.

**왜:**

핸드오프는 **다음 에이전트가 읽는 입력**이다. 수신 에이전트는 송신자의 `done` 을 믿고 자기 작업을 시작한다.
아키텍트가 검증 없이 `done` 을 내면 구현 에이전트가 그 아키텍처를 전제로 코드를 쓰고,
QA 가 검증 없이 `done` 을 내면 리뷰어가 테스트가 도는 상태를 전제로 리뷰한다.
**오염이 한 곳에서 끝나지 않고 전파된다.** 그리고 전파된 뒤에 발견하면 어느 단계의 `done` 이
거짓이었는지 역추적해야 한다.

나중에 검증하는 방식은 이 전파를 막지 못한다. 최종 단계에서 발견해봐야 이미 세 에이전트의 작업이
그 위에 쌓인 뒤다. 권고 사항으로 두는 방식은 더 확실히 실패한다 — 8번의 원칙 그대로,
문서에 적힌 규칙은 지켜지지 않는다.

**`blocked` 는 실패가 아니다.** 이게 이 결정의 나머지 절반이다. `done` 을 어렵게 만들기만 하면
에이전트는 검증을 지어내거나 억지로 통과시킬 유인을 갖는다. 그래서 **정보가 없을 때 멈추는 것을
정상 상태로 정의**했다. 실패는 `blocked` 를 내는 것이 아니라 **추측으로 채우고 `done` 하는 것**이다.
각 에이전트 정의의 `## 에러 핸들링` 섹션이 전부 이 원칙을 따른다 — 계약 위반이나 정보 부족은
추측이 아니라 `blocked` 보고다.

`partial` 은 그 사이다. 일부는 검증됐고 일부는 남았을 때 쓴다.

**뒤집으려면:** `scripts/schema/handoff.schema.json` 의 조건부 필수 규칙과
`scripts/validate-handoff.mjs`. 검증을 무엇으로 인정할지의 기준은 [품질 모델](quality-model.md)에 있다.

## 6. 리뷰어는 읽기 전용

**골랐다:** `curvez-reviewer` 와 `curvez-structure-reviewer` 는 파일을 쓰지 않는다.
`disallowedTools` 로 쓰기 도구를 막고, 결과는 **최종 응답 텍스트에 담은 핸드오프 JSON** 으로 반환한다.
그 JSON 을 `.curvez/handoff/` 에 파일로 남기는 것은 `curvez-orchestrator` 가 대필한다.

**버렸다:**

- **리뷰어가 직접 고친다.** 지적하면서 바로 수정까지 하는 방식.
- **리뷰어에게 `.curvez/` 안에서만 쓰기 허용.** 핸드오프 파일은 쓰되 소스는 못 쓰게 하는 방식.

**왜 읽기 전용인가:**

리뷰어가 직접 고치면 **리뷰 대상과 주체가 섞인다.** 다음 리뷰는 리뷰어 자신이 쓴 코드를 리뷰하게 되고,
그 코드는 이미 "리뷰어 기준으로 옳은" 코드라서 지적이 나올 수 없다. 검증의 기준점이 사라진다.
게다가 구현 에이전트는 자기 코드가 왜 바뀌었는지 모르는 채로 다음 작업을 이어받는다 —
지적을 받아 고치는 것과 남이 고쳐놓은 것을 발견하는 것은 학습 효과가 다르다.

### 여기서 실제로 드러난 문제 두 가지

**하나: `Write` 를 막으니 핸드오프 파일도 못 쓴다.**

`disallowedTools` 에 `Write` 를 넣은 순간 리뷰어는 계약 파일을 만들 수 없게 됐다.
모든 에이전트가 핸드오프를 남겨야 하는데 리뷰어만 남길 수단이 없는 모순이다.

"`.curvez/` 안에서만 쓰기 허용" 은 도구 권한 모델이 경로 단위 제어를 하지 않아서 성립하지 않는다.
그래서 **리뷰어는 핸드오프 JSON 을 응답 텍스트로 반환하고, 오케스트레이터가 그것을 받아 파일로 쓰는**
구조로 풀었다. 계약의 형식은 다른 에이전트와 동일하고, 저장 주체만 다르다.
이 대필 구조는 2번에서 오케스트레이터가 유일한 실행 주체가 된 것과 짝이 맞는다 —
리뷰어의 출력은 어차피 오케스트레이터를 거쳐 돌아온다.

**둘: 도구 권한만으로는 읽기 전용이 강제되지 않는다.**

리뷰어에게는 `Bash` 가 필요하다. `grep`, `git diff`, 순환 의존 검출 같은 조사를 해야 하기 때문이다.
그런데 `Bash` 가 있으면 `>` 리다이렉션이나 `sed -i` 로 파일을 얼마든지 고칠 수 있다.
`disallowedTools: Write, Edit, NotebookEdit` 는 **우회 가능한 울타리**였다.

완전히 막을 방법은 없다 — `Bash` 를 빼면 리뷰 자체가 불가능하다. 그래서 **에이전트 정의 본문에
금지 명령을 열거**하는 것으로 보완했다. 파일을 만들거나 고치거나 지우는 명령을 이름으로 나열하고,
허용되는 조사 명령도 함께 적었다. 이건 강제가 아니라 명시적 지시이고, 그 한계를 인정한 선택이다.
`agents/curvez-reviewer.md` 의 도구 사용 규칙 부분이 그 목록이다.

여기서 얻은 일반 원칙: **도구 권한은 의도를 표현하지 실행을 보장하지 않는다.**
권한으로 막았다고 안심하지 말고, 그 권한으로 무엇이 우회 가능한지 한 번 더 따져야 한다.

**뒤집으려면:** 두 리뷰어 정의의 `disallowedTools` 와 도구 사용 규칙,
그리고 `skills/team-orchestration/SKILL.md` 의 대필 절차. 대필을 없애려면 리뷰어에게 쓰기를 줘야 하고,
그러면 이 절 전체가 무너진다.

## 7. `Agent` 도구는 오케스트레이터만 갖는다

**골랐다:** 13종 에이전트 중 `curvez-orchestrator` 하나만 `tools` 에 `Agent` 를 갖는다.
서브에이전트는 다른 서브에이전트를 띄울 수 없다.

**버렸다:**

- **자유 위임.** 각 에이전트가 필요하면 자기 판단으로 하위 에이전트를 띄우는 방식.
- **깊이 제한 위임.** 2단계까지만 허용하는 절충안.

**왜:**

서브에이전트가 또 서브에이전트를 띄우면 **실행 트리의 깊이를 통제할 수 없다.**
구현 에이전트가 조사 에이전트를 띄우고, 그 조사 에이전트가 또 무언가를 띄우는 식으로
몇 층까지 내려갈지 정적으로 알 수 없다. 각 층이 컨텍스트와 시간을 소비하므로 비용도 예측할 수 없다.

더 큰 문제는 **추적이 끊긴다**는 것이다. 어딘가에서 작업이 실패했을 때, 트리가 평평하면
"이 라운드의 이 에이전트"로 바로 특정된다. 트리가 깊으면 실패가 상위로 전달되면서
요약되고, 3층 아래에서 무슨 일이 있었는지는 중간 층의 `summary` 한 줄로만 남는다.
회고(3번)가 이력을 재구성할 근거가 사라진다.

깊이 제한 절충안을 버린 이유는 강제 수단이 없어서다. "2단계까지" 는 문서에 적을 수는 있지만
검증기가 실행 시점의 깊이를 알 수 없다. 8번의 원칙대로, 강제할 수 없는 규칙은 규칙이 아니다.
반면 "`Agent` 도구는 한 에이전트만 갖는다" 는 프론트매터에 적혀 있고 기계적으로 확인된다.

**대가:** 오케스트레이터가 병목이 된다. 모든 위임이 한 곳을 거치므로 오케스트레이터의 컨텍스트에
전체 라운드의 정보가 쌓인다. 이걸 완화하는 것이 3번의 파일 기반 핸드오프다 —
오케스트레이터는 각 에이전트의 전체 작업 내용이 아니라 계약 파일만 읽으면 된다.

**뒤집으려면:** 각 에이전트 정의의 `tools` 필드. 다만 뒤집기 전에 실행 트리의 깊이를
어떻게 관측할지부터 정해야 한다.

## 8. 규약은 문서가 아니라 스크립트로 강제한다

**골랐다:** 작성 규약을 검증 스크립트로 만든다. `scripts/validate-agents.mjs` ·
`scripts/validate-skills.mjs` · `scripts/validate-handoff.mjs` 가 프론트매터 필수 필드,
본문 필수 섹션, 트리거 경계 섹션, 분량 상한, 참조 링크 유효성을 기계적으로 막는다.
`scripts/doctor.mjs` 가 이들을 한 번에 돌린다.

**버렸다:**

- **문서로만 규약을 정의.** 작성 가이드를 잘 써두고 사람과 에이전트가 따르기를 기대하는 방식.
- **리뷰로 강제.** 리뷰어가 규약 위반을 지적하게 하는 방식.

**왜:**

**문서에 적힌 규칙은 지켜지지 않는다.** 악의 때문이 아니라, 규칙이 많아지면 작성 시점에
전부 떠올릴 수 없기 때문이다. 에이전트 정의 하나에 필수 프론트매터 필드와 순서가 고정된 본문 섹션이
모두 필요한데(목록은 `scripts/lib/spec.mjs`), 이걸 매번 문서를 다시 읽어가며 맞추는 것은 현실적이지 않다.

리뷰로 강제하는 방식은 리뷰어의 판단에 의존한다. 같은 위반이 어떤 리뷰에서는 잡히고 어떤 리뷰에서는
넘어가면, 규약은 있으나 마나다. 그리고 리뷰어는 opus 모델이 매번 문서를 읽는 비용을 치른다 —
`grep` 한 번으로 끝날 검사에.

검증기를 먼저 만든 것도 같은 판단이다. 빌드 순서에서 규약 확정과 검증 스크립트가 에이전트 13종·스킬 15종보다
앞에 온다. **검증기가 있어야 이후 24개 산출물이 자동으로 품질을 유지한다.** 반대 순서였다면
24개를 다 만든 뒤에 규약 위반 24건을 손으로 고쳤을 것이다.

### 실제 사례 — 강제되지 않는 규칙은 통과한다

`new-agent.mjs` / `new-skill.mjs` 는 뼈대를 생성하면서 채워야 할 자리에 TODO 마커를 남긴다.
작성 가이드에는 **"TODO 를 채우지 않으면 통과하지 않는다"** 고 적혀 있었다.
그런데 그것을 강제하는 검사 규칙이 없었다.

결과는 예상대로다. **뼈대가 그대로 검증을 통과했다.** 필수 섹션은 헤딩이 있으니 존재하고,
필수 필드도 스캐폴드가 채워뒀으니 존재한다. 검증기 입장에서는 완벽한 문서였다.
문서에 그렇게 쓰여 있다는 사실은 아무것도 막지 못했다.

TODO 마커 검사 규칙을 추가하고서야 막혔다. 규칙을 추가할 때 한 가지 함정이 더 있었는데,
**문서가 그 마커를 설명하는 경우**를 제외해야 했다. `authoring-agents` 스킬은 TODO 마커가
무엇인지 설명하는 문서라서, 단순 문자열 검사로는 자기 자신이 걸린다.

이 사례가 이 절의 원칙을 가장 잘 보여준다. "문서에 적혀 있었다" 는 변명이 되지 않는다.
**규칙을 추가한다는 것은 검사를 추가한다는 뜻**이고, 그러지 않았다면 그 규칙은 존재하지 않는 것이다.

검증기가 무엇을 어떻게 막는지는 [에이전트 작성](agent-authoring.md)과 [스킬 작성](skill-authoring.md)에 있다.

**뒤집으려면:** 검사 규칙은 각 `validate-*.mjs`, 규칙 값은 `scripts/lib/spec.mjs`.
규칙을 완화하고 싶다면 값을 바꾸는 것이지 검사를 지우는 것이 아니다.

## 9. 같은 의미는 한 곳에만 — 단일 출처

**골랐다:** 정보의 종류마다 정본을 하나씩 정하고, 나머지는 그곳을 가리키기만 한다.

| 담는 것                                 | 정본                       | 읽는 주체            |
| --------------------------------------- | -------------------------- | -------------------- |
| 규약 **수치** (필수 필드, 허용값, 상한) | `scripts/lib/spec.mjs`     | 검증기               |
| **절차** (무엇을 순서대로 하는가)       | `skills/*/SKILL.md`        | 실행 중인 에이전트   |
| **조건부 상세** (도메인 분기, 긴 예시)  | `skills/*/references/*.md` | 분기에 걸린 에이전트 |
| **역할·권한·통신**                      | `agents/*.md`              | 서브에이전트         |
| **왜** (설계 근거, 배경, 실패 사례)     | `docs/*.md`                | 사람                 |

**버렸다:**

- **에이전트 정의에 절차를 함께 적기.** 각 에이전트가 자기 절차를 자기 정의 안에 갖는 방식.
- **문서마다 필요한 값을 옮겨 적기.** 읽는 사람이 다른 파일을 열지 않아도 되게 하는 방식.

**왜:**

**같은 의미가 두 곳에 있으면 한쪽만 고쳐진다.** 그리고 두 판본이 서로 다른 말을 하기 시작하면,
어느 쪽이 맞는지 판단할 근거가 없다. 더 나쁜 것은 이 상태가 조용하다는 점이다 —
에러도 경고도 없고, 낡은 쪽을 읽은 에이전트가 낡은 대로 동작한다.

절차를 에이전트 정의에 넣지 않은 이유는 재사용 때문이기도 하다. `quality-gate` 는 `curvez-qa` 와
`curvez-reviewer` 가 함께 쓰고, `agent-contract` 는 전 에이전트가 쓴다. 절차가 정의 안에 있으면
쓰는 에이전트 수만큼 사본이 생긴다.

### 실제 사례 — 낡은 판본이 계속 돈다

구조 리뷰 에이전트의 정의 안에 순환 의존 검출 명령이 들어 있었고, 같은 절차가
`structure-audit` 스킬에도 있었다. 스킬 쪽은 개선되고 정의 쪽은 그대로 남았다.

**결과: 같은 순환을 2건으로 중복 보고했고, 중복된 창을 병합하지 않았다.**
개선된 스킬 판본에는 중복 제거와 창 병합이 들어 있었지만, 에이전트가 자기 정의에 적힌
낡은 명령을 먼저 쓰면서 개선분이 적용되지 않았다.

이 사례의 교훈은 "두 판본이 있으면 낡은 쪽이 계속 돈다" 는 것이다.
낡은 쪽을 지우는 것이 아니라, **애초에 두 벌이 생기지 않게** 하는 것이 해법이다.
그래서 검출 절차는 스킬로 이관하고, 에이전트 정의는 스킬을 가리키기만 한다.

이 문서도 같은 규칙을 따른다. 여기 나온 수치나 절차는 하나도 없다 —
`spec.mjs` 의 값을 옮겨 적었다면, 상한을 바꿀 때 이 문서가 낡은 값을 계속 말하게 된다.
`docs/` 가 정본인 것은 **왜**뿐이다.

**뒤집으려면:** 뒤집을 대상이 아니다. 이 원칙은 다른 여덟 개를 유지하는 방식이다.
다만 경계가 애매한 내용을 만나면 판정 질문이 하나 있다 —
**이 문단이 바뀌면 에이전트의 동작이 바뀌는가?** 그렇다면 스킬이나 에이전트 정의에 있어야 하고,
그렇지 않다면 `docs/` 에 있어야 한다.

## 결정들이 서로를 지탱하는 방식

아홉 개가 독립된 선택이 아니다. 하나를 뒤집으면 다른 것들이 따라 무너진다.

```
1. 플러그인 배포
   └─ 개선이 한 곳에서 전파된다 → 9. 단일 출처가 성립하는 전제

2. 내장 서브에이전트
   ├─ 대화 불가 → 3. 파일 기반 핸드오프
   ├─ 유일한 실행 주체 → 7. Agent 도구 독점
   └─ 사용자에게 못 물음 → 오케스트레이터가 인터뷰 중계

3. 파일 기반 핸드오프
   ├─ 파일명이 <from> 으로 갈림 → 4. 소유권 분할과 같은 원리
   ├─ 스키마로 강제 가능 → 5. done 조건
   ├─ 쌓이므로 시간순 복원 → 회고가 가능해짐
   └─ 계약이 텍스트 → 6. 리뷰어 대필이 성립

4. 소유권 분할 ─ 겹치면 병렬 포기
5. 검증 없는 done 금지 ─ blocked 는 정상
6. 읽기 전용 리뷰어 ─ 권한은 의도, 강제는 아님

8. 스크립트 강제 ─ 4·5·6·7 의 규칙을 실제로 막는 층
9. 단일 출처 ─ 위 전부가 한 벌로 유지되게 하는 규칙
```

가장 아래에 있는 것은 8번과 9번이다. 나머지 일곱 개는 **결정**이고, 이 둘은 그 결정들이
시간이 지나도 실제로 지켜지게 만드는 **장치**다. 장치가 없으면 결정은 문서로만 남고,
문서로만 남은 규칙은 지켜지지 않는다 — 8번의 사례가 그것을 그대로 보여줬다.
