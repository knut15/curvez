# 확장 가이드

curvez 는 보일러플레이트다. 코어에 들어 있는 에이전트 13종과 스킬 15종은 **어느 프로젝트에나
해당하는 것들**만 남긴 결과다. 결제 도메인, 사내 디자인 시스템, 특정 백오피스 규칙 —
프로젝트 고유의 담당자와 절차는 프로젝트 담당자가 만든다.

이 문서는 그 담당자를 위한 실전 가이드다. 확장의 전체 흐름, 무엇을 어디에 둘 것인가,
그리고 이 프로젝트에서 실제로 나온 실수들을 담는다.

## 이 문서가 답하지 않는 것

확장 작업은 문서 넷에 걸쳐 있다. 어느 것을 펴야 하는지부터 정리한다.

| 궁금한 것                                                | 보는 곳                             |
| -------------------------------------------------------- | ----------------------------------- |
| **무엇을 코어에 두고 무엇을 프로젝트에 둘 것인가**       | 이 문서                             |
| **확장의 전체 흐름과 흔한 실수**                         | 이 문서                             |
| 에이전트 정의를 실제로 어떻게 쓰는가 (필드·섹션·검증)    | `authoring-agents` 스킬             |
| 스킬 문서를 실제로 어떻게 쓰는가 (description·경계·분량) | `authoring-skills` 스킬             |
| 에이전트 7섹션이 왜 그 7개인가                           | [에이전트 설계](agent-authoring.md) |
| 스킬 트리거와 progressive disclosure 의 근거             | [스킬 설계](skill-authoring.md)     |
| 규약 **값** (필수 필드, 허용 모델, 분량 상한)            | `scripts/lib/spec.mjs`              |

**스킬이 정본이고 이 문서는 아니다.** 아래에 나오는 절차는 뼈대만 보여준다.
각 단계에서 무엇을 어떻게 채우는지는 해당 스킬을 읽는다.
두 곳에 같은 규칙을 적으면 한쪽만 고쳐져 낡은 판본이 계속 돌기 때문이다.

## 코어 vs 프로젝트 — 어디에 두는가

| 위치                                                             | 무엇을                      |
| ---------------------------------------------------------------- | --------------------------- |
| curvez 코어 (`plugins/curvez/agents/`, `plugins/curvez/skills/`) | 모든 프로젝트에 공통인 것   |
| 프로젝트 (`.claude/agents/`, `.claude/skills/`)                  | 이 프로젝트에만 해당하는 것 |

스캐폴더의 기본 출력은 프로젝트 쪽이다. `--dir` 을 붙이지 않으면 `.claude/agents/`,
`.claude/skills/` 에 생긴다. 코어에 넣으려면 명시적으로 경로를 지정해야 한다.
**기본값이 프로젝트인 것이 의도다.** 코어에 넣는 편이 편해 보일 때가 많은데, 되돌리는 비용이 다르다.

### 판정 질문

> **다음 프로젝트에서도 이게 필요한가?**

- 그렇다 → 코어 후보다. 다만 "필요하다" 가 아니라 "지금 이 형태 그대로 필요하다" 여야 한다.
  경로 하나, 명령 하나가 프로젝트마다 달라진다면 그건 코어에 들어갈 게 아니라
  `.curvez/profile.json` 에서 읽어야 할 값이다.
- 아니다 → 프로젝트다. 고민할 것 없다.
- 모르겠다 → 프로젝트에 둔다. 두 번째 프로젝트에서 같은 것을 또 만들게 되면 그때 코어로 올린다.
  두 번 만들어본 뒤에야 무엇이 공통이고 무엇이 프로젝트 사정이었는지 갈린다.

### 되돌리기 비용이 다르다

코어를 고치면 **그 플러그인을 쓰는 모든 프로젝트에 전파된다.**
프로젝트 파일을 잘못 만들면 그 프로젝트만 고장 나고, 지우면 끝이다.
코어 에이전트의 소유 경로를 하나 바꾸면 이미 돌던 다른 프로젝트의 팀 편성이 조용히 달라진다 —
그쪽에서는 아무도 그 변경을 요청하지 않았는데.

그래서 순서는 **프로젝트에서 먼저 쓰고, 반복이 확인되면 코어로 올린다.**
반대 방향(코어에 먼저 넣고 안 맞으면 뺀다)은 이미 그것을 쓰기 시작한 프로젝트를 깨뜨린다.

### 프로파일에 넣을 것과 코어에 넣을 것

프로젝트마다 다른 값을 코어 문서에 하드코딩하지 않는다. 경로·명령·스택은 `.curvez/profile.json` 에 있고,
에이전트는 거기서 읽는다. 계약의 상세는 [핸드오프 계약](handoff-contract.md)에 있다.

| 이런 것                                                        | 여기에                 |
| -------------------------------------------------------------- | ---------------------- |
| `apps/web`, `pnpm test` 같은 **값**                            | `.curvez/profile.json` |
| "값이 없으면 추측하지 말고 blocked" 같은 **규칙**              | 코어 에이전트 정의     |
| "결제 금액은 정수 최소단위" 같은 **이 프로젝트의 도메인 규칙** | 프로젝트 스킬          |

## 이름 — 충돌은 조용히 일어난다

### 에이전트 `name` 은 전역 네임스페이스다

에이전트는 `name` 하나로 불린다. 플러그인 이름이 앞에 붙지 않는다.
prefix 없이 `reviewer`, `qa`, `architect` 같은 이름을 쓰면 다른 플러그인이 같은 이름을 들고 있을 때
**어느 쪽이 뜰지 예측할 수 없다.** 그래서 curvez 코어는 전부 `curvez-` 로 시작하고,
검증기가 코어 에이전트에 대해 그것을 강제한다.

프로젝트도 자기 prefix 를 정한다. 회사·제품 약어면 충분하다 — `acme-payments`, `acme-billing`.

### 검증기는 프로젝트 prefix 를 강제하지 않는다

실측으로 확인한 사실이다. 프로젝트 `.claude/agents/` 에 코어와 **똑같은 이름**(`curvez-qa`) 의
파일을 두고 `doctor.mjs` 를 돌렸더니 에이전트 13건 전부 통과, 오류 0개로 끝났다.
`agent/name-prefix` 규칙은 코어 디렉터리 안의 파일에만 걸린다.

**검증기가 잡아주지 않는다.** 이름은 사람이 지킨다.
prefix 를 정했으면 새 에이전트를 만들 때마다 지키고, 팀에 규칙으로 남긴다.

### 스킬은 다르다 — prefix 를 붙이지 마라

스킬은 플러그인 네임스페이스가 자동으로 붙는다. 코어의 `authoring-agents` 는
`curvez:authoring-agents` 로 불린다. 여기에 이름까지 `curvez-authoring-agents` 로 지으면
`curvez:curvez-authoring-agents` 가 되어 중복이다.

프로젝트 스킬(`.claude/skills/`)도 마찬가지로 짧게 짓는다.
스킬 이름은 디렉터리명과 같아야 하고, 검증기가 그것은 강제한다.

**주의할 곳은 이름이 아니라 트리거다.** 스킬이 잘못 뜨는 원인은 이름 충돌이 아니라
description 의 트리거가 인접 스킬과 겹치는 것이다. 아래 "새 스킬 만들기" 3단계를 보라.

## 새 에이전트 만들기 — 실전 순서

정본은 `authoring-agents` 스킬이다. 여기서는 뼈대만 보여준다.

### 1. 스캐폴드

```bash
node "$CLAUDE_PLUGIN_ROOT/scripts/new-agent.mjs" <name> --model <opus|sonnet|haiku|inherit> [--readonly]
```

- 출력은 기본으로 `.claude/agents/<name>.md` 다
- `--readonly` 는 쓰기 도구를 `disallowedTools` 에 넣는다. 리뷰·조사 계열이면 붙인다
- 코어에 넣을 때만 `--dir plugins/curvez/agents` 를 붙인다

### 2. TODO 를 전부 채운다

뼈대는 채울 자리를 `<!-- TODO: ... -->` 로 남긴다. **하나라도 남으면 검증이 막는다.**
빈 스캐폴드를 방금 돌려보니 에이전트 뼈대에 TODO 15개, 스킬 뼈대에 12개(references 2개 포함)가
그대로 오류로 잡혔다.

이게 의도다. 빈 섹션을 남긴 에이전트는 규약을 지킨 게 아니라, 실행 시점에 그 자리를
추측이 메우게 된다. 서브에이전트는 중간에 사람에게 되물을 수 없으므로 그 추측을 교정할 기회가 없다.

### 3. 파일 소유권이 겹치지 않는지 확인한다

`## 협업과 팀 내 위치` 의 소유 경로를 기존 에이전트 전부와 대조한다.

```bash
grep -rn "파일 소유권" "$CLAUDE_PLUGIN_ROOT/agents" .claude/agents
```

겹치면 병렬 실행에서 나중에 쓴 쪽이 앞선 쪽을 조용히 지운다. 에러도 로그도 남지 않는다.
왜 소유권이 팀 실행의 전제인지는 [팀 실행 모델](team-execution.md)에 있다.

**검증기는 소유권 충돌을 잡지 않는다.** 자유 서술이라 기계가 대조할 형태가 아니다.
사람이 대조한다.

### 4. 통신 상대의 `name` 을 정확히 적는다

`## 팀 통신 프로토콜` 에 적는 이름은 실제 `name` 과 글자 단위로 같아야 한다.
그리고 **상대 정의에도 역방향을 적어야 라우팅이 닫힌다.**
A 가 "B 에게 넘긴다" 고만 적고 B 정의에 "A 에게서 받는다" 가 없으면, B 는 자기가 받을 것이
있다는 사실을 모른 채 실행된다.

코어 에이전트를 상대로 지목한다면 그 코어 정의에는 새 에이전트가 적히지 않는다.
오케스트레이터가 팀을 짤 때 그 방향을 알아야 하므로, 그 사실을 팀 편성 시점에 명시한다.

### 5. 검증

```bash
node "$CLAUDE_PLUGIN_ROOT/scripts/validate-agents.mjs" .claude/agents/<name>.md
```

오류 0개가 될 때까지 고친다. 채우고 나면 통과한다 — 실제로 채워서 돌려보니
`검사 1건, 통과 1건, 실패 0건, 오류 0개` 로 끝났다.

## 새 스킬 만들기 — 실전 순서

정본은 `authoring-skills` 스킬이다.

### 1. 스캐폴드

```bash
node "$CLAUDE_PLUGIN_ROOT/scripts/new-skill.mjs" <name> [--with-references]
```

`--with-references` 는 `references/` 와 예시 파일 둘을 함께 만든다.
**그 참조 파일 안의 TODO 도 검증에 걸린다.** 쓰지 않을 참조를 만들었다면 지운다.
포인터를 따라간 곳이 비어 있으면 절차가 거기서 끊기기 때문이다.

### 2. description 의 트리거를 실제 발화로 채운다

여기가 스킬의 성패다. 본문을 아무리 잘 써도 호출되지 않으면 아무 일도 일어나지 않는다.
트리거는 **사용자가 실제로 말할 표현**을 따옴표째 넣는다. 기능 이름이 아니라 발화다.
한글과 영어를 함께 넣지 않으면 반대 언어 발화에서 뜨지 않는다.

최소 개수와 최소 길이는 `scripts/lib/spec.mjs` 가 정본이고 검증기가 센다.
트리거를 고르는 법은 [스킬 설계](skill-authoring.md)에 있다.

### 3. 인접 스킬과 트리거가 겹치는지 확인한다

새 스킬의 트리거로 기존 스킬을 훑는다.

```bash
grep -rn "결제" "$CLAUDE_PLUGIN_ROOT/skills" .claude/skills --include='SKILL.md'
```

(`--include` 는 반드시 따옴표로 감싼다. zsh 에서 따옴표가 없으면 `no matches found` 로 죽는다.
[셸 함정](shell-pitfalls.md) 참조.)

겹치는 스킬이 있으면 **양쪽** `## 언제 쓰지 않는가` 에 서로를 이름으로 적는다.
한쪽만 적으면 경계가 반쪽만 그어져 여전히 둘 다 반응한다.
경계는 "쓰는가" 가 아니라 배제로만 그어지기 때문이다.

### 4. 검증

```bash
node "$CLAUDE_PLUGIN_ROOT/scripts/validate-skills.mjs" .claude/skills/<name>
```

## 전체 점검

```bash
node "$CLAUDE_PLUGIN_ROOT/scripts/doctor.mjs"
```

플러그인 구조 + 에이전트 + 스킬 + 핸드오프를 한 번에 본다.
**코어와 프로젝트를 함께 검사한다.** 실측: 프로젝트 루트에서 돌리면 코어 11 + 프로젝트 2 로
에이전트 13건, 코어 13 + 프로젝트 1 로 스킬 14건을 검사했다.

두 가지를 기억한다.

- **cwd 가 프로젝트 루트여야 한다.** `doctor.mjs` 는 `process.cwd()` 기준으로
  `.claude/agents`, `.claude/skills`, `.curvez/handoff` 를 찾는다.
  다른 데서 돌리면 프로젝트 파일을 건너뛰고도 통과한다
- `--plugin` 을 붙이면 코어만 본다. 코어를 고쳤을 때 프로젝트 상태에 영향받지 않고 확인하는 용도다

`$CLAUDE_PLUGIN_ROOT` 는 Claude Code 세션 안에서만 설정된다.
터미널에서 직접 돌릴 때 이 변수가 비면 경로가 `/scripts/doctor.mjs` 로 접혀
`MODULE_NOT_FOUND` 가 난다. 실측으로 확인했다. 직접 돌릴 때는 절대경로를 쓰거나 먼저 `export` 한다.

## 흔한 실수

전부 이 프로젝트를 만들면서 실제로 나온 것들이다.

### 뼈대 TODO 를 남긴 채 완료 선언

검증이 막는다. 문제는 **막히기 전까지는 빈 계약으로 실행된다**는 것이다.
검증을 안 돌리고 팀에 투입하면 그 에이전트는 자기 역할이 뭔지, 뭘 만들어야 하는지,
언제 blocked 인지를 모르는 채로 돈다. 그리고 빈손으로 돌아오거나 남의 파일을 고친다.

만들었으면 반드시 검증까지 돌린다.

### `## 품질 자체 검증` 에 문장만 씀

"결과를 확인한다", "테스트가 통과하는지 본다" 는 검증이 아니다. 검증기가 실행 가능한 명령이
있는지 본다 — 백틱으로 감싼 명령이나 코드블록이 없으면 `agent/self-check-not-executable` 로 막힌다.

막히는 것보다 중요한 이유가 있다. 핸드오프에서 `status: done` 은 `verification` 이 비면 쓸 수 없다.
"확인했다" 로는 `verification` 을 채울 수 없으므로, 명령이 없는 에이전트는 **원리적으로 done 을
낼 수 없다.** 자체 검증 섹션은 형식 요건이 아니라 done 을 낼 자격 그 자체다.
그 설계 근거는 [검증 철학](quality-model.md)에 있다.

### 검증 명령을 문서에 쓰고 실제로 안 돌려봄

가장 비싼 실수다. 셸 명령은 **조용히 실패한다.** 이 프로젝트에서 실제로 나온 것만 해도,
마크다운 표를 awk 로 파싱하면서 `\|` 를 복원하지 않아 위반이 0건으로 나온 적이 있다.
파싱 실패가 "깨끗함" 으로 위장됐다.

에이전트 정의에 명령을 적었으면 **그 명령을 그 자리에서 한 번 돌려보고 출력을 눈으로 본다.**
결함이 있는 입력에도 0건이 나오는지 확인한다. 함정 목록은 [셸 함정](shell-pitfalls.md)에 있다.

### 같은 형식을 스킬과 에이전트 정의 양쪽에 적음

출력 JSON 의 필드 목록을 에이전트 정의에도 쓰고 스킬에도 쓰면, 필드를 하나 추가할 때
한쪽만 고쳐진다. 그러면 낡은 판본을 든 에이전트가 계속 돌면서 형식이 다른 산출물을 낸다.
어느 쪽이 맞는지 판정할 근거가 없어 매번 다른 결과가 나온다.

형식은 한 곳에만 둔다. curvez 에서는 핸드오프 형식이 `agent-contract` 스킬과
`scripts/schema/handoff.schema.json` 이고, 에이전트 정의는 "`agent-contract` 를 따른다" 고만 적는다.

### 이름 충돌

앞의 "이름" 절 참조. 검증기가 잡지 않는다는 것이 핵심이다.

### 새 규칙을 문서에만 적고 검증기에 안 넣음

문서에만 있는 규칙은 지켜지지 않는다. 지켜지는지 아무도 세지 않기 때문이다.
사람이 리뷰에서 잡을 것 같지만, 라운드가 몇 번 돌면 아무도 안 본다.

규칙을 새로 만들었으면 둘 중 하나다.

- **기계가 셀 수 있는 규칙이면** 검증기에 넣는다. 그러면 규칙은 값이 되고,
  값의 단일 출처는 `scripts/lib/spec.mjs` 다
- **기계가 셀 수 없는 규칙이면**(소유권 충돌, 트리거 겹침 같은 것) 그 사실을 인정하고
  사람이 언제 대조하는지를 절차에 박아 넣는다. "잘 하자" 로 남기지 않는다

## 규약 자체를 바꿀 때

에이전트 7섹션, 스킬 필수 섹션, 핸드오프 필드 — 이런 규약을 고치는 것은 확장이 아니라 개조다.

절차는 이렇다.

1. 회고(`curvez-retrospector`)가 규약 수정안을 낸다. 어떤 라운드에서 무엇이 문제였는지 근거와 함께
2. 오케스트레이터가 **사용자 승인을 받는다**
3. 승인된 것만 고친다

**승인 단계를 건너뛰지 않는 이유:** 규약 변경은 이후 모든 라운드의 동작을 바꾼다.
이미 통과했던 정의가 갑자기 실패하고, 이미 쓰인 핸드오프가 갑자기 스키마 위반이 된다.
되돌리기 비용이 개별 에이전트 수정과는 자릿수가 다르다.

**수치를 바꾸려면 `scripts/lib/spec.mjs` 한 곳이다.** 필수 필드 목록, 섹션 목록, 분량 상한,
허용값이 전부 거기 있고 검증기 3종이 그것을 import 한다. 검증기를 직접 고치지 마라 —
값이 두 군데로 갈라져 스킬 문서와 검증기가 서로 다른 규칙을 말하게 된다.

값을 바꾼 뒤에는 `doctor.mjs --plugin` 을 돌려 코어가 자기 새 규칙을 통과하는지 확인한다.
코어가 못 지키는 규칙을 프로젝트에 요구할 수는 없다.

## 구현 상태

동작하는 스크립트는 여덟이다.

| 스크립트                                               | 역할                                       |
| ------------------------------------------------------ | ------------------------------------------ |
| `validate-agents` `validate-skills` `validate-handoff` | 규약 검증                                  |
| `new-agent` `new-skill`                                | 스캐폴딩                                   |
| `bootstrap`                                            | 스택 감지 → 프로파일 → `.curvez/` 스캐폴드 |
| `quality-gate`                                         | 게이트 실행 → `verification[]` 출력        |
| `doctor`                                               | 종합 점검 (정적 규약 + 런타임 완비)        |

훅 세 종(`guard-bash` `validate-on-write` `check-handoff`)도 `hooks/hooks.json` 으로 등록된다.

**아직 확인되지 않은 것 하나:** `/plugin marketplace add` + `/plugin install` 로 실제 설치했을 때
로더가 에이전트·스킬·훅을 인식하는지는 검증되지 않았다. 스크립트를 직접 호출한 검증만 마쳤다.

한 번 이 구분을 놓친 적이 있다. `hooks/hooks.json` 에 최상위 `hooks` 키가 없어 훅이 전혀
등록되지 않는 상태였는데, 스크립트를 직접 실행하면 동작하므로 검증에서도 통과처럼 보였다.
**파일이 존재한다는 것과 로더가 읽을 수 있다는 것은 다르다.** 지금은 `doctor` 가
매니페스트 구조를 검사한다.

## 요약 — 새 담당자가 첫날 할 일

1. [README](README.md)로 전체 그림을 잡는다
2. `node "$CLAUDE_PLUGIN_ROOT/scripts/doctor.mjs" --plugin` 을 돌려 설치가 온전한지 본다
3. 프로젝트 prefix 를 정한다 (검증기가 안 잡아주므로 팀 규칙으로 남긴다)
4. 가장 아쉬운 담당자 **하나**만 만든다. 스캐폴드 → TODO 채우기 → 소유권 대조 → 검증
5. 한 라운드 돌려보고, 그때 드러난 것으로 두 번째를 만든다

처음부터 여러 개를 만들지 않는 이유는 단순하다. 에이전트 정의의 문제는 대부분 실행해봐야 드러나고,
정의는 실행 중에 고칠 수 없다. 하나씩 돌려보고 고치는 편이 결국 빠르다.
