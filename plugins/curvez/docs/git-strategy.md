# git 전략 — 왜 이렇게 정했는가

curvez 는 브랜치를 따고 커밋을 만들고 PR 을 올린다. 이 문서는 **그 동작에 걸린 제약들이 왜 그
모양인지**를 설명한다. 사람이 읽는 문서다.

- **실행 절차**(무엇을 순서대로 하는가)는 `skills/branching/SKILL.md` 와 `skills/commit/SKILL.md`
  가 정본이다. 브랜치 이름 규칙, PR 생성 명령, 머지 조건 같은 것은 그쪽에 있다
- **역할·권한·통신**(누가 무엇을 책임지고 무엇을 못 하는가)은 `agents/curvez-git.md` 가 정본이다
- **이 문서가 정본인 것:** 왜 이 전략인가, 무엇을 버렸는가, 어떻게 실패하는가, 두 스킬과 가드 훅이
  합쳐져 만드는 전체 그림

절차를 여기에 사본으로 두지 않는 이유는 git 작업의 성질과 관련이 있다. 같은 절차가 두 곳에 있으면
한쪽만 고쳐지고, 그 어긋남은 **원격에 반영된 뒤에** 발견된다. 문서 하나 고치는 것과 이력 하나
되돌리는 것의 비용 차이가 이 문서 전체의 주제다.

---

## 1. 브랜치 전략을 프로파일에서 읽는 이유

curvez 는 특정 저장소용 설정이 아니라 **범용 하네스**다. 어느 프로젝트에 붙여도 같은 에이전트와
스킬이 돌아야 한다. 그래서 브랜치 이름과 단수 구조는 코드에도 스킬에도 박히지 않고
`.curvez/profile.json` 의 `git` 에서 읽는다.

### 하드코딩이 실패하는 형태

참고 자산이 된 저장소는 `main ← release ← 작업 브랜치` 의 2단 구조를 쓴다. 이 구조를 기본값으로
박으면 GitHub Flow(`main ← 작업 브랜치`)를 쓰는 프로젝트에서 이렇게 된다.

```
작업 브랜치를 따려고 release 로 옮긴다
  → release 가 없다
  → 에이전트는 "브랜치가 없으면 만든다" 로 해석하거나, main 을 release 로 간주한다
  → 어느 쪽이든 사용자가 의도한 적 없는 브랜치 구조가 생긴다
```

두 번째 갈래가 더 나쁘다. 오류가 나지 않고, 커밋은 정상적으로 쌓이고, PR 도 열린다. 잘못된 것은
**PR 타겟 하나**뿐인데 그것은 리뷰 화면을 열어 봐야 보인다.

`commands` 와 `paths` 를 프로파일에서 읽는 것과 정확히 같은 원칙이다. 프로젝트마다 다른 값을
에이전트가 관례로 메우면, 메운 값이 틀렸다는 사실이 산출물이 나온 뒤에야 드러난다. 프로파일 형식과
그 설계 근거는 [설계 근거](design-rationale.md), 경로 폴백이 소유권 충돌을 만든 사례는
[팀 실행 모델](team-execution.md) 을 참조하라.

### 1단과 2단을 하나의 모델로 다루는 법

`git` 블록은 네 개의 값을 갖는다 — 작업 브랜치를 따는 곳이자 PR 타겟(`baseBranch`), 배포된
것(`releaseBranch`), 머지 방식(`mergeStrategy`), 직접 커밋 금지 목록(`protectedBranches`).
키의 정확한 이름과 허용값은 `skills/bootstrap/SKILL.md` 의 프로파일 형식이 정본이다.

설계에서 중요한 것은 **1단 구조를 별도의 모드로 만들지 않았다**는 점이다.

> `baseBranch === releaseBranch` 이면 1단 구조다.

`if (구조 == "github-flow")` 같은 분기를 두는 대신 두 값이 같은지만 보게 한 것은, 분기를 두면
스킬의 모든 단계가 두 벌이 되기 때문이다. 두 벌이 된 절차는 한쪽만 고쳐진다. 값 비교로 환원하면
릴리스 PR 절차가 "없는 단계" 가 아니라 **자기 자신으로 가는 PR 이라 자연히 사라지는 단계**가 된다.

대가도 있다. 1단 구조에서는 2절이 말하는 비대칭이 무너진다 — `baseBranch` 로 가는 머지가 곧
배포 브랜치로 가는 머지다. 그래서 1단 프로젝트에서는 "요청받으면 머지해도 되는" 범주가 존재하지
않고, 모든 머지가 사람 몫이 된다. 이것은 규칙의 예외가 아니라 같은 규칙의 결과다. 판정 기준은
브랜치 이름이 아니라 **그 머지가 배포된 것을 건드리는가** 이기 때문이다.

### 어떻게 판정하는가

구조 판정은 부트스트랩 시점에 한 번 일어난다. 근거는 원격 브랜치 목록이다 — 통합 브랜치로 쓰이는
이름(`release`·`develop` 등)이 원격에 있으면 2단, 없으면 1단으로 보고 사용자에게 확인받는다.

실측으로 두 저장소를 확인했다. `git branch -r` 의 출력이다.

| 저장소 | 원격 브랜치 | 판정 |
|---|---|---|
| `~/Workspace/weather` | `origin/main` 만 | 1단 — `baseBranch` 와 `releaseBranch` 가 모두 `main` |
| `~/Workspace/stamp` | `origin/main`, `origin/release` | 2단 — `baseBranch=release`, `releaseBranch=main` |

브랜치 목록은 **추정의 근거일 뿐 확정이 아니다.** `release` 라는 이름의 브랜치가 통합 지점이
아니라 오래된 유물일 수도 있다. 그래서 판정 결과는 프로파일에 쓰기 전에 사용자에게 확인받는다.

### 없으면 추측하지 않는다

프로파일에 `git` 이 없으면 에이전트는 `status: blocked` 로 돌아온다. `paths` 필수 키와 같은
규칙이고, 근거는 그보다 더 강하다.

경로를 잘못 짚으면 잘못된 위치에 파일이 생기고, 그것은 옮기면 된다. 브랜치를 잘못 짚으면
**남의 작업 위에 커밋이 쌓인다.** 이미 다른 사람이 작업 중인 브랜치에 얹힌 커밋은 파일을 옮기듯
분리할 수 없고, 분리하려면 이력을 재작성해야 하며, 그 재작성은 그 브랜치를 받아 간 모든 사람에게
전파된다. 추측의 비용이 다른 어떤 필드보다 비싼 자리다.

### 확인 시점의 구현 상태

이 문서를 쓰는 시점에 `skills/bootstrap/SKILL.md` 의 프로파일 형식에는 아직 `git` 블록이 없다.
브랜치 전략을 프로파일에서 읽는다는 결정은 확정됐지만, 부트스트랩 절차에 그 항목을 넣는 작업은
아직 반영되지 않았다. 위의 판정 규칙은 **설계이지 현재 구현된 절차가 아니다.**

## 2. 되돌리기 비용의 비대칭 — 이 전략의 뼈대

git 관련 규칙 대부분은 하나의 문장에서 파생된다.

> **틀렸을 때 되돌리는 비용이 얼마나 드는가에 따라 권한을 나눈다.**

에이전트가 무엇을 해도 되는지는 그 작업이 어려운가 위험한가로 정하지 않는다. **틀렸다는 것을
나중에 알았을 때 무엇을 해야 하는가**로 정한다.

### 두 머지가 다른 이유

| 어디로 가는 머지 | 틀렸을 때 | 누가 |
|---|---|---|
| `baseBranch` 로 | revert PR 하나를 열어 걷어낸다. 이력에 남지만 전방향이다 | 요청받으면 에이전트가 실행해도 된다 |
| `releaseBranch` 로 | 이미 배포된 것을 건드린다. 되돌린 뒤 뒤처진 통합 브랜치를 다시 맞춰야 하고, 그 맞춤에는 포인터 강제 이동이 따라온다 | 사람이 한다 |

두 번째 줄의 마지막 항목이 핵심이다. `releaseBranch` 로 가는 머지를 되돌리는 작업은 **되돌리기
그 자체로 끝나지 않는다.** rebase 머지는 커밋을 재작성하므로 되돌린 뒤 통합 브랜치를 릴리스
브랜치에 맞추려면 PR 이 아니라 포인터를 옮겨야 하고, 그것은 강제 갱신이다. 즉 실수 한 번의
복구 경로에 "가장 되돌리기 어려운 조작"이 들어 있다.

그리고 배포 시점 판단은 애초에 에이전트가 가진 정보로 내릴 수 있는 판단이 아니다. 지금 배포해도
되는지는 CI 통과 여부가 아니라 사람들의 일정과 대기 상태에 달려 있고, 그 정보는 저장소 안에 없다.

### 같은 논리가 놓인 다른 자리들

이 비대칭은 머지 권한 하나에만 적용되는 규칙이 아니다. 같은 판정이 곳곳에서 반복된다.

**편집 시점에 막는다 — 커밋 시점이 아니라.** 보호 브랜치 위에서 작업하고 있다는 사실을 커밋
단계에서 알아차리면, 이미 만들어진 커밋을 작업 브랜치로 옮기는 조작이 필요하다. 편집 전에
막으면 잃을 것이 아무것도 없다. 게이트는 **되돌리기 비용이 가장 싼 지점**에 놓는다 — 팀 실행의
승인 게이트가 워커를 띄우기 전에 놓인 것과 같은 이유다([팀 실행 모델](team-execution.md) 5절).

**강제 갱신은 확인받는다.** 강제 갱신 자체가 어려운 명령이라서가 아니다. 그것이 실패했을 때
잃는 것이 **다른 사람의 커밋**이기 때문이다. 내가 되돌릴 수 있는 손실과 남이 겪는 손실은 같은
등급이 아니다.

**요청 범위를 넘지 않는다.** 요청하지 않은 머지·브랜치 삭제는 사용자가 그것이 일어났다는 사실
자체를 모른다. 모르는 변경은 되돌릴 대상으로 인식되지도 않는다(5절).

**모르면 멈춘다.** 1절의 `blocked` 규칙도 같은 계산이다. 추측해서 진행한 결과를 되돌리는 비용이
멈춰서 묻는 비용보다 항상 크다.

네 규칙은 서로 다른 곳에 적혀 있지만 하나의 판정에서 나온 결과다. **어느 하나를 완화하려면 그
자리의 되돌리기 비용이 왜 낮은지를 먼저 보여야 한다.**

## 3. 작업 브랜치에서 다시 분기하지 않는 이유

절대 규칙 중 실무에서 가장 자주 어겨지는 것이다. 앞 작업의 코드가 필요하니 그 브랜치에서 새
브랜치를 따는 것은 자연스러워 보인다.

### 무엇이 깨지는가

작업 브랜치가 `baseBranch` 로 머지될 때 rebase 머지는 그 커밋들을 **재작성**한다. 새 기반 위에
같은 변경을 다시 적용하므로 내용은 같고 해시는 다르다. 그 순간 그 위에서 딴 브랜치는 이제
**존재하지 않는 커밋을 기반으로 갖는다.**

```
release ── A ── B          feature/one (A, B)
                 └── C     feature/two (A, B 위에서 딴 것)

feature/one 이 rebase 머지된 뒤

release ── A' ── B'        A·B 는 A'·B' 로 재작성됐다
      ...
                 └── C     feature/two 의 기반 A, B 는 어디에도 없다
```

이 상태에서 `feature/two` 의 PR 을 열면 diff 에 A·B 의 내용이 **다시** 나타난다. 이미 머지된
변경인데도 그렇다. 리뷰어가 보는 것은 "이미 통합된 코드를 또 넣는 PR" 이고, 그대로 머지하면
같은 변경이 다른 해시로 두 번 들어간다. 충돌이 나면 앞선 커밋과 재작성된 커밋 사이에서 나므로,
해결하는 사람은 자기가 무엇을 고르고 있는지 알기 어렵다.

**이 실패는 분기하는 시점에 아무 신호도 내지 않는다.** 브랜치를 따는 순간에는 모든 것이 정상이고,
앞 브랜치가 머지되는 시점에 — 대개 며칠 뒤, 다른 사람의 손에서 — 드러난다.

머지 방식이 `merge` 라면 커밋 재작성이 없으므로 이 문제가 약해진다. 그럼에도 규칙을 방식별로
가르지 않은 것은, `mergeStrategy` 가 프로젝트마다 다르고 도중에 바뀔 수 있는데 **이미 딴 브랜치는
그 변경에 소급해서 대응할 수 없기** 때문이다. 가장 나쁜 경우를 기준으로 하나의 규칙을 두는 편이
싸다.

### 대안 셋과 각각의 대가

앞 작업의 코드가 정말 필요할 때 고를 수 있는 것은 셋이다. 어느 것도 공짜가 아니다.

| 방법 | 대가 |
|---|---|
| 앞 작업을 먼저 머지시키고 갱신된 `baseBranch` 에서 새로 딴다 | 앞 작업의 리뷰·머지를 기다려야 한다. 가장 안전하지만 가장 느리다 |
| 두 작업을 하나의 브랜치로 합쳐 진행한다 | PR 이 커진다. 리뷰 품질이 떨어지고, 한쪽에 문제가 있으면 다른 쪽까지 같이 막힌다 |
| 앞 작업 없이 되는 부분만 먼저 만든다 | 나중에 합칠 때 인터페이스가 어긋날 수 있다. 두 번 작업하게 될 수 있다 |

세 번째가 가장 자주 정답인데 가장 덜 선택된다. "지금 다 만들 수 있는데 왜 쪼개나" 로 보이기
때문이다. 그러나 위 표의 대가는 전부 **예측 가능하고 앞에서 지불하는** 비용인 반면, 분기해서
얻는 시간은 뒤에서 이력 꼬임으로 청구된다. 언제 청구될지, 누가 지불하게 될지 모르는 채로.

에이전트에게 이 판단을 맡기지 않는 이유도 여기 있다. 세 대안의 비용은 팀의 일정과 리뷰 대기열에
달려 있고 그 정보는 저장소 안에 없다. 그래서 스킬은 세 선택지를 제시하고 고르게 한다.

## 4. 훅이 무엇을 막는가 — 경계는 "원격" 이 아니라 "이력 삭제" 다

`hooks/guard-bash.mjs` 는 `PreToolUse(Bash)` 에서 되돌리기 어려운 git 명령을 차단한다(exit 2).

경계선은 **원격에 닿는가**가 아니라 **되돌릴 수 있는가**다. 평범한 `git push` 는 원격 이력에
커밋을 얹는 append 이고, 틀렸으면 revert 커밋 하나로 되돌린다. 반면 강제 push 와 원격 브랜치
삭제는 원격에 있던 이력을 **지운다** — 다른 사람이 이미 받아 갔다면 로컬에서 복구할 방법이 없다.
비용이 비대칭인 쪽만 막는다.

한때 이 가드는 `git push` 전체를 막았다. 그 설정에서는 커밋 이후 모든 단계가 사용자 개입을
요구했고, 팀 실행에서는 워커가 사용자에게 직접 물을 수 없어([팀 실행 모델](team-execution.md) 6절)
**push 하나가 라운드 하나를 소비했다.** 그 비용은 매 작업마다 발생하는데, 막아서 피한 사고는
`--force` 와 원격 삭제뿐이었다. 그래서 규칙을 그 둘로 좁혔다.

### 실측 — 무엇이 막히고 무엇이 통과하는가

훅에 명령 문자열을 직접 넣어 exit code 를 확인했다. 아래는 실행 결과다.

| 명령 | exit | |
|---|---|---|
| `git push`, `git push -u origin main` | 0 | 통과 |
| `git push --dry-run` | 0 | 통과 |
| `git push --force-with-lease` | 0 | 통과 — 남의 커밋을 덮어쓰기 전에 실패한다 |
| `git push --force` | 2 | 차단 |
| `git push -f origin main` | 2 | 차단 — 축약형도 잡는다 |
| `git push --delete origin old` | 2 | 차단 |
| `git push origin :old` | 2 | 차단 — 콜론 문법 브랜치 삭제 |
| `git reset --hard`, `git clean -fd`, `git branch -D` | 2 | 차단 |
| `git rebase main` | 2 | 차단 |
| `git rebase <main 이 아닌 브랜치>` | 0 | 통과 |
| `git commit`, `git switch -c`, `git merge <브랜치>` | 0 | 통과 |
| `gh pr create`, `gh pr merge` | 0 | 통과 |
| `git pull` (인자 없음) | 0 | 통과 |
| `npm install` | 2 | 차단 — pnpm 고정 |
| `pnpm install --force` | 0 | 통과 |

`-f` 축약형 케이스가 회귀 테스트에 고정돼 있다(`hooks/tests/guard-bash.test.py`).
push 규칙을 통째로 빼면 `--force` 규칙이 문자열 `--force` 만 보기 때문에 `-f` 가 조용히
통과한다 — 규칙을 좁힐 때 실제로 열렸던 구멍이다.

그럼에도 가드를 완화하지 않는 이유는 손실의 성질이 다르기 때문이다. 개입 비용은 **매번 발생하지만
매번 작고 예측 가능**하다. 잘못된 push 의 비용은 **드물게 발생하지만 크고 예측 불가능**하며,
공유 브랜치에 닿으면 그 저장소를 쓰는 모든 사람에게 전파된다. 자주 내는 작은 비용으로 드물지만
큰 손실을 막는 거래다.

### 가드가 막지 못하는 것 — 알고 있어야 하는 구멍

위 표에서 exit 0 인 줄들이 이 가드의 한계다. **가드는 "원격에 영향을 주는가" 가 아니라 "git
명령이 이 패턴에 맞는가" 를 본다.** 둘은 같지 않다.

**`gh pr merge` 가 통과한다.** PR 머지는 원격 이력을 바꾸는 작업이고, 되돌리는 비용은 push 보다
오히려 비싸다(2절). 그런데 `git` 으로 시작하지 않아 패턴에 걸리지 않는다. 즉 `releaseBranch` 로
가는 머지를 사람이 한다는 규칙은 **가드가 아니라 스킬과 에이전트 정의로만 지켜진다.** 규칙을 못
읽은 세션에서는 아무것도 막지 않는다.

**`git commit --no-verify` 와 인자 없는 `git pull` 이 통과한다.** 둘 다 스킬의 금지 목록에 있지만
가드에는 없다. 문서로만 지켜지는 규칙이다.

**`git rebase` 는 `main` 이라는 이름만 본다.** 가드의 패턴에 브랜치 이름이 박혀 있어서,
릴리스 브랜치를 `production` 이나 `master` 로 부르는 프로젝트에서는 그 브랜치의 rebase 가
통과한다. **프로파일에서 브랜치를 읽는다는 1절의 원칙이 가드에는 아직 적용되지 않았다.**
전략은 프로파일에서 읽는데 가드는 이름을 하드코딩하고 있다 — 알려진 불일치다.

이 구멍들을 지금 메우지 않은 이유는 가드가 **최후의 방어선이지 유일한 방어선이 아니기** 때문이다.
1차 방어는 스킬과 에이전트 정의이고, 가드는 그것들이 읽히지 않았을 때 가장 비싼 실수만 잡는다.
다만 그 경계가 어디인지는 알고 있어야 한다 — **가드가 통과시킨다는 것이 허용된다는 뜻이 아니다.**

### 문자열 매칭의 부작용

가드는 명령 문자열에 패턴이 들어 있는지만 본다. 그래서 명령을 **설명하려는 시도**도 그것이 Bash
명령 안에 있으면 막힌다. 사용자에게 실행할 명령을 보여주려고 `echo "git push …"` 를 돌리면
차단된다 — 실측으로 확인했다(exit 2).

이 문서를 쓰는 과정에서도 같은 일이 있었다. 참고 저장소의 동종 가드가 걸린 명령 목록을 담은
테스트 명령을 통째로 거부해서, 문자열을 조립해 만드는 별도 스크립트 파일로 우회해야 했다.

실무적 귀결은 단순하다. **에이전트는 실행할 명령을 응답 텍스트로 제시해야 한다.** 셸을 거쳐
출력하려 하면 가드에 걸리고, 걸린 이유가 "명령이 위험해서" 로 보고되어 무엇이 문제인지
오해하기 쉽다. 같은 종류의 셸 함정은 [셸 함정](shell-pitfalls.md) 에 모여 있다.

## 5. 요청 범위를 넘지 않는 규칙

"커밋해줘" 에 푸시까지 하지 않고, "PR 만들어줘" 에 머지까지 하지 않는다. 단계별 경계는
`skills/commit/SKILL.md` 가 정본이다.

핵심은 규칙 자체가 아니라 그 해석이다.

> **요청받았을 때 해도 된다는 것이지, 알아서 하라는 것이 아니다.**

2절이 정한 것은 "이 작업은 에이전트가 실행해도 되는 등급이다" 라는 **상한**이다. 상한은 허가가
아니다. `baseBranch` 로 가는 머지가 허용 범주에 있다는 사실과, 지금 그것을 해야 한다는 판단은
별개다.

### git 에서 특히 중요한 이유

다른 작업에서 범위를 넘는 것은 대개 되돌릴 수 있다. 요청하지 않은 파일을 만들었으면 지우면 되고,
안 시킨 리팩터링을 했으면 diff 를 되돌리면 된다. **흔적이 남지 않는다.**

git 은 다르다. **되돌리기가 이력을 남긴다.**

| 되돌린 것 | 남는 것 |
|---|---|
| 요청하지 않은 머지 | 머지 커밋 + revert 커밋. 둘 다 영구히 남는다 |
| 요청하지 않은 push | 원격 이력. 지우려면 강제 갱신이 필요하고, 그 사이 누군가 받아 갔을 수 있다 |
| 요청하지 않은 브랜치 삭제 | 지운 사실이 남지 않는다. 되살릴 수 있는지는 reflog 가 살아 있는지에 달렸다 |

세 번째 줄이 특히 나쁘다. 다른 둘은 흔적이 남아서 최소한 **무슨 일이 있었는지 재구성할 수 있는데**,
삭제는 그 반대다. 사용자는 브랜치가 사라졌다는 사실 자체를 모르고, 모르는 손실은 되돌릴 대상으로
인식되지도 않는다.

그리고 앞서 나간 단계는 대체로 **되돌릴 수 없는 쪽에 있다.** 커밋 다음은 push 이고 push 다음은
머지다. 요청보다 한 단계 더 간다는 것은 언제나 되돌리기가 더 비싼 쪽으로 한 걸음 가는 것이다.
이 방향성 때문에 "친절하게 한 단계 더" 가 git 에서만큼은 친절이 아니다.

### 실제로 한 것만 보고한다

같은 원칙이 보고에도 걸린다. 핸드오프의 `artifacts` 에는 **실제로 만들어진 것**만 적는다 —
커밋 해시, PR URL 처럼 사후에 대조할 수 있는 값이어야 한다. 4절 때문에 어떤 조작을 사용자가
실행한 경우, 에이전트는 그것이 원격에 반영됐는지 직접 보지 못했으므로 반영됐다고 쓸 수 없다.
`done` 과 `verification` 의 관계는 [품질 모델](quality-model.md), 계약의 필드는
[핸드오프 계약](handoff-contract.md) 이 정본이다.

## 6. 커밋 메시지 규칙을 강제하지 않는 이유

curvez 는 커밋 메시지의 **언어와 형식을 규정하지 않는다.** 한글로 쓸지 영어로 쓸지, `feat:` 같은
타입 접두어를 붙일지는 프로젝트마다 다르다. 에이전트는 기존 커밋 로그를 읽어 그 프로젝트의 문체에
맞춘다. 로그를 읽는 절차는 `skills/commit/SKILL.md` 에 있다.

### 왜 규칙을 만들지 않는가

커밋 로그는 **에이전트가 오기 전부터 있었고 에이전트가 떠난 뒤에도 남는다.** 여기에 curvez 의
취향을 얹으면 이력의 어느 구간부터 문체가 갈리고, 나중에 로그를 읽는 사람은 그 경계에서 "규칙이
바뀌었나" 를 판단해야 한다. 아무도 그 질문에 답을 갖고 있지 않다.

게다가 커밋 메시지 규칙은 흔히 훅으로 강제된다. 프로젝트가 이미 자기 린터를 갖고 있는데 curvez 가
다른 규칙을 들고 들어가면 에이전트가 만든 메시지가 그 프로젝트의 훅에 거부된다. 그때 에이전트가
받는 유혹은 검증을 우회하는 것이고, 그것은 규칙이 없는 것보다 나쁘다.

**맞출 대상이 이미 있으면 규칙을 만들지 않고 읽는다.** 명령을 하드코딩하지 않고 프로파일의
`commands` 에서 읽는 것과 같은 원칙이다([품질 모델](quality-model.md)).

### 그럼에도 프로젝트와 무관하게 지키는 셋

형식은 프로젝트를 따르지만 내용에 대한 세 가지는 어디서나 지킨다.

**하나. 제목은 구체적이어야 한다.** "수정", "업데이트", "작업중" 같은 제목은 형식은 만족시키지만
정보를 담지 않는다. 이것이 보편적인 이유는 커밋 제목이 쓰이는 자리에 있다 — `git log --oneline`,
blame, 릴리스 노트, 이력 검색. 이 자리들에서는 **제목만 보인다.** 제목이 비면 그 커밋을 찾을
방법은 전체 diff 를 하나씩 여는 것뿐이고, 커밋이 늘수록 그 비용은 선형으로 는다.

**둘. 본문은 "무엇을" 이 아니라 "왜" 를 담는다.** 무엇을 했는지는 diff 가 이미 말한다. diff 가
절대 말하지 못하는 것은 **왜 이 방법이고 다른 방법이 아닌가** 이다. 이것이 보편적인 이유는 커밋
본문을 읽는 상황이 정해져 있기 때문이다. 사람이 커밋 본문을 여는 것은 대개 그 코드를 바꾸려다가
"왜 이렇게 돼 있지" 에서 막혔을 때다. 그 순간 필요한 정보는 하나뿐이고, 그것이 없으면 없는 것과
같은 결정을 다시 내리게 된다 — 대개 같은 이유로 되돌아온다.

**셋. 검증은 실제로 돌린 것만 쓴다.** 못 한 것은 못 했다고 쓴다. 이것이 보편적인 이유는 커밋
메시지의 검증 기록이 **나중에 다른 사람이 신뢰의 근거로 삼는 값**이기 때문이다. "테스트 통과" 라고
적힌 커밋은 그 뒤 사람에게 "여기는 확인된 구간" 으로 읽힌다. 실제로 안 돌렸다면 아무도 확인하지
않은 구간이 확인된 것으로 표시된 셈이고, 그 표시는 문제가 터졌을 때 **범인을 찾는 방향을 반대로
돌려놓는다.** 형식은 팀마다 달라도 이 손해는 어느 팀에서나 같다.

셋을 관통하는 것은 **커밋 메시지는 미래의 독자를 위한 것**이라는 사실이다. 형식은 팀의 취향이지만
독자가 필요로 하는 정보는 취향이 아니다. 그래서 형식은 맞추고 내용은 지킨다.

같은 세 가지가 핸드오프의 `summary`·`decisions`·`verification` 에도 그대로 적용된다. 이 문서와
[품질 모델](quality-model.md) 이 서로 다른 대상을 두고 같은 말을 하는 것은 우연이 아니다 —
둘 다 "나중에 읽는 사람이 판단할 수 있는가" 를 기준으로 삼는다.
