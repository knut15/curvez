# 핸드오프 계약

curvez 팀 실행에서 에이전트끼리 주고받는 유일한 통신 수단이 핸드오프다.
이 문서는 **왜 이 계약이 이런 모양인지**와 **어떻게 잘못될 수 있는지**를 다룬다.

## 이 문서가 다루지 않는 것

핸드오프에 관한 정본은 네 군데에 나뉘어 있다. 값을 찾으러 왔다면 이 문서가 아니라 아래를 봐야 한다.

| 알고 싶은 것                 | 정본                                                   |
| ---------------------------- | ------------------------------------------------------ |
| 필드 목록, 타입, 허용값      | `scripts/schema/handoff.schema.json`                   |
| 언제·어떤 순서로 쓰고 읽는가 | `skills/agent-contract/SKILL.md`                       |
| 특정 필드를 어떻게 채우는가  | `skills/agent-contract/references/field-reference.md`  |
| 검사 규칙의 구현             | `scripts/validate-handoff.mjs`, `scripts/lib/spec.mjs` |

이 문서가 정본인 것은 그 위의 층이다 — 왜 계약이 필요한가, 상태가 왜 셋인가,
검증기가 무엇을 왜 막는가, 실제로 무엇이 깨졌는가.
스키마가 바뀌면 이 문서는 따라오지 않아도 된다. 스키마와 이 문서가 어긋나면 스키마가 이긴다.

---

## 왜 파일 기반 계약인가

서브에이전트는 격리된 컨텍스트에서 돈다. 부모 에이전트의 대화 이력을 보지 못하고,
실행 중에 다른 에이전트에게 되물을 수도 없다. 사용자에게 직접 질문하는 것도 불가능하다.
한 번 시작하면 자기가 받은 프롬프트와 파일 시스템만으로 끝까지 가야 한다.

그래서 통신은 **비동기이고 단방향이며 한 번뿐**이다. 이 세 조건은 실시간 대화가 아니라
API 호출의 조건에 가깝다. 파일에 남긴 계약이 그 API의 역할을 한다.

여기서 계약의 성질 두 가지가 따라 나온다.

**전부 적어야 한다.** 수신 에이전트가 "이건 무슨 뜻이냐" 고 되물을 수 없으므로,
계약이 애매하면 수신 쪽은 멈추는 대신 추측한다. 추측은 잘못된 전제가 되고, 그 위에서
만들어진 산출물은 리뷰 단계까지 가서야 어긋난다.

**덮어쓰지 않는다.** 핸드오프 파일명에 타임스탬프가 들어가고 같은 이름이 두 번 나오지 않는
이유다. 회고 에이전트가 실행 이력을 시간순으로 재구성해 "어디서부터 어긋났나" 를 찾는데,
덮어쓰면 그 복원이 불가능해진다. 계약 파일은 로그이기도 하다.

파일 기반을 고른 것 자체의 근거 — 다른 통신 수단을 왜 버렸는가 — 는
[설계 근거](design-rationale.md)에 있다. 오케스트레이터가 이 계약들을 어떻게 수합해
다음 단계를 정하는지는 [팀 실행 모델](team-execution.md)에 있다.

## 상태 전이 모델

`status` 는 세 값뿐이다. 셋으로 자른 이유는 **수신 쪽의 행동이 세 갈래로 갈리기 때문**이다.
값이 더 많아도 수신 에이전트가 할 수 있는 일은 늘지 않는다.

| status    | 수신 쪽이 할 일                                                 |
| --------- | --------------------------------------------------------------- |
| `done`    | 이 결과를 전제로 자기 작업을 시작한다                           |
| `partial` | 남은 범위를 확인하고, 그 범위에 의존하지 않는 부분만 진행한다   |
| `blocked` | 시작하지 않는다. 오케스트레이터가 질문을 풀어줄 때까지 기다린다 |

### 강제되는 세 규칙

**`done` 은 `verification` 이 비면 쓸 수 없다.**
`done` 은 "내가 다 했다" 는 자기 신고인데, 팀 실행에서는 아무도 그것을 되묻지 않는다.
수신 에이전트는 검증하지 않고 믿는다. 그래야 병렬 실행이 성립한다.
그 신뢰의 대가로 송신 쪽이 근거를 붙인다. 검증을 못 돌렸으면 `done` 이 아니라 `partial` 이다.
검증되지 않은 `done` 하나가 그 뒤의 모든 작업을 잘못된 전제 위에 올리고,
잘못이 드러나는 시점은 대개 여러 단계 뒤라 되돌리는 비용이 훨씬 크다.

**`blocked` 는 `blocked_on` 이 비면 쓸 수 없다.**
`blocked` 는 실패 신고가 아니다. 정상 상태이고, 오케스트레이터가 처리할 수 있는 유일한 형태의
막힘이다. 오케스트레이터는 `blocked_on` 을 읽어 사용자에게 중계하거나 다른 에이전트에게 돌린다.
질문이 없는 `blocked` 는 "막혔다" 는 감정만 남기고 아무도 풀 수 없다.
그래서 질문은 **답하면 즉시 진행 가능한 형태**여야 한다. "요구사항이 불명확하다" 는 질문이 아니다.

**`done` 인데 `blocked_on` 이 남아 있으면 모순이다.**
이건 앞의 두 규칙에서 자동으로 따라 나오지 않는다. 별도로 막는 이유는, 실제로 자주 나오는
형태가 "대충 되긴 했는데 이건 나중에 확인해 주세요" 이기 때문이다. 이 조합은 수신 쪽에
서로 반대되는 신호를 준다 — `status` 는 진행하라고 하고 `blocked_on` 은 멈추라고 한다.
수신 에이전트는 둘 중 하나를 골라야 하는데, 계약에는 어느 쪽이 우선인지 없다.
그래서 계약 단계에서 아예 금지한다. 남은 질문이 있으면 `partial` 이거나 `blocked` 다.

### 전이는 새 파일로 일어난다

핸드오프에는 상태를 바꾸는 연산이 없다. 파일은 만들어지고 나면 고쳐지지 않는다.
어떤 에이전트가 `blocked` 를 낸 뒤 답을 받아 작업을 마쳤다면, 앞 파일의 `status` 를 고치는
것이 아니라 **새 핸드오프를 하나 더 쓴다.** 두 파일이 나란히 남고, 타임스탬프 순서가 곧 전이다.

```
curvez-architect.20260816-141203.json   status: blocked   (스택 질문)
curvez-architect.20260816-152740.json   status: done      (답 받고 완료)
```

여기서 주의할 점이 있다. **검증기는 파일을 하나씩 독립적으로 검사한다.**
"blocked 였던 것이 done 으로 풀렸는가", "partial 의 남은 범위가 나중에 채워졌는가" 같은
파일 간 관계는 검사하지 않는다. `blocked` 를 내고 아무도 답하지 않은 채 실행이 끝나도
검증기는 조용하다. 이건 오케스트레이터가 수합 단계에서 챙겨야 하는 몫이고,
계약이 자동으로 보장해 주지 않는 부분이다.

## 검증기가 막는 것과 그 이유

`validate-handoff.mjs` 의 규칙들은 "스키마를 지켰는가" 를 보는 것 같지만,
실제로는 **팀 실행에서 반복적으로 나온 특정 실수**를 하나씩 겨냥한 것이다.
규칙을 실수 쪽에서 보면 이렇게 읽힌다.

### 결과가 사라지는 실수

**받는 사람을 안 적는다.** `to` 가 비면 그 산출물은 아무도 읽지 않는다.
다음 단계에서 같은 작업이 다시 실행되고, 두 결과가 서로 다르면 어느 쪽이 맞는지 판정할
근거가 없다. 다음 담당이 안 정해졌더라도 `["curvez-orchestrator"]` 로 돌려주면 최소한
누군가는 읽는다. 그래서 빈 배열을 허용하지 않는다.

**누가 만들었는지 안 적는다.** `from` 이 비면 추적이 끊긴다.
회고가 "이 결정을 누가 언제 했나" 를 되짚을 때 이름이 없으면 그 지점부터 이력이 끊긴다.

**한 일이 없는 완료.** `done` 인데 `artifacts` 도 `decisions` 도 비어 있으면
남긴 것이 하나도 없는 완료다. 이건 **오류가 아니라 경고**로 둔다.
조사만 하고 결정을 못 내린 경우처럼 정당한 빈 완료가 실제로 있기 때문이다.
다만 대개는 산출물을 적는 것을 잊은 쪽이라, 확인하라고 표시만 한다.

### 판정 불가능한 기록을 남기는 실수

**검증 없는 완료 선언.** 위에서 다룬 `done` / `verification` 규칙이다.
검증기가 잡을 수 있는 것은 "비었는가" 까지다. 내용이 판정 가능한지는 못 잡는다 —
`{ "command": "타입 확인", "result": "통과" }` 는 규칙을 전부 통과한다.
이것이 왜 계약을 무력화하는지는 아래 [안티패턴](#안티패턴)에서 다룬다.

**위치 없는 지적.** `findings[].where` 를 필수로 둔다.
파일:라인이 없는 리뷰 지적은 재현할 수 없고, 재현 못 하는 지적을 받은 구현 에이전트는
어디를 고쳐야 하는지 추측한다. 추측으로 고친 것은 리뷰어가 지적한 것과 다른 곳일 수 있고,
그러면 같은 지적이 다음 라운드에 또 나온다.

**등급 없는 지적.** `severity` 도 `priority` 도 없으면 오류다.
등급이 없으면 모든 지적이 같은 무게로 들어오고, 오케스트레이터는 30개를 전부 P0 처럼
다루거나 전부 무시한다. 어느 쪽이든 리뷰가 신호를 잃는다.
**이 규칙은 검증기에만 있고 JSON Schema 에는 없다** — 스키마는 두 필드를 각각 선택으로만
정의한다. 스키마 파일만 보고 "등급은 선택이구나" 라고 판단하면 검증기에서 막힌다.

### 형태가 갈라지는 실수

**리뷰어마다 다른 키 이름.** `findings` 는 선택 필드지만, 있으면 형태를 강제한다.
두 리뷰어가 각자 편한 이름을 쓰면 오케스트레이터가 결과를 두 벌로 파싱해야 하고,
리뷰어가 하나 더 늘 때마다 파싱 코드도 한 벌씩 는다.

**빈 값을 `null` 이나 생략으로 표현.** 배열 필드는 없으면 `[]` 로 둔다.
읽는 쪽이 `Array.isArray` 하나로 처리할 수 있는 것과 세 가지 경우를 분기해야 하는 것의 차이다.

## `findings[]` — 두 리뷰어의 공용 필드

리뷰 결과는 원래 `summary` 와 `decisions` 에 섞여 들어갔다. 이것을 별도 필드로 뺐다.

이유는 **리뷰 결과만 소비하는 쪽이 따로 있기 때문**이다. 오케스트레이터는 두 리뷰어의 지적을
합쳐 우선순위를 매기고 구현 에이전트에게 배분한다. 지적이 자연어 요약 안에 녹아 있으면
그 배분이 기계적으로 안 되고, 오케스트레이터가 문장을 다시 해석하는 단계가 낀다.
해석이 끼면 리뷰어가 blocker 라고 쓴 것이 minor 로 전달되는 일이 생긴다.

### `severity` 와 `priority` 가 왜 따로인가

같은 것을 두 이름으로 부르는 것처럼 보이지만 **재는 축이 다르다.**

- `severity` (`blocker` / `major` / `minor`) — `curvez-reviewer` 가 매긴다. **결함의 파괴력.**
  이게 깨지면 무엇이 안 돌아가는가.
- `priority` (`P0` ~ `P3`) — `curvez-structure-reviewer` 가 매긴다. **영향 파일 수.**
  이걸 고치면 몇 개 파일이 움직이는가.

두 축은 자주 어긋난다. 구조 리뷰어가 P0 을 매긴 지적 — 예를 들어 도메인 레이어에서
프레임워크를 import 하는 패턴이 40개 파일에 퍼져 있는 것 — 은 지금 당장 아무것도
깨뜨리지 않는다. 코드 리뷰어 기준으로는 minor 다. 반대로 blocker 인 로직 결함은
파일 하나만 고치면 끝나는 경우가 많다.

합쳐서 하나의 5단계 척도로 만들면, 두 리뷰어 중 한쪽의 판정 기준표가 의미를 잃는다.
파괴력으로 등급을 매기는 리뷰어에게 "파일 수도 고려하라" 고 하면 그 리뷰어의 기준이 흐려지고,
반대도 마찬가지다. 각자 자기 축에서 정확하게 매기고, 합치는 판단은 오케스트레이터가 한다.

### `where` 가 두 형태인 이유

한 곳이면 문자열, 여러 곳이면 문자열 배열을 받는다.

구조 리뷰어의 지적은 **본질적으로 위치가 여럿**이다. 중복 코드 지적은 중복된 곳이 전부
위치이고, 순환 의존 지적은 순환에 참여한 모듈이 전부 위치다. 이걸 문자열 하나로 강제하면
`"a.ts:10, b.ts:22, c.ts:5 (외 3곳)"` 같은 문자열이 나오고, 읽는 쪽은 그걸 다시 파싱해야 한다.
파싱 규칙은 아무 데도 정의돼 있지 않으므로 파싱은 결국 깨진다.

`evidence` 가 문자열과 `{ command, output }` 을 모두 받는 것도 같은 맥락이다.
논리적 근거는 문장이지만, 실행으로 얻은 근거는 명령과 출력 두 조각이다.
한 형태로 뭉개면 "어떤 명령으로 재현하는가" 가 문장 안에 묻혀 기계 판독이 오히려 어려워진다.

읽는 쪽은 `where` 를 항상 `[].concat(where)` 로 배열화해서 쓴다.
이 관례를 지키지 않으면 문자열이 왔을 때 문자 단위로 순회하게 된다.

### 강제되지 않는 것: `id` 접두사

두 리뷰어의 `findings` 를 합칠 때 `id` 가 충돌한다. 각자 `R-001` 부터 매기기 때문이다.
그래서 오케스트레이터가 합치는 시점에 `<from>/<id>` 로 접두사를 붙인다.
`curvez-reviewer/R-001`, `curvez-structure-reviewer/R-001` 처럼 된다.

**이건 검증기가 강제하지 않는다.** 스키마에도 없다.
리뷰어가 낸 원본 핸드오프에는 접두사가 없는 것이 정상이고, 검증기는 파일을 하나씩 보므로
"합쳐질 때 충돌하는가" 를 볼 수 없다. 접두사는 오직 오케스트레이터의 절차로만 지켜진다.

즉 **오케스트레이터가 이 단계를 건너뛰어도 아무 도구도 경고하지 않고**, 두 리뷰어의
`R-001` 중 하나가 조용히 덮이거나 같은 것으로 취급된다. 지적 하나가 사라지는 형태라
결과물만 봐서는 알아채기 어렵다. curvez 를 확장해 리뷰어를 셋 이상으로 늘린다면
이 한계가 그만큼 커진다는 점을 염두에 둬야 한다.

## 실패 사례

설계 단계에서 실제로 드러난 것들이다. 전부 지금의 계약 모양에 흔적을 남겼다.

### 읽기 전용 에이전트가 계약 파일을 못 쓴다

리뷰어 2종은 코드를 고치면 안 된다. 그래서 정의에서 쓰기 도구를 막았다.
그러자 **핸드오프 파일도 못 만들게 됐다.** 계약 파일 역시 파일이기 때문이다.

"핸드오프만 예외로 허용" 은 성립하지 않는다. 도구 권한은 경로 단위로 열리는 것이 아니라
도구 단위로 열리고, 쓰기를 열어 주면 리뷰어가 소스를 고치는 것도 같이 열린다.

결국 리뷰어는 **응답 텍스트로 JSON 을 반환하고 오케스트레이터가 대신 파일로 쓴다.**
계약의 저자와 계약 파일의 작성자가 다른 구조다. 이 대필 구조가 위의 `id` 접두사 문제가
생기는 자리이기도 하다 — 어차피 오케스트레이터를 거치므로 접두사를 붙일 지점은 있지만,
그 지점이 도구가 아니라 절차라서 강제되지 않는다.

관련해서 하나 더 확인된 것이 있다. **도구 권한만으로는 읽기 전용이 강제되지 않는다.**
`Bash` 가 열려 있으면 리다이렉션이나 `sed -i` 로 파일을 고칠 수 있다.
그래서 에이전트 정의에 금지 명령을 따로 열거해야 했다. 자세한 것은
[에이전트 작성](agent-authoring.md)에 있다.

### `where` 를 문자열로만 좁혔다가 구조 리뷰어를 깼다

`findings` 를 정식 필드로 승격할 때, 스키마를 코드 리뷰어 관점으로만 봤다.
코드 리뷰어의 지적은 대부분 위치가 한 곳이라 `where: string` 으로 충분해 보였다.

그런데 구조 리뷰어는 이미 여러 위치를 넘기고 있었다. 중복과 순환은 위치가 하나일 수 없다.
스키마를 좁히자 그쪽의 기존 사용이 전부 검증에서 튕겼다.

교훈은 `where` 의 타입이 아니라 그 위다. **공용 필드를 한 소비자의 관점으로만 설계하면
다른 소비자가 부서진다.** `findings` 는 두 리뷰어가 공유하는 필드이므로, 필드를 좁힐 때는
양쪽의 실제 사용을 다 봐야 한다. `evidence` 를 두 형태로 둔 것은 이 경험을 먼저 적용한 결과다.

### 검증기와 스키마가 어긋난 자리

스키마에는 `additionalProperties: false` 가 걸려 있다. 최상위에 모르는 키가 있으면
안 된다는 뜻이다. 그런데 `validate-handoff.mjs` 는 **필수 필드가 있는지만 보고,
모르는 키가 섞여 있는지는 보지 않는다.** 작성 시점(2026-08-16) 기준으로 이 검사는 여전히 없다.

결과적으로 `verifications` 처럼 이름을 하나 틀린 필드는 이렇게 통과한다 —
`verification` 이 없다는 오류는 나지만, `verifications` 라는 낯선 키가 있다는 말은 없다.
오타를 낸 쪽은 "왜 없다는 거지" 하면서 원인을 못 찾는다.

이 어긋남이 생기는 구조적 이유가 있다. **검증기는 스키마 파일을 읽지 않는다.**
의존성 없이 돌리려고 규칙을 손으로 옮겨 구현했고, 그래서 둘이 따로 논다.
지금도 한 방향으로 어긋나 있다 — `findings` 의 "severity 나 priority 중 하나는 필수" 규칙은
검증기에만 있고 스키마에는 없다.

**스키마와 검증기가 둘 다 정본인 상태는 유지되지 않는다.**
curvez 를 확장하며 필드를 추가한다면 두 곳을 같이 고쳐야 하고, 어느 한쪽만 고치면
"스키마는 통과하는데 검증기가 막는" 또는 그 반대의 상태가 다시 생긴다.

## 안티패턴

계약이 형식적으로는 완벽한데 실질적으로는 무의미한 경우들이다.
검증기는 이것들을 대부분 못 잡는다 — 필드가 채워져 있기 때문이다.

### 재현 불가능한 명령

```json
{ "command": "타입 확인", "result": "통과" }
```

`command` 는 **실제로 셸에 입력한 문자열 그대로**여야 한다. "타입 확인" 은 그것을 읽는
누구도 다시 돌려볼 수 없다. 계약의 목적은 "내가 했다" 는 선언이 아니라
"의심스러우면 이렇게 다시 돌려 보라" 는 근거를 넘기는 것이다. 재현 못 하면 그건 선언일 뿐이다.

돌려볼 수 없는 검증은 돌리지 않은 검증과 구별되지 않는다. 그리고 실제로 이 형태는
검증을 안 돌리고 `done` 을 내고 싶을 때 나온다.

### 판정 불가능한 결과

```json
{ "command": "pnpm test", "result": "정상 동작" }
```

"정상 동작" 은 판정이지 근거가 아니다. 테스트가 **0개 실행돼도** 이 문장은 참이 된다.
실제로 프로젝트 초기에 0개 실행을 탐지하려고 정규식을 붙였을 때
`0 (tests?|passed)` 가 `10 passed` 를 오탐하는 일이 있었다
(자세한 것은 [셸 함정](shell-pitfalls.md)에 있다). 그런 검사조차 `result` 에 숫자가 있어야 가능하다.

`result` 에는 **개수, 수치, 또는 명시적 상태**를 적는다.
`"0 errors, 0 warnings"`, `"12 passed, 0 failed"` 처럼 판정을 읽는 쪽이 하게 만든다.
송신 쪽이 미리 판정해 버리면 수신 쪽에는 그 판정을 검증할 방법이 없다.

### 요약된 출력

긴 출력을 "대부분 통과" 나 "몇 개 경고" 로 줄이는 것.
줄이는 과정에서 사라지는 것이 정확히 문제가 되는 부분이다.
`"3 warnings, 0 errors"` 는 요약이지만 판정 가능한 요약이다.
`"경고 좀 있음"` 은 판정할 수 없다. 경계는 길이가 아니라 **숫자가 남아 있는가**다.

### 실패를 숨긴 `done`

실패한 검증도 그대로 적는다. `passed: false` 를 붙이면 된다.

```json
{
  "command": "pnpm test",
  "result": "10 passed, 2 failed (order.spec.ts)",
  "passed": false
}
```

이 경우 `status` 는 `partial` 이거나 `blocked` 다.
실패를 지우고 `done` 을 내는 것이 계약 위반의 가장 무거운 형태다 —
다른 안티패턴은 근거를 약하게 만들지만 이건 거짓을 만든다.

### 서사가 섞인 계약

`summary` 에 "작업을 진행했습니다. 여러 어려움이 있었지만..." 같은 문장을 넣는 것.
핸드오프는 기계가 읽는 계약이고, 사용자 보고는 사람이 읽는 문장이다.
둘을 섞으면 계약에서는 다음 행동을 못 정하고, 보고에서는 스키마 때문에 사람이 못 읽는다.
`summary` 는 **수신 에이전트가 그것만 읽고 다음 행동을 정할 수 있는 한 줄**이다.

## 계약이 보장하지 않는 것

마지막으로, 이 계약을 신뢰할 때의 경계를 명확히 해 둔다.
아래는 전부 **도구가 아니라 절차로만 지켜지는** 것들이다.

- `findings[].id` 의 `<from>/` 접두사 — 오케스트레이터가 붙인다
- 파일 간 상태 전이 — 검증기는 파일을 하나씩 독립적으로 본다
- `verification` 의 명령이 실제로 실행됐는지 — 검증기는 비었는지만 본다
- `verification.result` 가 판정 가능한 값인지 — 형식만 보고 내용은 안 본다
- 최상위에 모르는 키가 섞였는지 — 스키마에는 금지돼 있으나 검증기가 안 본다
- `blocked` 로 남은 질문이 결국 답을 받았는지 — 아무도 추적하지 않는다

검증기를 통과했다는 것은 **계약이 파싱 가능하다**는 뜻이지 **계약이 참이다**는 뜻이 아니다.
`done` 을 무엇으로 판정할 것인가라는 더 넓은 질문은 [품질 모델](quality-model.md)에서 다룬다.
