# 셸 검증 명령의 함정 — 실측 기록

curvez 의 스킬과 에이전트 정의에는 bash 검증 명령이 많이 들어간다. 아키텍처 금지 import 검사,
조사 브리프의 출처 누락 검사, 품질 게이트의 테스트 결과 판정 — 전부 문서에 적힌 한 줄짜리 명령이
실제 판정을 내린다.

이 문서는 그 명령들을 **실제로 돌려보다가 밟은 함정**을 모은 것이다. 일반적인 셸 팁이 아니라,
이 프로젝트에서 실행해 재현한 것만 담는다.

## 왜 이 문서가 특별히 위험한 주제인가

여기 적힌 함정은 **대부분 조용히 실패한다.**

에러를 내지 않는다. 종료 코드도 0 이다. 출력은 "위반 0건" 이고, 검증기는 그것을 "깨끗함" 으로
읽는다. 그러나 실제로 일어난 일은 **검사가 아예 수행되지 않은 것**이다.

이 차이는 명령을 눈으로 읽어서는 절대 드러나지 않는다. 문법이 맞고, 의도가 명확하고, 리뷰를 통과한다.
결함을 일부러 심은 파일에 대고 실제로 돌려봐야만 드러난다.

그래서 이 문서의 각 항목은 "증상 / 왜 생기는가 / 어떻게 확인했는가 / 올바른 형태" 네 부분으로 쓴다.
확인 방법을 적는 이유는, 읽는 사람이 자기 명령에 같은 검사를 다시 돌릴 수 있게 하기 위해서다.

## 측정 환경

아래 결과는 모두 이 환경에서 실행해 얻은 것이다. 다른 환경에서는 다를 수 있다.

| 항목 | 값 |
|---|---|
| OS | macOS 26.5.1 (arm64) |
| 사용자 로그인 셸 | `zsh` (`$SHELL=/bin/zsh`) |
| `bash` | GNU bash 3.2.57 — macOS 기본. **4.x 가 아니다** |
| `awk` | BSD awk `20200816` (gawk 아님) |
| `/bin/sh` | bash 3.2 의 POSIX 모드 |

특히 두 가지를 기억해 둘 만하다. 사용자가 명령을 손으로 붙여 넣는 곳은 **zsh** 이고,
스크립트나 도구가 명령을 실행하는 곳은 **bash 3.2 또는 sh** 다. 같은 명령이 두 곳에서
다르게 동작하는 항목이 이 문서에 두 개 있다(3번, 11번).

## 1. awk 로 마크다운 표를 파싱할 때

가장 많은 시간을 잡아먹었고, 가장 조용하게 실패한 항목이다.

`.curvez/architecture.md` 의 `## 금지 import` 표는 세 번째 열에 ERE 패턴을 담고, 그 패턴이
`grep -E` 에 그대로 들어간다. 그래서 표를 기계로 읽어야 하고, 패턴 안에 `|` 가 들어간다.
마크다운 표의 열 구분자와 정규식의 교대 연산자가 같은 문자라는 것 — 여기서 모든 문제가 나온다.

### 1-1. 필드 구분자를 `-F'|'` 로 쓰면 열이 잘린다

**증상.** 패턴 열이 중간에서 끊긴 채로 나온다. 잘린 조각이 `grep -E` 로 들어가 엉뚱한 것을
매칭하거나, 문법 오류로 아무것도 매칭하지 못한다.

**왜 생기는가.** awk 는 필드 구분자를 문자 그대로 적용한다. 패턴 안의 `|` 도 구분자로 세므로
행마다 필드 개수(`NF`)가 달라진다. 규칙 하나하나가 서로 다른 열 배치를 갖게 되어,
`$4` 같은 고정 인덱스가 성립하지 않는다.

**어떻게 확인했는가.** 규칙 3개짜리 픽스처를 만들어 두 구분자로 파싱했다.

```
$ awk -F'|' '/^\| ARCH-/ { printf "pat=[%s] NF=%d\n", $4, NF }' architecture.md
pat=[ ^import .*from '(next\] NF=7
pat=[ from '@/apps/mobile ] NF=6
pat=[ (useState\] NF=7
```

패턴에 `|` 가 있는 행은 `NF=7`, 없는 행은 `NF=6` 이다. 같은 표의 같은 형식 행인데 필드 수가
다르고, 패턴은 첫 `|` 에서 잘렸다.

```
$ awk -F' \| ' '/^\| ARCH-/ { printf "pat=[%s] NF=%d\n", $3, NF }' architecture.md
pat=[^import .*from '(next\|react)'] NF=4
pat=[from '@/apps/mobile] NF=4
pat=[(useState\|useEffect)] NF=4
```

**올바른 형태.** 구분자를 **공백-파이프-공백** `-F' \| '` 로 쓴다(awk 인자로 넘길 때는
백슬래시가 한 번 더 필요해 `-F' \\| '` 로 적는다). 표의 셀 경계에는 항상 양쪽 공백이 있고,
정규식 안의 이스케이프된 `\|` 에는 공백이 없다는 규약을 이용하는 것이다.
모든 행이 `NF=4` 로 일정해지고, 필드 인덱스가 한 칸씩 앞으로 당겨진다(`$3` 이 패턴 열).

### 1-2. `\|` 를 되돌리지 않으면 전부 0건이 된다 — 가장 위험한 부분

**증상.** 검사가 통과한다. 위반 0건. 그런데 결함을 일부러 심어 놓은 파일에서도 0건이다.

**왜 생기는가.** 표에 적힌 패턴은 마크다운이 깨지지 않도록 `\|` 로 이스케이프되어 있다.
그 문자열을 그대로 `grep -E` 에 넘기면, grep 은 `\|` 를 "교대 연산자" 가 아니라
**리터럴 파이프 문자** 로 해석한다. 즉 `(next\|react)` 는 "next 또는 react" 가 아니라
"`next|react` 라는 8글자" 를 찾는 패턴이 된다. 그런 문자열은 소스 코드에 없으므로 항상 0건이다.

**어떻게 확인했는가.** `next` 와 `react` 를 import 하고 `useState` 를 쓰는 결함 파일에 대고
복원 유무만 바꿔 두 번 돌렸다.

```
# 이스케이프 복원 없이
ARCH-001  pat=[^import .*from '(next\|react)']  hits=0
ARCH-002  pat=[from '@/apps/mobile]             hits=0
ARCH-003  pat=[(useState\|useEffect)]           hits=0

# gsub(/\\\|/,"|",p) 로 복원 후
ARCH-001  pat=[^import .*from '(next|react)']   hits=2
ARCH-002  pat=[from '@/apps/mobile]             hits=0
ARCH-003  pat=[(useState|useEffect)]            hits=1
```

**3개 규칙 전부 0건이었다.** 그리고 ARCH-002 는 원래 위반이 없어 양쪽 모두 0건이다 —
즉 위쪽 출력만 보면 "결함 없음" 과 구별할 방법이 전혀 없다. **파싱 실패가 "깨끗함" 으로
위장된 것이다.**

**올바른 형태.** 패턴을 grep 에 넘기기 전에 awk 안에서 되돌린다.

```awk
{ p = $3; gsub(/\\\|/, "|", p); print p }
```

### 1-3. 방어책 — 파싱한 규칙 개수를 함께 출력한다

1-2 가 무서운 이유는 실패 신호가 정상 결과와 똑같이 생겼다는 것이다. 이 위장을 깨는
가장 싼 방법은 **위반 개수와 함께 파싱된 규칙 개수를 출력하는 것**이다.

```
파싱된 규칙 수=3  총 위반=0     # 검사했고 깨끗하다
파싱된 규칙 수=0  총 위반=0     # 검사를 못 했다
```

두 줄은 위반 개수가 같지만 의미가 정반대다. **규칙 수가 0이면 "위반 없음" 이 아니라
"검사 못 함" 이고, 그때는 `done` 이 아니라 `blocked` 다.** 이 원칙 자체는
[품질 모델](quality-model.md)이 다룬다.

같은 이유로, 규칙 수가 표에 실제로 적힌 행 수와 다르면 그것도 파싱 실패 신호다.
표에 5행이 있는데 4개만 파싱됐다면 한 행이 형식을 벗어난 것이다.

### 1-4. 표를 쓰는 쪽의 실패 모드 두 가지를 구분하라

패턴 열에 `|` 를 이스케이프하지 않고 적었을 때, **공백이 있느냐 없느냐로 증상이 완전히 갈린다.**
둘을 같은 문제로 묶으면 진단이 어긋난다.

```
$ awk -F' \| ' '{ printf "%s  NF=%d  pat=[%s]\n", $1, NF, $3 }' bad.md
| ARCH-010  NF=5  pat=[(next]           # (next | react)  — 공백 있음
| ARCH-011  NF=4  pat=[(next|react)]    # (next|react)    — 공백 없음
```

아래 표의 "쓴 형태" 는 위 코드 블록의 세 가지를 가리킨다. 마크다운 표 안에서는 이스케이프하지 않은
`|` 를 그대로 보여줄 수 없으므로 — 그게 바로 이 항목이 말하는 문제다 — 형태는 말로 적는다.

| 쓴 형태 | awk | 마크다운 렌더링 | 결과 |
|---|---|---|---|
| 파이프를 `\|` 로 이스케이프 | `NF=4`, 정상 | 4열 정상 | 올바름 |
| 이스케이프 안 함 + 파이프 **양옆에 공백** | `NF=5`, 패턴이 `(next` 로 잘림 | 5열로 깨짐 | awk 가 열을 잘라먹는다 |
| 이스케이프 안 함 + 파이프 **양옆에 공백 없음** | `NF=4`, **패턴은 온전** | 5열로 깨짐 | awk 는 통과, **표가 깨진다** |

세 번째가 특히 헷갈린다. 파싱 스크립트를 아무리 돌려봐도 정상으로 보이는데, 문서를 렌더링하면
표가 어긋나 있고 사람이 읽는 아키텍처 문서가 망가진다. 검증기는 **파싱 성공과 별개로
"패턴 열에 이스케이프되지 않은 `|` 가 있는가" 를 따로 검사해야 한다.**

## 2. awk 의 interval `{n}` — 우려했지만 문제가 아니었다

이 항목은 함정이 아니다. **근거 없이 회피 코드를 넣지 않기 위한 기록**이다.

BSD awk 에서 `{3}` 같은 interval 표현식이 지원되지 않는다는 이야기가 널리 퍼져 있다.
그래서 `ARCH-[0-9]{3}` 을 `ARCH-[0-9][0-9][0-9]` 로 전개해 쓰는 코드를 흔히 본다.

**실측 결과 이 환경의 awk(`20200816`)는 interval 을 정상 지원한다.**

```
$ printf 'ARCH-001\nARCH-12\nARCH-9999\n' | awk '/^ARCH-[0-9]{3}$/ {print "match:", $0}'
match: ARCH-001
```

`ARCH-12`(2자리)와 `ARCH-9999`(4자리)는 걸러졌다. 정확히 3자리만 매칭됐다.

**따라서 전개형으로 바꿀 필요가 없다.** 전개형은 길고, 자릿수를 바꿀 때 실수하기 쉽고,
무엇보다 "왜 이렇게 썼는가" 를 설명할 근거가 없는 코드다.

이 항목을 남기는 이유는, 나중에 누군가 같은 우려로 코드를 되돌리려 할 때 **되돌리기 전에
자기 환경에서 위 한 줄을 먼저 돌려보게 하기 위해서다.** awk 구현이 다른 환경(오래된 BSD awk,
busybox)에서는 실제로 실패할 수 있고, 그때는 이 기록이 아니라 그 환경의 실측이 근거가 된다.

## 3. zsh 에서 `grep --include=*.ts` 가 죽는다

**증상.** grep 이 아예 실행되지 않고 `no matches found: --include=*.ts` 로 종료된다.
종료 코드 1.

**왜 생기는가.** 사용자 셸이 zsh 다. zsh 는 기본 설정에서 매칭되는 파일이 없는 glob 을
**에러로 처리한다**(bash 는 glob 을 그대로 문자열로 넘긴다). `--include=*.ts` 의 `*.ts` 는
셸이 먼저 확장을 시도하는 glob 이고, 현재 디렉터리에 `.ts` 파일이 없으면 그 자리에서 죽는다.

이 함정은 **디렉터리에 따라 나타났다 사라진다.** 프로젝트 루트에서 시험할 때는 `.ts` 파일이
있어서 잘 돌아가다가, 서브에이전트가 다른 cwd 에서 같은 명령을 돌리면 실패한다. 재현이
간헐적으로 보여 원인을 찾기 어렵다.

**어떻게 확인했는가.**

```
$ zsh -c 'grep -rn --include=*.ts "useState" src/'
zsh:1: no matches found: --include=*.ts        # exit=1, grep 은 실행조차 안 됨

$ zsh -c "grep -rn --include='*.ts' useState src/"
src/a.ts:2:import { useState } from 'react'    # exit=0
```

**올바른 형태.** glob 을 따옴표로 감싸 셸이 건드리지 못하게 한다: `--include='*.ts'`.
같은 이유로 `find . -name '*.ts'` 의 `-name` 인자, `grep --exclude-dir` 인자도 전부 감싼다.

## 4. `grep -c` 는 0건일 때 exit 1 이다

**증상.** `set -e` 를 켠 게이트 스크립트가 **결함이 하나도 없을 때 죽는다.** 결함이 있으면
잘 돌아간다. 정확히 거꾸로 동작한다.

**왜 생기는가.** grep 의 종료 코드는 "찾았는가" 를 뜻한다. `-c` 를 붙여도 마찬가지다.
0건이면 `0` 을 출력하면서 exit 1 을 낸다. `set -e` 는 이것을 실패로 보고 스크립트를 중단한다.
명령 치환 대입(`n=$(grep -c ...)`)도 예외가 아니다.

**어떻게 확인했는가.**

```
$ grep -c "TODO" src/a.ts
0
$ echo $?
1

$ bash -c 'set -e; echo "검사 시작"; n=$(grep -c "TODO" src/a.ts); echo "여기 도달: n=$n"'
검사 시작                                       # "여기 도달" 이 출력되지 않는다. exit=1

$ bash -c 'set -e; n=$(grep -c "TODO" src/a.ts || true); echo "여기 도달: n=[$n]"'
여기 도달: n=[0]                                # exit=0
```

중간의 실행에서 **에러 메시지가 한 줄도 나오지 않는다.** 스크립트가 조용히 멈추고 exit 1 만
남는다. 게이트 러너가 이 exit 1 을 "게이트 실패" 로 해석하면, **결함이 없다는 사실이
결함으로 보고된다.**

**올바른 형태.** 둘 중 하나를 쓴다.

- `n=$(grep -c ... || true)` — 값만 뽑고 종료 코드는 버린다
- `n=$(grep ... | grep -c . | tr -d ' ')` — 마지막 단계에서 세면 파이프라인 종료 코드가 grep 의
  "찾았는가" 와 분리된다

어느 쪽이든 `wc -l` 을 쓸 때는 8번을 함께 본다.

## 5. `eval "$cmd"` 가 러너 자신을 죽인다

**증상.** 품질 게이트가 첫 명령만 실행하고 조용히 끝난다. 또는 두 번째 명령부터
"파일을 찾을 수 없음" 이 쏟아진다.

**왜 생기는가.** 게이트 러너는 `.curvez/profile.json` 의 `commands` 값을 읽어 실행한다.
그 값은 프로젝트마다 사람이 적은 임의의 셸 문자열이다. 거기에 `exit` 가 섞이면
**현재 셸이 종료된다** — 즉 러너 자체가 끝난다. `cd` 가 섞이면 이후 모든 명령의
상대 경로가 어긋난다.

`exit` 를 일부러 넣는 사람은 없지만, `... && exit 0` 이나 `cd apps/web && pnpm test` 같은
형태는 흔하다. 그리고 이건 **프로파일을 쓴 사람의 실수가 아니라 러너의 설계 결함**이다.
러너는 남이 쓴 문자열을 자기 셸에서 실행하고 있다.

**어떻게 확인했는가.** `cmd='cd /; exit 3'` 을 넣고 두 형태를 비교했다.

```
$ ./runner-bad.sh        # eval "$cmd"
cwd 시작: /.../fx
러너 exit=3
# "게이트 계속 진행" 이 출력되지 않았다 — 러너가 그 자리에서 끝났다

$ ./runner-good.sh       # ( eval "$cmd" ); rc=$?
cwd 시작: /.../fx
게이트 계속 진행: rc=3
cwd 지금: /.../fx        # cwd 가 그대로다
러너 exit=0
```

**올바른 형태.** `( eval "$cmd" )` — 괄호 서브셸로 감싸고 종료 코드만 받는다.

```bash
( eval "$cmd" ); rc=$?
```

이렇게 하면 `exit 3` 은 **서브셸을 끝낼 뿐이고 `rc=3` 이라는 값으로 러너에 전달된다.**
`cd /` 도 서브셸 안에서만 유효해 러너의 cwd 는 보존된다. 실패는 여전히 실패로 잡히고,
러너는 다음 게이트로 넘어간다.

## 6. 개수를 세는 정규식이 부분 문자열을 잡는다

**증상.** 테스트가 잘 돌았는데 "테스트 0개 실행" 으로 판정된다.

**왜 생기는가.** "테스트가 하나도 안 돌았다" 를 잡으려고 `0 (tests?|passed)` 같은 패턴을 쓰면,
`10 passed` `100 tests passed` 의 **끝자리 0** 에 걸린다. 정규식에 숫자 경계가 없기 때문이다.

이건 방향이 다른 위험이다. 앞의 항목들은 "잡아야 할 걸 못 잡는" 실패였는데, 이건
**"잡지 말아야 할 걸 잡는" 실패**다. 성공한 실행을 실패로 보고하므로 조용하지는 않지만,
원인을 정규식에서 찾기까지 시간이 걸린다.

**어떻게 확인했는가.**

```
[0 passed]          경계없음=HIT  경계있음=HIT     # 진짜 잡아야 할 것
[10 passed]         경계없음=HIT  경계있음=miss    # 오탐
[100 tests passed]  경계없음=HIT  경계있음=miss    # 오탐
```

**올바른 형태.** 앞쪽에 숫자 경계를 붙인다: `(^|[^0-9])0 (tests?|passed)`.
`\b` 는 BSD grep 의 ERE 에서 신뢰하기 어려우므로 문자 클래스로 직접 쓴다.

더 근본적으로는, **테스트 러너의 출력 문자열을 정규식으로 파싱하는 것 자체가 취약하다.**
러너가 출력 형식을 바꾸면 조용히 깨진다. 가능하면 종료 코드나 JSON 리포터를 쓰고,
문자열 파싱은 그것이 불가능할 때의 차선책으로 둔다.

## 7. 검사 범위를 섹션으로 좁히지 않으면 정상 문서가 항상 실패한다

**증상.** 결함이 하나도 없는 조사 브리프가 **항상** 위반으로 잡힌다. 브리프를 아무리 고쳐도
`done` 을 낼 수 없다.

**왜 생기는가.** 조사 브리프의 `## 확인된 사실` 표는 모든 행에 출처가 있어야 한다.
그래서 "출처 없는 표 행" 을 센다. 그런데 같은 문서의 `## 확인 불가` 섹션에도 표가 있고,
그 표는 **정의상 출처가 없다** — 확인하지 못한 것을 모아 둔 자리이기 때문이다.
문서 전체를 grep 하면 그 행들이 전부 위반으로 계산된다.

이건 문서를 성실하게 쓸수록 더 나빠진다. 확인 불가 항목을 정직하게 많이 적을수록
위반 수가 늘어난다. 검증기가 정직함에 벌을 주는 셈이다.

**어떻게 확인했는가.** 결함 없는 브리프(확인된 사실 2행 전부 출처 있음, 확인 불가 3행)로 비교했다.

```
# 문서 전체를 grep
표 데이터 행 총계=7
출처 없는 행=5  -> 위반

# '## 확인된 사실' 섹션으로 범위 축소
섹션 내 출처 없는 행=0
```

같은 문서, 같은 검사 규칙인데 **5 대 0** 이다. 위쪽 5건은 전부 헤더행·구분행과
`## 확인 불가` 표의 행이다.

**올바른 형태.** 검사 전에 섹션을 잘라낸다.

```bash
awk '/^## 확인된 사실/{f=1;next} /^## /{f=0} f' brief.md > sect.txt
```

`f` 를 켠 다음 **다음 `## ` 헤딩에서 끈다.** 이 한 줄에 걸린 함정이 두 개 더 있다.

- `/^## /` 의 **끝 공백**을 빼면 안 된다. `/^##/` 로 쓰면 `###` 소제목에서도 꺼져,
  섹션 안에 소제목이 있으면 그 아래가 통째로 잘린다
- 잘라낸 뒤에도 표의 **헤더행과 `|---|` 구분행**은 데이터가 아니다. 따로 제외해야 한다

같은 종류의 오판이 검증기 쪽에서도 한 번 있었다. `## A` 바로 아래에 `### A-1` 이 오는 문서를
"본문 0줄인 빈 섹션" 으로 계산한 일이 그것인데, 원인이 같다 — **섹션의 끝을 어디로 볼 것인가**를
헤딩 레벨과 무관하게 정했기 때문이다.

## 8. macOS `wc -l` 은 앞에 공백을 붙인다

**증상.** 개수 비교가 항상 거짓이 된다. `if [ "$n" = "0" ]` 이 0인데도 통과하지 않는다.

**왜 생기는가.** BSD `wc` 는 숫자를 우측 정렬해 출력한다. GNU `wc` 는 그렇지 않아서,
리눅스에서 잘 돌던 명령이 macOS 에서 조용히 어긋난다.

**어떻게 확인했는가.**

```
$ printf 'a\nb\n' | wc -l | od -c | head -1
0000000                                2  \n

$ n=$(printf 'a\nb\n' | wc -l)
$ [ "$n" = "2" ] && echo true || echo "raw [$n] != 2"
raw [       2] != 2

$ m=$(printf 'a\nb\n' | wc -l | tr -d ' ')
$ [ "$m" = "2" ] && echo true
true
```

숫자 앞에 **공백 7칸**이 붙는다. 그리고 `$(...)` 는 후행 개행만 지우지 선행 공백은 지우지 않으므로,
명령 치환으로 받아도 그대로 남는다.

여기서 진짜 위험한 건 **따옴표를 뺀 `[ $n = "2" ]` 는 우연히 동작한다**는 것이다. 셸이
단어 분리를 하며 공백을 날리기 때문이다. 그래서 "따옴표를 제대로 쓴 쪽이 깨지는" 상황이 생기고,
고치는 방향을 잘못 잡기 쉽다.

**올바른 형태.** `wc` 결과에는 항상 `| tr -d ' '` 를 붙인다. 산술 비교를 쓰는 것도 방법이지만
(`[ "$n" -eq 2 ]`), 값이 문자열로 다시 쓰일 곳이 있으면 공백을 애초에 없애는 편이 안전하다.

## 9. 프로세스 치환 `<(...)` 은 실행 셸을 가린다

**측정 결과가 사전 예상과 달랐던 항목이다.** 예상은 "zsh 에서 조용히 실패한다" 였는데,
직접 돌려 보니 zsh 는 잘 동작했다. 실제로 재현된 실패는 두 가지였고, 둘 다 결론은 같다 —
**프로세스 치환은 어느 셸이 실제로 명령을 실행하는지에 의존하며, 그건 문서에 명령을 쓰는
시점에 알 수 없다.**

**확인 1 — zsh 에서는 정상 동작한다.**

```
zsh -c 'n=0; while read -r l; do n=$((n+1)); done < <(printf "a\nb\nc\n"); echo "n=$n"'
n=3

zsh -c 'grep -f <(printf "useState\n") src/a.ts'   # 정상
zsh -c 'diff <(printf "a\n") <(printf "b\n")'      # 정상
```

**확인 2 — `/bin/sh` 에서는 문법 오류로 죽는다.**

```
$ sh -c 'wc -l < <(printf "a\nb\n")'
sh: -c: line 0: syntax error near unexpected token `<'
exit=2
```

프로세스 치환은 POSIX 셸 기능이 아니다. macOS `/bin/sh` 는 bash 3.2 의 POSIX 모드라 이 문법을
거부한다. 스크립트 shebang 이 `#!/bin/sh` 이거나, 어떤 도구가 명령 문자열을 `sh -c` 로
넘기면 그 순간 죽는다.

이게 조용해지는 지점은 그다음이다. **게이트 러너가 stderr 를 버리고 stdout 만 세면,
문법 오류 메시지는 사라지고 출력이 비어 "위반 0건" 이 된다.**

**확인 3 — 출력 방향 `>(...)` 은 bash 에서 결과를 잃는다.**

```
$ for i in 1 2 3; do zsh  -c 'printf "a\nb\nc\n" > >(wc -l > out.txt); cat out.txt'; done
       3
       3
       3
$ for i in 1 2 3; do bash -c 'printf "a\nb\nc\n" > >(wc -l > out2.txt); cat out2.txt'; done
                                  # 3회 모두 아무것도 출력되지 않음
```

bash 는 프로세스 치환의 생산자 프로세스를 기다리지 않고 종료한다. `out2.txt` 는 만들어졌지만
비어 있고, `cat` 은 exit 0 을 낸다. **에러도 없고 종료 코드도 정상인데 결과만 없다.**
이 경우는 예상대로 완전히 조용한 실패다.

**올바른 형태.** 검증 명령에서는 프로세스 치환을 쓰지 않는다.

- 파이프로 충분한 경우가 대부분이다: `printf ... | wc -l`
- 중간 결과가 필요하면 **임시 파일을 명시적으로 만든다.** 못생겨 보이지만 어느 셸에서도 같게 돌고,
  중간 결과를 눈으로 확인할 수 있어 디버깅이 쉽다
- 루프에 값을 넣어야 하는데 파이프를 못 쓰는 경우는 11번을 본다

## 10. `node -e` 에 셸 변수는 전달되지 않는다

**증상.** `process.env.X` 가 `undefined` 라 경로가 빈 문자열이 되고, 스크립트가 잘못된 위치를
읽거나 쓴다. 에러 없이 "0개 처리" 로 끝난다.

**왜 생기는가.** `export` 없는 대입은 **셸 변수**를 만들 뿐 **환경 변수**를 만들지 않는다.
자식 프로세스인 node 에게는 전달되지 않는다.

같은 셸 안에서는 `echo $CURVEZ_ROOT` 가 값을 잘 보여주기 때문에 "설정은 됐는데 node 가 못 읽는다"
로 보여서, 원인을 node 쪽에서 찾게 되는 게 이 함정의 성가신 점이다.

**어떻게 확인했는가.**

```
$ bash -c 'CURVEZ_ROOT=/Users/kim/Workspace/curvez; node -e "console.log(process.env.CURVEZ_ROOT || \"\")"'
                                          # 빈 줄

$ bash -c 'export CURVEZ_ROOT=...; node -e "..."'
/Users/kim/Workspace/curvez

$ bash -c 'CURVEZ_ROOT=... node -e "..."'  # 명령 앞 인라인 prefix
/Users/kim/Workspace/curvez
```

**올바른 형태.** `export` 를 붙이거나, 명령 바로 앞에 인라인으로 붙인다.
인라인 형태(`VAR=값 node ...`)는 그 한 번의 실행에만 적용되므로 부작용이 없다 —
5번의 서브셸 격리와 같은 취지다.

애초에 값을 인자로 넘길 수 있으면 그게 낫다. `node script.mjs --root "$ROOT"` 는
전달 여부가 명령줄에 보여서 눈으로 검증된다.

## 11. 파이프 뒤의 `while` 루프는 카운터를 잃는다 — 셸마다 다르다

**증상.** 루프 안에서 잘 증가하던 변수가 루프 밖에서 0 이다.

**왜 생기는가.** 파이프라인의 각 단계는 서브셸에서 실행된다. `while` 루프 안의 변수 증가는
서브셸의 변수에만 반영되고, 서브셸이 끝나면 사라진다.

**여기가 이 문서에서 가장 함정 같은 부분이다. 이 동작은 셸마다 다르다.**

```
$ bash -c 'n=0; printf "a\nb\nc\n" | while read -r l; do n=$((n+1)); done; echo "n=$n"'
n=0

$ zsh  -c 'n=0; printf "a\nb\nc\n" | while read -r l; do n=$((n+1)); done; echo "n=$n"'
n=3
```

zsh 는 파이프라인의 **마지막** 단계를 현재 셸에서 실행하므로 값이 살아남는다. bash 3.2 는
그렇지 않다(bash 4.2+ 의 `lastpipe` 옵션은 이 환경에 없다).

즉 **사용자가 zsh 터미널에 붙여 넣어 시험하면 잘 돌아가고, 스크립트나 도구가 bash 로 실행하면
0 이 나온다.** 그리고 0 은 "위반 없음" 으로 읽히므로, 검사가 통과한 것처럼 보인다.
손으로 검증한 명령이 자동 실행에서만 조용히 깨지는 전형적인 경로다.

**어떻게 확인했는가.** 위 두 줄이 그대로 재현이다. 대안 두 가지도 확인했다.

```
$ bash -c 'n=0; while read -r l; do n=$((n+1)); done <<< "$(printf "a\nb\nc\n")"; echo "n=$n"'
n=3
$ bash -c 'n=$(printf "a\nb\nc\n" | wc -l | tr -d " "); echo "n=$n"'
n=3
```

**올바른 형태.** 우선순위 순서로,

1. **집계를 파이프라인의 마지막 단계로 옮긴다.** 세는 게 목적이면 루프가 필요 없는 경우가 많다.
   `... | grep -c . | tr -d ' '` (4번, 8번을 함께 본다)
2. **중간 파일을 만들고 `done < 파일` 로 읽는다.** 프로세스 치환(9번)을 쓰지 않고도
   루프가 현재 셸에서 돈다. 파싱한 규칙 목록을 한 번 파일로 떨어뜨리면
   1-3 의 "규칙 개수 출력" 도 같이 쉬워진다
3. here-string(`<<<`)이나 here-doc 도 되지만 12번의 인용 함정을 함께 본다

## 12. 부록 — 따옴표 없는 here-doc 이 awk 프로그램을 망가뜨린다

11번의 대안을 시험하다 새로 밟은 것이라 부록으로 남긴다. 앞의 항목들과 성질이 같다:
**에러 없이, 결과만 0이 된다.**

11번의 대안 3을 따라 awk 출력을 here-doc 으로 루프에 넣었더니 모든 규칙이 0건이 됐다.

```bash
done <<EOF
$(awk -F' \| ' '... gsub(/\\\|/,"|",p) ...' architecture.md)
EOF
```

**원인.** 따옴표 없는 `<<EOF` 는 본문에 셸 확장을 적용한다. 명령 치환 안에 있어도 마찬가지다.
그 과정에서 awk 프로그램의 백슬래시가 한 겹 벗겨져 **`-F' \| '` 이 `-F' | '` 으로 바뀌었다.**
awk 에서 `' | '` 은 ERE 로 "공백 또는 공백" 이므로 모든 공백에서 필드를 쪼갠다.
결과는 1번과 똑같은 증상 — 필드가 전부 어긋나고 위반 0건이다.

```
# 잘못된 실행 결과
  | hits=0
  | hits=0
  | hits=0                     # id 가 "|" 로 나온 것이 유일한 단서였다
  파싱된 규칙 수=3 / 총 위반=0
```

**여기서도 1-3 의 방어책이 작동했다.** "파싱된 규칙 수=3" 은 정상인데 규칙 id 가 `|` 로
찍힌 것이 유일한 단서였다. 위반 수만 봤다면 "결함 없음" 으로 넘어갔을 것이다.
**중간값을 같이 출력하는 습관이 실제로 한 건을 잡았다.**

**올바른 형태.** 중간 파일을 쓴다. 위 코드를 아래로 바꾸자 결함 픽스처에서 3건이 잡혔다.

```bash
awk -F' \\| ' '...' architecture.md > rules.tsv
while IFS=$'\t' read -r id pat; do ... done < rules.tsv
```

셸 코드 안에 다른 언어(awk, node, jq)의 프로그램을 문자열로 박아 넣을 때는 인용 층이 겹친다.
**인용 층이 두 겹을 넘으면 파일로 분리하는 게 거의 항상 낫다.**

## 13. 따옴표 없는 변수는 zsh 에서 단어 분리되지 않는다

**증상.** 검사 경로를 한 칸에 둘 이상 적은 규칙이 bash 에서는 위반을 잡고 zsh 에서는 **0건**을 낸다.

```
| ARCH-003 | src/domain/ src/application/ | from ['\"][^'\"]*infrastructure/ | ... |
```

```bash
PATHS="src/domain/ src/application/"
grep -rInE "$RE" $PATHS   # 따옴표 없음
```

**왜 생기는가.** bash 는 따옴표 없는 파라미터를 IFS 로 쪼개 두 경로로 넘기지만, zsh 는 기본적으로
분리하지 않는다(`SH_WORD_SPLIT` 이 꺼져 있다). zsh 에서는 `"src/domain/ src/application/"` 이라는
**이름에 공백이 든 경로 하나**가 되고, 그런 디렉터리는 없으므로 grep 이 아무것도 못 찾는다.

**어떻게 확인했는가.** 같은 규칙·같은 픽스처(도메인과 애플리케이션에 위반 1건씩)로 셸만 바꿔 실행했다.

```
bash : 2
zsh  : 0
```

curvez 개발 중 세 담당이 독립적으로 이 함정을 밟았고, 사용자 셸이 zsh 라 실사용에서는 항상 0건 쪽이었다.

**왜 특히 위험한가.** 1번 함정과 같은 유형이다 — 실패가 에러가 아니라 **"위반 없음"** 으로 나타난다.
규칙은 표에 멀쩡히 적혀 있고, 검사는 돌았고, 출력은 0이다. 규칙이 무력하다는 신호가 어디에도 없다.

**올바른 형태.** 규칙 하나에 경로 하나만 둔다. 두 경로를 검사해야 하면 규칙을 둘로 쪼갠다.

```
| ARCH-003 | src/domain/      | from ['\"][^'\"]*infrastructure/ | ... |
| ARCH-009 | src/application/ | from ['\"][^'\"]*infrastructure/ | ... |
```

쪼갠 뒤 같은 픽스처에서 두 규칙이 각각 1건씩 잡는 것을 확인했다.

경로를 배열로 넘길 수 있는 상황이면 배열을 쓰고(`"${paths[@]}"`), 문자열 하나만 가능하면
**경로에 공백을 넣지 않는 것**이 유일하게 이식성 있는 형태다.

## 마무리 — 규칙 하나

**문서에 bash 검증 명령을 쓰면, 반드시 픽스처를 만들어 실제로 돌려라.**

그리고 한 번으로는 부족하다. **양쪽으로** 돌려야 한다.

| 픽스처 | 확인하는 것 |
|---|---|
| 결함을 일부러 심은 것 | 잡아야 할 것을 **잡는가** |
| 결함이 없는 것 | 잡지 말아야 할 것을 **안 잡는가** |

한쪽만으로는 아무것도 증명되지 않는다.

- 결함 픽스처만 돌리면 **7번**(정상 문서가 항상 실패)을 못 잡는다. 위반이 나오는 게 정상이라
  생각하고 넘어간다
- 정상 픽스처만 돌리면 **1-2번**(전부 0건)을 못 잡는다. 0건이 나오는 게 정상이라 생각하고 넘어간다

이 문서에 적힌 함정 대부분은 **양쪽 픽스처를 돌리는 과정에서만 드러났다.** 명령을 읽어서 찾은
것은 하나도 없다.

실제 절차는 이런 모양이 된다.

1. 결함을 심은 픽스처와 결함 없는 픽스처를 각각 만든다. 결함 픽스처에는 **몇 건을 심었는지
   미리 세어 둔다**
2. 명령을 양쪽에 돌린다. 결함 쪽 결과가 심어 둔 수와 **정확히 같은지** 본다.
   "0보다 크다" 로는 부족하다 — 1-1 처럼 잘린 패턴이 엉뚱한 것을 잡아도 0보다는 크다
3. 위반 수와 함께 **검사 규모**(파싱한 규칙 수, 훑은 파일 수, 잘라낸 섹션의 줄 수)를 출력한다.
   이 값이 0이면 결과가 무엇이든 "검사 못 함" 이다
4. 명령을 문서에 넣을 때는 **실행될 셸을 확정한다.** 3번·9번·11번은 셸이 다르면 결과가 다르다

마지막 항목은 도구 문제라기보다 계약 문제다. `.curvez/profile.json` 의 `commands` 값이
어느 셸에서 어떤 cwd 로 실행되는지는 프로파일을 쓰는 사람이 알아야 하고,
그 실행 방식을 정하는 것은 러너의 책임이다(5번). 게이트가 무엇을 근거로 `done` 을 낼 수 있는지에
대한 판단 기준은 [품질 모델](quality-model.md)이, 그 결과를 어떤 형식으로 다음 에이전트에게
넘기는지는 [핸드오프 계약](handoff-contract.md)이 다룬다.
