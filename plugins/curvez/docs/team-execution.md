# 팀 실행 모델

curvez 는 에이전트 여러 명을 동시에 돌린다. 이 문서는 **그 병렬 실행에 무엇이 강제되고 왜 그런지**를
설명한다. 사람이 읽는 문서다.

- **실행 절차**(무엇을 순서대로 하는가)는 `skills/team-orchestration/SKILL.md` 가 정본이다
- **판정 수치**(한 라운드 동시 워커 상한, 재리뷰 루프 상한, 승인 예외 조건)는
  `agents/curvez-orchestrator.md` 가 정본이다. 이 문서는 값을 옮겨 적지 않는다 — 값이 필요하면
  그 파일의 `### 팀 규모 상한`, `### 재실행 루프 상한`, `### 승인 절차` 를 열어라
- **이 문서가 정본인 것:** 모델의 구조, 왜 이 제약들이 필요한가, 어떻게 실패하는가

수치를 여기에 사본으로 두지 않는 이유는 이 모델 자체가 말하는 것과 같다. 같은 값이 두 곳에 있으면
한쪽을 고칠 때 다른 쪽이 남고, 같은 실행 안에서 서로 다른 수를 말하게 된다.

---

## 1. 실행 수단 — 내장 서브에이전트 하나

curvez 의 병렬 실행은 **Claude Code 내장 서브에이전트(`Agent` 도구)** 로만 이루어진다.
tmux 패널에 CLI 워커를 띄우는 방식은 쓰지 않는다.

### 왜 하나로 고정하는가

두 방식을 섞으면 수합 단계가 무너진다. curvez 의 라운드 완료 판정은 "띄운 워커 수와 새로 생긴
핸드오프 파일 수가 같은가" 라는 대조에 기대는데, 프로세스로 띄운 워커와 서브에이전트로 띄운 워커가
섞이면 어느 쪽 규약으로 핸드오프를 남겼는지 갈린다. 파일이 있는 워커와 없는 워커가 뒤섞인 상태에서는
"덜 끝난 것"과 "규약을 안 따른 것"을 구분할 수 없고, 그러면 라운드가 끝났는지 자체를 판정할 수 없다.

tmux 방식 팀이 필요한 작업은 curvez 가 아니라 별도의 `team-lead` 스킬 영역이다. 경계는
`team-orchestration` 의 `## 언제 쓰지 않는가` 에 적혀 있다.

### `Agent` 도구는 오케스트레이터만 갖는다

라인업 전체에서 `tools` 에 `Agent` 가 있는 정의는 `curvez-orchestrator` 하나뿐이다. 실행 트리가
**두 층으로 고정**된다 — 오케스트레이터 하나와 그 아래 워커들.

```
curvez-orchestrator
├── curvez-nextjs
├── curvez-react-native
└── curvez-qa
```

워커가 또 워커를 띄울 수 있게 두면 세 가지가 동시에 깨진다.

| 깨지는 것 | 왜 |
|---|---|
| 깊이 통제 | 트리가 몇 층까지 자랐는지 아무도 모른다. 재귀를 멈출 주체가 없다 |
| 토큰 예측 | 워커 하나의 비용이 그 워커가 띄울 하위 워커 수에 달리게 되어, 라운드를 시작하기 전에 비용을 가늠할 수 없다 |
| 실패 추적 | 산출물이 잘못됐을 때 어느 층의 누가 그렇게 판단했는지 되짚을 수 없다. 핸드오프의 `from` 은 자기 이름만 담는다 |

이 규칙은 정의 파일의 프론트매터로 강제되고, 실측으로 확인할 수 있다.

```bash
grep -l '^tools:.*Agent' plugins/curvez/agents/*.md | wc -l   # 1
```

실제로 돌려 `1` 을 확인했다. 이 값이 2 이상이면 소유권 위반이므로, 오케스트레이터의
`## 품질 자체 검증` 체크리스트에도 같은 명령이 들어 있다.

## 2. 한 라운드의 흐름

curvez 의 실행은 라운드 단위다. 한 라운드는 **띄우고 → 기다리고 → 수합한다** 로 끝나며, 그 사이
오케스트레이터는 파일을 쓰지 않는다. 워커가 도는 동안 지휘자가 파일을 건드리면 워커가 읽는 시점의
상태가 불확정해지기 때문이다.

```
요구사항 ∥ 조사
      ↓
아키텍처 ∥ 디자인
      ↓
웹 구현 ∥ 모바일 구현
      ↓
        QA
      ↓
리뷰 ∥ 구조 리뷰
      ↓
       회고 (`curvez-retrospector`)
```

### 무엇이 병렬이고 무엇이 순차인가

| 묶음 | 판정 | 근거 |
|---|---|---|
| `curvez-requirements` ∥ `curvez-researcher` | 병렬 | 소유 경로가 `.curvez/requirements.md` 와 `.curvez/research/` 로 분리된다. 서로의 산출물을 입력으로 요구하지 않는다 |
| `curvez-marketer` ∥ `curvez-requirements` (∥ `curvez-researcher`) | 병렬 | `.curvez/brand/` 로 분리된다. 단, 브랜드 라운드 자체가 요청 시에만 돈다 — 아래 "브랜드 라운드" 참조 |
| `curvez-architect` ∥ `curvez-designer` | 병렬 | `.curvez/architecture.md` 와 `.curvez/design/` 로 분리된다. 아키텍트 정의가 소유 경로를 파일 하나로 좁혀 둔 것은 이 병렬을 지키기 위해서다 |
| `curvez-nextjs` ∥ `curvez-react-native` | 조건부 병렬 | `paths.web` 과 `paths.mobile` 은 분리되지만 `paths.domain` 은 소유자가 없다. 4절 참조 |
| `curvez-reviewer` ∥ `curvez-structure-reviewer` | 항상 병렬 | 둘 다 소유 경로가 **없다**. 쓰기를 포기한 대가로 어떤 워커와도 충돌하지 않는다 |
| 요구사항 → 아키텍처 | 순차 | 수용 기준이 안 굳은 상태에서 레이어를 정하면 아키텍트가 범위를 지어낸다 |
| 아키텍처·디자인 → 구현 | 순차 | 구현자는 `.curvez/architecture.md` 의 금지 import 목록과 `.curvez/design/` 의 화면 명세를 **읽어야** 시작할 수 있다. 없는 파일을 읽은 워커는 전제를 지어낸다 |
| 구현 → QA | 순차 | QA 는 구현 핸드오프의 `artifacts` 경로를 입력으로 받는다 |
| QA → 리뷰 | 순차 | 리뷰는 검증이 끝난 상태를 대상으로 한다. 테스트가 아직 빨간 코드를 리뷰하면 지적의 절반이 QA 가 이미 잡을 것과 겹친다 |
| 리뷰 → 회고 | 순차 | 회고는 이번 작업의 전체 핸드오프 목록을 시간순으로 재구성한다. 마지막 핸드오프가 나오기 전에는 재료가 없다 |

순차 관계의 근거는 전부 같은 형태다 — **한쪽이 다른 쪽의 산출 파일을 입력으로 읽어야 한다.**
읽어야 할 파일이 아직 없는데 띄우면 워커는 멈추지 않고 그 자리를 추측으로 채운다. 그 추측은
핸드오프에 "결정" 으로 기록되어 다음 라운드로 전파된다.

### 조사는 위치가 고정이 아니다

`curvez-researcher` 는 위 그림에서 요구사항과 같은 라운드에 놓았지만, 조사 질문이 요구사항 확정
결과에 달려 있으면 아키텍처 라운드로 미룬다. 어느 쪽이든 판정 기준은 동일하다 — **입력 파일을
읽어야 하면 순차, 아니면 병렬.** 라운드 배치는 흐름도가 아니라 이 판정에서 나온다.

### 라운드를 하나 더 만드는 쪽이 항상 옳다

한 라운드 동시 워커 수에 상한이 있다(값은 `curvez-orchestrator.md` 의 `### 팀 규모 상한`).
상한에 걸렸을 때 팀을 키우는 선택지는 없다. 라운드를 하나 더 만든다.

이유는 수합 쪽에 있다. 오케스트레이터는 워커가 돌려준 핸드오프를 **전부 자기 컨텍스트에 올려**
다음 라운드를 판정한다. 동시 워커가 많아지면 먼저 돌아온 핸드오프가 컨텍스트에서 밀려 나가고,
밀려 나간 것이 하필 `blocked_on` 을 담고 있으면 그 질문은 아무에게도 전달되지 않은 채 사라진다.
사라진 질문은 실패로 보이지 않는다 — 라운드는 정상 종료된 것처럼 보인다.

## 3. 병렬 판정의 실질 — 파일 소유권

병렬 안전성을 만드는 것은 **도구 권한이 아니라 경로 분할**이다.

두 에이전트가 모두 `Write` 를 갖고 있어도 쓰는 경로가 겹치지 않으면 안전하다. 반대로 권한을 아무리
좁혀도 같은 파일을 대상으로 삼으면 충돌한다. 그래서 curvez 의 모든 에이전트 정의는
`## 협업과 팀 내 위치` 에 **파일 소유권**을 명시하고, 오케스트레이터는 워커를 고를 때 그 항목을
읽어 교차 비교한다.

### 왜 겹치면 순차로 강등하는가

동시 쓰기의 위험은 "에러가 난다" 가 아니라 **조용하다**는 데 있다. 나중에 쓴 쪽이 앞선 쪽의 변경을
덮어쓰고, 파일에는 마지막 판본만 남는다.

- 실행 중에는 아무 오류도 나지 않는다
- diff 에는 최종 상태만 보이므로 "지워진 변경" 이 흔적으로 남지 않는다
- 리뷰어는 지금 파일에 있는 코드를 읽으므로, 사라진 쪽을 지적할 수 없다
- 잃어버린 변경을 낸 워커의 핸드오프에는 `status: done` 과 그 변경이 `artifacts` 로 적혀 있다

즉 **손실이 어디에도 기록되지 않는다.** 발견되는 시점은 보통 한참 뒤, 있어야 할 기능이 없다는 것을
사람이 눈치챌 때다. 그때는 어느 라운드에서 무엇이 지워졌는지 복원할 근거가 없다.

이 비용에 비하면 순차 강등의 비용은 라운드 하나가 늘어나는 것뿐이다. 그래서 판정은 대칭이 아니다 —
**겹칠 가능성이 있으면 무조건 순차**다.

### 소유권이 안 적혀 있으면 순차다

정의 파일에 파일 소유권이 없으면 그 워커는 병렬 후보에서 빠진다. "겹치지 않는다" 를 증명할 근거가
없기 때문이다. 근거 없는 병렬은 도박이고, 지는 쪽의 손실이 조용하다는 것은 위에서 본 대로다.

**이 판정을 검증기가 대신해 주지 않는다.** `validate-agents.mjs` 는 `## 협업과 팀 내 위치` 헤딩이
존재하는지만 검사한다 — 그 안에 파일 소유권이 적혀 있는지, 두 에이전트의 소유 경로가 겹치는지는
검사하지 않는다(`scripts/lib/spec.mjs` 의 `AGENT_REQUIRED_SECTIONS` 참조). 소유권 교차 검사는
오케스트레이터가 실행 시점에 눈으로 하는 절차다. 새 에이전트를 만들 때 소유권 항목을 빈 채로 두면
검증은 통과하고, 그 워커는 조용히 병렬 후보에서 빠지거나 — 더 나쁘게는 — 겹친 채로 실행된다.

### 포함은 겹침이 아니다 — 배제 목록을 차감한다

앞의 "겹치면 순차" 는 두 소유 경로가 **대등하게 교차**할 때의 판정이다. 한쪽이 다른 쪽을 통째로
**포함**하는 경우는 성질이 다르고, 실제로 흔하다.

`curvez-nextjs` 의 소유 경로는 `${paths.web}` 인데 **단일 저장소에서 이 값은 `.` 이다.**
`bootstrap.mjs` 가 워크스페이스가 아닌 저장소에 `.` 을 넣고 결정 로그까지 남기며,
`presets/stack/nextjs.md` 는 "`paths.web` 은 앱 패키지의 루트다. 소스 디렉터리가 아니다" 로
그것을 정본으로 못박는다. 즉 `.` 은 설정 실수가 아니라 **정상 값**이다.

그대로 교차 검사하면 `.` 이 `paths.tests` · `.curvez/` · `docs/retro/` 를 전부 삼켜,
구현 에이전트가 **쓰기 권한을 가진 어떤 워커와도 영원히 병렬이 안 된다.** 단일 저장소로 curvez 를
쓰는 프로젝트 전체가 팀 실행의 이점을 잃는다. 규약 두 조항이 각각은 옳은데 합치면 병렬을 없앤다.

빠져나갈 근거는 이미 정의 파일 안에 있다. `curvez-nextjs` 의 파일 소유권 항은 산문으로
"`.curvez/architecture.md`, `.curvez/design/`, `paths.tests` … 는 **읽기만 한다**" 를 선언한다.
코어 에이전트 13종 중 12종이 같은 형태의 배제 목록을 갖고 있다. **이 선언이 "여기는 안 쓴다" 는
계약이므로, 포함 관계에서는 배제 목록을 차감하고 판정한다.**

이것은 예외가 아니라 판정의 정밀화다. 차감 뒤에도 겹치면 여전히 순차이고, 배제 목록이 없는
에이전트는 차감할 근거가 없으므로 순차다 — 앞 소절의 "근거 없는 병렬은 도박이다" 가 그대로 적용된다.
절차의 정본은 `agents/curvez-orchestrator.md` 의 `### 병렬 판정` 이다.

**프로젝트가 직접 만든 에이전트는 배제 목록을 스스로 적어야 한다.** 안 적으면 검증은 통과하지만
그 워커는 포함 관계에서 항상 순차로 강등된다.

### 겹치지 않는 공유는 충돌이 아니다

`.curvez/handoff/` 는 모든 워커가 쓰지만 충돌하지 않는다. 파일명이
`<from>.<YYYYMMDD-HHmmss>.json` 이라 워커마다 고유하기 때문이다. **디렉터리 공유는 소유권 충돌이
아니다 — 판정 단위는 파일 경로다.**

## 4. `paths.domain` — 소유자를 두지 않는 예외

모노레포의 공유 도메인 패키지(`.curvez/profile.json` 의 `paths.domain`)는 **어느 에이전트도 자기
소유로 선언하지 않는 유일한 경로**다. `curvez-nextjs` 도 `curvez-react-native` 도 기본 쓰기 범위는
자기 앱 경로(`paths.web` / `paths.mobile`)뿐이다.

소유자를 정하지 않은 것은 회피가 아니라 판단이다. 한쪽에 소유권을 주면 다른 쪽은 공유 타입 하나를
고칠 때마다 blocked 로 돌아가야 하고, 양쪽에 주면 그것은 소유권이 아니다.

### 대신 규칙은 실행 순서로 건다

이번 라운드 작업이 `paths.domain` 을 건드리면 **구현 에이전트 2종을 동시에 띄우지 않는다.**
순차로 강등한다.

이 규칙이 필요한 이유는 도메인 변경의 실패가 **비대칭적으로 늦게 드러나기** 때문이다.
한쪽 스택 사정으로 공유 시그니처를 바꾸면 다른 스택은 그 자리에서 깨지지 않는다. 깨짐은 그쪽
에이전트가 **다음에 실행될 때** 비로소 나타난다. 동시 실행이면 그 "다음" 이 이번 라운드에 없으므로,
깨진 채로 QA·리뷰 라운드까지 흘러간다. 그 시점에는 실패가 여러 변경이 섞인 상태로 나타나므로
어느 시그니처 변경이 원인이었는지 특정할 수 없다.

순차로 돌리면 두 번째 에이전트가 첫 번째의 결과를 입력으로 받아 자기 스택에서 바로 확인한다.
같은 깨짐이 **같은 라운드 안에서**, 원인이 하나로 좁혀진 상태로 드러난다.

어느 쪽을 먼저 돌릴지와 양쪽이 동시에 시그니처 변경을 요청했을 때의 우선순위는
`curvez-orchestrator.md` 의 `#### 공유 도메인 패키지는 소유자가 없다` 표가 정본이다.

### 폴백이 소유권을 만든다 — 그래서 폴백을 없앴다

curvez 초기 설계에서 구현 에이전트는 `paths` 가 없을 때 각자 관례 경로로 폴백했다. 그 결과
모노레포에서 두 에이전트가 **같은 디렉터리를 자기 소유로 계산**하는 상황이 만들어졌다. 프로파일에
경로가 없다는 사실이 조용히 소유권 충돌로 번역된 것이다.

해결은 폴백을 없애는 것이었다. 지금은 `paths.web` 이나 `paths.mobile` 이 없으면 구현 에이전트가
경로를 지어내지 않고 `blocked` 로 돌아온다. 예외는 `paths.tests` 하나뿐인데, 이것은 소유자가
`curvez-qa` 한 명뿐이라 폴백해도 겹칠 상대가 없기 때문이다.

**규칙:** 폴백은 그 경로의 소유자가 한 명일 때만 허용된다. 폴백 값을 추가할 때는 "이 경로를 쓰고
싶어 하는 다른 에이전트가 있는가" 를 먼저 확인해야 한다. 계약의 상세는
[핸드오프 계약](handoff-contract.md), 프로파일 형식은 [설계 근거](design-rationale.md) 를 참조하라.

## 5. 승인 게이트 — 워커를 띄우기 전에

**워커를 하나라도 띄우기 전에 팀 구성을 사용자에게 보고하고 명시적 승인을 받는다.**
승인 이전 `Agent` 호출 횟수는 0 이어야 한다.

### 왜 하필 이 지점인가

승인 게이트의 위치는 **되돌리기 비용이 가장 싼 지점**에서 결정된다.

| 시점 | 틀린 것을 알았을 때의 비용 |
|---|---|
| 구성안 단계 | 텍스트 몇 줄을 고친다 |
| 워커 실행 중 | 워커는 격리된 컨텍스트에서 돌고 중간에 사람에게 되물을 수 없다. 끝날 때까지 못 멈춘다 |
| 라운드 종료 후 | 여러 명분의 토큰을 다 썼고, 파일은 이미 쓰였다. 어느 워커의 산출물을 어디까지 되돌려야 하는지 판정해야 한다 |

비용 곡선이 이 모양인 것은 curvez 의 다른 선택들에서 따라 나온 결과다. 워커가 실행 중에 사람에게
못 묻고(6절), 파일에 직접 쓰고, 그 파일이 다음 라운드의 입력이 되기 때문에, 잘못된 구성으로 한 번
띄우면 오염이 산출물을 타고 번진다. 승인은 그 번짐이 시작되기 전의 마지막 지점이다.

### 무엇을 승인받는가

구성안에는 다섯 항목이 다 있어야 한다 — **누가 / 왜 / 무엇을(소유 경로 포함) / 어떻게(병렬·순차와
근거) / 몇 라운드.** 하나라도 비면 승인 단계로 넘어가지 않는다.

이 다섯 항목은 사용자에게 정보를 주기 위한 목록이 아니라 **오케스트레이터의 판정이 실제로 끝났는지
확인하는 체크리스트**다. 소유 경로를 못 적었다면 병렬 판정을 안 한 것이고, 라운드 수를 못 적었다면
작업이 안 쪼개진 것이다. 승인 항목을 채우지 못하는 구성안은 승인 여부와 무관하게 실행 준비가 안 된
것이다.

### 예외가 최소여야 하는 이유

승인 없이 진행하는 예외는 **하나뿐**이다 — 같은 세션에서 이미 승인된 구성을 구성원 변경 없이
재실행하는 경우(리뷰 지적 → 수정 → 재리뷰의 2회차 이후). 정확한 조건은
`curvez-orchestrator.md` 의 `### 승인 절차` 마지막 문단이 정본이다.

이 예외가 필요한 이유는 리뷰 루프의 성질에 있다. 루프의 각 회차는 **같은 사람들이 같은 소유 경로에서
남은 지적만 닫는** 작업이다. 승인받을 새 정보가 없다. 그런데도 회차마다 승인 창을 띄우면 루프가
실질적으로 못 돈다 — 사용자는 같은 명단을 반복해서 승인하게 되고, 그 반복은 승인을 형식으로 만든다.
형식이 된 승인은 진짜로 확인해야 할 첫 승인까지 같이 무디게 만든다.

반대로 예외를 넓히면 게이트 자체가 사라진다. 그래서 예외의 경계가 **"구성원이 한 명이라도 바뀌면
다시 받는다"** 로 날카롭게 그어져 있다. 판단이 필요 없는 기계적 기준이라야 예외가 조용히 자라지 않는다.

## 6. 사용자 질문 중계 — 워커는 사람에게 못 묻는다

**서브에이전트는 격리된 컨텍스트에서 돌기 때문에 사용자에게 직접 질문할 수 없다.**

이것은 curvez 의 선택이 아니라 실행 환경의 성질이다. 그리고 curvez 설계에서 가장 넓게 영향을 미친
제약이다.

### 이 제약이 설계에 남긴 것

이 제약을 발견한 계기는 아키텍처 인터뷰였다. `curvez-architect` 는 레이어명과 경계 규칙을 확정하려면
사용자에게 몇 문항을 물어야 하는데, 워커로 띄우니 **그 인터뷰가 시작조차 되지 않았다.** 질문을 낼
통로가 없기 때문이다.

여기서 세 가지가 따라 나왔다.

**첫째, 질문은 데이터가 됐다.** 워커는 묻는 대신 핸드오프의 `blocked_on[]` 에 질문을 적고
`status: blocked` 로 돌아온다. `who` 필드가 수신자를 가리키고, `who: user` 면 오케스트레이터가
중계한다. 질문이 대화가 아니라 **파일에 기록되는 항목**이 되면서, 놓친 질문이 사후에 추적 가능해졌다.

**둘째, 오케스트레이터가 유일한 통로가 됐다.** 사용자와 대화하는 주체가 하나뿐이므로 질문·답변의
순서와 짝짓기를 한 곳에서 관리할 수 있다. 대신 오케스트레이터가 멈추면 팀 전체가 멈춘다.

**셋째, 답변은 원래 물은 에이전트에게 돌아가야 한다.** 사용자 답변을 받으면 **질문 원문과 짝지어**
그 에이전트를 같은 컨텍스트로 재실행한다. 답변만 다른 에이전트에게 넘기면 원래 질문을 낸 쪽이 왜
그것을 물었는지 아무도 모르고, 받은 쪽은 맥락 없는 지시로 해석한다.

### 모아서 한 번에 묻는다

`blocked_on[].who` 가 `user` 인 질문은 **전부 모아서 한 묶음으로** 사용자에게 올린다. 여러 워커에게서
올라온 것도 한 묶음이다.

질문마다 사용자를 멈춰 세우면 **팀 실행이 사용자 응답 대기로 직렬화된다.** 워커 여럿을 병렬로 띄워
놓고 첫 질문에서 전부 멈춰 세우면 병렬로 얻은 이득이 통째로 사라진다. 남는 것은 병렬 실행의 비용
(컨텍스트 복제, 핸드오프 왕복)뿐이다.

사용자 쪽 비용도 같은 방향이다. 개별로 오는 질문은 매번 맥락이 끊긴 채 도착하고, 앞 질문에 어떻게
답했는지 기억해 가며 답해야 한다. 한 묶음으로 오면 답들 사이의 일관성을 사용자가 직접 볼 수 있다.

그래서 중계는 **라운드 수합 직후, 다음 라운드 시작 전** 이라는 고정된 지점에서 일어난다. 질문이
올라오는 시점이 아니라 라운드 경계에 묶는 것이다.

### 아키텍처 인터뷰만 예외

`curvez-architect` 의 인터뷰는 예외적으로 **아키텍트를 띄우기 전에** 오케스트레이터가 직접 진행할 수
있다. 한 번에 다 던지고 한 번에 받는다. 문항 수 제한과 절차는
`curvez-orchestrator.md` 의 `#### 아키텍처 인터뷰는 예외 — 워커를 띄우기 전에 직접 진행한다` 가 정본이다.

예외인 이유는 답이 무엇을 결정하느냐에 있다. 인터뷰 답은 레이어명·경계·금지 import 목록 —
**아키텍처 산출물 전체**를 결정한다. 일반 절차대로 하면 이렇게 된다.

```
아키텍트를 띄운다 → 컨텍스트를 채운다 → 첫 질문에서 blocked → 중계 →
답을 받는다 → 아키텍트를 다시 띄운다 → 컨텍스트를 처음부터 다시 채운다
```

왕복 한 번에 아키텍트 컨텍스트가 두 번 채워지고, 그동안 같은 라운드의 `curvez-designer` 는 확정되지
않은 구조 위에서 대기한다. 답이 산출물 거의 전부를 좌우하는 질문에서는 이 왕복이 순수한 낭비다.

**이 예외를 다른 워커로 확대하지 않는다.** 오케스트레이터가 다른 워커의 질문을 미리 대신 묻지 않는
이유는 단순하다 — **무엇을 물어야 하는지는 그 워커가 자기 절차를 돌려 봐야 안다.** 미리 물으면
오케스트레이터가 상상한 질문에 대한 답을 받게 되고, 그 답은 실제로 필요했던 답이 아니다.
아키텍처 인터뷰가 예외인 것은 질문 후보가 이미 아키텍트 정의에 문서화돼 있어 상상할 필요가 없기 때문이다.

## 7. 읽기 전용 에이전트의 대필

`curvez-reviewer` 와 `curvez-structure-reviewer` 는 **파일을 쓸 수 없다.** `disallowedTools` 에 쓰기
도구가 전부 들어 있고, Bash 로 우회하는 것도 정의에서 명시적으로 금지된다.

이 두 에이전트에게 쓰기를 준 순간 리뷰의 전제가 무너진다. 리뷰 대상과 리뷰 주체가 같은 파일을 쓸 수
있으면 "리뷰가 지적한 것"과 "리뷰어가 고친 것"이 섞이고, 그 뒤로는 어느 변경이 누구 판단이었는지
분리할 수 없다. 소유 경로가 없다는 것이 이 둘을 **어떤 워커와도 병렬로 돌릴 수 있게** 만드는 근거이기도
하다(2절 표 참조). 병렬의 자유는 쓰기를 포기한 대가로 얻은 것이다.

### 대필이라는 해법

쓰기를 막으니 **핸드오프 계약 파일도 만들 수 없다는 문제**가 드러났다. 리뷰어만 핸드오프를 남기지
않으면, 회고 에이전트가 실행 이력을 시간순으로 재구성할 때 리뷰 단계만 통째로 비어 무엇이 언제
지적됐는지 복원할 수 없다.

해법은 역할을 나누는 것이었다. 리뷰어는 **최종 응답 텍스트 자체를 핸드오프 JSON 으로 반환**하고,
오케스트레이터가 그것을 파일로 기록한다. 판단은 리뷰어가 하고 기록은 쓰기 권한을 가진 쪽이 한다.
대필 절차 6단계(파싱 확인 → `from` 대조 → `findings` 보존 → 타임스탬프 → 기록 → 검증)는
`curvez-orchestrator.md` 의 `### 읽기 전용 에이전트의 핸드오프를 대신 기록한다` 가 정본이다.

**대필의 절대 금지 사항은 하나다 — 응답이 JSON 이 아닐 때 오케스트레이터가 JSON 을 지어내 채우지
않는 것.** 지어낸 리뷰 결과는 실제 리뷰와 형태가 같아서, 검증된 지적처럼 다음 라운드로 전파되고
사후에 분리할 수 없다. 파싱이 안 되면 1회 재요청하고, 그래도 아니면 원문을 남기고 `partial` 로 보고한다.

### 두 리뷰어의 `findings` 를 합칠 때 — `id` 충돌

두 리뷰어는 각자 `findings[]` 에 지적을 담아 돌려준다. 두 목록을 합칠 때 `id` 가 충돌할 수 있다.
양쪽 다 `DUP-01` 같은 관례적 id 를 쓸 수 있기 때문이다.

규칙은 **`<from>/<id>` 접두사**다. 원본 `id` 는 항목 안에 그대로 둔다.

```
curvez-reviewer/DUP-01            ← 원본 id: DUP-01 (중복 코드 지적)
curvez-structure-reviewer/DUP-01  ← 원본 id: DUP-01 (다른 지적)
```

접두사 없이 합치면 서로 다른 두 지적이 하나로 뭉개진다. 그러면 재리뷰 때 "이 id 가 닫혔는가" 를
대조할 수 없고, 하나만 고쳐도 둘 다 닫힌 것처럼 보인다.

### 이 규칙은 검증기가 강제하지 않는다

**중요한 한계다.** `validate-handoff.mjs` 는 `findings[]` 항목의 필수 필드
(`id` `kind` `where` `what` `why`)와 등급값은 검사하지만, **`id` 의 유일성은 검사하지 않는다.**
게다가 검증은 파일 단위로 돌기 때문에 서로 다른 두 파일에 있는 같은 `id` 는 원리적으로 보이지도 않는다.

실측으로 확인했다. 두 리뷰어의 핸드오프에 같은 `id: "DUP-01"` 을 넣고 검증기를 돌렸다.

```
$ node scripts/validate-handoff.mjs <디렉터리>
OK 핸드오프 검증 — 검사 2건, 통과 2건, 실패 0건, 오류 0개, 경고 0개
exit=0
```

**충돌한 채로 통과한다.** 즉 접두사 규칙은 **절차로만 지켜진다** — 오케스트레이터가 합치는 시점에
직접 붙여야 하고, 안 붙여도 아무 신호가 나지 않는다. 그 결과는 위에서 본 대로 "고치지 않은 지적이
닫힌 것처럼 보이는" 형태로 나타나므로, 발견되기 어려운 종류의 실패다.

`findings` 는 정식 필드로 승격됐지만(`handoff.schema.json`, 미지의 최상위 키는 이제 오류로 거부된다)
유일성 검사는 함께 들어가지 않았다. 승격이 가져온 것은 항목 형식 검사까지이고, 파일을 가로지르는
성질(`id` 유일성)은 검증이 파일 단위로 도는 한 원리적으로 못 본다. 합치는 시점의 접두사 규칙이
그 빈자리를 절차로 메운다 — 유일성 검사를 검증기에 넣는 것이 자연스러운 다음 단계다.

합친 목록은 **파일로 새로 만들지 않는다.** 리뷰어별 핸드오프 파일이 원본이고, 합친 결과는 다음
라운드 작업 목록과 사용자 보고에만 쓴다. 원본과 사본이 둘 다 있으면 다음 라운드에서 어느 쪽이
최신인지 판정할 근거가 없다.

## 8. 루프 상한

리뷰 지적 → 수정 → 재리뷰 루프에는 **상한이 있다.** 회수와 회차별 행동은
`curvez-orchestrator.md` 의 `### 재실행 루프 상한` 이 정본이다.

### 왜 상한이 필요한가

리뷰 루프가 수렴하지 않는 경우는 코드가 어려워서가 아니다. **리뷰어와 구현자가 같은 지점에 서로 다른
기준을 갖고 있을 때** 루프는 영원히 돈다. 구현자는 자기 기준으로 고치고, 리뷰어는 자기 기준으로 다시
지적하고, 양쪽 다 자기 일을 정확히 하고 있다. 이 상태는 회차를 늘려도 좋아지지 않는다 — 같은 왕복이
반복될 뿐이고 토큰만 소비된다.

그래서 상한의 의미는 "여기까지만 해 보자" 가 아니라 **문제의 종류를 판정하는 장치**다.

> 상한 안에 안 닫히는 것은 코드 문제가 아니라 **기준 문제**다. 그리고 기준은 사용자만 정할 수 있다.

에이전트끼리는 기준 불일치를 해소할 수 없다. 양쪽 다 자기 판단의 근거를 갖고 있고, 어느 쪽이 옳은지는
프로젝트의 의도에 달려 있는데 그 의도는 에이전트 안에 없다. 상한에 닿으면 남은 지적 목록·담당·시도
이력을 사용자에게 보고하고 판단을 받는 것이 유일하게 진행 가능한 경로다.

상한 도달은 실패가 아니라 **정상적인 종료 형태 중 하나**다. 이것을 실패로 취급하면 오케스트레이터가
상한을 넘겨 계속 돌리거나 — 더 나쁘게 — 남은 지적을 조용히 무시하고 라운드를 닫으려 한다.

### 회차마다 범위를 넓히지 않는다

재리뷰에서 새 지적이 추가되어도 루프의 대상 범위는 넓히지 않는다. 남은 지적만 닫는다. 범위를 넓히면
상한이 무의미해진다 — 회차마다 새 항목이 들어오는 한 목록은 절대 비지 않기 때문이다. 새 지적은
다음 라운드의 대상이다.

## 9. 실패 모드

팀 실행에서 실제로 발생하는 실패는 대부분 **조용하다.** 오류를 던지지 않고, 라운드는 정상 종료된 것처럼
보인다. 아래 세 가지가 대표적이다.

### 9-1. 검증 없는 `done` 이 전파된다

핸드오프의 `status: done` 은 다음 워커가 **자기 작업의 전제로 삼는 값**이다. QA 는 구현이 done 이라는
전제로 테스트를 짜고, 리뷰어는 검증이 끝났다는 전제로 리뷰 범위를 좁힌다.

그래서 계약은 `done` 에 `verification` 을 요구한다 — 실제로 돌린 명령과 그 출력이 1건 이상 있어야 한다.
[핸드오프 계약](handoff-contract.md) 참조.

**전파 경로는 이렇다.**

```
워커가 검증을 안 돌리고 done 으로 보고
  → 오케스트레이터가 verification 을 확인하지 않고 수합
  → 다음 라운드 워커가 "끝난 것" 위에서 시작
  → 그 라운드 산출물 전부가 잘못된 전제 위에 올라간다
  → QA·리뷰에서 증상만 나타나고, 원인은 두 라운드 전에 있다
```

**막는 지점은 수합이다.** 오케스트레이터는 `done` 인데 `verification` 이 비었으면 그 값을 믿지 않고
`partial` 로 취급한다. `done` 을 액면가로 받지 않는 것이 이 실패의 유일한 차단막이다 — `done` 을 쓴
워커 자신은 이미 자기 판단으로 그렇게 쓴 것이므로 그쪽에서는 잡히지 않는다.

같은 원칙이 오케스트레이터 자신에게도 적용된다. 자체 검증이 실패하면 실패한 명령과 **실제 출력을
그대로** 적고 `partial` 로 낮춘다. 요약하거나 숨기지 않는다. 검증 철학은
[품질 모델](quality-model.md) 이 정본이다.

### 9-2. 소유권이 문서에 없어 충돌이 뒤늦게 발견된다

3절에서 본 대로 소유권 교차 검사는 절차이고, 검증기는 `## 협업과 팀 내 위치` 헤딩의 존재만 본다.

**전파 경로.**

```
새 에이전트를 만들면서 소유 경로를 안 적었다
  → validate-agents.mjs 는 통과한다 (섹션은 있으므로)
  → 오케스트레이터가 병렬 판정을 하려고 읽었는데 근거가 없다
  → 순차로 강등되면 다행이다 — 라운드가 하나 늘 뿐이다
  → 강등을 놓치고 병렬로 띄우면 3절의 "조용한 덮어쓰기" 가 일어난다
```

두 번째 갈래가 문제다. 덮어쓰기는 오류를 내지 않고 diff 에도 흔적이 없으며, 지워진 쪽의 핸드오프에는
`done` 과 `artifacts` 가 남아 있다. **기록상으로는 두 워커 모두 성공했다.**

**막는 지점은 두 곳이다.** 에이전트를 만들 때 소유 경로를 반드시 적는 것(작성 원리는
[에이전트 작성](agent-authoring.md) 참조), 그리고 수합 때 `artifacts[].path` 가 그 워커의 소유 경로
밖인지 대조하는 것. 후자에서 위반을 발견해도 오케스트레이터가 되돌리지 않는다 — 위반 경로와 담당
워커를 보고해 사용자 판단을 받는다. 무엇이 정답인지는 소유권 정의를 고칠 것인지 산출물을 되돌릴
것인지의 문제이고, 그것은 규약 변경 영역이기 때문이다.

### 9-3. `blocked` 를 두려워해 추측으로 메운다

가장 흔하고 가장 비싼 실패다.

워커가 필요한 정보를 못 찾았을 때 `status: blocked` 로 돌아오는 것은 **정상 종료**다. 그런데 워커는
"끝내는 것" 을 성공으로 학습하기 쉬워서, 빈 칸을 그럴듯한 값으로 메우고 `done` 으로 보고하려는 압력을
받는다. 메워진 값은 형태가 정상이라 검증기에도 걸리지 않는다.

**전파 경로 — 그리고 왜 팀 실행에서 특히 비싼가.**

단독 실행이라면 추측 하나가 산출물 하나를 오염시킨다. 팀 실행에서는 다르다. 그 추측이 핸드오프의
`decisions` 나 `artifacts` 에 실려 다음 라운드 워커 **여러 명에게 동시에 배포된다.** 각자 그 전제 위에
자기 산출물을 만들면, 되돌릴 때 되돌릴 대상이 라운드 전체가 된다.

오케스트레이터 자신의 추측은 최악이다. 오케스트레이터는 워커 프롬프트를 쓰는 주체이므로, 그가 지어낸
전제는 **그 라운드의 모든 워커에게 한 번에** 들어간다. 그래서 오케스트레이터도 정보가 없으면
`blocked_on` 에 질문으로 남기고 워커를 띄우지 않는다.

**막는 지점은 프롬프트다.** 워커를 띄울 때 "막히면 추측하지 말고 `status: blocked` 로 돌아오라" 를
명시적으로 넣는다. 워커는 팀 명단도 다른 워커의 소유 경로도 모른다 — **프롬프트에 없는 것은 워커가
추측한다.** 이 문장이 팀 실행 프롬프트 규약의 근본 전제다.

관련해서, `blocked` 를 받은 오케스트레이터가 **대신 답하는 것**도 같은 실패다. `blocked_on[].who` 가
에이전트 이름이면 그 에이전트에게 라우팅하고, `user` 면 사용자에게 올린다. 오케스트레이터가 중간에서
답을 만들어 넣으면 그 답에는 아무 근거도 없다.

## 브랜드 라운드는 요청 시에만 돈다

2절의 흐름도에 `curvez-marketer` 가 없는 것도 빠뜨린 것이 아니라 결정이다. 브랜드 코어·네이밍은
모든 제품 작업에 필요한 단계가 아니므로, 사용자가 브랜드·네이밍·마케팅을 요청했을 때만 라운드가 선다.
서는 위치는 1라운드(`curvez-requirements` ∥ `curvez-researcher` 와 병렬)이거나, 브랜드 작업 단독이면
그 자체가 전체 파이프라인이다.

**네이밍 회의는 라운드 3개로 구현된다.** 워커끼리 실시간 대화할 수 없다는 제약(6절) 위에서
"회의" 는 이렇게 돈다.

```
R1  curvez-marketer            → 브랜드 코어 확정, 네이밍 브리프 작성,
                                 blocked_on 에 who: <참가자> 로 후보 요청
R2  참가자들 (designer, nextjs, …) → 브리프를 읽고 후보 3개 이상을
                                 핸드오프 decisions[] 에 `naming-candidate: <이름>` 으로 반환
R3  curvez-marketer (재실행)    → 후보 평가·충돌 검증 → 최종 A/B안 →
                                 blocked_on 에 who: user 로 최종 선택 요청
```

후보 요청이 `blocked_on` 을 타는 것은 새 통신 경로가 아니라 **기존 질문 중계 절차의 재사용**이다.
`who` 가 에이전트 이름이면 오케스트레이터가 다음 라운드의 첫 작업으로 라우팅한다 — 네이밍 후보 요청도
같은 길을 탄다. 후보가 `decisions[]` 관례(`naming-candidate:` 접두사)로 돌아오는 이유는 핸드오프
스키마가 미지의 최상위 키를 허용하지 않기 때문이다. 실사용에서 이 관례가 자리 잡으면 `findings` 가
그랬듯 정식 필드(`candidates[]`)로 승격하는 것이 자연스러운 다음 단계다.

최종 1안은 마케터가 정하지 않는다. A/B 두 개로 추려 근거·충돌 검증 결과와 함께 올리고, 선택은
사용자가 한다. 팀 실행 전체를 관통하는 원칙 — 기준은 사용자만 정할 수 있다(8절) — 이 여기에도 적용된다.

## git 라운드가 파이프라인에 없는 이유

위 흐름(요구사항 → 설계 → 구현 → QA → 리뷰 → 회고)에 `curvez-git` 이 없다.
빠뜨린 것이 아니라 **파이프라인에 넣지 않기로 한 결정**이다.

커밋·PR·머지는 사용자가 명시적으로 요청했을 때만 돈다. 라운드가 끝났다는 것과
"이 상태를 이력에 새겨도 된다" 는 것은 다른 판단이고, 후자는 사람의 것이다.

**되돌리기 비용이 다르기 때문이다.** 다른 산출물은 파일이라 덮어쓰면 그만이지만,
커밋은 지워도 흔적이 남고 push 된 뒤에는 남의 작업에 영향을 준다. 이 전략 전체를 관통하는
비대칭이 여기서도 판정 기준이 된다 — [git 전략](git-strategy.md).

`curvez-git` 은 `owns: none` 이라 소유권 충돌 검사에 걸리지 않지만 **병렬 안전하지 않다.**
브랜치 전환이 작업 트리 전체를 바꾸므로, 다른 워커가 도는 중에 띄우면 그들이 읽는 파일이
통째로 달라진다. 소유 경로가 없다는 것이 병렬 안전하다는 뜻이 아닌 유일한 사례다.
