# monorepo

웹 앱과 모바일 앱이 한 저장소의 워크스페이스로 함께 있고, 둘이 같은 도메인 패키지를 공유하는 스택이다.
`.curvez/profile.json` 의 필수 키가 셋(`paths.web`, `paths.mobile`, `paths.domain`)으로 세 스택 중 가장 많고,
그중 `paths.domain` 은 **어느 구현 에이전트도 소유하지 않는 유일한 경로**다. 이 값이 틀리면 문서가 아니라
실행 순서가 틀린다 — 순차로 강등해야 할 라운드를 병렬로 돌게 된다.

---

## 감지 신호

### 1차 — 이 저장소가 워크스페이스인가

루트 `package.json` 과 루트 파일만 본다. 아래 중 **하나라도** 있으면 워크스페이스다.

| 신호 | 어디서 보는가 | 비고 |
|---|---|---|
| `pnpm-workspace.yaml` | 저장소 루트 파일 | curvez 의 기본 전제(`packageManager: pnpm`)와 가장 잘 맞는 신호 |
| `workspaces` 필드 | 루트 `package.json` | 배열(`["apps/*"]`) 또는 객체(`{ "packages": [...] }`) 둘 다 쓰인다 |
| `turbo.json` | 저장소 루트 파일 | 태스크 러너다. 단독으로는 워크스페이스를 보장하지 않는다 |
| `nx.json` | 저장소 루트 파일 | 위와 같다 |
| `lerna.json` / `rush.json` | 저장소 루트 파일 | 오래된 저장소에서 나온다 |
| `"private": true` + 루트에 앱 의존성 없음 | 루트 `package.json` | 보조 신호일 뿐이다. 단독 판정 근거로 쓰지 마라 |

`bootstrap` 절차 2 의 감지 명령이 내는 `workspace: true` 가 정확히 이 1차 신호다.

### 2차 — 워크스페이스라는 것만으로는 `monorepo` 가 아니다

**루트 `package.json` 만으로는 판정이 끝나지 않는다.** 앱이 하위 패키지에 있으므로 루트 의존성에는
`next` 도 `expo` 도 나타나지 않는다. 실측한 픽스처의 루트 감지 출력이 그대로 이 모양이다.

```json
{ "workspace": true, "next": null, "expo": null, "reactNative": null }
```

여기서 `next`·`expo` 가 `null` 이라는 사실은 **정보가 아니다.** 워크스페이스를 순회해야 web·mobile 이 보인다.
순회 절차와 그 출력으로 스택을 판정하는 표는
[`skills/bootstrap/references/stack-detection.md`](../../skills/bootstrap/references/stack-detection.md) 가 정본이다.
**여기서 다시 적지 않는다.** 판정 결과만 옮기면 아래와 같다.

| 순회 결과 | 판정 |
|---|---|
| `web` 1개 **그리고** `mobile` 1개 | `monorepo` |
| `web` 1개, `mobile` 0개 | 워크스페이스여도 `nextjs` 다 |
| `web` 0개, `mobile` 1개 | 워크스페이스여도 `react-native` 다 |
| 어느 한쪽이 2개 이상 | 판정 불가. 어느 것이 주 앱인지 인터뷰로 묻는다 |

**요지: `monorepo` 는 "워크스페이스다" 가 아니라 "웹 앱과 모바일 앱이 둘 다 있다" 로 판정한다.**
`stack` 값은 저장소 구조가 아니라 **팀 편성**을 정하는 값이기 때문이다 — 모바일 앱이 없는데 `monorepo` 로
찍으면 `curvez-react-native` 가 존재하지 않는 경로를 담당으로 받는다.

### 오탐 케이스

| 상황 | 왜 오탐인가 | 행동 |
|---|---|---|
| `turbo.json` 만 있고 워크스페이스 정의가 없다 | Turborepo 는 단일 패키지에서도 태스크 러너로 쓴다 | 워크스페이스 신호를 다시 본다. 없으면 단일 패키지 스택으로 판정 |
| `pnpm-workspace.yaml` 은 있는데 `packages:` 목록이 비었거나 앱이 하나뿐 | 앞으로 늘릴 예정으로 미리 깔아 둔 경우 | 순회 결과가 정본이다. 앱 구성으로 판정한다 |
| 순회에 잡힌 web 후보가 `apps/web` 과 `apps/admin` 둘 | 어느 쪽이 주 앱인지 구조로 안 갈린다 | 첫 번째를 고르지 마라. 순회 순서는 파일시스템 순서다. 인터뷰로 묻는다 |
| `node_modules` 안의 패키지가 후보로 잡힌다 | `next` 를 의존하는 패키지가 수백 개다 | 순회 스크립트가 이미 `node_modules` 와 점 디렉터리를 건너뛴다. 직접 순회를 짜지 말고 그 스크립트를 쓴다 |
| 도구 저장소(플러그인·CLI 모노레포)라 앱이 아예 없다 | curvez 대상이 아닐 수 있다 | `web` 0개 `mobile` 0개는 판정 불가다. 지어내지 말고 인터뷰 1번 문항으로 올린다 |
| Expo Router 웹 빌드를 쓰는 RN 앱 하나뿐 | 웹 산출물이 나온다고 web 앱이 생긴 것이 아니다 | `next` 의존이 없으면 web 후보가 아니다. `react-native` 로 간다 |

## paths 후보

`monorepo` 의 필수 키는 `paths.web`, `paths.mobile`, `paths.domain` 셋이다.
**셋 중 하나라도 못 채우면 `status: blocked` 다. 관례 경로로 메우지 마라.**

값은 전부 **저장소 루트 기준 상대 경로**이고 끝에 `/` 를 붙이지 않는다.
`bootstrap` 절차 7 의 검증이 `fs.existsSync` 로 디스크 존재까지 확인하므로(`notOnDisk`),
패키지 이름(`@acme/domain`)이 아니라 **디렉터리 경로**(`packages/domain`)를 넣어야 한다.

### `paths.web` / `paths.mobile`

| 키 | 판정 근거 | 관례적 위치 |
|---|---|---|
| `paths.web` | 워크스페이스 패키지 중 `next` 를 **의존하는** 패키지 | `apps/web`, `apps/site`, `packages/web` |
| `paths.mobile` | 워크스페이스 패키지 중 `expo` 또는 `react-native` 를 **의존하는** 패키지 | `apps/mobile`, `apps/native`, `apps/app` |

디렉터리 이름으로 고르지 마라. `apps/web` 이라는 이름이 Next.js 앱을 보장하지 않고,
`apps/native` 라는 이름 없이도 Expo 앱은 존재한다. **의존성이 근거이고 이름은 참고다.**

값은 **패키지 루트**(`package.json` 이 있는 디렉터리)다. `apps/web/src` 가 아니라 `apps/web` 이다.
`paths.*` 는 구현 에이전트의 소유 경로 판정에 쓰이는데, `src` 만 소유로 잡으면 같은 앱의
`app/`·`next.config.ts`·`tsconfig.json` 이 누구 것도 아닌 상태가 된다.

### `paths.domain` — 이름이 아니라 의존 관계로 판정한다

**웹 앱과 모바일 앱이 둘 다 의존하는 워크스페이스 패키지가 후보다.**
`domain`·`core`·`shared` 라는 이름이 들어갔는지로 고르지 마라.

**이유:** 이름 규칙은 저장소마다 다르다. 같은 것을 `packages/domain`, `packages/core`,
`packages/shared`, `@acme/kernel` 로 부른다. 반면 "웹도 의존하고 모바일도 의존한다" 는
`package.json` 에 적힌 **구조적 사실**이고 저장소마다 흔들리지 않는다.
이 판정 방식은 `bootstrap` 담당이 순회 스크립트로 실측해 확정한 것이다 —
판정 코드와 그 근거는
[`skills/bootstrap/references/stack-detection.md`](../../skills/bootstrap/references/stack-detection.md) 의
`## paths.domain 은 "둘 다 의존하는 패키지" 다` 절에 있다.

이름 기반 판정이 실제로 어떻게 어긋나는지는 픽스처로 확인된다.
웹만 의존하는 `packages/ui` 는 이름이 공유물처럼 보여도 후보에서 빠지고,
`packages/cfg` 처럼 도메인과 무관해 보이는 이름이라도 양쪽이 의존하면 후보로 잡힌다.

#### 후보가 정확히 1개가 아닐 때

| 후보 수 | 행동 |
|---|---|
| **1개** | 그것을 `paths.domain` 으로 확정한다. 인터뷰하지 않는다 |
| **0개** | 인터뷰 2번 문항으로 묻는다. 답이 없으면 `blocked` |
| **2개 이상** | 인터뷰로 **하나**를 고르게 한다. 배열로 넣지 마라 — `paths.domain` 은 단일 문자열이다 |

**후보 0개는 흔하고, 대개 "공유 도메인이 아직 없다" 는 뜻이다.**
웹과 앱이 각자 도메인 로직을 갖고 있는 상태거나, 공유 패키지가 있지만 한쪽만 의존하는 상태다.
이때 선택지는 둘이고 **둘 다 사용자가 정할 일이다.**

1. 공유 패키지를 만들기로 한다 → 경로를 인터뷰로 받고, 그 디렉터리가 생긴 뒤에 프로파일을 확정한다
   (검증의 `notOnDisk` 가 없는 경로를 잡아낸다)
2. 공유할 것이 실제로 없다 → `stack` 이 `monorepo` 가 아닐 수 있다. 앱 두 개가 한 저장소에 있을 뿐인
   구성이면 주 앱 기준으로 `nextjs` 나 `react-native` 를 쓰는 편이 정확하다

**후보 2개 이상도 자주 나온다.** 순회는 "양쪽이 의존한다" 만 보므로 도메인 패키지와 함께
공용 설정 패키지(`packages/tsconfig`, `packages/eslint-config`), 공용 UI 킷, 공용 유틸이 같이 잡힌다.
실측 픽스처에서 설정 전용 패키지 하나를 양쪽 의존성에 넣자 후보가 `["packages/cfg", "packages/domain"]`
둘로 늘었다. **자동으로 좁히지 마라.** 인터뷰 문항으로 후보 목록을 그대로 제시하고 하나를 고르게 한다.

질문을 던질 때 후보를 나열하는 순서 정도로만 쓸 수 있는 힌트는 아래다. **판정 근거가 아니다.**

- 런타임 소스가 없고 설정 파일만 있는 패키지(`tsconfig.json`, `eslint.config.js` 뿐)는 도메인이 아닐 확률이 높다
- `react` 를 의존하는 패키지는 UI 킷이지 도메인이 아닐 확률이 높다
- 두 후보가 모두 진짜 도메인 성격이면 그것은 후보 문제가 아니라 **도메인이 둘로 갈려 있다**는 신호다.
  컨텍스트 분할 검토 대상이다

### `paths.tests` (선택)

모노레포에서는 테스트가 패키지마다 흩어져 있는 것이 정상이라 **이 키가 생략되는 경우가 다수**다.

- 루트에 `tests/`·`e2e/` 가 **하나** 있고 전 패키지 통합 테스트가 거기 모여 있으면 그 경로를 쓴다
- 패키지마다 `src/**/*.test.ts` 로 흩어져 있으면 **키째로 생략한다.** 여러 경로를 콤마로 잇거나
  `packages/*` 같은 글롭을 넣지 마라 — `paths` 값은 단일 경로 문자열이고 검증이 `existsSync` 로 확인한다
- `paths.tests` **만** 폴백이 허용된다. 소유자가 `curvez-qa` 한 명이라 폴백해도 겹칠 상대가 없기 때문이다.
  필수 키 셋에는 어떤 폴백도 쓰지 마라

### `expo.sdkVersion` (모노레포에서는 선택)

계약상 `monorepo` 의 선택 키지만, 모바일 앱이 있는 이상 사실상 필요한 값이다.
모바일 패키지 `package.json` 의 `expo` **범위 문자열**에서 첫 숫자 묶음만 뽑는다(`"~57.0.9"` → `"57"`).
루트가 아니라 **모바일 패키지**에서 읽어야 한다 — 루트에는 없다.
추출 방법은 `stack-detection.md` 의 `## expo.sdkVersion` 절에 있다.

## commands 후보

찾는 순서와 값 형식(`pnpm <스크립트명>`)은 `bootstrap` SKILL.md 절차 3 의 표가 정본이다.
`typecheck` → `type-check` → `tsc`, `lint`, `test`, `build` 순으로 **실제 있는 이름 하나**를 고른다.
**`package.json` 에 없는 스크립트는 키째로 생략한다. 지어내지 마라.**

모노레포에서만 갈리는 것은 "**어느 `package.json` 의 `scripts` 를 볼 것인가**" 다.

### 루트 명령을 기본으로 쓴다

모노레포의 루트 스크립트는 대개 워크스페이스 전체를 도는 래퍼다.

| 흔한 루트 스크립트 | 실제 내용 |
|---|---|
| `typecheck` | `pnpm -r typecheck` 또는 `turbo run typecheck` |
| `lint` | `turbo run lint` / `nx run-many -t lint` |
| `test` | `pnpm -r test` |
| `build` | `turbo run build` |

**기본은 루트 명령이다.** 근거는 커버리지다. `commands` 는 `curvez-qa` 가 그대로 실행하는 값인데,
모노레포에서 한 라운드의 변경은 웹·모바일·도메인 **여러 패키지에 걸친다.** 패키지별 명령을 쓰면
그 라운드에 안 걸린 패키지의 회귀가 검사되지 않고, `paths.domain` 변경이 반대편 앱을 깨뜨린 경우가
정확히 그 사각지대에 들어간다 — 공유 도메인 순차 실행 규칙이 잡으려는 실패를 QA 가 놓치게 된다.

### 루트 명령의 대가 — 어느 패키지가 깨졌는지 흐려진다

`turbo run typecheck` 나 `pnpm -r typecheck` 의 출력은 여러 패키지 로그가 섞여 나온다.
`tsc` 가 뱉는 경로는 **각 패키지 기준 상대 경로**라, 세 패키지에 같은 `src/index.ts` 가 있으면
어느 것이 깨졌는지 출력만으로 안 갈린다. Turborepo 는 접두사를 붙이지만 로그를 캐시해 재출력하기도 해서
**방금 실행한 결과가 아닌 줄이 섞여 보인다.**

이것이 문제가 되는 이유는 실패 자체가 아니라 **귀속**이다. 구현 에이전트는 자기 소유 경로만 고칠 수 있는데,
어느 패키지의 실패인지 못 가리면 자기 것이 아닌 실패를 자기 코드에서 찾기 시작한다.

**그래서 `commands` 는 루트로 두고, 좁히기는 실행 시점에 한다.** 프로파일에 패키지별 명령을 박아 넣으면
커버리지가 영구적으로 줄지만, 좁히기는 실패가 났을 때만 한 번 하면 되는 일이다.

| 상황 | 행동 |
|---|---|
| 루트 명령이 실패했다 | 출력에서 패키지가 안 갈리면 `pnpm --filter <패키지명> typecheck` 로 좁혀 재현한다. **프로파일은 고치지 않는다** |
| 캐시된 로그가 섞여 판정이 안 선다 | `turbo run typecheck --force` 로 캐시를 우회해 한 번 더 돌린다 |
| 루트에 스크립트가 아예 없다 | 그 키를 생략한다. 패키지별 명령을 임의로 승격하지 마라 — 어느 패키지를 고를지의 근거가 없다 |
| `typecheck`·`lint`·`test` 가 셋 다 비었다 | 인터뷰 4번 문항으로 올린다. 품질 게이트가 통째로 비면 `done` 을 판정할 근거가 없다 |

`--filter` 로 좁힌 명령은 프로파일이 아니라 **핸드오프 `verification` 에** 실제 출력과 함께 남긴다.

### 모노레포에서만 걸리는 함정

- **루트 `test` 가 없는 저장소가 흔하다.** 앱마다 러너가 다르기 때문이다(웹은 Vitest, 앱은 Jest).
  없으면 생략한다. 루트에 없는 명령을 적어 두면 `curvez-qa` 가 매 라운드 실패로 읽고,
  그 실패는 코드가 깨진 실패와 출력만으로 구분되지 않는다
- **`build` 는 루트에 있어도 시간이 길다.** 캐시 없는 첫 실행이 수 분이다. 값은 넣되,
  매 라운드 도는 게이트가 아니라는 판단은 `curvez-qa` 쪽에서 한다
- **`packageManager` 는 감지값과 무관하게 `pnpm` 으로 고정**한다. 루트 `package.json` 의
  `packageManager` 가 npm/yarn 이어도 프로파일에는 `pnpm` 을 쓰고, 그 불일치를 완료 보고에 남긴다.
  픽스처의 루트가 `npm@10.0.0` 이었지만 이 규칙대로 `pnpm` 을 쓴다

## 스택 고유 주의사항

### 1. `paths.domain` 은 소유자를 두지 않는다 — 순차로 강등한다

`paths.domain` 은 `curvez-nextjs` 도 `curvez-react-native` 도 자기 소유로 선언하지 않는 **유일한 경로**다.
소유자를 안 정한 것은 회피가 아니라 판단이다. 한쪽에 주면 다른 쪽은 공유 타입 하나 고칠 때마다
`blocked` 로 돌아가야 하고, 양쪽에 주면 그것은 소유권이 아니다.

**이번 라운드 작업이 `paths.domain` 을 건드리면 두 구현 에이전트를 동시에 띄우지 않는다. 순차로 강등한다.**

**이유:** 한쪽 스택 사정으로 공유 시그니처를 바꾸면 다른 스택은 그 자리에서 깨지지 않는다.
깨짐은 그쪽 에이전트가 **다음에 실행될 때** 비로소 나타난다. 동시 실행이면 그 "다음" 이 이번 라운드에
없으므로 깨진 채로 QA·리뷰까지 흘러가고, 그 시점에는 여러 변경이 섞여 있어 어느 시그니처 변경이
원인이었는지 특정할 수 없다. 순차로 돌리면 두 번째 에이전트가 첫 번째의 결과를 입력으로 받아
같은 라운드 안에서, 원인이 하나로 좁혀진 상태로 같은 깨짐을 만난다.

실행 순서 판정(어느 쪽을 먼저 돌리는가, 양쪽이 동시에 시그니처 변경을 요청했을 때의 우선순위)과
그 설계 근거는 [`docs/team-execution.md`](../../docs/team-execution.md) 의
`## 4. paths.domain — 소유자를 두지 않는 예외` 를 따른다.

`paths.domain` 값이 틀리면 이 규칙 자체가 발동하지 않는다. 오케스트레이터는 "이번 작업이
`paths.domain` 을 건드리는가" 로 병렬·순차를 가르는데, 경로가 엉뚱하면 그 판정이 항상 "안 건드림" 으로
나와 조용히 병렬로 돈다. **`paths.domain` 정확도는 문서 품질이 아니라 실행 안전 문제다.**

### 2. 공유 도메인은 양쪽 프레임워크 어느 쪽도 의존하면 안 된다 — "대부분 공유" 는 없다

`paths.domain` 패키지가 `next`·`next/headers` 를 한 줄이라도 import 하면 RN 앱이 그 패키지를 못 쓴다.
반대로 `react-native`·`expo` 를 import 하면 웹이 못 쓴다.

**공유는 "대부분 공유" 가 성립하지 않는다 — 한 줄이면 전체가 막힌다.**
번들러가 그 import 를 해석하지 못하는 순간 패키지 **전체**가 로드에 실패하기 때문이다.
파일 100개 중 99개가 순수해도, 배럴에서 이어진 한 파일이 `next/headers` 를 부르면 앱은 그 패키지를
통째로 못 읽는다. 이 실패에는 "일부만 못 쓴다" 는 중간 상태가 없다.

같은 이유로 도메인은 **요청 컨텍스트에 묶이면 안 된다.** 쿠키·세션·`AsyncStorage` 를 직접 읽는 함수는
반대편 스택에서 부를 수 없고, 테스트에도 요청 객체가 필요해진다. 필요한 값은 **인자로 받는다.**

이 원칙은 아키텍처 프리셋 4종 전부에 공통이고 인터뷰 문항에도 없다.
`.curvez/architecture.md` 의 `## 금지 import` 표에서 대개 첫 두 행이 이것이다 —
도메인 경로에서 웹 프레임워크를 막는 규칙과 RN/Expo 를 막는 규칙.
모노레포에서는 그 `검사 경로` 열이 `paths.domain` 값에 대응한다.

### 3. `workspace:*` 프로토콜과 버전 불일치

- **`workspace:*` 는 pnpm/yarn berry 전용이다.** npm 은 이 프로토콜을 해석하지 못한다.
  `packageManager` 를 `pnpm` 으로 고정하는 규칙과 맞물리는 지점이라, 루트가 npm 인 저장소에서
  의존성 문자열이 `workspace:*` 면 그 저장소는 이미 pnpm/yarn 으로 돌고 있다는 뜻이다
- **의존성 값이 `workspace:*` 라도 감지는 영향받지 않는다.** 순회 판정은 의존성의 **키**(패키지 이름)만
  보고 값은 보지 않는다. `"@acme/domain": "workspace:*"` 든 `"1.0.0"` 이든 후보 판정 결과는 같다
- **`react` 버전이 웹과 모바일에서 다르면 공유 패키지가 두 벌 설치된다.** RN 은 자기 버전에 묶여 있어
  웹만 먼저 올리는 일이 흔하다. 훅을 쓰는 공유 코드가 있으면 런타임에 두 개의 React 인스턴스로 깨진다.
  **도메인 패키지가 `react` 를 의존하지 않으면 이 문제는 애초에 생기지 않는다** — 2번 원칙을 지키는
  실용적 이유가 하나 더 있는 셈이다
- **`expo` SDK 는 자기가 지원하는 `react-native`·`react` 버전을 강제한다.** 루트에서 버전을 통일하려다
  모바일 앱을 깨뜨리는 변경은 모노레포에서 자주 나온다. `expo.sdkVersion` 을 프로파일에 남기는 이유가
  이것이다 — 어느 버전 조합이 전제인지 기록이 남는다

### 4. 빌드 순서 의존성

웹·모바일은 도메인 패키지를 **빌드 산출물**로 소비할 수도, **소스**로 소비할 수도 있다.
어느 쪽인지에 따라 실패 양상이 갈린다.

| 소비 방식 | 신호 | 걸리는 것 |
|---|---|---|
| 산출물 소비 | 도메인 `package.json` 의 `main`·`exports` 가 `dist/` 를 가리킨다 | 도메인을 빌드하지 않으면 웹·모바일 `typecheck` 가 **소스 오류가 아닌 이유로** 실패한다. 클론 직후·CI 첫 실행에서 나온다 |
| 소스 소비 | `main` 이 `src/index.ts` 를 가리키거나 `publishConfig` 로 갈라 둔다 | 빌드 순서는 사라지지만 각 앱의 번들러·`transpilePackages` 설정에 의존한다 |

**`commands` 로 루트 명령을 쓰면 이 문제는 대개 덮인다.** `turbo run typecheck` 는 태스크 그래프대로
도메인을 먼저 처리하고, `pnpm -r` 은 워크스페이스 의존 순서로 돈다. 반대로 `--filter` 로 좁혀 돌릴 때
`^build` 의존을 빠뜨리면 "고쳤는데 여전히 깨진다" 가 나온다 — 실패 좁히기를 프로파일이 아니라
실행 시점에 하라고 한 이유 중 하나다.

이 항목은 **감지 대상이 아니라 실패 해석 근거**다. `bootstrap` 은 빌드 순서를 프로파일에 적지 않는다.
적을 자리가 없고, 적어도 실행하는 주체가 없다.

## 아키텍처 프리셋과의 조합

각 프리셋의 레이어 정의·금지 import·폴더 구조는
`presets/architecture/<이름>.md` 가 정본이다. 아래는 **모노레포에서만 갈리는 지점**만 다룬다.

### 공통 — `paths.domain` 이 "가장 안쪽 레이어" 의 자리다

프리셋마다 안쪽 레이어의 이름은 다르다. 모노레포에서 갈리지 않는 것은 하나다 —
**그 레이어가 공유 패키지(`paths.domain`)로 나가고, 프레임워크를 참조하지 않는다.**
`## 스택 고유 주의사항` 2번이 4종 전부에 그대로 적용된다.

### `ddd` — 모노레포와 가장 잘 맞는다

`domain` 레이어가 이미 프레임워크 독립이므로 `packages/domain` 하나를 웹과 앱이 그대로 공유한다.
`paths.domain` 이 `domain` 레이어에 대응하고, 나머지 레이어는 각 앱 안에 남는다.

갈리는 지점은 `application` 이다. 유스케이스를 공유 패키지로 올릴지 각 앱에 둘지는 저장소마다 다르고,
**올리는 순간 그 레이어도 프레임워크 독립이어야 한다.** 웹 유스케이스가 서버 전용 API 를 부르는 관례가
있으면 올리지 않는 편이 안전하다. 상세는 [`presets/architecture/ddd.md`](../architecture/ddd.md).
