아키텍처 확정은 설계가 아니라 **선택과 기록**이다. 프리셋 하나를 고르고, 팀 어휘에 맞춰 몇 군데만 틀고,
기계가 검사할 수 있는 금지 import 목록으로 굳힌다. 산출물은 `.curvez/architecture.md` 한 파일이다.

주 사용 에이전트는 `curvez-architect` 다. 산출물의 **헤딩·표 형식·통과 기준은 그 에이전트 정의가 정본**이고,
이 스킬은 **순서와 검증**을 정한다. 형식이 필요한 지점마다 아래에서 경로로 가리킨다.

## 언제 이 스킬을 쓰는가

- `.curvez/architecture.md` 가 없는 상태에서 구현 에이전트를 띄우려 할 때
- DDD 레이어 경계를 처음 정할 때
- 이미 있는 `architecture.md` 의 레이어명·예외·금지 import 를 바꿔 다시 확정할 때
- 스택이 `monorepo` 로 바뀌어 웹·모바일 레이어 매핑을 다시 잡아야 할 때
- 구현 에이전트가 "이 파일을 어느 레이어에 두는가" 로 매번 다르게 판단할 때

## 언제 쓰지 않는가

- 프로젝트 초기 세팅 전체(`.curvez/` 스캐폴드, `profile.json` 생성)를 할 때 → `bootstrap` 을 쓴다. 이 스킬은 `profile.json` 이 **이미 있다는 전제**로 시작한다
- 이미 있는 코드에서 경계 위반·순환 의존을 찾아낼 때 → `structure-audit` 을 쓴다. 이 스킬은 판정 **기준을 만들고**, 그 기준으로 코드를 **판정하는 것**은 `structure-audit` 이다
- 무엇을 만들지·수용 기준을 정할 때 → `requirements` 단계 산출물(`.curvez/requirements.md`)이 이 스킬의 **입력**이다
- 화면 구성·디자인 토큰을 정할 때 → `wireframe-spec` 을 쓴다. 레이어 경계와 와이어프레임은 서로를 입력으로 쓰지 않는다
- 후보 기술의 버전 제약·API 사실을 아직 확인하지 않았을 때 → `research-brief` 를 먼저 쓴다. 조사가 선행이고, 이 스킬은 확인된 사실 위에서 **고르고 기록**한다

**이유:** 네 스킬 전부 "구조" 라는 말에 반응한다. 경계를 배제로 긋지 않으면 `structure-audit` 이 떠서
아직 없는 코드를 감사하거나, 이 스킬이 떠서 이미 확정된 문서를 다시 쓴다.

## 1. 입력을 확인한다

```bash
test -f .curvez/profile.json && echo "profile OK" || echo "profile MISSING"
ls .curvez/handoff/curvez-requirements.*.json 2>/dev/null | tail -1
test -f .curvez/architecture.md && echo "재실행" || echo "최초 실행"
```

- `profile.json` 이 없으면 진행하지 마라. 스택을 추측한 레이어 매핑과 금지 import 는 전부 무효다. 처리 방법은 `agents/curvez-architect.md` 의 `## 에러 핸들링` 을 따른다
- `.curvez/architecture.md` 가 이미 있으면 **재실행**이다. 아래 6단계를 먼저 읽는다

## 2. 프리셋을 확인한다

curvez 는 **DDD 하나만** 제공한다. 고를 것이 없으므로 이 단계는 확인만 하고 지나간다.

**다른 구조를 쓰고 싶다는 요청이 없으면 되묻지 마라.** DDD 로 진행한다.

**DDD 가 과한 규모라면** 레이어를 줄인다 — 구조를 바꾸는 것이 아니라 `application` 을 두지 않는
쪽으로 조정한다. 판정선은 `presets/architecture/ddd.md` 의 `### application 을 둘 것인가` 에 있다.

### DDD 를 쓰지 않기로 했을 때 — 인터뷰로 직접 구성한다

사용자가 명시적으로 다른 구조를 요청했을 때만이다. curvez 는 대안 프리셋을 갖고 있지 않으므로,
**그 프로젝트의 아키텍처를 인터뷰로 처음부터 만든다.**

3단계 인터뷰를 아래로 **교체한다.** 문항 수는 그대로 3문 이상 5문 이하다 —
레이어를 조정하는 것이 아니라 정의하는 것이라 질문의 내용만 달라진다.

| # | 묻는 것 | 답에서 확정되는 것 |
|---|---|---|
| 1 | 어떤 구조인가. 그 구조에서 가장 안쪽(가장 오래 사는) 층은 무엇인가 | `## 레이어 정의` 의 첫 행 |
| 2 | 층을 안쪽에서 바깥쪽 순서로 나열하면 | `## 레이어 정의`, `## 의존 방향` |
| 3 | 어느 층이 어느 층을 참조하면 안 되는가 | `## 금지 import` 의 규칙 후보 |
| 4 | 가장 안쪽 층이 프레임워크를 참조해도 되는가 | 아래 참조 |
| 5 | 각 층이 실제로 어느 디렉터리인가 | `## 폴더 구조`, 금지 import 의 검사 경로 |

**4번의 답이 "된다" 여도 그대로 받아 적는다.** 다만 그 결정이 무엇을 포기하는지 한 번 말하고
`## 결정 로그` 에 남긴다 — 프레임워크를 바꿀 때 그 층을 다시 써야 하고, monorepo 에서 웹과 앱이
같은 로직을 공유할 수 없게 된다. 설득하지 말고 기록한다. 아키텍처는 사용자의 결정이다.

산출물은 DDD 와 **완전히 같다.** 필수 헤딩 7개를 채우고, `## 금지 import` 표를 만들고,
`references/eslint-layer-rules.md` 를 따라 lint 로 강제한다. 프리셋이 없다는 것은
**초안이 없다는 뜻이지 규약이 없다는 뜻이 아니다.**

`## 결정 로그` 에 반드시 남길 것:

```json
{ "what": "<구조 이름> 을 쓴다. DDD 를 쓰지 않는다",
  "why": "<사용자가 말한 근거>",
  "reversible_at": ".curvez/architecture.md:레이어 정의" }
```

**직접 구성한 아키텍처는 다음 프로젝트로 전파되지 않는다.** 그 프로젝트에만 남는다.
같은 구조를 반복해서 쓰게 되면 그때 프리셋으로 승격할지 판단한다 — 한 번 쓴 구조를
프리셋으로 만들면 검증되지 않은 것이 기본값이 된다.

프리셋 본문은 `$CLAUDE_PLUGIN_ROOT/presets/architecture/<이름>.md` 에서 읽는다.

**이 파일이 없어도 멈추지 마라.** 정상 설치에는 있지만, 설치가 불완전하거나 프로젝트가 지웠을 수 있다.

```bash
PRESET=ddd   # 고른 값
test -f "$CLAUDE_PLUGIN_ROOT/presets/architecture/$PRESET.md" \
  && echo "preset file OK" || echo "preset file MISSING -> 내장 폴백"
```

`MISSING` 이면 `agents/curvez-architect.md` 의 **절차 1 내장 폴백 레이어 표**를 그대로 쓰고,
핸드오프 `decisions` 에 아래를 남긴다.

```json
{ "what": "프리셋 파일 부재로 내장 폴백 사용",
  "why": "presets/architecture/ 를 읽지 못했다",
  "reversible_at": ".curvez/architecture.md:레이어 정의" }
```

**이유:** 하네스가 자기 미완성을 이유로 사용자 작업을 막으면 하네스가 아니라 장애물이다.

## 3. 인터뷰한다 — 3문 이상 5문 이하

인터뷰는 **레이어명과 경계 규칙만** 조정한다. 프리셋 자체를 재설계하지 않는다.

문항 후보 5개와 묻지 않을 것의 목록은 `agents/curvez-architect.md` 의 `## 절차 2` 에 있다.
그중 **아래 규칙으로 3~5개를 골라** 한 번에 던지고 한 번에 받는다.

| 상황 | 반드시 고르는 문항 |
|---|---|
| 항상 | 레이어 이름을 팀 용어로 바꿀 것인가 / 공유 코드를 어디에 둘 것인가 |
| `stack: monorepo` | 앱 간 공유 경계를 패키지로 자를 것인가, 폴더로 자를 것인가 |
| `stack: react-native` 또는 `monorepo` | 플랫폼 분기를 어느 레이어에서만 허용할 것인가 |
| 예외가 필요해 보일 때 | 경계 예외를 허용할 지점과 그 범위 |

**5문을 넘기지 마라.** 6문째부터는 프리셋 없이 처음부터 설계하는 것과 같아져 프리셋의 이점이 사라지고,
더 나쁘게는 사용자가 근거 없이 답을 지어내기 시작한다. 그렇게 나온 답이 `.curvez/architecture.md` 에
확정으로 굳으면 되돌릴 근거조차 남지 않는다.
**이유:** 확신 없는 답은 침묵보다 비싸다. 못 정하는 항목은 묻지 말고 프리셋 기본값으로 정한 뒤
`decisions` 에 `reversible_at` 을 남긴다.

**서브에이전트는 사용자에게 직접 묻지 못한다.** 경로는 둘 중 하나다.

| 경로 | 언제 | 어떻게 |
|---|---|---|
| 워커 기동 전 직접 인터뷰 | 오케스트레이터가 아직 `curvez-architect` 를 띄우지 않았다 | 오케스트레이터가 5문을 한 번에 묻고, 답을 프롬프트에 실어 워커를 띄운다 |
| 중계 | 워커가 이미 돌고 있다 | 워커는 `blocked_on` 에 질문을 담아 반환하고, `curvez-orchestrator` 가 사용자에게 묻고 답과 함께 재기동한다 |

**중계 경로가 없으면 인터뷰를 건너뛴다.** 프리셋 기본값으로 문서를 확정하고, 건너뛴 문항마다
`## 결정 로그` 에 `되돌릴 위치` 를 채운다. 이때도 `status` 는 `done` 을 쓸 수 있다.
사용자가 인터뷰를 **명시적으로 요청**했는데 중계가 끊긴 경우에만 `blocked_on` 에 질문을 남긴다.
**이유:** 물어볼 통로가 없다는 이유로 멈추면 아무 산출물도 남지 않는다. 기본값으로 굳힌 결정은
되돌릴 위치가 적혀 있는 한 언제든 뒤집을 수 있다.

## 4. `.curvez/architecture.md` 를 쓴다

필수 헤딩은 아래 7개다. **이 문자열 그대로** 쓴다.

```
## 레이어 정의   ## 의존 방향   ## 금지 import   ## 폴더 구조   ## 스택 매핑   ## 예외   ## 결정 로그
```

각 헤딩에 무엇을 어떤 표로 담는지, 빠지면 무슨 일이 생기는지는
`agents/curvez-architect.md` 의 `## 입출력 프로토콜 > 출력 1` 표가 정본이다. 쓰기 전에 그 표를 읽는다.

절차를 따라가는 데 꼭 필요한 최소 형식은 `## 금지 import` 표 하나다. **열 순서가 고정**이고
세 번째 열이 `grep -E` 에 그대로 들어간다.

```
| 규칙 ID | 검사 경로 | 금지 패턴 (ERE) | 이유 |
| ARCH-001 | src/domain/ | from ['\"](next\|next/.*\|react\|react-dom) | 도메인은 프레임워크 교체에서 분리돼야 한다 |
```

- ID 는 `ARCH-001` 부터 이어 붙인다. **최소 3건**
- 패턴 안의 `|` 는 반드시 `\|` 로 이스케이프한다
  **이유:** 마크다운 표는 이스케이프하지 않은 `|` 를 열 구분자로 읽어 표 자체가 깨진다. 게다가
  패턴 안에 ` | ` 처럼 공백이 붙으면 아래 검증의 awk 가 3열을 그 자리에서 자른다 —
  `from ['\"](next | react)` 는 `from ['\"](next` 만 읽혀 괄호가 안 닫힌 정규식이 된다 (실행 확인함)
- 정규식으로 표현할 수 없는 규칙은 `## 예외` 가 아니라 `## 권고` 에 적는다
  **이유:** 검사할 수 없는 규칙은 위반해도 아무 일이 없고, 아무 일이 없는 규칙은 3주 뒤에 존재하지 않는다

파일은 **Write 로 전체를 다시 쓴다.** 부분 수정은 레이어 정의만 바꾸고 금지 import 표를 그대로 두는
절반 갱신을 만든다. **이유:** 네 구성 요소가 서로 모순된 문서는 구현 에이전트가 어느 쪽을 따를지 판정할 수 없다.

## 5. 검증한다

문서를 쓴 직후 아래를 **실제로 실행하고** 출력을 그대로 핸드오프 `verification` 에 옮긴다.

```bash
ARCH=.curvez/architecture.md
test -f "$ARCH" || { echo "FAIL: $ARCH 없음"; exit 1; }

# (1) 필수 헤딩 7개 — MISSING 이 0건이어야 한다
for h in "레이어 정의" "의존 방향" "금지 import" "폴더 구조" "스택 매핑" "예외" "결정 로그"; do
  grep -q "^## $h" "$ARCH" && echo "OK      $h" || echo "MISSING $h"
done

# (2) 금지 import 규칙 개수 — 3 이상이어야 한다
grep -cE '^\| ARCH-[0-9]{3} \|' "$ARCH"

# (3) 3열 ERE 가 grep -E 에서 실제로 도는지
#     표에서는 `|` 가 `\|` 로 이스케이프돼 있으므로 되돌린 뒤 검사한다.
awk -F' \\| ' '/^\| ARCH-[0-9]{3} \|/ { p=$3; gsub(/\\\|/,"|",p); print p }' "$ARCH" |
while IFS= read -r re; do
  grep -Eq "$re" /dev/null 2>/dev/null; st=$?
  if [ "$st" -le 1 ]; then echo "REGEX-OK  $re"; else echo "REGEX-BAD $re"; fi
done
```

**판정**

| 출력 | 통과값 | 실패했을 때 |
|---|---|---|
| (1) | `MISSING` **0건** | 빠진 헤딩을 채우고 다시 실행한다 |
| (2) | **3 이상** | 규칙을 추가한다. 3건을 못 채우면 경계가 검사 불가능하다는 뜻이다 |
| (3) | `REGEX-BAD` **0건** | 거의 항상 `\|` 이스케이프 누락이다. 3열을 다시 본다 |

(3) 이 `awk: syntax error` 없이 돌았는데 출력이 **한 줄도 없으면** 표 행 형식이 어긋난 것이다.
`| ARCH-001 | ` 처럼 파이프 양쪽에 공백이 정확히 하나씩 있는지 확인한다.
**이유:** 필드 구분자가 `' | '`(공백-파이프-공백)라서 공백이 없거나 두 개면 열이 통째로 밀린다.
이 함정은 실행 테스트로 두 번 잡혔다.

위반 실측(규칙별 `grep -rInE` 건수), 의존 방향 역방향 검사, 핸드오프 스키마 검증까지 포함한
**전체 통과 기준**은 `agents/curvez-architect.md` 의 `## 품질 자체 검증` 을 그대로 따른다.
하나라도 못 채우면 `status: done` 을 쓰지 말고 `partial` 로 낮춘다.

## 6. 재실행 — 이미 `architecture.md` 가 있을 때

**문서 본문은 덮어쓰고, `## 결정 로그` 는 보존한다.**

1. 기존 파일을 **먼저 Read** 한다. 읽지 않고 쓰면 결정 로그가 통째로 사라진다
2. `## 결정 로그` 의 기존 행을 **한 줄도 지우지 않고** 새 문서에 그대로 옮긴다
3. 이번 실행의 결정을 그 아래에 **추가**한다. 앞선 결정을 뒤집었다면 지우지 말고 새 행에
   `무엇을` 열에 "ARCH-002 를 폐기하고 …로 교체" 처럼 뒤집었다는 사실을 적는다
4. 인터뷰는 **결정 로그에 답이 이미 있는 문항을 빼고** 남은 것만 묻는다. 3~5문 예산을 미결 항목에 쓴다

**이유:** 결정 로그를 덮어쓰면 "왜 이렇게 정했는가" 가 사라진다. 그러면 다음 재실행이 같은 질문을
다시 묻고, 사용자는 이전과 다르게 답하고, 문서는 매 실행마다 흔들린다.
본문(레이어 정의·금지 import)은 반대로 **누적하면 안 된다** — 낡은 규칙과 새 규칙이 함께 남으면
구현 에이전트가 어느 쪽을 따를지 판정할 수 없다.

## 7. 핸드오프를 쓴다

`.curvez/handoff/curvez-architect.<YYYYMMDD-HHmmss>.json`. 스키마와 작성 절차는 `agent-contract` 를 따른다.

- `artifacts` 에 `{ "path": ".curvez/architecture.md", "kind": "decision" }`
- `verification` 에 5단계 명령과 **실제 출력값**. 요약하지 마라
- `to` 는 최소 `["curvez-orchestrator"]`. 구현 담당이 정해졌으면 함께 넣는다
- 소스 트리가 아직 없어 검사 대상이 0개면 실패가 아니다. `result` 에 `"검사 대상 0개 (소스 미생성). 정규식 문법 검사만 통과"` 로 적는다
