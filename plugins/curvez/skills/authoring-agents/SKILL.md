에이전트 정의는 실행 중에 고칠 수 없는 계약이다. 서브에이전트는 자기 정의만 들고 격리된 컨텍스트에서
돌아가며, 중간에 사람에게 되물을 수 없다. 정의에 빠진 것은 실행 중에 추측으로 메워진다.
그래서 curvez 는 프론트매터 5필드와 본문 7섹션을 스크립트로 강제한다.

## 언제 이 스킬을 쓰는가

- 프로젝트에 새 담당 에이전트를 추가할 때
- 기존 에이전트의 역할·권한·통신 대상을 바꿀 때
- 에이전트가 엉뚱한 범위를 침범하거나 빈손으로 돌아와 정의를 손볼 때
- `agents/` 아래 `.md` 파일을 편집할 때
- 에이전트 정의가 규약을 지키는지 검증할 때

## 언제 쓰지 않는가

- 스킬 문서를 만들 때 → `authoring-skills` 를 쓴다
- 에이전트가 결과를 넘기는 형식을 정할 때 → `agent-contract` 를 쓴다
- 이미 있는 에이전트들로 팀을 짜서 돌릴 때 → `team-orchestration` 을 쓴다

**이유:** 에이전트 정의(누가)와 핸드오프 계약(무엇을 주고받나)과 팀 실행(언제 누굴 돌리나)은
수명이 다르다. 정의는 오래 살고, 계약은 프로젝트 단위로 굳고, 팀 구성은 작업마다 바뀐다.
한 문서에 섞으면 팀 구성을 바꿀 때마다 정의를 건드리게 된다.

## 절차

### 1. 뼈대를 만든다

```bash
node "$CLAUDE_PLUGIN_ROOT/scripts/new-agent.mjs" <name> --model <opus|sonnet|haiku> [--readonly]
```

- 프로젝트 전용 에이전트는 `.claude/agents/` 에 생긴다
- curvez 코어 에이전트는 `--dir plugins/curvez/agents` 를 붙이고 이름을 `curvez-` 로 시작한다
  - **이유:** 에이전트 `name` 은 전역 네임스페이스다. prefix 없이 `reviewer` 같은 이름을 쓰면
    다른 플러그인의 에이전트와 충돌해 어느 쪽이 뜰지 예측할 수 없다

### 2. 프론트매터 5필드를 채운다

```yaml
---
name: curvez-architect
description: 프로젝트 아키텍처를 확정하고 레이어 경계 규칙을 정한다. "아키텍처 잡아줘", "구조 설계", "architecture" 라고 할 때 부른다.
tools: Read, Grep, Glob, Bash, WebFetch, WebSearch
disallowedTools: Write, Edit, NotebookEdit
model: opus
---
```

| 필드              | 규칙                                                          |
| ----------------- | ------------------------------------------------------------- |
| `name`            | 파일명과 같아야 한다. 소문자 kebab-case                       |
| `description`     | 40자 이상. 언제 이 에이전트를 부르는지. 한글·영어 트리거 병기 |
| `tools`           | 실제로 필요한 것만 나열한다                                   |
| `disallowedTools` | 금지할 것이 없으면 `none` 이라고 적는다                       |
| `model`           | `opus` / `sonnet` / `haiku` / `inherit`                       |

모델과 도구를 고르는 기준은 [references/model-and-tools.md](references/model-and-tools.md) 를 읽는다.

### 3. 본문 7섹션을 채운다

헤딩 문자열과 순서가 고정이다. 하나라도 빠지거나 순서가 다르면 검증이 실패한다.

```
## 핵심 역할
## 판단 기준
## 입출력 프로토콜
## 팀 통신 프로토콜
## 에러 핸들링
## 협업과 팀 내 위치
## 품질 자체 검증
```

각 섹션에 무엇을 어떻게 쓰는지는 [references/section-guide.md](references/section-guide.md) 를 읽는다.

### 4. 제어면에 등록한다

**정의를 만드는 것만으로는 그 에이전트가 호출되지 않는다.** 오케스트레이터가 존재를 모르면
라운드 그래프에 자리가 없어 영원히 안 뜬다.

아래에 행을 추가하거나 개수를 올린다.

| 파일                                                  | 무엇을                                                                                         |
| ----------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| `agents/curvez-orchestrator.md` 의 팀 통신 표         | 무엇을 넘기는가 / 언제 띄우는가                                                                |
| `agents/curvez-orchestrator.md` 의 `### 팀 규모 상한` | 팀 인원 상한 N명 · `subagent_type` 허용 목록 N종. **워커 수다 — 오케스트레이터는 세지 않는다** |
| `skills/team-orchestration/SKILL.md`                  | 라운드 배치. 자동으로 도는가, 요청 시에만 도는가                                               |
| `docs/team-execution.md`                              | 파이프라인의 어디인가. 넣지 않기로 했다면 그 근거                                              |
| `docs/README.md`                                      | 개수 표("에이전트 N종")와 빌드 상태                                                            |

**이유:** 실제로 `curvez-git` 을 만들고 세 곳 어디에도 등록하지 않아, 정의와 스킬은 검증을
통과하는데 오케스트레이터가 그 존재를 모르는 상태가 됐다. 검증기는 "정의가 규약을 지키는가" 만
보고 "그것이 연결됐는가" 는 보지 않는다.

**개수를 고칠 때는 그 문장이 무엇을 세는지 먼저 본다.** 13번째 에이전트를 추가할 때 "11종"
다섯 곳을 12로 일괄 치환했는데, 그중 두 곳은 오케스트레이터를 **포함해** 세는 문장이라 13이어야
했다. 전체를 세는 문장은 수를 빼고 쓴다("라인업 전체에서"). 남는 개수 표기는 전부 워커 수이고,
`doctor` 의 문서 동기화 검사가 이 표기를 판정한다.

파이프라인에 **넣지 않기로** 결정했다면 그것도 적는다. 빠진 것과 뺀 것은 다르고,
근거가 없으면 다음 사람이 빠뜨린 것으로 보고 다시 넣는다.

```bash
# 등록 확인 — 세 곳 모두 1 이상이어야 한다
for f in agents/curvez-orchestrator.md skills/team-orchestration/SKILL.md docs/team-execution.md; do
  printf '%-46s %s\n' "$f" "$(grep -c '<name>' "$f")"
done

# 개수·연결을 기계로 확인한다. 손으로 세지 마라
node "$CLAUDE_PLUGIN_ROOT/scripts/doctor.mjs" --plugin
```

`doctor` 가 개수 불일치·고립·제어면 미등록을 전부 잡는다. 문서 관계의 전체 그림은
`docs/README.md` 의 `## 문서는 서로 어떻게 연결되는가` 에 있다.

### 5. 검증한다

```bash
node "$CLAUDE_PLUGIN_ROOT/scripts/validate-agents.mjs" .claude/agents/<name>.md
```

오류 0개가 될 때까지 고친다. 뼈대의 `<!-- TODO -->` 를 지우지 않으면 통과하지 않는다.
**이유:** 빈 섹션을 남긴 에이전트는 규약을 지킨 것이 아니다. 실행 시점에 그 자리를 추측이 메운다.

## 설계 규칙

### 역할은 하나로 좁힌다

한 에이전트가 조사도 하고 구현도 하고 리뷰도 하면, 자기가 쓴 코드를 자기가 리뷰하게 된다.

**이유:** 서브에이전트는 자기 출력을 컨텍스트에 들고 있다. 같은 컨텍스트에서 검토하면
자기가 내린 판단을 다시 정당화하지, 뒤집지 않는다. 검토는 반드시 다른 에이전트가 한다.

### 리뷰 계열은 쓰기 도구를 막는다

`name` 에 `review`·`audit`·`critic` 이 들어가면 `disallowedTools` 에 `Write, Edit, NotebookEdit`
셋을 전부 넣는다. 검증기가 강제한다.

**이유:** 리뷰어가 직접 고치기 시작하면 리뷰 대상과 리뷰 주체가 섞인다. 무엇이 원래 코드였고
무엇이 리뷰어가 바꾼 것인지 구분이 사라져, 다음 리뷰의 기준점이 없어진다.

### 파일 소유권을 명시한다

`## 협업과 팀 내 위치` 에 이 에이전트만 쓰는 경로를 적는다.

**이유:** 병렬 실행에서 두 에이전트가 같은 파일을 고치면 나중에 쓴 쪽이 앞선 쪽을 조용히 지운다.
소유권이 문서에 없으면 오케스트레이터가 충돌을 미리 잡아낼 근거가 없다.

### 자체 검증은 명령으로 쓴다

`## 품질 자체 검증` 에 "확인한다" 같은 문장을 쓰지 마라. 검증기가 실행 가능한 명령이 있는지 검사한다.

```bash
pnpm typecheck && pnpm lint
```

- [ ] typecheck 오류 0건
- [ ] 도메인 레이어에서 프레임워크 import 0건

**이유:** "확인했다" 는 판정이 불가능하다. 무엇을 돌려 어떤 값이 나왔는지가 있어야 핸드오프의
`verification` 을 채울 수 있고, 그래야 `status: done` 을 쓸 자격이 생긴다.

### 금지는 이유와 함께 적는다

정의에 "~하지 마라" 를 쓸 때는 왜 안 되는지 한 줄을 붙인다.

**이유:** 에이전트는 문서에 없는 상황을 반드시 만난다. 규칙만 있으면 거기서 판단이 멈추거나
규칙을 잘못 확장한다. 이유가 있으면 새 상황에서도 같은 방향으로 판단을 이어간다.

## 자주 나오는 실패

| 증상                               | 원인                                     | 고칠 곳                           |
| ---------------------------------- | ---------------------------------------- | --------------------------------- |
| 에이전트가 빈손으로 돌아온다       | `## 입출력 프로토콜` 에 출력 경로가 없다 | 출력 파일 경로와 형식을 명시      |
| 엉뚱한 파일을 고친다               | `## 협업과 팀 내 위치` 에 소유권이 없다  | 담당 경로를 명시                  |
| 막혔는데 그냥 done 으로 끝낸다     | `## 에러 핸들링` 에 blocked 조건이 없다  | 어떤 상황에서 blocked 인지 명시   |
| 검증 없이 완료를 선언한다          | `## 품질 자체 검증` 이 문장뿐이다        | 실행 명령과 통과 기준 수치로 교체 |
| 다른 플러그인 에이전트가 대신 뜬다 | `name` 이 너무 일반적이다                | prefix 를 붙인다                  |
