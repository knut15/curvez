# 에이전트 본문 7섹션 작성 가이드

`SKILL.md` 의 절차 3단계에서 각 섹션을 어떻게 채울지 막혔을 때 읽는다.
헤딩 문자열과 순서는 고정이다. 바꾸면 `validate-agents.mjs` 가 실패한다.

---

## 1. `## 핵심 역할`

이 에이전트가 책임지는 **단 하나**를 쓰고, 넘기는 범위를 함께 쓴다.

```markdown
## 핵심 역할

프로젝트 아키텍처를 확정하고 레이어 경계 규칙을 문서로 굳힌다.
`.curvez/architecture.md` 가 이 에이전트의 유일한 산출물이며, 이후 모든 구현 에이전트가 이 파일을 전제로 움직인다.

**하지 않는 것:** 실제 코드 작성(구현 에이전트), 기존 코드의 구조 위반 검출(`curvez-structure-reviewer`),
요구사항 확정(`curvez-requirements`).
```

### 판정 기준

역할을 한 문장으로 못 쓰면 에이전트가 둘로 쪼개져야 한다는 신호다.
**이유:** 역할이 넓으면 실행마다 다른 부분에 집중해 결과가 매번 달라진다. 팀 실행에서
수신 에이전트는 매번 다른 형태의 입력을 받게 된다.

---

## 2. `## 판단 기준`

무엇을 보고 결정하는가. **우선순위가 충돌할 때의 tie-break 까지** 쓴다.

```markdown
## 판단 기준

| 상황 | 판단 | 이유 |
|---|---|---|
| 레이어를 더 둘지 말지 | 화면 12개 이하면 두지 않는다 | 경계 없이 파일만 늘어난다 |
| 도메인이 프레임워크를 참조 | 항상 금지 | 도메인을 프레임워크 교체에서 분리하는 것이 DDD 를 쓰는 유일한 이유다 |
| 규칙 준수와 개발 속도 충돌 | 규칙을 지키고 예외를 문서에 남긴다 | 예외가 문서에 없으면 다음 사람이 규칙을 폐기한다 |

**tie-break:** 위 표로 갈리지 않으면 `.curvez/architecture.md` 에 이미 적힌 결정을 따른다.
그것도 없으면 하나를 고르고 `decisions` 에 `reversible_at` 과 함께 남긴다. 멈추지 않는다.
```

### 반드시 넣을 것

- 결정이 갈리는 지점 최소 3개
- 표로 안 갈릴 때의 최종 규칙 (멈출지, 고르고 진행할지)

**이유:** tie-break 이 없으면 애매한 지점마다 에이전트가 멈추거나, 매 실행 다른 선택을 한다.

---

## 3. `## 입출력 프로토콜`

에이전트 간 API 계약. **경로와 형식을 정확히** 쓴다.

```markdown
## 입출력 프로토콜

**입력**

| 경로 | 필수 | 없을 때 |
|---|---|---|
| `.curvez/profile.json` | O | blocked. `blocked_on` 에 "profile 이 없다. bootstrap 먼저" 를 남긴다 |
| `.curvez/handoff/curvez-requirements.*.json` | O | blocked |
| `.curvez/research/*.md` | X | 없이 진행한다 |

**출력**

| 경로 | 형식 |
|---|---|
| `.curvez/architecture.md` | 레이어 정의 / 의존 방향 / 금지 import / 폴더 구조 |
| `.curvez/handoff/curvez-architect.<timestamp>.json` | `agent-contract` 스키마 |
```

### 반드시 넣을 것

- 입력이 없을 때의 행동. **`blocked` 인지 무시하고 진행인지 명시**
- 출력 파일의 경로와 최소 구성 요소

**이유:** 입력 부재 시 행동이 없으면 에이전트는 빈 컨텍스트로 작업을 시작하고 전부 지어낸다.

---

## 4. `## 팀 통신 프로토콜`

누구에게 / 무엇을 / 언제. 대상 에이전트의 `name` 을 그대로 적는다.

```markdown
## 팀 통신 프로토콜

| 누구에게 | 무엇을 | 언제 |
|---|---|---|
| `curvez-nextjs`, `curvez-react-native` | `.curvez/architecture.md` 경로와 금지 import 목록 | 아키텍처 확정 직후 |
| `curvez-orchestrator` | `status` 와 미해결 질문 | 항상. 모든 핸드오프의 `to` 에 포함한다 |
| `curvez-requirements` | 요구사항이 아키텍처와 모순될 때의 이의 | 모순을 발견한 즉시, 구현 시작 전 |

**받는 쪽:** `curvez-requirements` 의 수용 기준, `curvez-researcher` 의 기술 제약 브리프.
```

### 반드시 넣을 것

- 대상은 역할 이름이 아니라 `name` 문자열
- "언제" 는 조건으로. "필요하면" 은 조건이 아니다

**이유:** 서브에이전트는 팀 명단을 모른다. `name` 이 정확해야 오케스트레이터가 라우팅한다.

---

## 5. `## 에러 핸들링`

```markdown
## 에러 핸들링

| 상황 | 행동 |
|---|---|
| 입력 핸드오프가 계약 위반 | `status: blocked`. 어느 필드가 왜 부족한지 `blocked_on` 에 적는다. 스스로 메우지 않는다 |
| 요구사항이 두 가지로 해석됨 | 결과가 크게 갈리면 `blocked`. 비슷하면 하나 고르고 `decisions` 에 `reversible_at` 을 남긴다 |
| 앞 단계 결정과 충돌 | 조용히 뒤집지 않는다. `blocked_on` 에 이의를 남기고 오케스트레이터에게 돌린다 |
| 자체 검증 실패 | `status: partial`. 실패한 명령과 실제 출력을 `verification` 에 그대로 적는다 |
| 도구 호출이 반복 실패 | 2회까지 재시도. 그 뒤 `partial` 로 보고하고 무엇이 실패했는지 남긴다 |
```

### 반드시 넣을 것

- 정보 부재 시 **추측 금지**를 명시
- 검증 실패 시 **숨기지 않고 그대로 보고**를 명시
- 재시도 상한

**이유:** 이 셋이 없으면 실패가 조용한 `done` 으로 바뀐다. 팀 실행에서 이것이 가장 비싼 실패다.

---

## 6. `## 협업과 팀 내 위치`

```markdown
## 협업과 팀 내 위치

- **선행:** `curvez-requirements` (수용 기준 확정), `curvez-researcher` (기술 제약)
- **후행:** `curvez-nextjs`, `curvez-react-native`, `curvez-structure-reviewer`
- **병렬:** `curvez-designer` — 와이어프레임과 아키텍처는 서로를 기다리지 않는다
- **파일 소유권:** `.curvez/architecture.md` 만 쓴다. 소스 트리는 건드리지 않는다
```

### 반드시 넣을 것

- 소유 경로. 다른 에이전트와 겹치면 병렬 실행이 순차로 강등된다
- 병렬 가능 상대와 그 근거

**이유:** 오케스트레이터는 이 섹션만 읽고 병렬 가능 여부를 판정한다. 없으면 전부 순차로 돌린다.

---

## 7. `## 품질 자체 검증`

완료 선언 전에 **실제로 돌리는** 명령과 통과 기준.

~~~~markdown
## 품질 자체 검증

```bash
node "$CLAUDE_PLUGIN_ROOT/scripts/validate-handoff.mjs" .curvez/handoff/
grep -rn "from ['\"]next\|from ['\"]react-native" src/domain/ | wc -l
```

- [ ] 핸드오프 검증 오류 0개
- [ ] 도메인 레이어의 프레임워크 import 0건
- [ ] `.curvez/architecture.md` 에 레이어 정의·의존 방향·금지 import 세 항목이 전부 있다
~~~~

### 반드시 넣을 것

- 백틱 코드블록 안의 실행 명령. 검증기가 존재를 검사한다
- 통과 기준을 **수치**로. "잘 되면" 은 기준이 아니다

**이유:** 이 섹션의 출력이 그대로 핸드오프의 `verification` 이 된다. 여기가 비면
`status: done` 을 쓸 근거가 없고, 검증기가 `done` 을 거부한다.
