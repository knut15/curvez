스킬은 에이전트가 특정 상황에서 읽어들이는 절차서다. 두 가지가 전부다 —
**호출되는가**(description 이 상황을 잡아내는가), **실행되는가**(본문이 판정 가능한 절차인가).
둘 중 하나라도 실패하면 스킬은 없는 것과 같다. 잘 쓴 본문도 호출되지 않으면 아무 일도 하지 않는다.

## 언제 이 스킬을 쓰는가

- 반복되는 작업 절차를 스킬로 굳힐 때
- 기존 스킬이 호출되지 않거나 엉뚱한 상황에서 호출돼 고칠 때
- SKILL.md 가 길어져 references 로 나눠야 할 때
- `skills/` 아래 `SKILL.md` 를 편집할 때
- 스킬이 규약을 지키는지 검증할 때

## 언제 쓰지 않는가

- 에이전트 정의를 만들 때 → `authoring-agents` 를 쓴다
- 핸드오프 형식을 정할 때 → `agent-contract` 를 쓴다
- 절차가 아니라 사실·구조를 설명하는 문서를 쓸 때 → `docs/` 에 일반 문서로 쓴다

**이유:** 스킬은 컨텍스트 예산을 매 턴 소비한다. description 은 스킬이 호출되지 않아도
항상 로드된다. 절차가 아닌 것을 스킬로 만들면 호출되지 않을 문서의 설명문에 예산을 계속 낸다.

## 절차

### 1. 뼈대를 만든다

```bash
node "$CLAUDE_PLUGIN_ROOT/scripts/new-skill.mjs" <name> [--with-references]
```

### 2. description 을 쓴다

여기가 스킬의 성패다. 규칙 넷을 지킨다.

| 규칙            | 내용                                                                         |
| --------------- | ---------------------------------------------------------------------------- |
| 동사로 시작     | "~를 한다" 로 시작한다. 명사구로 시작하면 무엇을 하는 스킬인지 늦게 드러난다 |
| 트리거 3개 이상 | 사용자가 실제로 말할 표현을 따옴표로 감싸 나열한다                           |
| 한글·영어 병기  | 한쪽만 쓰면 반대 언어 발화에서 호출되지 않는다                               |
| 짧게            | 한두 문장. 본문에 있는 내용을 여기서 다시 설명하지 마라                      |

```yaml
description: 반복 절차를 스킬 문서로 만들고 규약 준수를 검증한다. "스킬 만들어줘", "스킬 추가", "create a skill", "SKILL.md" 라고 하거나 skills/ 아래를 편집할 때 실행한다.
```

트리거를 고르는 법은 [references/description-craft.md](references/description-craft.md) 를 읽는다.

### 3. 트리거 경계를 쓴다

`## 언제 이 스킬을 쓰는가` 와 `## 언제 쓰지 않는가` 두 섹션이 필수다.

`## 언제 쓰지 않는가` 에는 **인접 스킬을 이름으로 지목**한다.

```markdown
- 에이전트 정의를 만들 때 → `authoring-agents` 를 쓴다
```

**이유:** "쓰는가" 만 있으면 비슷한 스킬 여럿이 같은 발화에 다 반응한다. 어느 것이 뜰지 예측할 수
없고, 잘못 뜬 스킬이 자기 절차를 끝까지 밀어붙인다. 경계는 배제로만 그어진다.

### 4. 본문을 쓴다

- **절차는 번호로.** 각 단계는 무엇으로 끝났다고 판정하는지가 드러나야 한다
- **금지 규칙에는 `이유:` 를 붙인다.** 검증기가 강제한다
- **명령형으로 쓴다.** `~하라`, `~한다`
- **완료 기준을 체크리스트로.** 실제로 돌린 명령과 나온 수치로 판정 가능하게

### 5. 길면 references 로 내린다

SKILL.md 는 500줄이 상한이다. 한 섹션이 120줄을 넘으면 경고가 뜬다.

내리는 기준과 방법은 [references/progressive-disclosure.md](references/progressive-disclosure.md) 를 읽는다.

### 6. 문서를 갱신한다

**스킬을 만드는 것만으로는 아무도 그것을 찾지 못한다.** 아래를 함께 고친다.

| 파일                              | 무엇을                                   |
| --------------------------------- | ---------------------------------------- |
| 인접 스킬의 `## 언제 쓰지 않는가` | 트리거가 겹치면 **양쪽에** 서로를 적는다 |
| 주 사용 에이전트 정의             | 이 스킬을 어느 절차에서 부르는지         |
| `docs/README.md`                  | 개수 표("스킬 N종")                      |

**이유:** 실제로 스킬을 만들고 개수 표를 안 고쳐 README 가 "13종" 이라고 말하는 동안
실제로는 15종이었다. 사용자가 가장 먼저 읽는 문서가 틀리면 나머지가 맞아도 신뢰를 잃는다.

문서 관계의 전체 그림은 `docs/README.md` 의 `## 문서는 서로 어떻게 연결되는가` 에 있다.
층마다 참조 형태가 다르므로(스킬은 이름, docs 는 링크) 그 규칙을 먼저 읽는다.

```bash
# 개수·연결·고립을 기계로 확인한다
node "$CLAUDE_PLUGIN_ROOT/scripts/doctor.mjs" --plugin
```

### 7. 검증한다

```bash
node "$CLAUDE_PLUGIN_ROOT/scripts/validate-skills.mjs" .claude/skills/<name>
```

오류 0개가 될 때까지 고친다.

## 작성 규칙

### 금지에는 이유를 붙인다

"~하지 마라" 만 쓰면 문서에 없는 상황에서 판단이 멈춘다.

**이유:** 규칙은 나열된 경우만 덮는다. 이유는 나열되지 않은 경우까지 덮는다.
에이전트는 반드시 문서에 없는 상황을 만나므로, 이유가 있어야 같은 방향으로 판단을 이어간다.

### 금지보다 목표를 먼저 쓴다

"주석을 길게 쓰지 마라" 대신 "주석은 한 줄로 쓴다" 를 먼저 쓴다.

**이유:** 금지형은 금지 대상을 컨텍스트로 끌어와 오히려 더 떠오르게 만든다.
목표 행동을 직접 지시하면 금지 대상이 아예 언급되지 않는다.
하드 가드레일로 금지가 꼭 필요하면 목표와 함께 쓴다.

### 환경이 이미 아는 것을 옮겨 적지 마라

`package.json` 의 스크립트 이름, 디렉터리 구조, `--help` 출력은 스킬에 복사하지 않는다.

**이유:** 복사본은 원본이 바뀌어도 따라가지 않는다. 낡은 사본이 문서에 있으면 에이전트가
그것을 믿고 존재하지 않는 명령을 실행한다. 찾아보면 알 수 있는 것은 환경에 맡기고,
찾아봐도 모르는 것(규약의 이유, 함정, 관례)만 문서에 남긴다.

### 같은 의미를 두 곳에 쓰지 마라

**이유:** 규칙을 바꿀 때 한 곳만 고치면 두 문서가 서로 다른 규칙을 말하게 된다.
어느 쪽이 맞는지 판정할 근거가 없어 에이전트가 매번 다른 쪽을 따른다.
curvez 에서 규약 값의 단일 출처는 `scripts/lib/spec.mjs` 다. 스킬은 "무엇을·왜" 만 설명한다.

### 기본 동작을 지시하지 마라

"꼼꼼히 읽어라", "정확하게 써라" 같은 문장은 예산만 쓰고 행동을 바꾸지 않는다.

**이유:** 이미 하고 있는 것을 지시하면 아무 변화가 없다. 판정 방법은 하나다 —
그 문장을 지우고 돌려본 뒤 결과가 달라지는가. 안 달라지면 지운다.

## 자주 나오는 실패

| 증상                     | 원인                                            | 고칠 곳                        |
| ------------------------ | ----------------------------------------------- | ------------------------------ |
| 스킬이 호출되지 않는다   | description 에 사용자가 실제로 쓰는 표현이 없다 | 트리거를 실제 발화로 교체      |
| 엉뚱한 상황에서 호출된다 | `## 언제 쓰지 않는가` 가 비었거나 추상적이다    | 인접 스킬을 이름으로 지목      |
| 뒷부분 지시가 무시된다   | 본문이 너무 길다                                | references 로 분리             |
| 매번 다른 결과가 나온다  | 각 단계의 완료 조건이 모호하다                  | 판정 가능한 기준으로 교체      |
| 엣지 케이스에서 멈춘다   | 규칙만 있고 이유가 없다                         | `이유:` 추가                   |
| references 를 안 읽는다  | 본문의 포인터 문구가 약하다                     | 언제 읽어야 하는지 조건을 명시 |
