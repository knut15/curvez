# description 작성법

`SKILL.md` 절차 2단계에서 트리거를 고를 때 읽는다.

description 은 스킬이 호출되지 않아도 항상 컨텍스트에 올라간다. 매 턴 비용을 내는 유일한 부분이고,
동시에 스킬이 뜰지 말지를 혼자 결정한다. 본문보다 더 깎아 쓴다.

---

## 구조

```
<동사로 시작하는 한 문장> + <트리거 나열> + <실행 조건>
```

```yaml
description: 반복 절차를 스킬 문서로 만들고 규약 준수를 검증한다. "스킬 만들어줘", "스킬 추가", "create a skill", "SKILL.md" 라고 하거나 skills/ 아래를 편집할 때 실행한다.
```

세 부분이 각각 다른 일을 한다.

| 부분        | 하는 일                                                   |
| ----------- | --------------------------------------------------------- |
| 동사 문장   | 무엇을 하는 스킬인지. 앞에 둬야 첫 단어에서 판별이 끝난다 |
| 트리거 나열 | 사용자 발화와 직접 매칭된다. 여기가 호출률을 좌우한다     |
| 실행 조건   | 발화가 아닌 상황(파일 편집, 특정 단계 진입)에서의 트리거  |

---

## 트리거 고르는 법

### 사용자가 실제로 말할 표현을 쓴다

문서용 정식 명칭이 아니라 실제 발화를 넣는다.

| 나쁨                  | 좋음                           |
| --------------------- | ------------------------------ |
| "스킬 저작 요청"      | "스킬 만들어줘"                |
| "코드 품질 검토 수행" | "리뷰해줘", "봐줘"             |
| "의존성 그래프 분석"  | "구조 정리해줘", "중복 찾아줘" |

**이유:** 매칭 대상은 사용자의 실제 문장이다. 문서에만 쓰이는 표현을 넣으면 그 표현이
발화에 나타나지 않아 아무것도 잡지 못한다.

### 서로 다른 갈래를 하나씩 넣는다

같은 뜻의 동의어를 여럿 넣는 것은 트리거 하나를 여러 번 쓴 것이다.

| 갈래 하나를 반복                   | 갈래를 나눔                            |
| ---------------------------------- | -------------------------------------- |
| "리뷰해줘", "리뷰 부탁", "리뷰 좀" | "리뷰해줘", "PR 봐줘", "머지해도 되나" |

**이유:** 매칭은 표현 하나하나가 아니라 의미 영역을 덮는다. 같은 영역을 세 번 덮는 대신
세 영역을 한 번씩 덮어야 잡히는 범위가 넓어진다.

### 한글과 영어를 함께 넣는다

검증기가 강제한다. 둘 중 하나가 없으면 오류다.

**이유:** 같은 사용자도 상황에 따라 언어를 바꾼다. 명령어·도구 이름을 말할 때는 영어가,
의도를 말할 때는 한글이 나온다. 한쪽만 있으면 절반의 발화를 놓친다.

### 슬래시 커맨드 이름을 넣는다

`/authoring-skills` 처럼 스킬 자신의 호출 이름도 트리거에 넣는다.

**이유:** 사용자가 이름을 정확히 부를 때가 가장 확실한 호출 의도다. 이것을 놓치면 안 된다.

---

## 실행 조건 (발화가 아닌 트리거)

발화 없이도 떠야 하는 상황을 조건으로 적는다.

| 조건 유형 | 예시 문구                         |
| --------- | --------------------------------- |
| 파일 편집 | `skills/ 아래 파일을 편집할 때`   |
| 단계 진입 | `서브에이전트가 결과를 반환할 때` |
| 상태 발견 | `.curvez/profile.json 이 없을 때` |

**이유:** 사용자가 항상 말로 요청하지는 않는다. "이 파일 좀 고쳐줘" 라고만 해도 그 파일이
스킬 문서라면 규약이 적용돼야 한다.

---

## 넣지 않을 것

| 넣지 않는다                       | 이유                                                            |
| --------------------------------- | --------------------------------------------------------------- |
| 본문에 있는 절차 설명             | description 은 호출 판정용이다. 절차는 호출된 뒤에 읽힌다       |
| 스킬 이름을 문장으로 재서술       | 이름이 이미 있다. 반복은 예산만 쓴다                            |
| "필요할 때 사용" 같은 무조건 문구 | 모든 상황에 걸려 다른 스킬을 밀어낸다                           |
| 두 문단 이상의 긴 설명            | 매 턴 비용이다. 트리거 밀도가 떨어지면 오히려 호출률이 낮아진다 |

---

## 점검 방법

description 을 쓴 뒤 스스로 묻는다.

1. 사용자가 이 작업을 부탁할 때 실제로 뭐라고 말하는가. 그 문장이 트리거에 있는가
2. 이 트리거로 **뜨면 안 되는** 상황이 떠오르는가. 그렇다면 `## 언제 쓰지 않는가` 에 적었는가
3. 인접 스킬의 description 과 겹치는 트리거가 있는가. 있다면 어느 쪽이 떠야 하는가

3번에서 겹침을 발견하면 트리거를 옮기지 말고 **양쪽 스킬의 `## 언제 쓰지 않는가` 에 서로를 적는다**.

**이유:** 트리거를 지우면 그 발화에서 아무 스킬도 뜨지 않는다. 겹침 자체는 문제가 아니고,
겹쳤을 때 어느 쪽이 이기는지가 문서에 없는 것이 문제다.
