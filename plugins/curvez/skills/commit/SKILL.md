---

이 스킬이 다루는 것은 **이미 만들어진 변경을 이력에 올리는 절차**다. 코드를 쓰지 않고,
검증을 직접 설계하지 않는다.

커밋은 되돌릴 수 있지만 **push 부터는 되돌리는 비용이 급격히 오른다.** 그래서 이 스킬은
사용자가 말한 단계에서 정확히 멈춘다. 원격 이력을 **지우는** 조작(강제 push, 원격 브랜치 삭제)은
가드가 막으므로 명령을 제시해 사용자가 실행하게 한다.

## 언제 이 스킬을 쓰는가

- 작업이 끝나 변경을 커밋할 때
- 커밋을 원격에 올릴 때(요청받았을 때만 push 한다)
- PR/MR 을 만들 때, 또는 만든 PR 을 요청받아 머지할 때
- 커밋이 훅에 거부되어 메시지를 고쳐야 할 때
- 여러 주제가 섞인 작업 트리를 커밋 단위로 나눠야 할 때
- 핸드오프의 `artifacts` 에 커밋 해시·PR URL 을 남겨야 할 때

## 언제 쓰지 않는가

- **브랜치를 따거나 옮기거나 지울 때 → `branching` 을 쓴다.** "브랜치 따줘", "새 브랜치에서 작업해줘",
  "브랜치 이름 뭐로 해" 는 저쪽이다. 이 스킬은 **이미 올라타 있는 브랜치 위에서** 커밋한다.
  트리거가 겹치는 지점("작업 브랜치 만들고 커밋해줘")에서는 `branching` 을 먼저 돌리고 이 스킬로 넘어온다
- **검증 명령을 실제로 돌릴 때 → `quality-gate` 를 쓴다.** 커밋 전 typecheck·lint·test 는 그쪽 절차다.
  여기서 게이트 절차를 복제하지 않는다.
  **이유:** 같은 게이트 정의가 두 곳에 있으면 한쪽만 갱신됐을 때 어느 수치가 맞는지 판정할 근거가 없다
- 핸드오프 JSON 의 스키마·필드 규칙 → `agent-contract` 를 쓴다. 이 스킬은 `artifacts` 에 들어갈
  **값**(커밋 해시, PR URL)만 만든다
- `.curvez/profile.json` 이 없을 때 → `bootstrap` 을 먼저 쓴다. 브랜치 이름을 추측하지 않는다
- 커밋되지 않은 실패를 고치려고 코드를 쓸 때 → 구현 스킬(`nextjs-implementation` /
  `react-native-implementation`)로 돌아간다. 깨진 것을 커밋으로 덮지 않는다

## 어디까지 하는가

**사용자가 말한 단계에서 멈춘다. 다음 단계로 스스로 넘어가지 않는다.**

| 사용자가 이렇게 말하면 | 어디까지 |
|---|---|
| "커밋해줘" | 1~6 (커밋까지) |
| "푸시해줘" | 1~7 (push 실행까지) |
| "PR 만들어줘" / "mr 올려줘" | 1~8 (PR 생성까지) |
| "머지까지 해줘" | 1~9 (단 타겟이 `humanMergeTargets` 에 없는 PR 만) |

**이유:** 각 단계는 되돌리는 비용이 한 자릿수씩 오른다. 커밋은 `git reset` 으로 지역에서 끝나고,
push 는 남의 클론에 퍼지며, PR 은 리뷰어 알림과 CI 사용량을 만들고, 머지는 다른 사람의
작업 기반을 바꾼다. 사용자가 "커밋해줘"라고 말한 것은 **그 지점에서 결과를 보고 판단하겠다는 뜻**이다.
앞질러 가면 그 판단 기회가 사라지고, 사라진 뒤에 되돌리는 것은 앞질러 간 만큼 비싸다.

**"PR 만들어줘"에 머지하지 않는다.** 요청받았을 때 해도 된다는 것이지 알아서 하라는 것이 아니다.

**MR 과 PR 을 되묻지 않는다.** GitLab 용어(MR)로 말해도 원격이 GitHub 이면 만드는 것은 PR 이고
`gh pr create` 를 쓴다. 같은 것을 가리키므로 확인하지 않고 진행한다.

## 0단계 — git 설정을 프로파일에서 읽는다

**브랜치 이름을 하드코딩하지 마라. `.curvez/profile.json` 의 `git` 에서 읽는다.**
**이유:** `main ← release ← 작업` 2단 구조와 `main ← 작업` 1단 구조는 PR 타겟이 서로 다르다.
`release` 를 박아 두면 GitHub Flow 저장소에서 존재하지 않는 브랜치로 PR 을 열려다 실패하고,
반대로 `main` 을 박아 두면 2단 구조에서 통합 브랜치를 건너뛰어 검증되지 않은 것이 배포 브랜치에 닿는다.

```bash
P=.curvez/profile.json
[ -f "$P" ] || { echo "BLOCKED: $P 없음. bootstrap 먼저 돌린다"; exit 1; }
pf() { node -p "(JSON.parse(require('fs').readFileSync('$P','utf8'))$1)||''"; }

BASE=$(pf "?.git?.baseBranch")
RELEASE=$(pf "?.git?.releaseBranch")
STRATEGY=$(pf "?.git?.mergeStrategy")
PROTECTED=$(pf "?.git?.protectedBranches?.join(' ')")
echo "base=[$BASE] release=[$RELEASE] strategy=[$STRATEGY] protected=[$PROTECTED]"

if [ -z "$BASE" ] || [ -z "$RELEASE" ]; then
  echo "BLOCKED: profile.json 에 git.baseBranch / git.releaseBranch 가 없다"
  exit 1
fi

if [ "$BASE" = "$RELEASE" ]; then
  echo "구조: 1단 (작업 브랜치 → $BASE PR 하나로 끝난다. 릴리스 PR 절차 없음)"
else
  echo "구조: 2단 (작업 → $BASE 는 이 스킬, $BASE → $RELEASE 릴리스 PR 은 사람이 누른다)"
fi

case "$STRATEGY" in
  rebase) MERGE_FLAG=--rebase ;;
  squash) MERGE_FLAG=--squash ;;
  merge)  MERGE_FLAG=--merge ;;
  *) echo "BLOCKED: git.mergeStrategy 가 rebase|merge|squash 가 아니다: [$STRATEGY]"; exit 1 ;;
esac
echo "merge flag=$MERGE_FLAG"
```

**`git` 키가 없으면 추측하지 말고 `status: blocked` 로 보고한다.**
**이유:** 브랜치를 잘못 짚으면 남의 작업 위에 커밋이 쌓이고, 그것을 떼어내려면 이력을 다시 쓰는
조작이 필요하다. 값을 모르는 상태에서 멈추는 비용보다 항상 비싸다.

보호 브랜치 위에 서 있는지 커밋 전에 확인한다.

```bash
CUR=$(git rev-parse --abbrev-ref HEAD)
case " $PROTECTED " in
  *" $CUR "*) echo "STOP: $CUR 는 보호 브랜치다. branching 스킬로 작업 브랜치를 먼저 딴다" ;;
  *) echo "현재 브랜치: $CUR (보호 대상 아님)" ;;
esac
```

## 1. 무엇이 바뀌었는지 읽는다

```bash
git status --short
git diff --stat
git diff            # 스테이징 전
git diff --cached   # 스테이징 후
```

**diff 를 읽지 않고 메시지를 쓰지 마라.**
**이유:** 파일 이름만 보고 쓴 메시지는 "무엇이 바뀌었는가"가 아니라 "어디가 바뀌었는가"만 말한다.
그 메시지는 회귀를 추적할 때 아무것도 좁혀 주지 못하고, 결국 커밋을 하나씩 열어보게 만든다.

## 2. 커밋 단위를 정한다

**한 커밋은 한 주제다.** 되돌릴 수 있는 단위로 나눈다.

- 목적이 다른 변경이 섞였으면 `git add <경로>` 로 나눠 담는다
- 관련 없는 파일을 "겸사겸사" 넣지 않는다.
  **이유:** 그 커밋 하나를 revert 할 때 상관없는 변경까지 함께 사라진다
- `git add -A` 로 쓸어 담지 않는다. `git status` 로 눈으로 확인한 경로만 담는다.
  **이유:** 빌드 산출물·`.env`·에디터 임시 파일이 섞여 들어가고, 비밀값은 push 된 뒤에는
  이력에서 지워도 이미 노출된 것이다

### `git add -p` 를 쓸 수 없다 — 한 파일에 두 주제가 섞였을 때

**`git add -p` 는 대화형이라 이 환경에서 쓸 수 없다.**
**이유:** Bash 도구는 명령에 stdin 을 연결하지 않는다. 대화형 프롬프트는 응답을 받지 못한 채
타임아웃되거나 빈 입력으로 종료되고, 그때 무엇이 스테이징됐는지 알 수 없는 상태가 남는다.

대안은 셋이다. **위에서부터 시도한다.**

1. **아직 편집 전이면 순서로 푼다.** 주제 A 만 편집 → 커밋 → 주제 B 편집 → 커밋.
   섞이기 전에 나누는 것이 가장 싸다
2. **이미 섞였고 나눌 가치가 있으면 사본으로 되돌린다.** 최종 상태를 먼저 백업한 뒤,
   편집 도구로 주제 B 를 되돌려 A 만 남기고 커밋하고, 백업을 복원해 B 를 커밋한다

```bash
mkdir -p .curvez/tmp
cp src/features/cart/total.ts .curvez/tmp/split-total.ts   # 최종 상태 백업
# 편집 도구로 src/features/cart/total.ts 에서 주제 B 를 되돌려 A 만 남긴다
git add src/features/cart/total.ts && git commit -F - <<'EOF'
주제 A 제목
EOF
cp .curvez/tmp/split-total.ts src/features/cart/total.ts   # 최종 상태 복원
git add src/features/cart/total.ts && git commit -F - <<'EOF'
주제 B 제목
EOF
rm -f .curvez/tmp/split-total.ts
```

   **백업을 먼저 만든다.** **이유:** 백업 없이 되돌리면 최종 상태가 작업 트리에서 사라지고,
   그것은 아직 어디에도 커밋되지 않았으므로 복구할 곳이 없다.
   중간 커밋이 컴파일되지 않을 수 있음을 감수한다면 이 방법을 쓰고, 감수할 수 없으면 3번으로 간다

3. **억지로 나누다 실수하는 것보다 하나로 두는 편이 낫다.** 한 커밋으로 두고 본문에서 문단을 나눠
   두 주제를 각각 설명한다. 나누기 실패는 조용히 깨진 중간 커밋을 남기지만, 합쳐 둔 커밋은
   설명이 충분하면 읽을 수 있다

## 3. 메시지를 쓴다 — 규칙은 기존 로그에서 읽는다

**커밋 메시지 규칙을 새로 만들지 마라. 이 저장소가 이미 쓰고 있는 것을 따른다.**
**이유:** 메시지 형식은 팀의 합의이지 옳고 그름이 있는 것이 아니다. 한글로 쓰는 팀도 영어로 쓰는
팀도 Conventional Commits 를 쓰는 팀도 있다. 에이전트가 자기 취향을 들고 들어오면 이력이
두 가지 문체로 갈라지고, `git log` 를 훑거나 자동 changelog 를 뽑을 때 어느 쪽도 신뢰할 수 없게 된다.

```bash
git log --format='%s' -20
```

여기서 **관찰할 것 셋**이다.

| 관찰 | 무엇을 보는가 |
|---|---|
| 언어 | 제목이 한글인가 영어인가. 섞여 있으면 최근 10건의 다수를 따른다 |
| 타입 접두어 | `feat:` `fix(scope):` 가 붙는가 안 붙는가. 붙는다면 쓰이는 타입 목록을 그대로 쓴다 |
| 제목 길이 | 실제 관행. 대부분 50자 안이면 50자를, 72자까지 쓰면 72자를 따른다 |

본문·꼬리말도 같이 본다.

```bash
git log --format='%B%n---' -5     # 본문 유무, 검증 줄, Co-Authored-By 관행
```

**로그가 비어 있으면(첫 커밋) 사용자에게 묻는다.** 언어와 타입 접두어 여부만 물으면 충분하다.
**이유:** 첫 커밋이 이후 모든 커밋의 기준이 된다. 여기서 임의로 정하면 팀이 나중에 바꾸려 할 때
이력 전체가 예외가 된다. 되돌릴 수 없는 선택이라 묻는 것이 맞다.

### 프로젝트와 무관하게 지키는 것 셋

**1. 제목은 무엇이 바뀌었는지 구체적으로 쓴다.**

```
✗ 버그 수정 / 업데이트 / fix stuff / chore: update
✓ 로그인 후 프로필 조회가 이전 토큰으로 도는 문제 수정
✓ fix: profile query reusing stale token after login
```

**이유:** 제목은 `git log --oneline` 과 `git blame` 에서 **유일하게 보이는 줄**이다. "버그 수정"이
열 줄 쌓이면 서로 구별되지 않아, 회귀를 일으킨 커밋을 찾을 때 전부 열어봐야 한다. 제목의 값은
읽는 순간이 아니라 **몇 달 뒤 범위를 좁힐 때** 나온다.

**2. 본문은 "무엇을" 이 아니라 "왜" 를 쓴다.** 그리고 왜 다른 방법을 쓰지 않았는지를 쓴다.

**이유:** 무엇을 했는지는 diff 가 이미 빠짐없이 말한다. 본문에 그것을 다시 쓰면 diff 의 열등한
복사본이 되고, 코드가 바뀌면 그 복사본만 틀린 채 남는다. diff 가 절대 복원할 수 없는 것은
**그 시점에 무엇을 알고 있었고 어떤 대안을 왜 버렸는가**뿐이다. 그것이 없으면 다음 사람이
같은 대안을 다시 검토하고 같은 이유로 다시 버린다.

**3. 검증은 실제로 돌린 것만 쓴다. 못 한 것은 못 했다고 쓴다.**

```
✓ 검증: typecheck 0 errors, lint 0 errors 5 warnings, 47 tests 47 passed.
        가드의 거부 경로는 재현 데이터가 없어 확인하지 못했다.
✗ 검증: 테스트 통과 / 정상 동작 확인
```

**이유:** 커밋의 검증 줄은 나중에 "이 시점에 무엇이 통과한 상태였는가"의 기준선이 된다.
지어낸 줄은 그 기준선을 오염시켜 회귀 추적 범위를 엉뚱한 곳으로 좁힌다. 값은 `quality-gate` 가
낸 수치를 그대로 옮기고, 핸드오프의 `verification[]` 과 같은 값이어야 한다.

## 4. 커밋 전 검증

**`quality-gate` 스킬의 절차를 그대로 돌린다. 여기서 게이트를 다시 정의하지 않는다.**
`done` 최소 구성은 typecheck + lint + test 이며, 설정·의존성이 바뀌었으면 build 까지다.
판정 기준·0개 실행 함정·수치 형식은 전부 그쪽이 정본이다.

**게이트가 빨간 상태로 커밋하지 마라.**
**이유:** 깨진 커밋은 그 뒤 모든 이등분 탐색(`git bisect`)의 기준점을 오염시킨다.
고치는 커밋이 뒤따르더라도, 그 사이 어느 커밋으로 되돌아가도 빌드가 되지 않는 구간이 남는다.
게이트가 빨갛고 그대로 남겨야 할 이유가 있으면 **커밋 메시지 검증 줄에 실패를 그대로 적고**
사용자에게 알린다.

## 5. 커밋한다

**여러 줄 메시지는 heredoc 으로 넘긴다.**
**이유:** `-m` 을 여러 번 쓰면 문단 사이 빈 줄이 git 의 조합 규칙에 맡겨져, 제목 다음 빈 줄이나
문단 구분이 의도와 다르게 나온다. 그것을 검사하는 훅이 있으면 그 자리에서 거부된다.

```bash
git add src/features/cart/total.ts   # git status 로 확인한 경로만. 와일드카드·-A 금지
git commit -F - <<'EOF'
제목

왜 이렇게 했는가. 어떤 대안을 왜 버렸는가.

검증: typecheck 0 errors, lint 0 errors, 47 tests 47 passed
EOF
git log -1 --format='%H %s'   # 해시를 artifacts 에 남긴다
```

`<<'EOF'` 로 따옴표를 붙인다. **이유:** 붙이지 않으면 메시지 안의 `$`, 백틱, `\` 가 셸에서
전개되어 원문과 다른 메시지가 커밋된다.

## 6. 훅에 거부되면

거부는 정상 동작이다. **우회하지 말고 원인을 고친다.**

1. 출력에서 어느 규칙에 걸렸는지 읽는다. 린터가 규칙 id 를 찍으면 그것으로 좁힌다
2. 쓴 메시지는 `.git/COMMIT_EDITMSG` 에 남아 있다. 처음부터 다시 쓰지 말고 그것을 고친다
3. 규칙 정의를 직접 읽어 무엇을 요구하는지 확인한다

```bash
cat .git/COMMIT_EDITMSG
git config core.hooksPath            # 훅 위치
ls -a .husky 2>/dev/null             # husky 를 쓰는 저장소
cat commitlint.config.* 2>/dev/null  # commitlint 규칙
```

**`--no-verify` 를 쓰지 마라.**
**이유:** 훅은 팀이 "이것만은 자동으로 막자"고 합의해 실행으로 걸어 둔 것이다. 우회하면 규칙이
없는 것과 같아지고, 더 나쁘게는 **규칙이 있다고 믿는 상태에서 없는 것**이 된다. 다음 사람은
훅이 걸러 줬다고 가정하고 검사를 생략한다. 규칙이 현실과 맞지 않으면 우회하지 말고 규칙을
고치고, 그 변경을 별도 커밋으로 남긴다.

훅이 아예 안 도는 것 같으면 `core.hooksPath` 를 확인한다. 안 걸린 채로 커밋하면 위반이
그대로 들어가고, CI 에서야 발견된다.

## 7. 푸시

**평범한 `git push` 는 에이전트가 직접 실행한다.** 가드가 막지 않는다.
원격 이력에 커밋을 얹는 것은 append 라, 틀렸으면 revert 커밋으로 되돌린다.

**가드가 exit 2 로 막는 것은 원격 이력을 지우는 두 가지다.**

| 막힌다 | 이유 |
|---|---|
| `git push --force`, `git push -f` | 그 브랜치를 받아 간 사람의 커밋을 소리 없이 덮는다 |
| `git push --delete origin <브랜치>`, `git push origin :<브랜치>` | 원격 브랜치를 지운다. 복구할 방법이 없다 |

`git reset --hard`, `git clean -f…`, `git branch -D`, `main` 대상 rebase 도 같이 막힌다.

**막힌 명령의 우회 명령을 만들지 마라** — 변수에 담아 쪼개거나, 별칭·스크립트 파일로 감싸거나,
`gh api` 로 대신 밀어 넣는 것 전부 금지다.
**이유:** 우회하면 가드가 없는 것과 같고, 사용자는 가드가 지켜 준다고 믿은 채로 남는다.

### 절차

push 전에 무엇을 올리는지 읽기 전용 명령으로 확인하고, **사용자에게 한 줄로 알린 뒤** 실행한다.

```bash
git status -sb
git log --oneline @{u}.. 2>/dev/null || git log --oneline -5
```

> 올라가는 커밋 N건: `<해시> <제목>` … → `origin/<브랜치>`

```bash
git push -u origin <브랜치>
```

**요청받지 않았으면 push 하지 않는다.** "커밋해줘" 는 6절까지다. 7절은 "푸시해줘" 부터다.
**이유:** push 는 남의 클론에 퍼지고 CI 를 돌린다. 커밋과 달리 조용히 되돌릴 수 없다.

push 뒤에 원격에 반영됐는지 확인한다.

```bash
git status -sb
```

**강제 푸시를 제안하지 마라.** `--force` 도 `--force-with-lease` 도 마찬가지다.
`--force-with-lease` 는 가드를 통과하지만(남의 커밋이 있으면 실패하므로) 그것이 제안해도
된다는 뜻은 아니다.
**이유:** 강제 갱신은 그 브랜치를 받아 간 사람의 커밋을 덮는다. 정말 필요해 보이면
무엇이 사라지는지 명시하고 사용자 판단을 받는다.

## 8. PR 생성

**PR 은 push 가 끝난 뒤에만 가능하다.** 브랜치가 원격에 없으면 `gh` 가 실패한다.

**PR 을 만들기 전에 무엇을 올리는지 사용자에게 한 줄로 알린다.**
**이유:** PR 은 리뷰어 알림과 CI 실행을 만드는 외부 산출물이다. 잘못 열면 닫아도 알림은 이미 갔다.

```bash
gh pr create --base "$BASE" --head "$CUR" --title "<제목>" --body "$(cat <<'EOF'
## 무엇을

## 왜

## 검증
- 실제로 돌린 명령과 결과 (돌리지 않은 것은 "미실행" 으로 적는다)
EOF
)"
```

- **`--base "$BASE"` 를 빠뜨리지 마라.**
  **이유:** `gh` 의 기본 타겟은 저장소 기본 브랜치다. 2단 구조에서 생략하면 통합 브랜치를 건너뛰고
  배포 브랜치로 열려, 검증되지 않은 변경이 릴리스 대상이 된다
- **`hotfix/` 브랜치만 `--base "$RELEASE"`** 로 연다. 그 외 예외는 없다
- **1단 구조(`$BASE` = `$RELEASE`)** 에서는 이 PR 하나가 전부다. 릴리스 PR 절차가 없다
- **2단 구조**에서 `$BASE` → `$RELEASE` 로 가는 **릴리스 PR 은 이 스킬이 만들지 않는다.**
  배포 시점 판단이므로 사람이 연다
- 제목은 3절에서 관찰한 커밋 제목 규칙을 그대로 따른다
- 만든 뒤 **PR URL 과 CI 상태를 보고**하고, URL 을 핸드오프 `artifacts` 에 남긴다
- **머지까지 요청받지 않았으면 여기서 멈춘다**

## 9. 머지

**넷을 모두 만족할 때만 머지한다.**

1. **PR 타겟이 `git.humanMergeTargets` 에 없다.** 있으면 사람이 누른다 — 1단/2단으로
   추론하지 말고 프로파일 값을 읽는다. 판정 근거는 `curvez:branching` 의
   `### 머지 권한은 humanMergeTargets 가 정한다`
2. **CI 가 통과했다.** 눈으로 확인한다
3. `mergeStrategy` 가 정한 플래그로 머지한다
4. **사용자가 머지까지 요청했다**

1번의 근거: `$BASE` 로 가는 머지는 revert PR 로 되돌릴 수 있다. 반대로 2단 구조의 릴리스 PR 은
배포된 것을 움직이고 뒤에 태그·포인터 조정이 따라온다. 1단 구조에서는 작업 브랜치 → `main` 이
곧 `$BASE` PR 이므로 요청받으면 머지해도 된다 — 여기에는 승격 단계가 없어 revert 로 충분하다.

```bash
PR=123                                     # 8절에서 만든 PR 번호로 바꾼다
gh pr checks "$PR"                         # 통과를 눈으로 확인하고
gh pr merge "$PR" "$MERGE_FLAG" --delete-branch
git switch "$BASE" && git pull --ff-only   # 다음 작업이 최신 기반에서 시작하도록
```

**마지막 줄을 빠뜨리지 마라.**
**이유:** 지역 `$BASE` 가 뒤처진 채로 다음 브랜치를 따면 그 작업이 낡은 기반 위에서 시작하고,
충돌은 PR 을 열 때가 되어서야 드러난다.

- **CI 를 확인하지 않고 머지하지 마라.**
  **이유:** 머지된 실패는 그 뒤 모든 사람의 기반을 빨갛게 만들고, 누가 깼는지 찾는 데
  머지 자체보다 훨씬 많은 시간이 든다
- `git pull` 을 인자 없이 쓰지 마라. **이유:** 기본 동작이 저장소 설정에 따라 merge 커밋을
  만들 수 있어, 의도하지 않은 병합 이력이 지역에 생긴다. `--ff-only` 를 붙인다
- **`git merge` 로 지역에서 합치지 마라.** 머지는 PR 을 통과한다.
  **이유:** 지역 머지는 CI 와 리뷰를 건너뛰고, 그 사실이 이력에 남지 않는다
- 머지한 뒤에도 PR URL 과 CI 결과를 보고한다

## 핸드오프에 무엇을 남기는가

`artifacts` 에는 **실제로 만들어진 것**만 적는다. 스키마는 `agent-contract` 가 정본이다.

| 단계까지 갔으면 | `artifacts` 에 |
|---|---|
| 커밋 | 커밋 해시(`git log -1 --format=%H`)와 제목 |
| 푸시 | 사용자가 실행했음을 확인한 뒤의 원격 sha |
| PR | PR URL |
| 머지 | PR URL 과 머지된 커밋 해시 |

- `status: done` 은 `verification` 이 비면 쓸 수 없다. 값은 `quality-gate` 가 낸 수치를 옮긴다
- push 를 사용자에게 넘기고 결과를 못 받았으면 `status` 는 `partial` 이고,
  `blocked_on` 에 실패한 명령과 원문 출력을 남긴다
- **만들지 않은 PR 의 URL 을 지어내지 마라.** **이유:** 지어낸 URL 은 수신 에이전트가 열어보기 전까지
  존재하는 것으로 취급되고, 그 위에 다음 단계가 쌓인다

## 하지 않는 것

- **요청하지 않은 단계로 넘어가지 않는다.** "커밋해줘"에 push 하지 않고, "푸시해줘"에 PR 을
  만들지 않고, "PR 만들어줘"에 머지하지 않는다
- **가드를 우회하지 않는다.** 강제 push·원격 브랜치 삭제를 쪼개거나 감싸거나 다른 도구로 대신하지 않는다
- **`--no-verify`, `--force`, `--force-with-lease` 를 쓰지 않는다**
- **`git add -A` 로 쓸어 담지 않는다.** `git status` 로 확인한 경로만 담는다
- **보호 브랜치에 직접 커밋하지 않는다.** `protectedBranches` 위면 `branching` 으로 돌아간다
- **커밋 메시지 규칙을 새로 만들지 않는다.** 기존 로그가 정본이다
- **확인하지 않은 검증 결과를 커밋 메시지나 PR 본문에 쓰지 않는다**
- **브랜치를 만들거나 지우지 않는다.** 그것은 `branching` 이다
