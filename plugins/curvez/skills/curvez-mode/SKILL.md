curvez 의 입구다. 에이전트 정의가 **누가** 하는지를 정한다면, 플레이북은 작업 **종류마다 무엇을 어떤 순서로**
하는지를 정한다. 버그 수정은 재현부터, 리팩터링은 동작 고정부터 시작한다. 같은 라운드 구성으로 모든 작업을
돌리면 이 차이가 사라진다.

## 언제 이 스킬을 쓰는가

- 사용자가 "curvez 로 해줘", "curvez 모드", "플레이북으로" 라고 할 때
- 기능 추가·버그 수정·리팩터링·조사·자율 실행·머지 준비 가운데 하나에 해당하는 작업을 받았을 때
- 자율 실행(goal 하나를 완료 조건까지)을 맡았을 때

## 언제 쓰지 않는가

- 프로젝트에 `.curvez/profile.json` 이 없을 때 → `bootstrap` 을 먼저 쓴다
- 사용자가 팀 구성만 요청했을 때("팀으로 해줘") → `team-orchestration` 을 쓴다
- 커밋·PR 만 요청했을 때 → `commit` 을 쓴다
- 질문 하나에 짧게 응하면 끝나는 일이면 플레이북을 열지 않는다

**이유:** 플레이북은 여러 라운드를 도는 작업의 순서다. 한 번의 조회나 커밋에 씌우면 단계만 늘고 결과는 같다.

## 플레이북 고르기

| 플레이북                                      | 언제                                                                     |
| --------------------------------------------- | ------------------------------------------------------------------------ |
| [feature](playbooks/feature.md)               | 새 동작을 추가하거나 기존 동작을 바꾼다                                  |
| [bug-fix](playbooks/bug-fix.md)               | 보고된 결함을 재현하고, 원인을 찾고, 고친다                              |
| [refactoring](playbooks/refactoring.md)       | 동작은 그대로 두고 구조만 바꾼다                                         |
| [investigation](playbooks/investigation.md)   | 읽기 전용 질문. 어떻게 동작하는가, 왜 이렇게 만들었는가, 정말 그런가     |
| [autonomous-run](playbooks/autonomous-run.md) | goal 하나를 완료 조건까지 사람 없이 끌고 간다. 위 플레이북들을 이어 쓴다 |
| [shipping](playbooks/shipping.md)             | 끝난 작업을 머지해도 되는지 독립적으로 판정한다. 다른 플레이북의 마지막  |

둘 이상이 맞으면 좁은 쪽을 고른다(버그 수정 > 기능). 작업이 여러 종류로 나뉘면 `autonomous-run` 을 고른다.
그래도 정해지지 않으면 `principles/tie-break-order.md` 를 따른다.

## 첫 응답의 형식

플레이북을 고른 직후, 다른 도구를 부르기 전에 **이 형식으로 한 번 쓴다.** 단계 문장은 플레이북 파일에서
**줄여 쓰지 않고 글자 그대로** 옮긴다. 괄호 안의 원칙 경로까지 옮긴다.

```
플레이북: <이름> — <고른 이유 한 줄>
- [ ] 1. <플레이북 1단계 원문>
- [ ] 2. <플레이북 2단계 원문>
…
```

할 일 목록 도구(TodoWrite 등)가 있으면 같은 항목을 그 도구에도 넣는다. 마지막 보고에서 이 목록을 다시 싣고
`[x]`, `skip: <이유>`, `멈춤: <이유>` 로 표시한다.

**이유:** 절차 안에 한 줄로만 적어 두었더니 실제 세션(2026-09-28 `claude -p`, sonnet)에서 두 번 모두 목록을
쓰지 않고 바로 실행에 들어갔다. 목록이 없으면 어떤 단계를 건너뛰었는지 보고에서도 알 수 없다.

## 절차

1. **플레이북을 하나 고른다.** 고른 이름과 이유를 한 줄로 사용자에게 알린다
2. **단계를 할 일 목록으로 옮긴다.** 플레이북 파일을 열어 번호 단계를 할 일 목록의 첫 항목들로 **글자 그대로** 옮긴다.
   작업에 맞춘 할 일은 그 뒤에 붙인다
   - 할 일 목록 도구(TodoWrite 등)가 있으면 그것에 넣는다. 없으면 첫 응답에 `- [ ] 1. …` 체크리스트로 싣는다
   - 하지 않을 단계도 지우지 않는다. 그 항목에 `skip: <이유>` 를 붙여 남긴다
   - **이유:** 단계를 요약해 옮기면 요약하면서 빠진 조건이 조용히 사라진다. 지운 단계는 보고에서도 사라져
     무엇을 건너뛰었는지 아무도 모른다. 세션마다 쓸 수 있는 도구가 달라서(2026-09-28 `claude -p` 세션에는
     TodoWrite 가 없었다) 도구가 없을 때의 형식을 정해 둔다
3. **단계를 순서대로 실행한다.**
   - 단계가 `principles/<slug>.md` 를 가리키면 그 원칙 파일을 끝까지 읽고 따른다. **`principles/` 는 이 스킬 폴더가
     아니라 플러그인 루트 기준이다:** `$CURVEZ_ROOT/principles/<slug>.md`. 원칙 목록은 `$CURVEZ_ROOT/principles/README.md` 다
   - **이유:** 스킬 기준 경로로 읽으면 원칙 파일이 없다고 판단한다(2026-09-28 실측에서 그렇게 판단했다)
   - **단계에 `curvez-*` 에이전트 이름이 있으면 그 단계를 직접 하지 않는다.** `curvez-orchestrator` 에게
     `agent-contract` 의 `## 지시서` 형식으로 넘긴다. 직접 하는 것은 에이전트 이름이 없는 단계(재현, 조사, 판정)뿐이다
     (원칙: `principles/orchestrator-owns-spawn.md`)
   - **이유:** 단계에 이름이 붙은 에이전트는 그 일의 소유 경로와 검증 절차를 갖고 있다. 메인 세션이 대신하면
     소유권 검사와 핸드오프가 빠지고, 리뷰 라운드가 무엇을 기준으로 볼지 사라진다(2026-09-28 실측에서
     `curvez-qa` 몫의 테스트 파일을 메인 세션이 직접 쓰려 했다)
   - 경로가 필요한 명령은 `$CURVEZ_ROOT` 아래에서 찾는다
4. **막히면 멈춘다.** 입력이 없거나 승인이 필요한 행동이면 그 자리에서 멈추고 이유를 보고한다
   (원칙: `principles/blocked-over-guessing.md`, `principles/approval-boundary.md`)
5. **플레이북의 `보고:` 형식으로 끝낸다.** 2번의 단계 목록을 다시 싣고 단계마다 완료·`skip: <이유>`·멈춤을
   표시한다. 적용한 원칙 이름과 그 원칙 때문에 바뀐 선택을 함께 적는다

## 완료 기준

- [ ] 고른 플레이북 이름과 이유를 알렸다
- [ ] 플레이북의 모든 단계가 할 일 목록에 있고, 각각 완료되었거나 `skip: <이유>` 가 붙어 있다
- [ ] 보고가 플레이북의 `보고:` 항목을 모두 담았다
