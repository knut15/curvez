게이트 루프는 **이미 정해진 기준(수용 기준과 테스트)을 통과할 때까지** 구현과 수정을 되풀이하는
절차다. 한 번 승인받은 계획 안에서는 반복마다 사람에게 다시 묻지 않는다. 대신 계속할지 멈출지는
모델이 아니라 `scripts/loop-state.mjs` 가 반복 횟수·시간·실패 결과로 판정한다.

상한 값(수정 반복 횟수, 시간, 진전 없음 판정)은 `scripts/lib/spec.mjs` 의 `LOOP_*` 가 정본이다.
승인 예외의 조건은 `plugins/curvez/agents/curvez-orchestrator.md` 의 `### 승인 절차` 가 정본이다.
이 문서는 **순서와 완료 조건**만 정한다.

## 언제 이 스킬을 쓰는가

- 수용 기준과 테스트가 이미 있고, 그것을 통과할 때까지 구현을 되풀이하라는 요청을 받았을 때
- 구현 라운드가 끝났는데 게이트가 실패해, 실패 → 수정을 여러 번 돌려야 할 때
- 앞 세션에서 멈춘 게이트 루프(`.curvez/loop.json`)를 이어 갈 때

## 언제 쓰지 않는가

- 게이트를 한 번 돌려 수치만 뽑을 때 → `quality-gate` 를 쓴다
- 무엇을 만들지, 무엇이 통과 기준인지 아직 정해지지 않았을 때 → `curvez-requirements` 라운드를
  먼저 돈다 (`team-orchestration`)
- 테스트를 새로 설계·작성할 때 → `curvez-qa` 라운드를 먼저 돈다
- 리뷰 지적 → 수정 → 재리뷰를 돌릴 때 → `team-orchestration` 의 재리뷰 루프를 쓴다. 상한이 다르다
- 팀 구성·병렬 판정·핸드오프 수합 자체 → `team-orchestration` 을 쓴다. 이 스킬은 그 절차를 반복에 쓴다

**이유:** 게이트 루프는 기준이 이미 있을 때만 수렴한다. 기준이 없는 상태에서 돌리면 구현자가
기준을 추측하고, 게이트는 그 추측을 검증할 뿐이라 반복할수록 엉뚱한 쪽으로 굳는다. 리뷰 루프와
나눈 이유는 상한의 근거가 달라서다. 리뷰가 2회 안에 안 닫히는 것은 기준 문제라 사람이 정하지만,
테스트 실패는 기준이 테스트로 이미 정해져 있어 더 돌 여지가 있다.

## 절차

### 1. 입력을 확인한다

1. `.curvez/profile.json` 을 읽는다. 없으면 `status: blocked`, `blocked_on` 에 "bootstrap 먼저" 를 남기고 끝낸다
2. `commands.test` 가 있는지 본다. 없으면 루프를 시작하지 않는다
3. 통과 기준이 될 테스트가 있는지 본다. 없으면 루프를 시작하지 않고 `curvez-qa` 라운드를 먼저 제안한다
4. `.curvez/loop.json` 이 있으면 `node "$CLAUDE_PLUGIN_ROOT/scripts/loop-state.mjs" status` 를 돌린다.
   `status: running` 이면 새로 시작하지 말고 `### 7. 세션이 바뀌어 이어 갈 때` 로 간다

**완료 조건:** `commands.test` 값과 통과 기준 테스트 경로를 적었다. 하나라도 없으면 여기서 멈췄다.

### 2. 루프 계획을 만든다

`team-orchestration` 의 `### 2. 구성안을 만든다` 다섯 항목(누가·왜·무엇을·어떻게·몇 라운드)에 아래를 더한다.

| 항목            | 내용                                                                                           |
| --------------- | ---------------------------------------------------------------------------------------------- |
| 통과 기준       | 어떤 게이트가 통과하면 끝인가. 기본은 arch·typecheck·lint·test, 마지막에 build 까지            |
| 반복 구성       | 반복마다 도는 구성. 보통 구현 에이전트 1명(`curvez-nextjs`) → 게이트                           |
| 보호하는 테스트 | 루프 동안 고치지 않을 테스트 경로                                                              |
| 상한            | `lib/spec.mjs` 의 `LOOP_MAX_FIX`·`LOOP_MAX_MINUTES`·`LOOP_NO_PROGRESS` 값을 읽어 그대로 적는다 |
| 끝난 뒤         | 통과하면 리뷰 라운드로 넘긴다. git 라운드는 자동으로 돌지 않는다                               |

**완료 조건:** 구성안 다섯 항목과 위 다섯 항목이 전부 있다.

### 3. 계획을 승인받는다

`team-orchestration` 의 `### 3. 승인을 받는다` 를 따른다. 이 루프 계획을 승인받으면, **계획에 적은
반복 구성 그대로의 재실행**은 반복마다 다시 묻지 않는다. 조건은 `curvez-orchestrator.md` 의
`### 승인 절차` 에서 확인한다.

**계획에 없는 워커를 띄우거나 소유 경로를 바꾸려면 루프를 멈추고 다시 승인받는다.**
**이유:** 승인은 계획 전체에 대한 것이다. 계획 밖의 구성은 사용자가 본 적이 없다.

**완료 조건:** 사용자의 승인 문장을 받았다. `Agent` 호출은 이 시점까지 0회다.

### 4. 루프를 시작한다

```bash
node "$CLAUDE_PLUGIN_ROOT/scripts/loop-state.mjs" init --plan "<승인받은 계획 한 줄>"
```

출력의 `limits` 가 계획에 적은 상한과 같은지 대조한다. `.curvez/team.md` 에 루프 계획과 승인 시각을 적는다.

### 5. 반복한다

한 반복은 다섯 단계다. `verdict` 가 `continue` 인 동안 되풀이한다.

1. **구현 워커를 띄운다.** `team-orchestration` 의 `### 4. 띄운다` 를 따른다.
   두 번째 반복부터는 프롬프트에 직전 게이트의 실패한 명령·결과 원문·그 하나만 다시 돌리는 재현 명령을 넣는다
2. **수합한다.** `team-orchestration` 의 `### 5. 수합한다` 를 따른다. `blocked` 가 오면 반복을 멈추고 6으로 간다
3. **보호한 테스트가 바뀌었는지 본다.**
   ```bash
   git diff --name-only -- <보호하는 테스트 경로>
   ```
   한 줄이라도 나오면 `loop-state.mjs stop --reason "보호한 테스트가 바뀌었다: <경로>"` 를 부르고 6으로 간다
4. **게이트를 돌린다.**
   ```bash
   mkdir -p .curvez/qa
   node "$CLAUDE_PLUGIN_ROOT/scripts/quality-gate.mjs" --json --only arch,typecheck,lint,test > .curvez/qa/loop-gate.json
   ```
5. **판정을 받는다.**
   ```bash
   node "$CLAUDE_PLUGIN_ROOT/scripts/loop-state.mjs" record --gate .curvez/qa/loop-gate.json
   ```
   `verdict` 가 `continue` 면 1로, `pass` 면 아래 "통과한 뒤" 로, `stop` 이면 6으로 간다

**통과한 뒤:** build 까지 넣은 전체 게이트를 한 번 더 돌린다(`--only` 없이). 루프는 이미 `passed` 로
끝났으므로 이 결과는 `record` 하지 않고 핸드오프의 `verification` 에만 넣는다. build 가 실패하면 새 루프를
시작하지 말고 실패를 원문 그대로 보고한다. 통과하면 리뷰 라운드
(`curvez-reviewer` ∥ `curvez-structure-reviewer`)를 `team-orchestration` 대로 제안한다.

**`verdict` 를 스스로 뒤집지 마라.** `stop` 이 나왔는데 "한 번만 더" 돌리지 않는다.
**이유:** 판정을 스크립트로 옮긴 이유가 이것이다. 모델이 판정하면 상한이 매번 한 번씩 늘어나고,
그 사실이 기록에 남지 않는다.

**실패한 테스트를 지우거나 skip 하거나 기대값을 실제 출력에 맞추지 마라.** 구현자 프롬프트에도 넣는다.
**이유:** 루프는 게이트가 초록불이 될 때까지 돈다. 테스트를 고쳐 초록불을 만드는 것이 가장 빠른 길이라,
막지 않으면 루프가 그쪽으로 수렴한다. `quality-gate` 의 `## 실패를 숨기지 않는다` 와 같은 규칙이다.

### 6. 멈추면 보고한다

`verdict: stop` 이거나 워커가 `blocked` 를 냈으면 반복을 멈추고, 셋을 묶어 사용자에게 올린다.

| 항목         | 내용                                                                                |
| ------------ | ----------------------------------------------------------------------------------- |
| 상태         | `loop-state.mjs status` 의 `reason`, 마지막 실패한 명령과 결과 원문                 |
| 이력         | 반복마다 무엇을 고쳤고 게이트 결과가 어땠는지 (`.curvez/loop.json` 의 `iterations`) |
| 다음에 할 일 | 사람이 정할 것을 질문 형태로. 예: "기대값 X 와 구현 Y 중 어느 쪽이 맞는가"          |

**멈춘 뒤 스스로 새 루프를 시작하지 마라.** 상한을 바꾸려면 `lib/spec.mjs` 를 고쳐야 하고, 그것은
사용자 승인이 필요한 규약 변경이다.
**이유:** 멈춤은 사람이 판단할 차례라는 신호다. 새 루프를 열면 그 판단 없이 같은 추측이 이어진다.

### 7. 세션이 바뀌어 이어 갈 때

1. `loop-state.mjs status` 로 계획·반복 수·남은 상한·마지막 실패를 읽어 사용자에게 한 번에 보여 준다
2. 이어 가도 되는지 확인받는다. 앞 세션의 승인은 이번 세션으로 넘어오지 않는다
3. 확인받으면 `loop-state.mjs resume` 을 부른 뒤 5로 간다

**`resume` 을 빠뜨리지 마라.**
**이유:** 시간 상한은 루프가 실제로 돈 시간만 센다. `resume` 없이 `record` 하면 세션 사이 공백(밤사이 등)이
그대로 더해져, 이어 가자마자 시간 상한에 닿는다.

## 완료 기준

- [ ] 승인 전 `Agent` 호출 **0회**, `.curvez/team.md` 에 루프 계획과 승인 시각이 있다
- [ ] 반복마다 `quality-gate.mjs --json` 출력이 `.curvez/qa/loop-gate.json` 으로 남았고 `record` 로 기록됐다
- [ ] 계속·통과·멈춤을 전부 `loop-state.mjs` 의 `verdict` 로 정했다. 스스로 뒤집은 사례 **0건**
- [ ] 보호한 테스트 경로의 변경 **0줄**
- [ ] 끝난 상태가 `passed` 면 build 를 포함한 전체 게이트도 돌려 결과를 `verification` 에 넣었다
- [ ] 끝난 상태가 `stopped` 면 상태·이력·다음에 할 일을 한 번에 보고했다
- [ ] 반복마다 `validate-handoff.mjs` 오류 **0개**
