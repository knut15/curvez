모션은 취향이 아니라 값이다. 이 스킬은 그 값을 어디서 가져오는지와, curvez 프로젝트에서
무엇이 이기는지를 정한다. 값 자체의 정본은 `vendor/emilkowalski-skills/` 사본이다.

## 언제 이 스킬을 쓰는가

- 화면에 새 애니메이션·전환을 넣을 때
- 구현 도중 이징 커브·지속 시간·스프링 설정을 정해야 할 때
- 이미 있는 모션이 굼뜨다·튄다·끊긴다는 지적을 받아 고칠 때
- 코드베이스 전체 모션을 감사해 고칠 순서를 정할 때
- 어디에 모션을 넣을지, 넣지 말지를 판정할 때

## 언제 쓰지 않는가

- 화면 구조·색·간격·타이포 토큰을 확정할 때 → `wireframe-spec` 을 쓴다
- 컴포넌트를 처음부터 구현할 때 → `nextjs-implementation` 을 쓴다. 그 절차 안에서 모션 값이 필요해지는 지점에만 이 스킬로 들어온다
- 레이어 경계·중복·순환 의존을 볼 때 → `structure-audit` 을 쓴다
- typecheck·lint·test 를 실제로 돌릴 때 → `quality-gate` 를 쓴다
- 결과를 다음 에이전트에게 넘기는 JSON 형식이 궁금할 때 → `agent-contract` 를 쓴다
- 화면 전체를 어느 디자인 스킬이 맡을지 갈릴 때 → `design-routing` 을 먼저 쓴다. 이 스킬은 모션 값만 다룬다

**이유:** 모션은 구현·디자인·리뷰 세 단계에 걸쳐 나타나서 세 스킬 모두와 겹친다. 경계를 긋지
않으면 "버튼 만들어줘" 에 이 스킬까지 함께 떠서 구현 절차 위에 자기 절차를 덮어쓴다.

## 값의 정본

이 문서는 값을 갖지 않는다. 값은 벤더 사본에 있고, 상황마다 열 파일이 다르다.

| 하려는 일                     | 열 파일 (`plugins/curvez/vendor/emilkowalski-skills/` 아래)      |
| ----------------------------- | ---------------------------------------------------------------- |
| 웹 애니메이션을 만든다        | `animate/SKILL.md` → 해당 컴포넌트가 있으면 `animate/RECIPES.md` |
| 만든 모션을 리뷰한다          | `review-animations/SKILL.md` + `review-animations/STANDARDS.md`  |
| 코드베이스 모션을 감사한다    | `improve-animations/SKILL.md` + `AUDIT.md` + `PLAN-TEMPLATE.md`  |
| 넣을 자리를 찾는다            | `find-animation-opportunities/SKILL.md`                          |
| 제스처·스프링 원칙이 필요하다 | `apple-design/SKILL.md`                                          |
| UI 디테일 판단이 필요하다     | `emil-design-eng/SKILL.md`                                       |
| 효과의 이름을 모른다          | `animation-vocabulary/SKILL.md`                                  |

`SKILL.md` 는 결정 순서만 담고 값 카탈로그는 옆 파일에 있다. **옆 파일은 해당할 때만 연다.**

**사본을 고치지 마라.** 출처·커밋·복사 시점은 `vendor/emilkowalski-skills/VENDOR.md` 에 있다.
**이유:** 고치는 순간 원본과 대조할 수 없어 벤더링이 아니라 포크가 된다. 개정된 원본을 다시 받을 때
무엇이 우리 변경이고 무엇이 원본인지 가릴 방법이 없어진다.

## 절차

### 1. 움직여야 하는지부터 판정한다

`animate/SKILL.md` 의 빈도 표로 판정한다. 하루 100회 이상 보는 것과 키보드로 시작되는 동작은
**애니메이션 없이 끝낸다.** 판정 결과를 한 줄로 남긴다 — 빈도 등급과 목적 한 단어.

목적을 한 단어로 못 대면 만들지 마라.
**이유:** "보기 좋아서" 는 자주 보이는 요소에서 반드시 방해가 된다. 목적이 없으면 나중에 그 모션을
지울 근거도 없어져 계속 남는다.

**완료 판정:** 만들지 않기로 했으면 여기서 끝이다. 코드 0줄이 정상 결과다.

### 2. 값의 출처를 정한다

`.curvez/design/tokens.md` 에 이징·지속 시간 토큰이 이미 있으면 **그것이 이긴다.** 사본의 값과
달라도 프로젝트 토큰을 쓴다.

없으면 사본의 표에서 가져와 `.curvez/design/tokens.md` 에 토큰으로 먼저 추가하고, 코드에서는
그 토큰 이름으로 참조한다. 토큰 이름 규칙은 `wireframe-spec` 이 정본이다.

**값을 지어내지 마라.** 커브는 사본의 표나 사본이 지목한 출처에서만 가져온다.
**이유:** 익숙해 보이는 `cubic-bezier` 를 손으로 쓰면 프로젝트마다 미묘하게 다른 곡선이 쌓이고,
어느 것이 의도된 값인지 판정할 근거가 사라진다.

**완료 판정:** 쓰려는 커브·지속 시간이 전부 `.curvez/design/tokens.md` 에 이름을 갖는다.

### 3. 구현한다

레시피가 있으면 빈 파일이 아니라 레시피에서 시작한다. `prefers-reduced-motion` 과 hover 게이팅은
나중이 아니라 이때 함께 넣는다.

**완료 판정:** 애니메이션되는 속성이 `transform` 과 `opacity` 뿐이다. 예외(`clip-path`, 아코디언의
`height`)를 썼으면 왜 그것이어야 했는지 한 줄로 남긴다.

### 4. 자체 검사한다

바꾼 파일에만 돌린다.

```bash
rg -n "transition:\s*all|scale\(0\)|ease-in[^-]|transform-origin:\s*center" <바꾼 경로>
```

걸린 줄마다 판정한다 — 모달의 `transform-origin: center` 는 정상이고, 트리거에 붙은 팝오버의
같은 값은 결함이다.

**완료 판정:** 검출 0건이거나, 남은 건마다 정상인 이유가 한 줄씩 적혀 있다.

### 5. 판정할 수 없는 것을 밝힌다

코드만 보고 정할 수 없는 것이 있다 — 크로스페이드의 자연스러움, 스프링의 튐 정도, 목록이 들어올 때
투명도와 높이의 균형. 이런 것은 추측해서 값을 박지 말고 **무엇을 어떻게 확인해야 하는지**를 남긴다.
느린 재생(2~5배), 프레임 단위 확인, 제스처는 실기기, 다음 날 다시 보기.

**완료 판정:** 핸드오프의 `verification` 에 돌린 검사와 결과가 들어갔고, 확인이 필요한 항목은
`blocked_on` 이 아니라 사람이 볼 목록으로 남았다.

## 규칙

- **빈도 판정 없이 커브부터 고르지 마라.** 1단계가 2단계를 막는 관문이다.
  **이유:** 값을 먼저 고르면 그 값을 쓰기 위해 애니메이션을 정당화하게 된다. 판정 순서가 뒤집히면
  "넣지 않는다" 라는 결론이 나오지 않는다.
- **모션 규칙을 이 문서에 옮겨 적지 마라.** 표가 필요하면 사본을 열어 읽는다.
  **이유:** 사본이 개정되면 옮겨 적은 값만 낡는다. 두 값이 다를 때 어느 쪽이 맞는지 판정할 근거가 없다.
- **리뷰는 사본의 출력 형식을 그대로 쓴다.** `| Before | After | Why |` 표와 마지막 판정 한 줄.
  보고 문장은 한글로 쓰고, 코드·식별자·`cubic-bezier` 값은 원문 그대로 둔다.
