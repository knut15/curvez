조사의 산출물은 머릿속의 지식이 아니라 **검증 가능한 문서**다. 후행 에이전트는 브리프를 사실로 믿고
그 위에 아키텍처·구현·테스트를 쌓으므로, 링크 없는 한 줄이 팀 전체에서 가장 비싼 실패가 된다.
이 스킬은 그 한 줄이 들어갈 자리를 없앤다 — 모든 주장에 출처 URL 과 확인 날짜를 붙이고,
채우지 못한 칸은 `확인 불가` 로 남긴다.

**이 스킬이 브리프 문서 형식의 정본이다.** 섹션 구성·표의 열 순서·등급 표기는 아래 `## 브리프 형식` 이 정한다.
에이전트 정의(`agents/curvez-researcher.md`)는 역할·권한·통신 상대를 정하고, 형식은 이 스킬을 가리킨다.
**이유:** 같은 형식이 두 곳에 적히면 열 하나를 늘릴 때 한쪽만 고쳐지고, `## 검증 명령` 이 어느 쪽을
기준으로 세는지 판정할 근거가 사라진다. 형식과 검증 명령은 같은 문서에 있어야 서로 어긋나지 않는다.

## 언제 이 스킬을 쓰는가

- 라이브러리·프레임워크 후보를 비교해 선택지와 근거를 모을 때
- 특정 API 가 프로젝트가 쓰는 버전에서 실제로 되는지 확인할 때
- 버전 호환·peer 의존성·플랫폼 제약을 확정해야 할 때
- 다른 에이전트의 핸드오프 `blocked_on` 중 `who` 가 `curvez-researcher` 인 질문에 답할 때
- 아키텍처·디자인 결정 전에 전제로 깔 기술 사실이 필요할 때
- 이미 있는 브리프가 낡았는지(확인 날짜가 오래됐는지) 다시 확인할 때

## 언제 쓰지 않는가

- 기술 선택의 **최종 결정**·레이어 경계 확정 → `architecture-setup` 을 쓴다. 조사는 선택지와 근거까지다
- 구현 중에 모르는 API 를 만났을 때 → 스스로 조사해 우회하지 말고 `agent-contract` 의 `blocked_on` 에 질문으로 올린다
- `.curvez/profile.json` 이 없어 기준 버전을 세울 수 없을 때 → `bootstrap` 이 먼저다
- 품질 게이트가 뱉은 에러의 원인 추적 → `quality-gate` 를 쓴다. 이건 조사가 아니라 진단이다
- 화면·컴포넌트 스펙 작성 → `wireframe-spec` 을 쓴다. 플랫폼 제약 **사실 확인**까지만 이 스킬이다

**이유:** 조사자가 결정까지 하면 자기 조사 범위 안에서만 답을 찾고, 조사에서 빠진 선택지는
검토 대상에조차 오르지 못한다. 조사와 결정을 분리해야 결정자가 "이 조사가 충분한가" 를 따질 수 있다.
구현 중 조사도 마찬가지다 — 구현자가 조사를 겸하면 근거가 코드에만 남고 브리프에 남지 않는다.

## 절차

### 1. 기준 버전을 먼저 고정한다

조사 질문에 손대기 전에 **프로젝트가 실제로 쓰는 버전**을 읽는다.

```bash
TODAY=$(date +%F)                       # 확인 날짜. 추측하지 말고 여기서 얻는다
test -f .curvez/profile.json || echo "BLOCKED: profile.json 없음"
```

`.curvez/profile.json` 의 `stack` 과 `package.json` / lockfile / `.nvmrc` 에서 관련 패키지 버전을 읽어
브리프 머리말 `기준 버전` 에 **패키지명@버전 + 읽은 파일 경로**로 적는다.

**버전을 못 읽었으면 조사를 시작하되 모든 버전 의존 주장을 `확인 불가(프로젝트 버전 미상)` 로 남긴다.**
**이유:** 버전을 모르는 상태에서 시작한 조사는 최신 문서만 보게 되고, 결과 전체가 프로젝트에 안 맞을 수 있다.
프레임워크 API 는 메이저 사이에서 조용히 바뀐다. 버전 없는 사실은 사실이 아니다.

`TODAY` 를 셸에서 얻는 이유도 같다 — 확인 날짜는 브리프의 유효기간을 판정하는 유일한 근거인데,
기억으로 적은 날짜는 세션마다 어긋나 유효기간 판정 자체를 무의미하게 만든다.

### 2. 조사 질문을 한 줄로 확정한다

답이 `예/아니오` 또는 `목록` 으로 떨어지는 한 문장으로 줄인다. 줄지 않으면 질문을 쪼갠다.

질문이 모호해 답이 두 갈래로 갈리고 **결과가 크게 달라지면** 조사하지 말고 `status: blocked` 로
`blocked_on` 에 올린다. 갈래가 비슷하면 넓은 쪽을 조사하고 `decisions` 에 `reversible_at` 을 남긴다.

### 3. 출처를 등급으로 분류하며 모은다

`## 출처 등급` 표대로 A/B/C 를 매긴다. **매기지 않은 출처는 브리프에 넣지 마라.**
**이유:** 등급 없는 행은 `## 검증 명령` 이 세지 못하고, 나중에 읽는 사람이 블로그와 공식 문서를
같은 무게로 읽는다.

검색은 A 출처로 가는 통로일 뿐이다. C 등급 글에서 답을 봤어도, **그 글이 인용한 A 출처를 직접 열어**
같은 내용이 있는지 확인한 뒤에 그 A 출처의 URL 을 적는다.

### 4. 모순을 해결한다

출처끼리 다르면 `## 모순 처리` 의 tie-break 를 순서대로 적용하고, 결과를 `## 모순과 선택` 표에 남긴다.
버린 쪽 URL 을 반드시 함께 적는다. **한쪽을 조용히 지우지 마라.**
**이유:** 모순을 숨기면 나중에 반대쪽 출처를 본 사람이 조사 전체를 불신하고 처음부터 다시 한다.

### 5. 브리프를 쓴다

`.curvez/research/<주제>.md` 에 `## 브리프 형식` 그대로 쓴다. `<주제>` 는 소문자 kebab-case.

같은 주제를 다시 조사할 때는 기존 파일을 고치지 않고 `<주제>-v2.md` 로 새로 쓴다.
**이유:** `retrospective` 가 조사 이력을 시간순으로 재구성한다. 덮어쓰면 언제 무엇이 바뀌었는지 복원할 수 없다.

기술 선택형(후보를 고르는) 조사라면 [references/option-comparison.md](references/option-comparison.md) 를 읽고
`## 선택지 비교` 를 채운다. 사실 확인형 조사라면 그 섹션은 비운 채 둔다.

### 6. 검증 명령을 돌린다

`## 검증 명령` 을 그대로 실행하고 **출력 수치를 핸드오프 `verification` 에 그대로 옮긴다.**
기준을 못 넘으면 `status` 를 `done` 으로 올리지 말고 `partial` 로 낮춘다.

### 7. 핸드오프를 쓴다

`agent-contract` 스키마대로 `.curvez/handoff/curvez-researcher.<YYYYMMDD-HHmmss>.json` 에 쓴다.
`artifacts[].kind` 는 `research`. `summary` 에는 결론이 아니라 **답한 질문과 `확인 불가` 개수**를 적는다.
**이유:** `summary` 만 읽고 진행하는 수신자를 막을 수 없으므로, `summary` 자체가 "브리프를 읽어야 한다" 는
신호여야 한다. 결론을 요약해 두면 조건절이 탈락한 채로 전파된다.

## 출처 등급

| 등급      | 출처                                                                                                                              | 취급                                              |
| --------- | --------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------- |
| A (1차)   | 공식 문서, 저장소 소스 코드, 릴리스 노트·CHANGELOG, RFC·표준 스펙, 공식 타입 정의, `package.json` 의 `engines`·`peerDependencies` | 근거로 인용한다                                   |
| B (준1차) | 공식 저장소의 이슈·PR 논의, 메인테이너가 직접 쓴 글                                                                               | 인용하되 A 로 뒷받침한다. A 가 없으면 `확인 불가` |
| C (2차)   | 블로그, 튜토리얼, Stack Overflow, AI 요약글, 뉴스                                                                                 | A 를 찾는 **단서로만** 쓴다                       |

**C 등급을 `## 확인된 사실` 의 근거로 인용하지 마라.**
**이유:** 2차 출처는 작성 시점의 버전이 명시되지 않는 경우가 대부분이고, 원문의 조건절이 요약 과정에서
탈락한다. "된다" 로 적힌 것이 원문에서는 "실험 플래그를 켜면 된다" 인 일이 반복해서 생긴다.
잘못된 사실 하나가 그 위에 쌓인 설계 전체를 무효로 만든다.

**C 를 봤다면 숨기지 말고 `## 조사 경로` 에 남긴다** — 어떤 글을 단서로 봤고 거기서 어떤 A 출처에
도달했는지 적는다. 숨기면 다음 사람이 같은 검색을 처음부터 반복한다.

## 확인 불가는 확인 불가로 남긴다

찾지 못한 것을 그럴듯하게 채우지 마라. 네 가지를 전부 한다.

1. `## 확인 불가` 표에 행을 추가한다
2. **왜** 확인 불가인지 적는다 — 문서에 없음 / 유료 문서 / 접근 실패(403·타임아웃·robots) / 버전 불일치 / 조사 상한 도달
3. **어디까지** 확인됐는지 적는다 (예: `v14.2 까지는 Y 로 동작 (URL)`)
4. 핸드오프 `blocked_on` 에 `{ "question": "...", "who": "..." }` 로 1:1 로 올린다

**이유:** 후행 에이전트는 브리프를 사실로 믿고 그 위에 설계와 코드를 쌓는다. 추측 한 줄이 사실처럼
적히면 그것을 전제로 한 아키텍처·구현·테스트가 전부 무효가 되고, 어디서 틀렸는지 역추적할 근거조차 사라진다.
`확인 불가` 는 실패가 아니라 정상 산출물이다. 조사 결과가 "이 방식은 불가능하다" 로 나온 것도 마찬가지로
정상 산출물이고, 근거 URL 을 붙이면 `status: done` 이다.

## 조사 상한

| 항목                                                    | 상한 |
| ------------------------------------------------------- | ---- |
| 질문 1개당 인용하는 A 등급 출처                         | 5개  |
| 브리프 1개당 웹 도구 호출 (`WebSearch` + `WebFetch` 합) | 30회 |
| 미해결 질문 1개당 검색어를 바꾼 재시도                  | 3회  |
| 같은 URL 의 `WebFetch` 재시도                           | 2회  |

호출할 때마다 세고, 최종 횟수를 `## 조사 경로` 에 `24/30` 형식으로 적는다.

**상한에 걸리면 그 자리에서 멈추고 `확인 불가(조사 상한 도달)` 로 남긴 뒤 `status: partial` 로 보고한다.
상한을 조용히 늘리지 마라.**
**이유:** 조사는 상한이 없으면 끝나지 않는다. 출처를 6개째 읽어도 결론이 안 바뀌면 5개째에서 이미
답이 나온 것이고, 그 뒤는 후행 에이전트를 기다리게 만드는 비용일 뿐이다. 상한을 늘려도 되는 유일한 경우는
오케스트레이터가 명시적으로 재호출할 때이고, 그때는 새 브리프(`-v2`)로 쓴다.

## 모순 처리

출처가 서로 다를 때 위에서부터 순서대로 적용한다. 먼저 걸리는 규칙이 이긴다.

| #   | 상황                                | tie-break                                                                                       |
| --- | ----------------------------------- | ----------------------------------------------------------------------------------------------- |
| 1   | 등급이 다르다                       | 등급이 높은 쪽(A > B > C)                                                                       |
| 2   | 공식 문서와 실제 소스 코드가 다르다 | **소스 코드.** 문서 URL 과 소스 URL 을 둘 다 남기고 `문서 미갱신` 이라고 적는다                 |
| 3   | 대상 버전이 다르다                  | 프로젝트 기준 버전에 가까운 쪽. 기준 버전 문서가 없으면 `확인 불가`                             |
| 4   | 등급·버전이 같고 날짜가 다르다      | 날짜가 최신인 쪽                                                                                |
| 5   | 위 넷으로 안 갈린다                 | **더 보수적인 쪽**(제약이 강한 쪽, "안 된다" 쪽). `decisions` 에 `reversible_at` 과 함께 남긴다 |

2번이 1번보다 아래인 이유는 소스 코드도 A 등급이기 때문이다 — 1번은 A 와 B·C 사이에서만 갈린다.
5번에서 보수적인 쪽을 택하는 **이유:** 조사 단계에서 낙관적으로 판정하면 구현 단계에서 막힌다.
구현 중의 되돌리기가 조사 중의 재확인보다 훨씬 비싸다. 멈추지 말고 하나를 택하되 되돌릴 위치를 남긴다.

조사 결과가 앞선 에이전트의 결정을 뒤집을 때는 조용히 뒤집지 않는다. 사실과 URL 만 브리프에 적고
`blocked_on` 에 이의를 올려 `curvez-orchestrator` 에게 돌린다.

## 브리프 형식

**이 블록이 형식의 정본이다.** 머리말 4항목과 `##` 섹션 4개는 필수고, `## 선택지 비교` 는 기술 선택형일 때만 채운다.
표의 열 순서를 바꾸지 마라. **이유:** `## 검증 명령` 이 첫 열의 번호와 열 안의 문자열로 행을 세므로,
열이 밀리면 검증이 통과한 것처럼 보이면서 아무것도 검사하지 않는다.

```markdown
# <주제>

- **조사 질문:** <답해야 할 질문. 한 줄>
- **조사 일자:** YYYY-MM-DD
- **기준 버전:** <패키지명@버전 목록. 확인한 근거 파일 경로>
- **결론 한 줄:** <질문에 대한 답. 확정할 수 없으면 "확정 불가" 와 이유>

## 확인된 사실

| #   | 주장                                | 출처 URL                    | 등급 | 확인 날짜  | 대상 버전 |
| --- | ----------------------------------- | --------------------------- | ---- | ---------- | --------- |
| 1   | RSC 안에서 `useState` 를 쓸 수 없다 | https://nextjs.org/docs/... | A    | 2026-08-16 | next@15.1 |

## 확인 불가

| #   | 확인하려던 것 | 왜 확인 불가인가                         | 어디까지 확인됐나            |
| --- | ------------- | ---------------------------------------- | ---------------------------- |
| 1   | v15 의 X 동작 | 릴리스 노트·문서·소스 어디에도 언급 없음 | v14.2 까지는 Y 로 동작 (URL) |

## 모순과 선택

| 쟁점 | 택한 쪽 (URL) | 버린 쪽 (URL) | 근거 |
| ---- | ------------- | ------------- | ---- |

## 선택지 비교

| 후보 | 근거 URL | 제약 | 프로젝트 버전과의 적합성 |
| ---- | -------- | ---- | ------------------------ |

## 조사 경로

- 단서로 본 C 등급 글과 거기서 도달한 A 출처
- 검색어 목록
- 웹 도구 호출 횟수: 24/30
```

- 첫 열 `#` 은 1부터의 정수다. 검증 명령이 이 번호로 데이터 행을 식별한다
- `등급` 열에는 `A` `B` `C` 중 하나만 쓴다
- `확인 날짜` 는 1단계에서 얻은 `$TODAY` 값이다
- 표에 채울 행이 없으면 헤더만 남긴다. 섹션 자체를 지우지 마라 — 검증 명령이 섹션 개수를 센다

## 검증 명령

브리프를 쓴 직후 실행한다. `<주제>` 를 실제 파일명으로 바꾼다.

```bash
BRIEF=".curvez/research/<주제>.md"
test -f "$BRIEF" || { echo "FAIL: 브리프 없음"; exit 1; }
FACTS="${TMPDIR:-/tmp}/curvez-facts.$$"

# `## 확인된 사실` 섹션의 데이터 행만 뽑는다 (다른 표의 번호 행이 섞이지 않게 섹션을 먼저 자른다)
awk '/^## 확인된 사실/{f=1;next} /^## /{f=0} f' "$BRIEF" \
  | grep -E '^\|[[:space:]]*[0-9]+[[:space:]]*\|' > "$FACTS"

echo "행수:      $(grep -c . "$FACTS")"
echo "URL없음:   $(grep -vcE 'https?://' "$FACTS")"
echo "날짜없음:  $(grep -vcE '[0-9]{4}-[0-9]{2}-[0-9]{2}' "$FACTS")"
echo "C등급인용: $(grep -cE '\|[[:space:]]*C[[:space:]]*\|' "$FACTS")"
echo "섹션:      $(grep -cE '^## (확인된 사실|확인 불가|모순과 선택|선택지 비교|조사 경로)' "$BRIEF")"
echo "머리말:    $(grep -cE '^- \*\*(조사 질문|조사 일자|기준 버전|결론 한 줄):\*\*' "$BRIEF")"
echo "확인불가:  $(awk '/^## 확인 불가/{f=1;next} /^## /{f=0} f' "$BRIEF" | grep -cE '^\|[[:space:]]*[0-9]+[[:space:]]*\|')"
rm -f "$FACTS"

# 핸드오프의 blocked_on 개수 — 위 `확인불가` 수치와 같아야 한다
HANDOFF=$(ls -t .curvez/handoff/curvez-researcher.*.json 2>/dev/null | head -1)
[ -n "$HANDOFF" ] && node -e 'const j=JSON.parse(require("fs").readFileSync(process.argv[1],"utf8"));console.log("blocked_on:",j.blocked_on.length)' "$HANDOFF"
node "$CLAUDE_PLUGIN_ROOT/scripts/validate-handoff.mjs" .curvez/handoff/
```

`grep -c` 는 0건일 때 종료 코드 1을 낸다. `set -e` 아래에서 돌리면 첫 0에서 스크립트가 죽으므로
위 블록을 `set -e` 로 감싸지 마라. **이유:** 검증이 죽은 것과 통과한 것을 출력만 보고 구분할 수 없게 된다.

## 완료 기준

- [ ] `URL없음` 이 `0` — 출처 URL 없는 주장 0건
- [ ] `날짜없음` 이 `0` — 확인 날짜 없는 주장 0건
- [ ] `C등급인용` 이 `0` — C 등급을 근거로 인용한 주장 0건
- [ ] `섹션` 이 `5`, `머리말` 이 `4` — 필수 섹션·머리말 누락 0개
- [ ] `확인불가` 수치와 핸드오프 `blocked_on` 개수가 같다
- [ ] `행수` 가 `0` 이 아니거나, 0이라면 `## 확인 불가` 에 그 이유가 적혀 있다
- [ ] `## 조사 경로` 에 웹 도구 호출 횟수가 `N/30` 으로 적혀 있다
- [ ] `validate-handoff.mjs` 오류 0개
- [ ] 위 수치를 핸드오프 `verification` 에 명령과 함께 그대로 옮겼다

**하나라도 못 넘기면 `status` 를 `done` 으로 올리지 마라. `partial` 로 낮추고 실제 출력 수치를
`verification` 에 그대로 적는다.**
**이유:** 이 명령들의 출력이 곧 `verification` 의 내용이다. 여기가 비면 `done` 을 쓸 근거가 없고,
수신 에이전트는 검증되지 않은 `done` 을 검증된 것과 구분하지 못한다.
