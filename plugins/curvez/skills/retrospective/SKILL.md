회고의 산출물은 **규약 수정안**이다. 감상이 아니다.
독자는 사람이 아니라 다음 라운드의 에이전트이고, 에이전트는 회고 문서를 읽지 않고 자기 정의 파일과
스킬 문서만 읽는다. 그러므로 **어느 파일의 어느 섹션을 어떻게 고치는가**까지 나오지 않은 회고는
다음 라운드에서 아무것도 바꾸지 못한다.

주 사용 에이전트는 `curvez-retrospector` 다.

## 언제 이 스킬을 쓰는가

- 팀 실행 한 라운드가 끝나 무엇이 어긋났는지 정리할 때
- "회고", "돌아보자", "뭐가 문제였지", "retrospective" 라는 말이 나올 때
- 같은 지적·같은 막힘이 라운드를 넘어 반복돼 규약을 고쳐야 할 때
- 이전 회고의 액션 아이템이 또 재발했는지 판정할 때
- `curvez-retrospector` 를 띄울 때

## 언제 쓰지 않는가

- 중복·순환 의존·레이어 경계 위반 같은 **코드 구조** 문제를 찾을 때 → `structure-audit` 를 쓴다
- 타입체크·테스트·린트를 돌려 **동작이 되는지** 판정할 때 → `quality-gate` 를 쓴다
- 버그 하나의 원인을 추적할 때 → 회고가 아니라 진단이다. 재현·이분 탐색으로 원인을 좁히고,
  그 버그가 **여러 라운드에 걸쳐 반복됐을 때만** 회고 대상이 된다
- 핸드오프 파일 하나를 쓰거나 읽을 때 → `agent-contract` 를 쓴다
- 회고에서 나온 수정안을 **실제로 파일에 반영**할 때 → `authoring-agents` / `authoring-skills` 를 쓴다
- 개인 볼트에 노트를 남기는 것 자체가 목적일 때 → `note` 를 쓴다

**이유:** 회고는 "규약이 비었는가" 만 본다. 코드가 나쁜가(`structure-audit`), 동작하는가(`quality-gate`)는
증거의 종류가 다르다. 셋을 한 문서에 섞으면 규약 수정안이 코드 지적에 묻혀 아무도 규약을 고치지 않는다.

## 절차 (1) 증거를 모은다

### 1. 입력을 확인한다

| 경로 | 필수 | 없을 때 |
|---|---|---|
| `.curvez/profile.json` | O | `status: blocked` |
| `.curvez/handoff/*.json` | O | `status: blocked`. **회고 문서를 만들지 마라** |
| `docs/retro/*.md` (이전 회고) | X | 반복 항목 승격을 못 한다는 점을 `summary` 에 남기고 진행 |
| 지목할 규약 파일 | O | 실제로 열어 섹션이 있는지 확인한다. 못 열면 액션 아이템이 아니다 |

```bash
test -f .curvez/profile.json || echo "BLOCKED: profile.json 없음"
ls .curvez/handoff/*.json 2>/dev/null | wc -l   # 0 이면 BLOCKED
```

**증거가 없으면 회고를 쓰지 마라.**
**이유:** 증거 없는 회고는 의견문이다. 의견문이 규약 수정으로 이어지면 있지도 않았던 문제를 막는
규칙이 생기고, 그 규칙이 다음 라운드의 진짜 작업을 방해한다.

### 2. 날짜를 실제로 확인한다

```bash
date +%F              # 회고 파일명의 YYYY-MM-DD
date +%Y%m%d-%H%M%S   # 핸드오프 파일명의 timestamp
```

**추측한 날짜를 쓰지 마라.**
**이유:** 모델의 내부 날짜 감각은 세션마다 틀린다. 날짜가 틀리면 `docs/retro/` 의 시간순 정렬이 깨져
다음 회고가 "이전 라운드" 를 찾지 못하고, 반복 항목 승격 판정이 통째로 무력해진다.

### 3. 핸드오프를 시간순으로 전부 읽는다

파일명의 `<timestamp>` 가 정렬 키다. 요약본을 만들지 말고 원본을 연다.

```bash
ls -1 .curvez/handoff/*.json | sort
```

읽으면서 다음 신호만 뽑는다. 뽑은 것마다 **파일 경로를 함께 적는다.**

| 신호 | 무엇을 뜻하는가 |
|---|---|
| `status: blocked` | 실행이 멈춘 지점. `blocked_on[].question` 과 `who` 를 함께 본다 |
| `status: partial` | 남은 일이 다음 라운드로 넘어갔는지, 그대로 사라졌는지 |
| `verification` 이 비었거나 `result` 가 "통과"·"확인함" | 검증 없는 완료 선언 |
| 같은 `blocked_on.question` 이 여러 파일에 반복 | 반복 지적 |
| 뒤 핸드오프의 `decisions.what` 이 앞 결정을 뒤집음 | 조용한 결정 뒤집기 |
| 서로 다른 `from` 의 `artifacts[].path` 가 겹침 | 소유권 충돌 |
| `findings[]` 의 `kind` 가 여러 라운드에 반복 | 구조가 만든 지적 |
| `to` 가 비었거나 실재하지 않는 `name` | 라우팅 단절 |
| 타임스탬프 간격이 비정상적으로 긴 구간 | 대기·재작업 구간 |

```bash
# 검증 없는 done 후보 — 결과 경로를 그대로 증거로 쓴다
grep -l '"status"[[:space:]]*:[[:space:]]*"done"' .curvez/handoff/*.json
```

**로그에 없는 것은 `## 확인 불가` 에 남긴다. 기억·인상·추론으로 채우지 마라.**
**이유:** 회고의 유일한 권위는 증거다. 한 항목이라도 인상으로 쓰면 읽는 쪽은 어느 항목이 증거인지
구분할 수 없게 되고, 그 순간 회고 전체가 의견문으로 격하돼 아무도 규약을 고치지 않는다.
"확인 불가" 는 실패가 아니라 정상 산출물이다 — 다음 라운드에 무엇을 더 남겨야 하는지를 알려준다.

### 4. 반복될 것만 고른다

**반복될 것만 규약을 고친다. 한 번 일어난 일은 기록만 하고 액션 아이템으로 올리지 마라.**
**이유:** 일회성 사건마다 규칙을 하나씩 추가하면 규약이 부풀어 아무도 끝까지 읽지 않는다.
읽히지 않는 규약은 없는 규약과 같고, 그때부터는 정말 중요한 규칙까지 함께 무시된다.

판정 기준표는 `plugins/curvez/agents/curvez-retrospector.md` 의 `## 판단 기준` 이 정본이다.
요지는 셋이다 — **서로 다른 핸드오프 2건 이상에서 같은 원인**이면 반복,
**이전 회고에 같은 항목이 있으면** 반복이자 우선순위 승격,
**1건이라도 재발 시 되돌리기 불가**면 반복으로 취급한다.

**애매하면 일회성으로 판정한다.**
**이유:** 반복이 아닌 것을 규약에 올리는 비용은 영구적이고(규칙이 계속 읽힌다),
반복인 것을 놓치는 비용은 한 라운드다 — 재발하면 다음 회고가 승격한다. 비대칭이 명확하다.

## 절차 (2) 수정안을 낸다

### 5. 고칠 위치를 확정한다

각 관찰에 대해 **그 상황을 다루는 문장이 정의·스킬 문서에 있었나**를 실제 파일을 열어 확인한다.

| 확인 결과 | 판정 | 고치는 방식 |
|---|---|---|
| 그런 문장이 없다 | 규약의 공백 | 문장을 추가한다 |
| 있는데 적용 여부가 즉시 안 보인다 | 규약의 모호함 | 서술을 **조건문**으로 바꾼다 |
| 있고 명확한데 안 지켜졌다 | 규약의 무력함 | `## 품질 자체 검증` 에 **실행 가능한 명령**을 추가한다 |

**"규약은 충분했는데 지키지 않았다" 가 반복되면 문장을 한 번 더 쓰지 마라.**
**이유:** 지켜지지 않는 규칙에 같은 규칙을 다시 쓰는 것은 아무것도 바꾸지 않는다.
사람이 읽고 지키는 규칙과 기계가 잡는 규칙은 강제력이 다르다.

지목한 섹션이 실재하는지 그 자리에서 확인한다.

```bash
grep -n '^## 품질 자체 검증' plugins/curvez/agents/curvez-qa.md
```

**고칠 위치가 없는 항목은 액션 아이템이 아니다.** `## 어긋난 지점` 에만 남긴다.
**이유:** 고칠 파일과 섹션이 없는 항목은 아무도 실행할 수 없다. 실행 불가능한 항목이 섞이면
목록 전체가 "읽고 넘기는 것" 이 되고, 실행 가능한 항목까지 함께 방치된다.

어느 수준까지 구체적으로 써야 "고칠 위치" 로 인정되는지 판단이 서지 않으면
[references/action-item-examples.md](references/action-item-examples.md) 를 읽는다.

### 6. 우선순위를 매기고 7건으로 자른다

P0(잘못된 전제 전파) → P1(실행 중단) → P2(비용 증가) → P3(읽기 어려움).
등급 정의와 tie-break 규칙은 `plugins/curvez/agents/curvez-retrospector.md` 의 `## 판단 기준` 이 정본이다.

**액션 아이템 상한은 한 회고당 7건이다.** 넘으면 P0 → P1 순으로 7건까지만 올리고
나머지는 `## 이번엔 올리지 않은 것` 에 이유와 함께 남긴다.
**이유:** 액션 아이템 20건은 0건과 같다. 다음 라운드 전에 아무도 다 못 고치고,
못 고친 목록이 남으면 회고 자체가 신뢰를 잃는다.

### 7. 회고 문서를 쓴다

```
docs/retro/YYYY-MM-DD-<주제>.md
```

`<주제>` 는 소문자 kebab-case. 같은 날 두 번째 회고는 `<주제>-2` 로 이름을 바꾼다.
**덮어쓰지 마라. 이유:** 회고 이력 자체가 반복성 판정의 증거다. 덮어쓰면 "이전에도 지적했다" 를
증명할 수 없다.

**문서 골격(필수 섹션 6개와 표 형식)의 정본은
`plugins/curvez/agents/curvez-retrospector.md` 의 `## 입출력 프로토콜` 이다.** 그대로 따른다.

아래 액션 아이템 블록만 여기에 옮겨 둔다. **이 마커들은 8단계 검증 명령과
`curvez-orchestrator` 의 액션 아이템 수신 절차가 grep 으로 세는 대상이라 문자열이 고정이다.**

~~~markdown
### A1. <한 줄 제목>  — P0

- **무엇이 어긋났나:** <사실만>
- **증거:** `.curvez/handoff/<파일>.json`
- **왜 어긋났나:** <규약의 어느 부분이 비었는가>
- **고칠 위치:** `plugins/curvez/agents/curvez-qa.md` 의 `## 품질 자체 검증`
- **어떻게 고치나:** <추가·삭제·교체할 내용을 문장 수준으로>
- **우선순위:** P0
- **검증 방법:** <고친 뒤 무엇을 돌리면 고쳐졌다고 판정하나>
~~~

**`### A<n>.`, `- **고칠 위치:**`, `- **증거:**` 의 표기를 바꾸지 마라.**
**이유:** 세 문자열은 회고자의 자체 검증 명령과 오케스트레이터의 수신 절차가 동시에 grep 하는
파싱 앵커다. 한쪽만 표기를 바꾸면 검증은 0건을 세고 통과하고, 오케스트레이터는 액션 아이템을
하나도 못 찾은 채 "고칠 것 없음" 으로 라운드를 닫는다. 형식을 바꿔야 한다면 회고 문서가 아니라
`curvez-retrospector.md` 와 `curvez-orchestrator.md` 를 함께 고치는 액션 아이템으로 올린다.

### 8. 검증한다

```bash
RETRO="docs/retro/$(date +%F)-<주제>.md"

# 액션 아이템 수
A=$(grep -cE '^### A[0-9]+\.' "$RETRO")

# 고칠 위치가 붙은 항목 수 → A 와 같아야 한다
W=$(grep -cE '^- \*\*고칠 위치:\*\*' "$RETRO")

# 증거가 붙은 항목 수 → A 와 같아야 한다
E=$(grep -cE '^- \*\*증거:\*\*' "$RETRO")

# 지목한 규약 파일이 실재하는지 → 0 이어야 한다
M=$(grep -E '^- \*\*고칠 위치:\*\*' "$RETRO" | grep -oE '`[^`]+\.md`' | tr -d '`' \
  | sort -u | while read -r p; do test -f "$p" || echo "MISSING $p"; done | wc -l | tr -d ' ')

# 증거로 든 핸드오프가 실재하는지 → 0 이어야 한다
H=$(grep -hoE '`\.curvez/handoff/[^`]+\.json`' "$RETRO" | tr -d '`' \
  | sort -u | while read -r p; do test -f "$p" || echo "MISSING $p"; done | wc -l | tr -d ' ')

echo "액션=$A 고칠위치=$W 증거=$E 없는규약파일=$M 없는핸드오프=$H"
test "$A" -le 7 && test "$A" = "$W" && test "$A" = "$E" \
  && test "$M" -eq 0 && test "$H" -eq 0 && echo PASS || echo FAIL
```

필수 섹션 개수·실행 이력 행 수 대조를 포함한 전체 체크리스트는
`plugins/curvez/agents/curvez-retrospector.md` 의 `## 품질 자체 검증` 에 있다. 그것도 함께 돌린다.

**`FAIL` 이면 `status` 를 `done` 으로 올리지 마라.** `partial` 로 낮추고 위 `echo` 의 실제 수치를
`verification` 에 그대로 적는다.
**이유:** 증거와 고칠 위치가 붙지 않은 회고는 다음 라운드에 아무것도 바꾸지 못하므로,
그 상태의 `done` 은 사실이 아니다.

### 9. 핸드오프를 쓴다

`agent-contract` 스키마를 따른다. `artifacts[].kind` 는 `retro`, `to` 에 `curvez-orchestrator` 를 반드시 포함한다.
**액션 아이템은 `decisions` 가 아니라 `summary` + `artifacts` 로 전달한다.**
**이유:** `decisions` 는 "이 에이전트가 확정한 것" 을 뜻한다. 규약 수정은 아직 제안이므로
여기에 넣으면 후행 에이전트가 이미 반영된 규칙으로 오인한다.

## 범위 — 고치지 않고 반출도 기본이 아니다

**직접 고치지 않는다. 수정안까지가 이 스킬의 범위다.**
실제 편집은 `curvez-orchestrator` 가 사용자 승인을 받아 `authoring-agents` / `authoring-skills` 로 한다.
**이유:** 회고 도중에 정의가 바뀌면 이번 라운드의 증거(핸드오프)와 정의가 어긋나
"그때 정의가 무엇이었나" 를 복원할 수 없게 된다.

**Obsidian 반출은 옵션이다.** 사용자가 "옵시디언에 정리해줘", "vault 에 넣어줘", "노트로 남겨줘" 라고
명시적으로 말했을 때만 `note` 스킬을 호출한다. 그 경우에도 `docs/retro/` 의 원본을 **먼저 쓰고**
반출은 복사본이다.
**이유:** 프로젝트 지식은 프로젝트에 남아야 다음 담당자가 찾는다. 개인 볼트로만 나가면
저장소를 클론한 사람은 그 회고의 존재조차 모르고, 규약을 고친 근거가 저장소에서 사라진다.

## 쓰지 않을 문장

산출물은 규약 수정안이다. 아래는 회고 문서에 넣지 마라.

| 넣지 않는다 | 대신 |
|---|---|
| "소통이 부족했다", "다음엔 더 꼼꼼히" | 어느 파일의 어느 섹션에 어떤 조건문을 넣을지 |
| "A 가 실수했다" | 그 상황을 다루는 문장이 규약에 있었는지 |
| "전반적으로 잘 진행됐다" | 삭제. 판정에 쓰이지 않는다 |
| "앞으로 주의하자" | 기계가 잡을 검증 명령 |

**이유:** 감상은 다음 라운드의 정의 파일로 옮겨지지 않는다. 옮겨지지 않는 문장은 읽히지 않고,
읽히지 않으면 다음 라운드는 이번 라운드와 정확히 같은 방식으로 실패한다.
개인 평가를 쓰지 않는 이유는 하나 더 있다 — 누가 못했는지가 적히는 순간 다음 라운드의 핸드오프는
방어적으로 쓰이고, 회고의 유일한 증거원인 로그가 오염된다.
