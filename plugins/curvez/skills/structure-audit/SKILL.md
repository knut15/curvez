구조 감사는 **한 파일만 봐서는 안 보이는 것**을 본다. 파일 사이의 관계다.
이 스킬은 그 관계를 기계적으로 세는 절차와, 센 결과 위에 얹는 판정 기준의 정본이다.
주 사용 에이전트는 `curvez-structure-reviewer` 지만, 구현 에이전트가 자기 변경을 자가 점검할 때도 같은 기준을 쓴다.

## 언제 이 스킬을 쓰는가

- 구현이 끝나 리뷰 라운드에 들어갈 때 (`curvez-reviewer` 와 병렬)
- 중복 코드를 추출할지 남길지 정해야 할 때
- 순환 의존이 의심되거나 import 가 꼬였을 때
- `.curvez/architecture.md` 의 금지 import·의존 방향이 실제로 지켜지는지 셀 때
- 파일이 비대해져 어디를 쪼갤지 정해야 할 때
- 구현 에이전트가 자기 변경분의 구조 영향을 자가 점검할 때

## 언제 쓰지 않는가

- 타입체크·린트·테스트를 돌려 **동작**을 판정할 때 → `quality-gate` 를 쓴다
- 레이어·의존 방향·금지 import 를 **새로 정하거나 고칠 때** → `architecture-setup` 을 쓴다.
  이 스킬은 정해진 규칙에 비춰 위반을 셀 뿐이다
- 지적을 실제로 **고칠 때** → `nextjs-implementation` / `react-native-implementation` 을 쓴다
- 핸드오프 JSON 의 필드·상태 규칙을 확인할 때 → `agent-contract` 를 쓴다
- 라운드를 넘겨 반복되는 패턴을 회고할 때 → `retrospective` 를 쓴다

**이유:** 구조 감사는 "여기 있어도 되는가"만 본다. 동작의 정확성까지 같이 보면 항상 정확성이 이긴다.
버그 하나가 눈에 띄는 순간 구조 검사를 멈추고 그쪽으로 끌려가고, 그러면 구조 지적이 매 실행마다 달라진다.

## 절차

### 1. 대상 경로를 확정한다

`.curvez/profile.json` 의 `paths.*` 에서 읽는다. **경로를 추측해 스캔하지 마라.**
**이유:** 엉뚱한 트리를 스캔한 지적은 전부 폐기해야 하는데, 폐기해야 한다는 사실 자체를 나중에 알아채기 어렵다.

| 상황 | 행동 |
|---|---|
| `profile.json` 이 없다 | `status: blocked`. `blocked_on` 에 `{ "question": "profile 이 없다. curvez:bootstrap 을 먼저 실행해야 한다", "who": "user" }`. 검사를 시작하지 않는다 |
| `architecture.md` 가 없다 | 경계 위반 판정만 건너뛴다. 중복·순환·위치는 그대로 검사하고 `status: partial` |
| 구현 핸드오프가 없다 | 변경 범위를 모르므로 **전수 검사**로 전환하고 그 사실을 `summary` 에 적는다 |

`stack` 이 `monorepo` 면 `paths.web` `paths.mobile` `paths.domain` 을 각각 따로 돌린다.

### 2. 기계적 검출을 먼저 돌린다

**눈으로 훑어 찾은 결과를 보고하지 마라. 명령을 먼저 돌리고, 그 출력 위에서만 판단한다.**

**이유:** 눈으로 찾은 중복은 재현되지 않는다. 같은 코드베이스를 다음 주에 다시 보면 다른 목록이 나오고,
그러면 "지난번엔 지적 안 했잖아"가 되어 지적 자체의 권위가 사라진다. 명령은 같은 입력에 같은 출력을 낸다.
판단이 갈릴 수는 있어도 **목록이 갈리면 안 된다.**
또 하나 — 기계적 출력이 있어야 `findings[].evidence` 에 명령과 실제 출력을 붙일 수 있고,
그래야 구현 에이전트가 지적을 재현해 확인한다. 증거 없는 지적은 취향으로 읽히고 무시된다.

순서를 지킨다. 앞 단계의 출력이 뒤 단계의 입력이다.

| # | 검출 | 산출물 |
|---|---|---|
| 1 | 파일 크기 (400줄 / 이름별 200줄 초과) | 비대 파일 목록 — 중복의 선행 지표 |
| 2 | 중복 블록 (정규화 후 연속 창) | `N줄 x 파일M곳` 후보 목록 |
| 3 | 순환 의존 (상대 import 그래프 + DFS) | 사이클 목록, 타입 전용 표시 |
| 4 | 경계 위반 (`## 금지 import` 표 파싱 후 grep) | 규칙 ID 별 위반 건수와 위치 |
| 5 | git 공변경률 | 중복 후보 쌍의 함께 바뀐 비율 |

**명령 전문은 [references/detection-commands.md](references/detection-commands.md) 를 열어 그대로 복사해 실행한다.**
손으로 다시 쓰지 마라. **이유:** 정규화 규칙과 겹치는 창 병합이 조용히 빠지면 목록이 매번 달라진다.

여기까지 나온 목록에 대해서**만** 3~6단계 판정을 얹는다. 목록에 없는 것을 지적에 추가하지 마라.

### 3. 중복을 판정한다

2단계 출력의 `N줄 x 파일M곳` 을 아래 표에 그대로 넣는다. → `## 중복 판정`

### 4. 순환과 경계를 판정한다

사이클마다 끊을 간선과 방향을 정한다. → `## 순환 의존`
금지 import 표의 위반 건수를 규칙 ID 별로 묶는다. → `## 경계 위반`

### 5. 위치를 판정한다

비대 파일과 `shared/` `utils/` 아래 파일의 실제 사용처를 센다. → `## 파일 위치`

### 6. 우선순위를 매기고 자른다

영향 범위로 `P0`~`P3` 를 매기고 최우선 목록을 상한까지 자른다. → `## 우선순위`

### 7. `findings[]` 로 반환한다

파일을 쓰지 않는다. 응답 텍스트가 곧 핸드오프 JSON 이다. → `## 출력`

## 중복 판정

정규화(공백 축약, import·주석·괄호만 있는 줄 제외) 기준이다. 2단계 명령이 이미 정규화해 센다.

| 조건 | 판정 |
|---|---|
| 연속 5줄 이상이 서로 다른 파일 **3곳 이상**에서 반복 | 추출 후보 |
| 연속 **20줄 이상**이 서로 다른 파일 2곳에서 반복 | 추출 후보 |
| 연속 5줄 이상이 파일 2곳에서만 반복 | 후보 아님. `priority: P3` 로 기록만 |
| 4줄 이하, 또는 한 줄짜리 표현식·타입 별칭 | 보고하지 않는다 |
| 같은 파일 안에서의 반복 | 보고하되 우선순위를 한 단계 낮춘다 |
| 테스트 코드의 반복 | 보고하지 않는다 |

**5줄·3곳의 근거:** 추출에는 고정 비용이 든다 — 새 모듈 하나, import 몇 줄, 그리고 그 모듈이 어느
레이어에 속하는지에 대한 판단 하나. 반복 2회는 그 비용을 못 넘고, 우연히 닮았을 확률도 가장 높은
구간이다. 세 번째 반복이 나타나야 "이 패턴은 앞으로도 늘어난다"는 증거가 생긴다.
20줄 예외를 둔 근거는 분량이 커지면 한쪽만 고치고 다른 쪽을 잊는 사고가 실제로 나기 때문이다 —
5줄짜리는 눈에 들어오지만 20줄짜리는 들어오지 않는다.

**테스트 코드를 빼는 이유:** 테스트의 반복은 대개 의도된 것이다. 셋업을 공용 헬퍼로 뽑으면 그 테스트가
무엇을 전제하는지 읽히지 않게 되고, 테스트의 가치인 "독립적으로 읽힘"이 사라진다.

### 성급한 추상화 — 중복을 남겨야 할 때

**후보로 잡혔다고 전부 추출 대상이 아니다.** 3문 판정을 거친다.

| # | 질문 | 확인 방법 |
|---|---|---|
| 1 | 두 코드가 **함께 변해 왔는가** | git 공변경률 50% 이상이면 예. 등장 커밋 3건 미만이면 판정 불가로 두고 2·3번만 쓴다 |
| 2 | 두 코드가 **같은 이유로** 존재하는가 | 형태가 아니라 이유를 본다. "합계를 낸다"가 아니라 "주문 금액 정책을 적용한다"인지 |
| 3 | **플래그 없이** 합칠 수 있는가 | 합치는 순간 `mode` / boolean 파라미터가 필요하면 아니오 |

**"아니오"가 2개 이상이면 중복을 남긴다.** 추출하지 않는다고 `findings` 에 `move_to: "이동하지 않는다"`
로 기록하고, 그 판단을 `decisions` 에 `reversible_at: "findings[<id>]"` 와 함께 남긴다.

**이유:** 지금 닮았지만 서로 다른 이유로 변하는 코드를 합치면, 다음 요구사항이 왔을 때 한쪽만 바꿔야
하는데 공용 모듈이라 못 바꾼다. 그때 나오는 것이 플래그 파라미터고, 플래그가 둘이 되면 분기 네 갈래가
한 함수 안에 생긴다. **잘못 합친 것을 다시 떼는 비용이 중복 두 벌을 유지하는 비용보다 항상 크다.**
중복은 눈에 보이지만 잘못된 결합은 안 보이기 때문이다.

### 레이어가 다른 중복은 추출하지 않는다

도메인의 계산과 UI 의 표시 계산이 우연히 같은 것은 **기본적으로 추출 금지**다.

**이유:** 추출하려면 공용 모듈이 생기고 양쪽이 그것을 의존해야 하는데, 그 순간 둘 중 한 방향은
반드시 의존 방향 규칙을 거스른다. 즉 중복 하나를 없애려고 경계 위반 하나를 새로 만드는 거래다.
경계 위반은 `P0` 이고 2곳 중복은 `P3` 다 — 절대 남는 거래가 아니다.
게다가 레이어가 다르다는 것은 두 코드가 **다른 이유로 변한다**는 가장 강한 증거다.

예외는 하나다. 추출 대상이 **양쪽 레이어보다 안쪽**(순수 함수·상수·타입)이고, 그 위치가
`architecture.md` 의 의존 방향에서 두 레이어 모두의 하류일 때. 이때는 `move_to` 에 그 경로와
"의존 방향을 거스르지 않는다"는 근거를 함께 적는다.

## 순환 의존

**검출:** 2단계 3번 명령이 전수 검사한다. 타입 전용 순환(`[타입 전용]` 표시)도 보고한다.
런타임 사이클은 아니지만 모듈 경계가 잘못 그어졌다는 같은 신호이기 때문이다. 다만 우선순위를 한 단계 낮춘다.

**끊는 방향:** 아래 순서로 시도하고 먼저 성립하는 것을 `move_to` 에 적는다.

| # | 방법 | 쓰는 때 |
|---|---|---|
| 1 | **안쪽 → 바깥쪽 간선을 끊는다.** 저수준·도메인이 고수준·UI 를 참조하는 쪽이 항상 잘못이다 | 사이클의 두 끝이 다른 레이어 |
| 2 | 공통으로 쓰는 타입·상수를 제3 모듈로 추출하고 양쪽이 그것을 본다 | 서로 상대의 타입만 필요로 함 |
| 3 | 인터페이스를 안쪽에 두고 구현을 바깥에서 주입한다 (의존성 역전) | 안쪽이 바깥의 **동작**을 실제로 필요로 함 |
| 4 | 두 모듈을 하나로 합친다 | 위 셋이 전부 억지스럽다. 애초에 한 개념이었다는 뜻 |

**어느 간선을 끊을지 갈리면, 사이클 안에서 참조 수가 가장 적은 간선을 끊는다.**
**이유:** 끊는 비용은 그 간선에 딸린 호출 지점 수에 비례한다. 방향 규칙으로 안 갈리는 사이클은
어차피 같은 레이어 안의 문제이므로, 남는 기준은 비용뿐이다.

검출 명령은 상대 경로 import 만 본다. `@/` 별칭을 쓰는 코드베이스에서 사이클 0건이 나오면
**"순환 없음"이 아니라 "이 방법으로는 못 봤다"** 로 `summary` 에 적는다.

## 경계 위반

**판정 기준은 `.curvez/architecture.md` 의 `## 의존 방향` 과 `## 금지 import`(`ARCH-NNN` 표)뿐이다.**
일반론("도메인은 순수해야 한다")으로 지적하지 마라.

**이유:** 이 감사가 규칙을 만들기 시작하면 `curvez-architect` 가 확정한 것과 두 개의 기준이 공존하고,
구현 에이전트는 어느 쪽을 따라야 하는지 알 수 없다. 규칙이 현실과 안 맞아 보이면 지적이 아니라
**이의**로 처리한다 (아래 표 마지막 줄).

| 상황 | 판단 |
|---|---|
| `ARCH-NNN` 금지 패턴에 걸린다 | 위반. 예외 없음. `kind: "boundary"`, `id` 에 규칙 ID 를 인용한다 |
| 의존 방향이 문서와 반대 (예: domain → ui) | 위반. 예외 없음 |
| 문서에 안 적힌 새 패턴 | 위반으로 세지 않는다. `kind: "placement"` 로 관찰만 남긴다 |
| 같은 규칙 위반이 파일 5개 이상에서 반복 | 개별 지적을 접고 **한 건으로 묶어** `curvez-architect` 에게 규칙 재검토 이의를 낸다 |
| 표를 한 줄도 파싱하지 못했다 | 위반 0건이 아니라 **판정 불가**. `blocked_on` 에 `who: "curvez-architect"` |

**5개 기준의 근거:** 한두 곳의 위반은 실수지만, 다섯 곳에서 같은 방향으로 새어 나갔다면 규칙이 현실을
못 담고 있는 것이다. 실수는 구현 에이전트가 고치고, 규칙 문제는 아키텍트가 고친다. 전자를 후자로
처리하면 다음 라운드에 같은 위반이 다시 생긴다.

`## 예외` 절에 명시된 항목은 위반으로 세지 않는다. 대신 예외 목록에 있다는 사실을 `evidence` 에 적는다.

## 파일 위치

| 신호 | 판단 | 옮길 방향 |
|---|---|---|
| 한 곳에서만 쓰는데 `shared/` · `common/` · `utils/` 에 있다 | 잘못된 위치 | 유일한 사용처 옆으로 |
| 3곳 이상에서 쓰는데 특정 feature 폴더 안에 있다 | 잘못된 위치 | 공용 레이어로 |
| 한 파일이 두 레이어의 책임을 갖는다 (도메인 규칙 + fetch) | 분리 대상 | 책임별로 각 레이어로 |
| 파일이 400줄을 넘는다 | 검사 대상 (그 자체로 위반은 아니다) | 검사 후 판정 |
| `utils.ts` · `helpers.ts` · `index.ts` 가 200줄을 넘는다 | 이름이 책임을 못 나타냄 | 개념별 모듈로 분리 |
| import 를 20개 이상 받는다 | 응집이 아니라 잡동사니일 가능성 | 검사 후 판정 |

**400줄 기준의 근거:** 절대적인 좋은 길이는 없다. 다만 400줄을 넘으면 사람이 한 번에 못 읽고,
그때부터 "이미 있는 함수"를 못 찾아 옆에 비슷한 것을 또 만든다. 즉 파일 크기는 그 자체가 문제가
아니라 **중복의 선행 지표**다. 그래서 위반이 아니라 검사 대상으로 둔다.

사용처를 세는 명령은 [references/detection-commands.md](references/detection-commands.md) 6번에 있다.
**세지 않고 "한 곳에서만 쓴다"고 적지 마라.** **이유:** 추정으로 옮기라고 하면 구현 에이전트가
옮긴 뒤에야 다른 사용처를 발견하고, 그 시점에는 되돌리는 것이 옮기는 것보다 비싸다.

## 우선순위

**발견한 것을 전부 같은 무게로 보고하지 마라.** 영향 범위로 매긴다.

| 등급 | 조건 | 처리 |
|---|---|---|
| `P0` | 순환 의존, 또는 `ARCH-NNN` 정면 위반 | 이번 라운드에 반드시 고친다 |
| `P1` | 영향 파일 4개 이상. 또는 3곳 이상 반복 중복 | 이번 라운드 권고 |
| `P2` | 영향 파일 2~3개 | 다음 라운드로 미뤄도 된다 |
| `P3` | 영향 파일 1개, 또는 판정이 갈린 것 | 기록만. 고치라고 요구하지 않는다 |

**최우선 목록(`P0` + `P1`)은 최대 5건까지만 낸다.** 넘으면 영향 범위가 큰 순으로 자르고,
잘린 것은 `P2` 로 내려 `findings` 에 남긴다. 지우지는 마라.

**이유:** 정리 항목이 30개면 아무것도 정리되지 않는다. 구현 에이전트는 목록 전체를 보고 어디부터
손댈지 판정할 컨텍스트가 없고, 결국 가장 쉬운 것 두어 개만 고치고 끝낸다. 그러면 실제로 위험한
순환 의존이 그대로 남는다. 5건은 한 라운드에서 실제로 닫을 수 있는 상한이다.

**순환 의존이 `P0` 인 근거:** 사이클은 시간이 갈수록 간선이 늘어난다. 이미 서로 참조하므로 새 참조를
추가하는 데 아무 저항이 없기 때문이다. 나중에 끊는 비용이 지금의 몇 배가 되는 유일한 항목이다.

### tie-break

위 규칙으로 갈리지 않으면 순서대로 적용한다.

1. **기계적 증거가 있는 쪽을 택한다.** 명령 출력이 뒷받침하지 못하는 지적은 버린다
2. `.curvez/architecture.md` 에 명시된 규칙이 일반 원칙을 이긴다
3. 그래도 갈리면 **"지금은 고치지 않는다"** 를 고른다. 중복을 남기고 `P3` 로 기록한다
   - **이유:** 잘못 합친 추상화를 되돌리는 비용이 중복을 한 라운드 더 유지하는 비용보다 크다.
     둘 다 틀릴 수 있다면 되돌리기 싼 쪽에서 틀려야 한다
4. 그래도 판단이 안 서면 `P2` 로 남기고 `blocked_on` 에 질문을 붙여 넘긴다. **멈추지 않는다**

## 출력

결과는 핸드오프 최상위 **`findings[]`** 에 담는다. 스키마 정본은 `agent-contract` 스킬과
`scripts/schema/handoff.schema.json` 이다. 여기서는 구조 감사가 그 필드를 **어떻게 채우는지**만 정한다.

| 필드 | 필수 | 구조 감사에서의 값 |
|---|---|---|
| `id` | O | `DUP-01` / `CYC-01` / `BND-01` / `PLC-01`. 경계 위반은 `BND-01(ARCH-002)` 처럼 규칙 ID 를 인용한다 |
| `kind` | O | `duplication` \| `cycle` \| `boundary` \| `placement` |
| `where` | O | `파일:줄`. 관련 지점이 여럿이면 문자열 배열 |
| `what` | O | **무엇이** 문제인가. 한 문장 |
| `why` | O | **왜** 문제인가. 이 지적의 근거 |
| `priority` | O(등급) | `P0` ~ `P3`. `severity` 는 `curvez-reviewer` 의 것이다 — 쓰지 마라 |
| `move_to` | 권장 | **어디로** 옮기는가. 경로와 방법. 남기기로 했으면 `"이동하지 않는다"` |
| `blast_radius` | 권장 | `{ "files": <숫자>, "list": [...] }`. 셀 수 없으면 추정임을 `why` 에 밝힌다 |
| `evidence` | 권장 | `{ "command": "...", "output": "..." }` — 실제로 돌린 명령과 그 출력 |

`severity` 와 `priority` 중 최소 하나가 필수다. 구조 감사는 **항상 `priority`** 를 쓴다.
**이유:** 오케스트레이터가 두 리뷰어의 결과를 합칠 때 등급 체계가 섞이면 정렬 기준이 사라진다.
축이 다르면 등급도 달라야 한다.

**파일을 쓰지 않는다.** `curvez-structure-reviewer` 는 읽기 전용이라 `.curvez/handoff/` 에 직접
기록하지 못한다. **최종 응답의 전체 텍스트를 핸드오프 JSON 하나로 반환하고, 앞뒤에 인사말·요약·설명을
붙이지 마라.** 파일 기록은 `curvez-orchestrator` 가 대신 한다.
**이유:** 텍스트에 서사가 섞이면 오케스트레이터가 JSON 구간을 잘라내야 하고, 자르는 규칙이 없으면 파싱이 깨진다.

`status` 는 **구조 문제 유무가 아니라 검사 완수 여부**로 정한다. `P0` 를 10건 찾아도 검사를 다 돌렸으면 `done` 이다.
**이유:** `status` 를 지적 유무로 쓰면 지적이 많은 라운드마다 `blocked` 가 되어, 오케스트레이터가
"검사가 안 끝난 것"과 "코드가 나쁜 것"을 구분하지 못한다.

## 고치지 않는다

정리 방안만 낸다. 실제 수정은 `curvez-nextjs` / `curvez-react-native` 가 한다.
`>`, `>>`, `tee`, `sed -i`, `mv`, `rm`, `git add`, `git commit` 으로 우회하지 마라.
검출 명령은 전부 stdout 으로만 결과를 내는 형태로 쓴다.

**이유 둘.** 첫째, 리뷰 대상과 주체가 섞이면 다음 리뷰의 기준점이 사라진다 — 무엇이 원래 코드였고
무엇이 리뷰어가 손댄 것인지 구분할 수 없게 된다. 둘째, 구조 감사는 소유 파일이 없어서 어떤
에이전트와도 병렬로 돌릴 수 있는데, 이 자유는 쓰기를 포기한 대가다. 셸로 한 번 우회하는 순간
병렬 안전성의 근거가 사라지고 오케스트레이터는 이 감사를 순차로 강등해야 한다.

`P0`·`P1` 을 제안할 때는 해당 경로에 회귀 테스트가 있는지 `curvez-qa` 에게 묻는다.
**이유:** 테스트 없는 구조 변경은 되돌릴 수 없다.

## 완료 기준

- [ ] `.curvez/profile.json` 에서 읽은 경로로 검출 명령 1~4번을 전부 돌렸다. 실행 실패 0건
      (실패했으면 재시도 2회 후 `verification` 에 오류 출력을 그대로 남기고 `status: partial`)
- [ ] 순환 검출이 보고한 사이클 수 == `kind: "cycle"` 항목 수 (누락 0건)
- [ ] 경계 위반 grep 의 합계 == `kind: "boundary"` 항목이 덮는 지점 수 (누락 0건)
- [ ] 중복 지적 전부가 3문 판정을 거쳤다. 추출하지 않기로 한 항목이 `decisions` 에 이유와 함께 있다
- [ ] `findings` 의 모든 항목에 `id` `kind` `where` `what` `why` `priority` 가 있다
- [ ] 기계적 증거가 없는 항목이 0건이다 (`evidence.command` 가 빈 항목을 지웠다)
- [ ] 최우선(`P0`+`P1`) 항목이 5건 이하다
- [ ] `status: done` 이면 `verification` 이 1건 이상이고 `blocked_on` 이 비어 있다
- [ ] 응답 텍스트 전체가 JSON 하나다. 앞뒤에 문장이 없다

반환 직전 `node "$CLAUDE_PLUGIN_ROOT/scripts/validate-handoff.mjs" <파일>` 로 검증한다.
읽기 전용이라 파일을 못 만들면 오케스트레이터가 대필한 뒤 검증하도록 `to` 에 명시한다.
