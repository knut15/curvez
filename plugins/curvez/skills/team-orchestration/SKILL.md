curvez 팀 실행의 절차서다. 주 사용 에이전트는 `curvez-orchestrator` 이고, **`Agent` 도구를 가진
유일한 에이전트**다. 워커는 격리된 컨텍스트에서 돌고 중간에 사람에게 되묻지 못하므로, 순서를
어기면 되돌릴 수 없는 지점에서 틀린 것이 드러난다.

판정 **수치와 근거**(팀 규모 상한, 재리뷰 루프 상한, 승인 예외, 소유권 표)는
`plugins/curvez/agents/curvez-orchestrator.md` 가 정본이다. 이 문서는 **순서와 완료 조건**만 정한다.
값이 필요할 때마다 그 파일의 해당 섹션을 열어 읽어라. 여기에 옮겨 적은 사본을 믿지 마라.
**이유:** 상한값이 두 곳에 있으면 하나를 고칠 때 다른 하나가 남아, 같은 실행에서 서로 다른 수를 말한다.

## 언제 이 스킬을 쓰는가

- 사용자가 "팀으로", "병렬로", "나눠서" 라고 하거나 역할 분배를 요청할 때
- 작업이 파일·모듈 여러 곳에 걸쳐 누가 무엇을 맡을지 정해야 할 때
- 구현과 검증을 같은 라운드에 굴릴 수 있는지 판정할 때
- 라운드가 끝나 `.curvez/handoff/` 를 수합하고 다음 라운드를 정할 때
- 리뷰 지적을 담당 구현자에게 되돌릴 때

## 언제 쓰지 않는가

- 프로젝트를 처음 세팅하고 `.curvez/profile.json` 을 만들 때 → `bootstrap` 을 쓴다
- 검증 명령만 돌려 수치를 뽑을 때 → `quality-gate` 를 쓴다
- 단일 파일·단일 관심사 작업 → 팀을 만들지 않는다. 플랫폼과 파일 범위가 이미 정해진 구현이면 `nextjs-implementation` / `react-native-implementation` 을 직접 쓴다
- 핸드오프 JSON 의 필드와 `status` 판정 → `agent-contract` 를 쓴다
- 에이전트 정의·스킬 문서를 고칠 때 → `authoring-agents` / `authoring-skills` 를 쓴다
- tmux 패널에 CLI 워커를 띄우는 팀 → curvez 가 아니다. `team-lead` 를 쓴다

**이유:** curvez 는 **Claude Code 내장 서브에이전트(`Agent` 도구)** 로만 병렬 실행한다. tmux 워커를
쓰지 않는다. 두 방식을 섞으면 워커가 어느 쪽 규약으로 핸드오프를 남기는지 갈리고, 수합 단계에서
파일이 있는 워커와 없는 워커가 뒤섞여 라운드 완료를 판정할 수 없게 된다.

## 절차

### 1. 입력을 확인하고 팀이 필요한지 판정한다

1. `.curvez/profile.json` 을 읽는다. 없으면 **워커를 하나도 띄우지 않고** `status: blocked` 로 끝낸다.
   `blocked_on` 에 `who: user` 로 "bootstrap 을 먼저 실행해야 한다" 를 남긴다
2. 사용자 지시가 한 문장으로 굳는지 본다. 안 굳으면 `curvez-requirements` **단독 1라운드**를 먼저 돈다
3. 팀 필요 여부를 `curvez-orchestrator.md` 의 `### 팀이 필요한가` 표로 판정한다

**완료 조건:** `profile.json` 의 `stack` 값을 읽었고, "팀이다 / 팀이 아니다" 를 근거 한 줄과 함께 적었다.
팀이 아니면 여기서 절차를 끝낸다.

**팀이 아닌 것을 팀으로 만들지 마라.**
**이유:** 워커 1명을 띄우는 비용(컨텍스트 복제 + 핸드오프 왕복)이 단일 파일 작업 자체보다 크다.

### 2. 구성안을 만든다

1. 워커 후보를 **아래 라인업 안에서만** 고른다. 이름을 지어내지 마라

| 에이전트 | 담당 | 라운드 배치 |
|---|---|---|
| `curvez-requirements` | 수용 기준 확정 | 1라운드. `curvez-researcher` 와 병렬 |
| `curvez-researcher` | 1차 출처 조사 | 1라운드 |
| `curvez-architect` | 레이어·경계 확정 | 요구사항 뒤. `curvez-designer` 와 병렬 |
| `curvez-designer` | 화면·토큰 스펙 | 요구사항 뒤 |
| `curvez-nextjs` | 웹 구현 | 설계 뒤. `curvez-react-native` 와 병렬 |
| `curvez-react-native` | 모바일 구현 | 설계 뒤 |
| `curvez-qa` | 게이트 실행 | 구현 뒤. 단독 |
| `curvez-reviewer` | 정확성·계약 리뷰 | QA 뒤. `curvez-structure-reviewer` 와 병렬 |
| `curvez-structure-reviewer` | 구조·중복·순환 | QA 뒤 |
| `curvez-retrospector` | 회고·규약 수정안 | 마지막. 단독 |
| `curvez-git` | 커밋·PR·머지 | **자동으로 돌지 않는다.** 아래 참조 |

라인업이 바뀌면 이 표와 `curvez-orchestrator.md` 의 팀 통신 표를 함께 고친다.
   - **이유:** `Tools: *` 를 가진 범용 타입(`general-purpose`, `claude` 등)은 `Agent` 도구까지
     갖고 있어 규약을 모르는 채로 실행되고 실행 트리를 한 층 더 만든다. 반면 **지어낸 이름은
     런타임이 거부하므로 위험하지 않다.** 제한 규칙의 정본은 `curvez-orchestrator.md` 의
     `### 팀 규모 상한` 이다
2. 후보마다 정의 파일 `plugins/curvez/agents/<name>.md` 의 `## 협업과 팀 내 위치` 를 열어
   **파일 소유권**을 그대로 옮겨 적는다
3. `## 병렬 판정` 절차를 돌려 병렬 / 순차를 확정한다
4. 라운드로 쪼갠다. 한 라운드 동시 워커 수 상한은 `curvez-orchestrator.md` 의 `### 팀 규모 상한` 을 따른다.
   상한을 넘겨야 할 것 같으면 **팀을 키우지 말고 라운드를 하나 더 만든다**
   - **이유:** 워커가 돌려준 핸드오프를 전부 자기 컨텍스트에 올려 다음 라운드를 판정해야 한다.
     상한을 넘기면 앞선 핸드오프가 밀려 나가 `blocked_on` 을 놓친다
5. 재리뷰 루프 상한(회수와 회차별 행동)은 `### 재실행 루프 상한` 에서 읽어 구성안에 명시한다

**완료 조건:** 구성안에 다섯 항목이 전부 있다 — **누가**(워커 `name` 목록) / **왜**(각 한 줄) /
**무엇을**(담당 범위와 소유 경로) / **어떻게**(병렬·순차와 그 근거) / **몇 라운드**(예상 라운드 수와 리뷰 루프 상한).
하나라도 비면 승인 단계로 넘어가지 마라.

### 3. 승인을 받는다

**워커를 하나라도 띄우기 전에 구성안을 사용자에게 보고하고 명시적 승인을 받는다.**

**승인 없이 `Agent` 도구를 호출하지 마라.**
**이유:** 워커는 격리된 컨텍스트에서 돌고 실행 중에 사람에게 되물을 수 없다. 구성이 틀린 채로 띄우면
여러 명분의 토큰을 다 쓰고 나서야 틀린 것이 드러나고, 이미 쓰인 파일은 되돌려야 한다.
승인은 되돌리기 비용이 가장 싼 유일한 지점이다.

승인 없이 진행해도 되는 **예외는 하나뿐**이다. 조건과 범위는 `curvez-orchestrator.md` 의
`### 승인 절차` 마지막 문단에서 확인하라 — 요지는 **같은 세션에서 이미 승인된 구성의 무변경 재실행**
(리뷰 지적 → 수정 → 재리뷰의 2회차 이후)이고, **구성원이 한 명이라도 바뀌면 다시 받는다.**

사용자가 승인하지 않으면 지적받은 부분만 고쳐 구성안을 다시 낸다. 워커는 여전히 띄우지 않는다.

**완료 조건:** 사용자의 승인 문장을 받았다. 또는 예외에 해당한다는 근거(직전 승인 구성과 이번 구성이
같다는 대조 결과)를 적었다. `Agent` 호출 횟수는 이 시점까지 **0** 이다.

### 4. 띄운다

1. `.curvez/team.md` 를 `Write` 로 **전체를 다시 쓴다.** 부분 수정하지 마라
   - **이유:** 라운드마다 구성이 바뀌는데 누적하면 지난 라운드의 죽은 항목이 남아 어느 것이 이번
     라운드의 구성인지 판정할 수 없게 된다
   - 담을 것: 팀 명단 / 각자 담당 범위와 소유 경로 / 라운드 구성 / 병렬·순차 판정과 근거 / 승인 시각
2. 병렬 워커는 **한 메시지에서 `Agent` 를 동시에 호출한다.** 한 명씩 순차로 호출하면 병렬이 아니다
   - `subagent_type` 에 넣는 값은 **`curvez:` 를 붙인 `curvez:curvez-nextjs` 형태**다.
     이 문서에 적힌 `curvez-nextjs` 는 지칭이지 호출 값이 아니다. 접두사 없이 부르면 거부된다.
     대응표는 `curvez-orchestrator.md` 의 `#### 호출 값에는 플러그인 접두사가 붙는다` 에 있다
3. 각 워커 프롬프트에 반드시 넣는다
   - 담당 범위와 **소유 경로**, "이 경로 밖은 쓰지 마라"
   - 읽어야 할 입력 파일의 정확한 경로
   - 핸드오프를 `.curvez/handoff/<name>.<timestamp>.json` 으로 남기라는 지시
     (읽기 전용 2종은 제외 — `## 핸드오프 수합` 참조)
   - 막히면 추측하지 말고 `status: blocked` 로 돌아오라는 지시
   - **이유:** 워커는 팀 명단도 다른 워커의 소유 경로도 모른다. 프롬프트에 없는 것은 워커가 추측한다
4. **워커에게 `Agent` 도구를 쓰라고 지시하지 마라.** 라인업 11종 중 `tools` 에 `Agent` 가 있는 것은
   `curvez-orchestrator` 하나뿐이다
   - **이유:** 서브에이전트가 또 서브에이전트를 띄우면 실행 트리의 깊이를 아무도 통제하지 못한다.
     토큰 소비가 예측 불가능해지고, 실패했을 때 어느 층에서 무엇이 깨졌는지 추적이 끊긴다
5. 워커가 도는 동안 오케스트레이터는 파일을 쓰지 않는다. 띄우고 → 기다리고 → 수합한다

**완료 조건:** 이번 라운드에 띄운 워커 수를 숫자로 기록했고, `.curvez/team.md` 에 4항목
(팀 명단·소유 경로·병렬 판정 근거·승인 기록)이 전부 있다.

### 5. 수합한다

`## 핸드오프 수합` 을 따른다. 수합이 끝나면 `## 검증` 을 돌려 오류 0개를 확인하고, 다음 라운드가
있으면 절차 2로 돌아간다.

**완료 조건:** `validate-handoff.mjs` 오류 0개, 띄운 워커 수와 새로 생긴 핸드오프 파일 수의 차이 0,
`who: user` 인 질문이 남아 있으면 전부 한 묶음으로 사용자에게 올린 상태.

## 병렬 판정

절차 2의 3단계에서 돌린다. 판정 표 자체는 `curvez-orchestrator.md` 의 `### 병렬 판정` 이 정본이다.
여기서는 **읽는 순서**만 정한다.

1. 후보 워커의 정의 파일에서 `## 협업과 팀 내 위치` 의 **파일 소유권** 항목을 읽는다
2. 후보끼리 소유 경로를 교차 비교한다
3. **한쪽 `owns` 가 다른 쪽을 포함하면** 정의 파일의 "…는 읽기만 한다" 배제 목록을 차감하고
   다시 판정한다. 절차는 `curvez-orchestrator.md` 의 배제 목록 차감 소절을 따른다
   - 단일 저장소는 `paths.web` 이 `.` 이다. 차감하지 않으면 구현 에이전트가 저장소 전체를
     소유해 병렬이 영구히 불가능해진다
4. **차감하고도 소유 경로가 겹치면 병렬을 포기하고 순차로 강등한다**
   - **이유:** 동시 쓰기는 나중에 쓴 쪽이 앞선 쪽을 조용히 덮어쓴다. 리뷰에서도 안 잡히고 diff 에도 안 남는다
5. **소유권이 정의에 안 적혀 있으면 그 워커는 순차로 강등한다**
   - **이유:** 겹치지 않는다는 근거가 없다. 근거 없는 병렬은 도박이다
6. 한쪽이 다른 쪽 산출물을 읽어야 하면 순차다
   - **이유:** 없는 파일을 읽은 워커는 전제를 지어낸다
7. `.curvez/handoff/` 를 여럿이 쓰는 것은 충돌이 아니다. 파일명이 `<from>.<timestamp>.json` 이라 고유하다

### 공유 도메인 패키지는 소유자가 없다

`.curvez/profile.json` 의 `paths.domain` 은 **소유자가 없는 경로**다. `curvez-nextjs` 도
`curvez-react-native` 도 자기 소유로 선언하지 않는다.

**이번 라운드 작업이 `paths.domain` 을 건드리면 구현 에이전트 2종을 동시에 띄우지 않는다.** 순차로 강등한다.

**이유:** 한쪽 스택 사정으로 공유 시그니처를 바꾸면 다른 스택이 조용히 깨지고, 그 깨짐은 그쪽
에이전트가 **다음에 실행될 때까지 발견되지 않는다.** 동시 실행이면 그 다음이 이번 라운드에 없으므로
깨진 채로 리뷰·QA 라운드까지 흘러가 어느 변경이 원인이었는지 특정할 수 없게 된다.

어느 쪽을 먼저 돌릴지, 양쪽이 동시에 시그니처 변경을 요청했을 때의 우선순위는
`curvez-orchestrator.md` 의 `#### 공유 도메인 패키지는 소유자가 없다` 표를 따른다.

강등한 사실과 근거는 **구성안에 적어 승인받는다.** 겹친 채로 병렬 실행하지 마라.

## 핸드오프 수합

라운드가 끝나면 `.curvez/handoff/` 를 읽어 `status` 별로 분류한다. `status` 판정 규칙 자체는
`agent-contract` 가 정본이다.

| `status` | 행동 |
|---|---|
| `done` | `verification` 이 1건 이상인지 확인한다. 비었으면 `done` 을 믿지 말고 `partial` 로 취급한다 |
| `partial` | `summary` 의 "남은 것" 을 다음 라운드 작업 목록에 넣는다. 남은 범위가 안 적혀 있으면 그것부터 되묻는다 |
| `blocked` | `blocked_on[].who` 로 라우팅한다. 아래를 따른다 |

### `blocked` 라우팅

1. `blocked_on[].who` 가 **에이전트 이름**이면 그 에이전트에게 넘긴다. 질문을 다음 라운드의 첫 작업으로
   두고, 묻는 쪽 이름과 원문 질문을 프롬프트에 그대로 싣는다. **오케스트레이터가 대신 답하지 마라**
2. `who: user` 인 질문은 **전부 모아서 한 번에** 사용자에게 묻는다. 여러 워커에게서 올라온 것도 한 묶음이다
   - **이유:** 질문마다 사용자를 멈춰 세우면 팀 실행이 응답 대기로 직렬화된다. 병렬로 띄워 놓고 첫
     질문에서 전부 멈추면 병렬의 이점이 통째로 사라지고, 사용자는 맥락이 끊긴 질문을 여러 번 받는다
3. 답변을 받으면 **원래 물어본 에이전트를 같은 컨텍스트로 재실행한다.** 질문 원문과 답변을 짝지어
   프롬프트에 넣는다. 새 작업으로 던지지 마라
   - **이유:** 답변만 다른 에이전트에게 넘기면 원래 질문을 낸 쪽이 왜 그것을 물었는지 아무도 모른다

아키텍처 인터뷰만 예외로 워커를 띄우기 전에 직접 진행할 수 있다. 조건과 문항 수 제한은
`curvez-orchestrator.md` 의 `#### 아키텍처 인터뷰는 예외 — 워커를 띄우기 전에 직접 진행한다` 를 읽어라.
그 예외에 해당하지 않는 질문을 미리 대신 묻지 마라.
**이유:** 무엇을 물어야 하는지는 그 워커가 자기 절차를 돌려 봐야 안다.

### 읽기 전용 2종은 대필한다

`curvez-reviewer` 와 `curvez-structure-reviewer` 는 `disallowedTools` 에 쓰기 도구가 전부 들어 있어
파일을 못 쓴다. 두 에이전트는 **최종 응답 텍스트 자체를 핸드오프 JSON 으로 반환**하고,
오케스트레이터가 그것을 파일로 기록한다. 대필 6단계(파싱 확인 → `from` 대조 → `findings` 보존 →
타임스탬프 → 기록 → 검증)는 `curvez-orchestrator.md` 의
`### 읽기 전용 에이전트의 핸드오프를 대신 기록한다` 를 그대로 따른다.

**응답이 JSON 이 아닐 때 오케스트레이터가 JSON 을 지어내 채우지 마라.** 1회 재요청하고, 그래도
아니면 원문을 `.curvez/tmp/` 에 남기고 `partial` 로 보고한다.
**이유:** 지어낸 리뷰 결과는 검증된 것처럼 다음 라운드에 전파되고, 어느 지적이 실제 리뷰였는지
사후에 분리할 수 없다.

**리뷰어의 핸드오프를 생략하지 마라.**
**이유:** 회고 에이전트가 실행 이력을 시간순으로 재구성할 때 리뷰 단계만 통째로 비어 무엇이 언제
지적됐는지 복원할 수 없다. 기록의 책임은 쓰기 권한을 가진 쪽에 있다.

### 두 리뷰어의 `findings[]` 를 합친다

각 리뷰어의 최상위 `findings[]` 를 **그대로 보존**한 채 목록만 합친다. 항목을 줄이거나 요약하거나
필드를 떼지 마라. 합칠 때 `id` 는 **`<from>/<id>`** 로 접두사를 붙인다. 원본 `id` 는 항목 안에 그대로 둔다.

```
curvez-reviewer/DUP-01            ← 원본 id: DUP-01
curvez-structure-reviewer/DUP-01  ← 원본 id: DUP-01, 다른 지적
```

**이유:** 접두사 없이 합치면 두 리뷰어가 같은 `id` 로 낸 다른 지적이 하나로 뭉개져, 재리뷰 때 어느
지적이 닫혔는지 대조할 수 없다.

합친 목록을 **파일로 새로 만들지 마라.** 리뷰어별 핸드오프 파일이 원본이다. 합친 결과는 다음 라운드
작업 목록과 사용자 보고에만 쓴다.
**이유:** 원본과 사본이 둘 다 있으면 다음 라운드에서 어느 쪽이 최신인지 판정할 근거가 없다.

구현자에게 넘길 때는 `where` 가 그 구현자의 **소유 경로에 걸리는 항목만** 고른다. 등급이 높은 것
(`severity: blocker`, `priority: P0`·`P1`)을 먼저 넘긴다.

### 수합할 때 반드시 대조한다

- 띄운 워커 수 == 이번 라운드에 새로 생긴 핸드오프 파일 수. 다르면 빠진 워커를 특정해 보고한다
- `decisions` 끼리 모순되는지. 모순이면 **조용히 한쪽을 고르지 말고** 양쪽 결정과 `reversible_at` 을
  나란히 적어 사용자에게 올린다
  - **이유:** 두 산출물이 서로 다른 전제를 갖게 되면 이후 어느 쪽이 맞는지 판정할 근거가 사라진다
- `artifacts[].path` 가 그 에이전트의 소유 경로 밖인지. 밖이면 **되돌리지 말고** 위반 경로와 담당
  워커를 보고해 사용자 판단을 받는다
- 리뷰어 2종의 핸드오프에 최상위 `findings[]` 가 보존됐는지

`curvez-retrospector` 의 액션 아이템을 받았으면 **규약 파일을 고치기 전에 사용자 승인을 받는다.**
항목 형식과 승인 절차는 `curvez-orchestrator.md` 의 `### 회고 액션 아이템을 받는다` 를 따르고,
실제 편집은 `authoring-agents` / `authoring-skills` 로 한다.
**이유:** 규약 변경은 이 라운드가 아니라 이후 모든 라운드의 동작을 바꾼다.

## 검증

수합 직후 돌린다. 대필한 리뷰어 핸드오프도 포함된다.

```bash
node "$CLAUDE_PLUGIN_ROOT/scripts/validate-handoff.mjs" .curvez/handoff/
```

**오류 0개를 확인하기 전에 다음 라운드를 시작하지 마라.**
**이유:** 스키마가 깨진 핸드오프를 근거로 다음 라운드를 짜면, 워커가 읽는 시점에 필드가 없어
전제를 지어낸다. 그 오염은 그 라운드 산출물 전부로 퍼진다.

수치 대조에 쓰는 명령이다.

```bash
# status 별 개수 — done / partial / blocked
grep -h '"status"' .curvez/handoff/*.json | sort | uniq -c

# 핸드오프 파일 수 — 띄운 워커 수와 대조한다
ls -1 .curvez/handoff/*.json | wc -l

# Agent 도구 독점 확인 — 결과가 1이어야 한다
grep -l '^tools:.*Agent' "$CLAUDE_PLUGIN_ROOT"/agents/*.md | wc -l
```

검증 실패를 요약하거나 숨기지 마라. 실패한 명령과 실제 출력을 그대로 `verification` 에 적고
`status: partial` 로 낮춘다.
**이유:** 수신 에이전트는 `done` 을 믿고 자기 작업을 시작한다. 검증 안 된 `done` 하나가 그 뒤의
모든 작업을 잘못된 전제 위에 올린다.

## git 라운드는 자동으로 돌지 않는다

구현·QA·리뷰가 끝나도 `curvez-git` 을 자동으로 띄우지 마라. 사용자가 커밋·PR·머지를
**명시적으로 요청했을 때만** 띄운다.

**이유:** 라운드가 끝났다는 것과 "이 상태를 이력에 새겨도 된다" 는 것은 다른 판단이다.
파일은 덮어쓰면 그만이지만 커밋은 지워도 흔적이 남고, push 된 뒤에는 남의 작업에 영향을 준다.
후자는 사용자의 판단이다.

띄울 때는 **사용자 요청 원문을 그대로 넘긴다.** "커밋해줘" 와 "머지까지 해줘" 는 실행 범위가
다르고, 요약하면 워커가 넘겨짚는다. 절차는 `curvez:commit` 과 `curvez:branching` 이 정본이다.

**단독 실행한다.** `curvez-git` 은 `owns: none` 이지만 브랜치 전환이 작업 트리 전체를 바꾼다.
다른 워커와 같은 라운드에 두지 마라.
