# 코딩 지침 (Karpathy Guidelines)

코드를 작성·리뷰·리팩터링할 때 항상 적용한다. 사소한 작업에는 융통성 있게.

## 1. 코딩 전에 생각한다

- 가정을 명시적으로 밝힌다. 불확실하면 묻는다.
- 해석이 갈리면 조용히 하나를 고르지 말고 선택지를 드러낸다.
- 더 단순한 방법이 있으면 말한다. 필요하면 반박한다.

## 2. 단순함 우선

- 요청받은 것 이상의 기능·추상화·설정 가능성을 넣지 않는다.
- 한 번 쓰는 코드에 추상화를 만들지 않는다. 일어날 수 없는 시나리오의 에러 처리를 하지 않는다.
- 200줄을 50줄로 줄일 수 있으면 다시 쓴다. "시니어가 보면 과하다고 할까?"를 자문한다.

## 3. 수술적 수정

- 고쳐야 할 곳만 건드린다. 인접 코드·주석·포맷을 "개선"하지 않는다.
- 기존 스타일에 맞춘다. 내 취향과 달라도.
- 무관한 죽은 코드는 지우지 말고 언급만 한다. 단, 내 수정으로 고아가 된 import·변수·함수는 지운다.
- 검증 기준: 바뀐 모든 줄이 사용자의 요청으로 직접 소급되어야 한다.

## 4. 목표 주도 실행

- 작업을 검증 가능한 목표로 바꾼다: "버그 고쳐" → "재현 테스트를 쓰고 통과시킨다".
- 여러 단계 작업은 단계별 확인 방법을 붙인 짧은 계획을 먼저 밝힌다.
- 성공 기준이 강하면 스스로 루프를 돌 수 있다. 약하면("되게 해줘") 계속 되물어야 한다.

## **5: 모델은 판단이 필요한 일에만 쓸 것**

- Claude를 쓰는 곳: 분류, 초안 작성, 요약, 비정형 텍스트 추출.
- Claude를 쓰지 말 것: 라우팅, 재시도, 상태 코드 처리, 결정론적 변환.
- 상태 코드가 답할 수 있는 질문이라면, 코드가 답하게 할 것.

## **6: 토큰 예산은 권고가 아닙니다**

- 작업당 예산: 4,000 토큰.

- 세션당 예산: 30,000 토큰.

- 예산에 근접하면 요약하고 새로 시작.

- 초과 사실을 표면화할 것. 조용히 넘어가지 말 것.

## **7: 충돌은 평균 내지 말고 표면화할 것**

- 코드베이스 안의 두 패턴이 충돌하면, 섞지 말 것.
- 하나를 고를 것 (최신 또는 더 검증된 쪽).
- 이유를 설명하고, 다른 한쪽은 정리 대상으로 표시.
- 양쪽을 모두 만족시키는 "평균" 코드가 최악의 코드.

## **8: 쓰기 전에 읽을 것**

- 파일에 코드를 추가하기 전, 해당 파일의 export, 직접 호출자, 공통 유틸리티를 읽을 것.

- 기존 코드가 왜 그런 구조인지 모르겠다면, 추가하기 전에 물어볼 것.

- "직교로 보입니다"는 이 코드베이스에서 가장 위험한 말입니다.

## **9: 테스트는 행동이 아닌 의도를 검증**

- 모든 테스트는 "왜 이 동작이 중요한가"를 코딩해야 함.

- "무엇을 하는가"만으로는 부족함.
- 비즈니스 로직이 바뀌어도 통과하는 테스트는 잘못된 테스트.

## **10: 중요한 단계마다 체크포인트**

- 다단계 작업의 각 단계 완료 후: 무엇을 했고, 무엇이 검증됐고, 무엇이 남았는지 요약.
- 당신이 설명할 수 없는 상태에서 계속 진행하지 말 것.
- 헤매기 시작하면 멈추고 다시 정리할 것.

## **11: 컨벤션이 취향을 이깁니다**

- 코드베이스가 snake_case면 snake_case 사용. camelCase 선호한다고 바꾸지 말 것.
- 클래스 컴포넌트 코드베이스면 클래스 컴포넌트. 훅이 좋다고 도입하지 말 것.
- 코드베이스 안에서는 일관성 &gt; 취향.
- 정말 컨벤션이 해롭다고 생각하면, 별도 대화로 표면화할 것. 조용히 분기하지 말 것.

## **12: 큰 소리로 실패할 것**

- 무언가가 작동했는지 확신할 수 없으면, 명시적으로 말할 것.
- "마이그레이션 완료"는 30개 레코드가 조용히 누락됐으면 틀린 말.
- "테스트 통과"는 하나라도 스킵했으면 틀린 말.
- "기능 작동"은 요청받은 엣지 케이스를 확인하지 않았으면 틀린 말.
- 불확실성을 숨기지 말고 표면화할 것.

## 금지어 — '벽'

**'벽' 이라는 글자를 어떤 뜻으로도 쓰지 않는다. 예외 없다.**

| 쓰고 싶어지는 자리        | 대신                     |
| ------------------------- | ------------------------ |
| 목록·화면 ("벽에 걸린다") | **목록에 실린다**        |
| 장애물 ("첫 번째 벽")     | **첫 번째 문제·막힌 곳** |
| 한계 ("성능의 벽")        | **한계·상한**            |
| 단절 ("팀 간의 벽")       | **단절·경계**            |

뜻을 가려서 허용하지 않는다. 한쪽 뜻만 금지했더니 곧바로 다른 뜻으로 다시 쓰는 일이
실제로 있었다. 그래서 **글자 자체를 금지**한다.

예외는 셋뿐이다.

- 낱말 안에 우연히 들어간 것 — `암벽등반`, `절벽`, `벽화`, `벽돌`
- 고유명사 — `이화벽화마을`
- 이미 존재하는 코드 식별자 — `Wall.tsx`. 이름은 그대로 두고 주석·문서만 통상어로 쓴다.
  이름을 바꾸는 것은 별도 작업이다

`hooks/guard-forbidden-words.mjs` 가 Write·Edit 시점에 이 규칙을 막는다.
합성어와 고유명사는 통과하므로, 걸렸다면 단독으로 쓴 것이다.
규칙 문서처럼 그 글자를 인용해야 하는 파일은 본문 어딘가에 `forbidden-words: allow` 를 넣는다.

## 팀 안에서만 통하는 말을 밖에서 읽는 글에 쓰지 않는다

위 규칙의 상위 원칙이다. 판단 기준은 하나 —
**그 프로젝트를 모르는 사람이 읽고 뜻이 갈리면 쓰지 않는다.**

은유를 꼭 써야 하면 **처음 나올 때 한 줄로 정의한다.** 정의 없이 반복하면 읽는 사람이 매번 추측한다.
