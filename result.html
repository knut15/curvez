curvez는 역할·소유권·라운드·핸드오프·품질·Git 이력을 제어면에 연결하고 문서 연결성까지 자동 검사하는 92점의 A급 오케스트레이션 하네스다. 문서 정본도 대부분 현재 구현과 맞아졌다. 남은 과제는 실제 멀티에이전트 end-to-end 증명, 핸드오프 실행 ID, GOAL 완료 기준 한 줄이다.

핵심 선택

  • 오케스트레이터만 Agent 도구 보유: 실행 트리를 오케스트레이터→워커 두 층으로 제한해 재귀적 위임과 비용 폭증을 차단한다.
  • 동시 워커 최대 5명: 핸드오프 수합 시 컨텍스트 압박과 누락 위험을 제어한다.
  • 기계 검증되는 소유권: 12개 에이전트의 owns에 대해 경로 교집합, 무소유 경로, 읽기전용 모순을 검사한다.
  • Git 이력 전담: curvez-git은 사용자 명시 요청에만 단독 실행된다. owns: none이어도 작업 트리를 바꾸므로 병렬 금지다.

4. 런타임: 단계형 라운드와 승인 게이트

R1요구사항 ∥ 조사
→
R2아키텍처 ∥ 디자인
→
R3웹 ∥ 모바일
→
R4QA
→
R5리뷰 ∥ 구조 리뷰
  1. 프로파일과 선행 산출물을 읽어 작업 범위를 정한다.
  2. 팀 필요성, 구성원, 소유 경로, 병렬성, 예상 라운드를 판정한다.
  3. 워커 호출 전에 사용자 승인을 받는다. 승인 전 Agent 호출은 0회여야 한다.
  4. 독립 경로만 병렬로 실행하고, 의존 산출물이 있거나 경로가 겹치면 다음 라운드로 미룬다.
  5. 라운드 종료 후 워커 수와 새 핸드오프 파일 수를 대조하고 상태별로 수합한다.
  6. blocked_on 질문은 수신자별로 라우팅하며, 사용자 질문은 한 번에 모아 중계한다.
  7. QA와 읽기 전용 리뷰를 거쳐 수정→재검증 루프를 제한 횟수 내 반복한다.
운영상 좋은 점: 승인 시점을 “가장 되돌리기 싼 지점”에 두고, 워커가 사용자에게 직접 묻지 못하는 제약을 blocked_on[]이라는 데이터 계약으로 바꿨다. 실패를 숨기지 않고 정상 상태로 모델링한 점이 강하다.

새로 구현된 실행기

  • bootstrap: package.json과 워크스페이스 의존 관계에서 스택·앱·공유 도메인·Git 전략을 판정하고, 모호한 값은 추측 대신 questions[]로 반환한다.
  • quality gate: 아키텍처→typecheck→lint→test→build 순으로 실행하며 앞 단계 실패 시 중단한다. 테스트 0개 실행과 아키텍처 규칙 0개 파싱을 성공으로 위장하지 않는다.
  • hook scripts: 공식 매니페스트 형식, doctor 의미 검사, 15개 회귀 사례를 모두 통과했다.

계약의 장점과 한계

  • 장점 완료에 실제 검증 근거를 묶고, 질문·의사결정·산출물의 추적성을 확보한다.
  • 장점 JSON Schema와 무의존성 검증기를 함께 제공해 설치 부담을 낮춘다.
  • 장점 소유권 충돌이 프론트매터와 검증기로 구조화돼 조용한 덮어쓰기를 사전에 잡는다.
  • 한계 타임스탬프 파일명과 “새 파일 수” 대조는 명시적 run_id/round_id/task_id가 없어 재실행 수합에 취약하다.

7. 주요 발견사항

P1 실제 팀 실행의 end-to-end 증거가 없다

README도 이를 정확히 공개한다. 플러그인·마켓플레이스 manifest 검증과 개별 실행기는 통과했지만 실제 설치→bootstrap→승인→복수 Agent→핸드오프→질문 중계→QA·리뷰까지 왕복한 기록은 없다. 오케스트레이션은 구성요소보다 상호작용에서 실패하므로 마지막 신뢰 구간이다.

P2 문서 동기화 검사에 작은 사각지대가 남았다

GOAL 상단 라인업과 아키텍처 프리셋 설명은 수정됐다. 다만 doctor는 “문서 동기화 OK”를 출력하면서 완료 기준의 에이전트 11/11 · 스킬 13/13 한 줄을 놓친다. 실제 값은 12/12·15/15다.

P2 실행 상관관계 식별자가 없다

워커 수와 새 핸드오프 파일 수를 대조하지만 스키마에 run_id, round_id, task_id, attempt가 없다. 동시 실행·재실행·부분 재개 시 파일 소속 판정이 오케스트레이터 컨텍스트에 의존한다.

P2 문서 수치 검사가 비율 표기를 다루지 못한다

현재 검사는 “12종 에이전트” 형태는 잘 잡지만 11/11 같은 완료 비율은 실제 파일 개수와 대조하지 않는다. 과거 실패 사례의 숫자와 현재 상태를 구분하기 위해 상태 블록을 기계 판독 가능한 마커로 제한하는 편이 안정적이다.

8. 권장 개선 순서

  1. end-to-end smoke test를 먼저 수행한다. weather에 실제 설치하고 bootstrap→2개 독립 워커→handoff 검증→quality gate까지 왕복해 실행 기록을 보존한다.
  2. GOAL 완료 기준의 남은 수치를 고친다. 에이전트 11/11 · 스킬 13/13을 실제 12/12 · 15/15로 맞춘다.
  3. 문서 상태 표를 생성형으로 바꾼다. 에이전트·스킬 개수와 런타임 파일 목록을 한 manifest에서 읽어 README/GOAL 상태 블록을 생성하거나 검증 가능한 마커로 감싼다.
  4. 핸드오프 실행 식별자를 추가한다. 이미 구조화된 owns는 유지하고 run_id/round_id/task_id/attempt로 수합과 재실행을 결정적으로 만든다.
가장 작은 유효 개선: GOAL 완료 기준 한 줄을 고치고 doctor에 N/N 완료 비율을 실제 개수와 대조하는 회귀 사례를 추가한다.
